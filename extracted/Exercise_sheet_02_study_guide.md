## 0.5 Sheet 02 例题逐题拆解（8 题全解）

**例题 1（B+ 树叶子/内部节点，NOT correct）** 答案：**D**。
- A 对：删除叶子最小键时，父节点分隔键可能需要更新为新的最小键，且可沿最左边界向上级联（对应 Ch14 删除时"借用"后分隔键更新，如 Mozart→Kim）。
- B 对：叶子存 record ID（指针）而不是完整元组，不改变查找路径逻辑，主要影响叶子扇出和取记录的代价。
- C 对：标准 B+ 树内部节点只有分隔键 + 子指针，**数据只在叶子**，内部键可以与叶子键重复。
- D 错：**B+ 树精确查找必须走到叶子**，即使查找键等于内部分隔键也不能提前终止——因为 payload 只在叶子。"能提前终止"是 **B-tree**（不是 B+ 树）的性质。→ 手法 5（张冠李戴）。

**例题 2（`std::unordered_map` 底层结构）** 答案：**C**（哈希表，平均 O(1)）。注意配套知识：`std::map` 是红黑树 O(log N)、有序；`unordered_map` 是哈希表、无序、不支持高效范围查询。

**例题 3（B+ 树计数题）** 答案：**D (13, 42)**。计算方法（必须掌握）：
- **每个内部节点：键数 = 子节点数 − 1**。根有 4 个孩子 → 3 个键；四个内部节点分别有 3、5、4、2 个孩子 → 2+4+3+1 = 10 个键。合计内部分隔键 = 3 + 10 = **13**。
- 叶子数 = 内部节点的孩子总数 = 3+5+4+2 = 14；每叶 3 条记录 → 14×3 = **42**。
- 诱饵 (12, 45)：12 来自漏算根的一个键或者按"孩子数=键数"算错；45 来自把叶子数算成 15。

**例题 4（GROUP BY + ORDER BY 流水线，NOT correct）** 答案：**C**。哈希聚合 (HashAggregation) 的输出顺序由**哈希函数**决定，与键的大小顺序无关——planner **不能**假设其输出有序。A 对（模块化框架允许在后面插 Sort）；B 对（planner 要决定 Sort 位置）；D 对（分组键=排序键时可改用有序聚合策略，例如基于排序的聚合，从而省掉单独的 Sort）。

**例题 5（Patricia Trie 增量计数）** 答案：**C (2, 1)**。这是最有区分度的题型，第 3 章给出完整方法论。核心结论：
- 插入 `heli`：沿 `he`→`l` 走，剩余 `i` 与子边 `ium` 的公共前缀是 `i`（比 `ium` 短）→ **分裂**：`ium` 拆成 `i`（terminal 标在此节点）+ 子节点 `um`。新增节点 = 1；字符增量 = (1+2) − 3 = **0**（分裂不增加字符总量！）。
- 插入 `help`：剩余 `p` 与任何子边无公共前缀 → 新建节点 `p`。新增节点 = 1；字符 +1。
- 合计 (Δnodes, Δchars) = **(2, 1)**。

**例题 6（R-Tree vs B+ Tree，NOT correct）** 答案：**B**。R-Tree 没有全局全序，**不存在**"按坐标排序枚举矩形的中序遍历"。A、C、D 都是标准性质（多维 vs 一维；单一全序 vs 可重叠空间区域；同层 MBR 可重叠/部分包含）。

**例题 7（Select 谓词的 direct/indirect 引用，NOT correct）** 答案：**A**。indirect（间接）引用 = 谓词里存**元组内的列下标**，运行时到元组里取值——它的用途是支持"同一元组内两列比较"（如 `start_time < end_time`）和动态条件，**不是**"在索引查找中大量使用并被高度优化"（索引查找用的是键值/常量）。B、C、D 是 transcript 原话的转写。

**例题 8（Web 级倒排索引分片，best describes）** 答案：**A**（document-partitioned：按文档切 shard，每个 shard 建本地倒排索引，查询广播给所有 shard 后由 coordinator 归并）。⚠️ 注意：**Module 8 transcript 讲的是 word-based sharding（term-partitioned）作为教学示例**，但真实生产系统（Google 等）**以 document partitioning 为主**——这题证明出题人会考"超出 transcript 一小步的业界常识"。两种方案的完整对比见第 4 章。

# 第 1 章：B+ 树（Module 7 + Ch14）

## 1.1 为什么需要 B+ 树：范围查询 vs 点查询

- **点查询 (point query)**：找某列**恰好等于**某个值的所有元组。例：找价格 = $30 的商品。
- **范围查询 (range query)**：找某列**落在区间内**的所有元组。例：找价格在 $10–$20 之间的商品。

**哈希表**能用 O(1) 回答点查询（按键直接定位桶），但**对范围查询无能为力**：哈希表按哈希值打乱存放、键无序（30 可能在 slot 0，12 在 slot 2），要回答范围查询只能**扫描整个哈希表逐键判断**。

> 【易错点】"哈希索引处理范围查询很慢"的原因是**键不按顺序存放**，不是"哈希函数太慢"。

**有序索引 (ordered index)** 把数据按键排序维护，因此支持快速范围查询。B+ 树就是最常用的有序索引。

## 1.2 B+ 树结构：必须一字不差记住的事实

```text
                 [ 20 ]                ← 根（也是内部节点）
               /        \
        [5 | 11]        [23 | 25]      ← 内部节点（存分隔键+子指针）
       /   |    \       /   |   \
   [1,2] [5,7] [11,17] [20,21] [23,24] [25,30]   ← 叶子（存键+真实值）
     └──→──┴──→──┴──→──┴──→──┴──→──┘   叶子间有兄弟指针（sibling pointers）
```

| 事实 | 内容 |
|---|---|
| 平衡性 | 所有叶子到根的距离**相同**（balanced）→ 所有键查找时间一致 |
| 内部节点（inner node） | 存**分隔键 + 子节点指针**；**K 个指针配 K−1 个键**（键比指针少 1） |
| 叶子节点（leaf node） | 存**键 + 真实值**（如 tuple ID / record ID）；**K 个键配 K 个值** |
| 数据位置 | **payload 只存在叶子**；内部键只是"路标"，可与叶子键重复 |
| 叶子链表 | 叶子间用 sibling/next 指针串成有序链表 → 范围查询水平扫描 |
| 扇出 (fanout) | 每节点可容纳的键/指针数，实际系统可达 100–1000 |
| 高度 | 因为扇出大，树非常"矮胖"，通常只有 3–4 层 |
| 磁盘映射 | **每个节点 = 一个磁盘页**（典型 4KB） |

【易错点】内部节点 "K−1 键 / K 指针" vs 叶子 "K 键 / K 值"——计数题的根基（例题 3 就考这个）。

**Ch14 的正式占用率规则**（设 n = 每节点最大指针数）：

| 节点类型 | 最少 | 最多 |
|---|---|---|
| 非根内部节点的**子节点数** | ⌈n/2⌉ | n |
| 叶子节点的**值数** | ⌈(n−1)/2⌉ | n−1 |
| 根（非叶）| 2 个子节点 | n |
| 根（同时是叶，即整棵树只有根）| 0 个值 | n−1 个值 |

例：n = 6 → 叶子 3–5 个值，非根内部节点 3–6 个孩子。**给你 n 让你判断"哪个节点是非法的"是标准出题模板。**

**高度上界公式**：若共有 K 个搜索键，树高 ≤ **⌈log⌈n/2⌉(K)⌉**。
- 经典算例（Ch14 原文）：K = 100 万，n = 100 → log₅₀(10⁶) ≈ 3.53 → 高度 ≤ 4；而平衡二叉树要 ~20 层。每层可能是一次磁盘 I/O，这就是 B+ 树赢的原因。

## 1.3 查找与范围查询

**精确查找 find(v)**：从根出发，在每个内部节点找到第一个 ≥ v 的键决定走哪个孩子，**一路走到叶子**，在叶子里找 v。
- 【易错点】即使 v 等于某个内部分隔键也**不能停**——数据在叶子（例题 1 选项 D）。

**范围查询 [lb, ub] 的两种做法**（Module 7 专门对比过，必考）：

| 做法 | 步骤 | 问题 |
|---|---|---|
| 朴素法（naive） | 垂直下降到**最左**叶子 → 沿链表扫**所有**叶子 | 无视 lb（总从最小键开始）、无视 ub（扫到最右）→ 读了大量无关页 |
| 高效法（targeted） | ① **垂直遍历**：按 lb 下降到正确叶子；② **水平遍历**：沿 sibling 指针右扫，遇到 key > ub 立即停止 | 只访问相关节点 → 磁盘页读取数最少 |

每个节点 = 一个磁盘页，因此"少访问节点"直接等于"少做磁盘 I/O"。

## 1.4 插入与节点分裂（split）——机制细节必须精确

插入是**递归**的：从根下降到目标叶子，把 (key, value) 按序插入。若插入使节点超容量 → **分裂**：

1. **叶子分裂**：把 n 个条目按序对半分（前 ⌈n/2⌉ 个留原节点，其余进新节点），然后把**新节点的最小键**作为分隔键插入父节点。**该键在叶子中仍然保留**（是"复制上去"，copy up）。同时维护叶子链表：新节点的 next = 旧节点原来的 next，旧节点的 next = 新节点。
2. **内部节点分裂**：若父节点也满了，继续分裂。此时**中位键（median key）被"移上去"（move up / push up）**——它离开子节点，只出现在上层。
3. **根分裂**：分裂传播到根时，创建**新根**，仅含那一个被提升的中位键，有两个孩子。**树高 +1，且所有路径同时加高**——这是 B+ 树保持平衡的机制（树从根部长高，不是从叶子长高）。

【易错点】叶子分裂 = **复制**分隔键（键同时在叶子和父节点出现）；内部分裂 = **搬移**中位键（键只在上层出现）。出题人极爱混淆这两者。

**BuzzDB 实现细节（C++，可直接出代码题）**：
- 用 **path vector** 记录下降路径上访问过的节点，分裂向上传播时靠它回溯找父节点；分裂到根时 path vector 为空 → 新建根。
- 下降选孩子用 **`std::upper_bound`**（找第一个大于插入键的键）；叶子内定位插入点用 **`std::lower_bound`**（找第一个**不小于**目标键的位置）配合 **lambda 比较器**（匿名函数，就地定义，用于比较 Entry 与 key）。
- 键已存在 → **更新值**（insert_or_update 语义），不产生重复键。
- B+ 树类是**模板类** `template <typename KeyT, typename ValueT>`：同一份代码支持 int→int、string→int、自定义结构体（如 TicketKey{date, seat}）等键值类型；**自定义键类型必须重载比较运算符 `<`**，否则无法维持有序。模板在**编译期**实例化为具体类型（不是运行期）。

## 1.5 删除（Ch14，Module 7 未细讲但例题 1 考了）

删除叶子条目后，若节点**低于最小占用率**（underfull）：

1. **合并（merge/coalesce）**：若与兄弟的条目能装进一个节点 → 合并两节点，并从父节点删除对应的分隔键+指针。**内部节点合并时，父节点中的分隔键被"拉下来"（pull down）进入合并后的节点**。
2. **重分配（redistribute/borrow）**：若装不下 → 从兄弟"借"一个条目，并**更新父节点的分隔键**（例：叶子 [Mozart] 从左兄弟借来 Kim 后，父分隔键 Mozart → Kim）。
3. 删除可**级联向上**；若根只剩 1 个孩子 → 删除根，唯一的孩子成为新根，**树高 −1**。

【易错点】删除叶子最小键 → 父节点（甚至更上层，沿最左边界）的分隔键可能需要更新（例题 1 选项 A 是正确陈述）。

**更新代价**：插入/删除单条目的 I/O 与树高成正比 = O(log⌈n/2⌉ K)。实际更少：内部节点常驻 buffer、分裂/合并罕见。平均占用率：随机插入 ≈ 2/3，顺序插入 ≈ 1/2。

## 1.6 磁盘化 B+ 树（on-disk B+ tree）——Module 7 重点

**为什么要磁盘化**：① 索引大表（不受 DRAM 容量限制）；② **持久性**——内存 B+ 树在崩溃/断电后消失，重启要重建；磁盘 B+ 树重启后仍在。

**怎么做**：
1. **节点大小对齐磁盘块**（典型 4KB）→ 一个节点恰好一页。
2. **序列化 (serialization)**：把内存节点转成字节流写盘。关键：**内存指针不能直接写盘**（进程重启后地址无意义），必须把节点指针**转换成文件偏移量 (file offset)**。固定大小的键值用 `std::memcpy` 直接拷贝；**变长类型（如 string）必须额外存长度元数据**。
3. 文件布局：节点按 4KB 的倍数偏移依次存放 → 可**随机访问**任意节点（offset = 节点号 × 页大小），不必读中间节点。

**【必考计算】节点容量公式**（Module 7 原文）：节点含 m 个键 + (m+1) 个值 的空间 = 键 4B×m + 值 4B×m + 预留 1 个值 4B + 节点元数据 9B = **8m + 13 字节**。
- 4KB 页：8m+13 ≤ 4096 → m ≈ **510** 个键
- 16KB 页：m ≈ **2046** 个键
- 推论（记数量级）：fanout=510 时，3 层树 = 510² 个叶子 ≈ **1.32 亿键 / ~1GB 文件**；4 层树 ≈ **670 亿键 / ~0.5TB**。

**减少磁盘 I/O 的两招**：
1. **Buffer manager 缓存热点节点**（根 + 第二层几乎必在内存）→ 随机点查通常只需 **1 次**磁盘读（读叶子）。
2. **懒写回 (lazy write-back)**：修改过的节点（脏页）只在被驱逐时写盘；**没修改过的页驱逐时直接丢弃、不写盘**。

**为什么 B+ 树天生适合磁盘**（总结陈述，反选题素材）：为磁盘而设计（二叉搜索树的磁盘泛化）；操作 I/O 数可预测（所有叶子同高）；高扇出 → 矮 → 垂直遍历 I/O 少；叶子链表 → 范围扫描不读无关页。

## 1.7 Ch14 补充考点（Module 7 没有但例题范围覆盖）

**索引分类**：
- **有序索引 vs 哈希索引**；**聚簇/主索引 (clustering/primary)**：索引键顺序 = 文件物理顺序；**二级/非聚簇索引 (secondary/nonclustering)**：顺序不同。
- **稠密索引 (dense)**：**每个搜索键值**都有索引项。**稀疏索引 (sparse)**：只有部分键值有索引项——**仅当文件按该键顺序存放（聚簇）时才可用**；查找方法：找 < K 的最大索引项，再顺序扫。好的折中：**每个块一个稀疏索引项**。
- 【易错点】**二级索引必须是稠密的**（文件不按它排序，漏了谁都找不到）；二级索引指向**桶 (bucket)**，桶里放指向所有同键值记录的指针。
- 用二级索引做顺序扫描很贵：每条记录都可能换一个磁盘块（机械盘每次 5–10ms）。
- **多级索引 (multilevel)**：外层稀疏索引压在内层索引之上；B+ 树的内部层本质上就是"叶子层之上的多级稀疏索引"。

**非唯一键**：主流方案是**加记录 ID 组成复合键 (aᵢ, Ap) 使其唯一**；查 aᵢ=v 变成范围查询 (v,−∞)–(v,+∞)。
**复合键 (composite key)** 按**字典序**排序：(a1,a2)<(b1,b2) ⟺ a1<b1 或 (a1=b1 且 a2<b2)。索引 (dept, salary) 能高效处理 `dept='F' AND salary=80000`、`dept='F' AND salary<80000`，**不能**高效处理 `dept<'F' AND salary=80000`（第一列是范围时第二列条件失效）。
**覆盖索引 (covering index)**：把额外属性塞进**叶子**，查询不必回表取记录。

**B-tree vs B+ 树**（例题 1D 的知识背景）：

| | B+ 树 | B-tree |
|---|---|---|
| 键的出现次数 | 内部键可在叶子重复 | 每个键**只出现一次** |
| 数据指针 | 只在叶子 | 内部节点也带记录指针 → **可提前命中** |
| 扇出 | 高（内部节点小） | 低（内部节点多存指针）→ **更深** |
| 实现/插删 | 简单 | 复杂 |
| 结论 | 广泛使用 | 优点通常不敌缺点 |

**批量装载 (bulk loading)**：逐条插入 ≥1 I/O/条，太慢。方案 1：**先外部排序再按序插入**（I/O 好转但叶子约半满）；方案 2：**自底向上构建 (bottom-up build)**——排序后逐层建树，主流数据库的 bulk-load 工具都用它。
**字符串索引**：变长键 → 变扇出，按空间利用率决定分裂；**前缀压缩**（内部节点只存足以区分子树的前缀，如 "Silb" 区分 Silas/Silberschatz）。
**B+ 树文件组织 (file organization)**：叶子直接存**记录**而非指针，保持数据聚簇；记录比指针大 → 叶子容量更小；用 2 个兄弟参与重分配可把最低占用率提高到 **⌊2n/3⌋**。
**记录搬家问题**：二级索引存记录指针时，记录一搬家全部二级索引都要改 → 解决：二级索引存**主索引的搜索键**而非物理指针（查询多一次主索引遍历，但分裂便宜）。

# 第 2 章：哈希索引、LSM 树、位图索引、空间索引基础（Ch14）

## 2.1 静态哈希 (Static Hashing)

- **桶 (bucket)** = 存放条目的存储单元，通常一个桶 = 一个磁盘块。
- 哈希函数 h：搜索键集合 K → 桶地址集合 B。查找/插入/删除都先算 h(key) 定位桶，**桶内仍需顺序查找**（不同键可能同桶）。
- **hash index**：桶里存"键 + 记录指针"；**hash file organization**：桶里直接存记录。
- **桶溢出 (overflow)** 的原因：① 桶数不足；② **倾斜 (skew)**——大量记录同键值，或哈希函数分布不均。溢出**只能缓解不能消除**，用**溢出桶链表 (overflow chaining)** 处理——这叫 **closed addressing**。
- 【易错点】**open addressing（开放寻址，冲突时找下一个空槽）不适合数据库**——删除困难、桶与块的对应被破坏。教材原话："not suitable for database applications"。

## 2.2 静态哈希的缺陷与动态哈希

静态哈希桶数固定，但数据库会增长/收缩：桶太少 → 溢出链拖垮性能；预留太多 → 空间浪费。周期性用新哈希函数整体重组又太贵。→ **动态哈希**三方案：

| 方案 | 思想 |
|---|---|
| **周期性 rehash** | 条目数 > 1.5× 表大小时，建 2× 大的新表、全量重哈希 |
| **线性哈希 (Linear Hashing)** | **增量式** rehash，每次只分裂一个桶 |
| **可扩展哈希 (Extendable Hashing)** | 面向磁盘；目录（哈希前缀表）翻倍但**桶不必翻倍**（多个目录项共享桶） |

**有序索引 vs 哈希的选择**（教材结论，常考）：
- 哈希适合**等值/点查询**；**范围查询必须用有序索引**。
- 实践现状：**PostgreSQL 支持 hash index 但不鼓励用（性能差）**；Oracle 只支持静态哈希文件组织；SQL Server 只支持 B+ 树。→ "实际系统里 B+ 树几乎总是默认选择"。

## 2.3 写优化索引：LSM 树与 Buffer Tree

**动机**：B+ 树写入差——每次插入≈1 次叶子 I/O，机械盘 <100 插入/秒/盘。

**LSM 树 (Log-Structured Merge Tree)**：
- 插入先进**内存中的 L0 树**；L0 满 → 与磁盘上的 **L1 树归并**（用 bottom-up build 重建 L1）；L1 超阈值 → 并入 L2……**每层容量是上一层的 k 倍**。
- **好处**：① 写盘全是**顺序 I/O**；② 叶子全满（不浪费空间）；③ 每条记录的摊销 I/O 低。
- **代价**：① **查询要搜索多棵树**（每层都可能有）；② 每层内容被反复复制（写放大）。
- **删除不是原地删**：插入一条**删除标记 (delete entry)**；查询要把原条目和删除标记配对后过滤；**归并时配对的条目+标记一起丢弃**。更新 = 插入+删除。
- **Stepped-merge 变体**：每层保留**多棵树** → 写更便宜、查更贵 → 用 **Bloom filter** 跳过大多数树的无谓查找。
- 应用：BigTable、Cassandra、MongoDB、LevelDB、MyRocks；对 flash 也有价值（减少擦除）。

**Buffer Tree**：B+ 树每个**内部节点带一个缓冲区**，插入先囤在缓冲区，满了才批量下推。查询开销比 LSM 小、可用于任意树索引（PostgreSQL GiST 用它），但**随机 I/O 比 LSM 多**。

【易错点】"LSM 删除会立即从所有层物理删除条目" ——错（删除标记）；"LSM 查询和 B+ 树一样只查一棵树"——错。

## 2.4 位图索引 (Bitmap Indices)

- 适用条件：记录**顺序编号**（第 n 条能直接定位，定长记录最佳）+ 属性**取值种类少**（性别、州、收入档位）。
- 结构：**每个属性值一张位图**，位图长度 = 记录数，第 i 位 = 1 ⟺ 第 i 条记录取该值。
- 用途：**多属性条件查询**——位图之间做 AND/OR/NOT。例：`gender=m AND income=L1` → `10010 AND 10100 = 10000`。**单属性查询没什么用**。
- **【必考计算】空间**：位图 = 每记录 1 bit。记录 100 字节时，一张位图 = 关系大小的 **1/800**；8 个取值的属性全部位图 ≈ 关系的 **1%**。
- **高效实现**：位图打包成字（word），一条 64 位 AND 指令处理 64 条记录 → 100 万位的位图 AND 只需 ~15,625 条指令（教材以 32 位举例：31,250 条）。**数 1 的个数**用 256 项的预计算表按字节查。
- 混合技巧：B+ 树叶子对高频值可以**用位图替代 tuple-ID 列表**（当 >1/64 的记录都是该值时划算，假设 tuple-id 64 位）。

## 2.5 空间索引三兄弟：k-d 树、四叉树、R-tree（Ch14 视角）

| 结构 | 分割方式 | 特点 |
|---|---|---|
| **k-d tree** | 每层用**一个维度**把点集对半分，维度轮换 (x,y,x,y,…) | 早期内存结构；k-d-B tree 扩展成多路，适合外存 |
| **Quadtree（四叉树）** | 每个节点把自己的矩形区域切成**四个相等象限** | 区域内点数超阈值才继续分 |
| **R-tree** | 用**最小包围矩形 (MBR, bounding box)** 层次分组 | B+ 树的 N 维推广；**兄弟 MBR 允许重叠**；查询可能要走多条路径（最坏低效、实践可用）；只适合**较低维度** |

空间查询类型：**nearest neighbor（最近邻）**、**范围查询（含于/相交某区域）**、**spatial join**。
**时态索引 (temporal)**：每条元组带 [start, end] 有效区间（当前有效 end=∞）→ 用 R-tree 把 (属性, 时间区间) 当二维数据索引；**当前元组（end=∞）单独建 (a, start-time) 索引**避免无穷值问题。

# 第 3 章：Trie 与 Patricia Trie（Module 8）

## 3.1 为什么 B+ 树不适合前缀查询

**前缀查询 (prefix query)**：找所有以某前缀开头的字符串（如搜 "Samsung Galaxy" 系列产品）。B+ 树存字符串的问题：长键（如 "Samsung Galaxy S21 Ultra"）要**在树的多层重复存储**、每次节点遍历都要**比较又长又相似的键** → 空间和计算开销都大。

## 3.2 Trie 与 Patricia Trie

- **Trie**（名字来自 re**TRIE**val）：树形结构，每个节点存一个字符（或共享的字符段），**根到叶的路径拼出一个字符串**。前缀查询 = 沿前缀字符下行即可；共享前缀只存一次 → 省空间。
- **Patricia Trie**（压缩/基数 trie）：**把单字符节点链合并成一个节点**——一个节点/边可以携带多个字符甚至整个字符串（如一个节点直接存 "Samsung Galaxy"）。节点更少 → 插入/查找比普通 trie 更快、更省空间。
- 节点结构（BuzzDB 版）：`{ bool isEndOfWord; Value value; map<string, Node*> children; }`——**终止用节点上的布尔标志表示，不额外造"空后缀边"**。键可以带值（hello→1）；一个键是另一个键前缀也没问题（hero→3, heron→4，hero 节点 isEndOfWord=true 且有孩子）。

## 3.3 插入算法的三种情形（增量计数题的根基）

设当前要插入的剩余子串为 rest，考察当前节点的所有子边标签：

| 情形 | 条件 | 动作 | Δ节点 | Δ字符 |
|---|---|---|---|---|
| ① 无公共前缀 | rest 与任何子边标签都没有公共前缀 | 新建节点存整个 rest | **+1** | **+len(rest)** |
| ② 完全匹配子边 | rest 以某子边标签开头 | 沿该边下降，消耗标签后递归 | 0 | 0 |
| ③ 部分匹配 → **分裂 (split)** | rest 与子边标签有公共前缀 p，且 p 短于标签 | 标签拆为 p + 余下部分：p 成为新的中间节点，原节点保留余下标签；rest 若还有剩余则再建新分支 | 分裂本身 **+1**（若 rest 消耗完，终止标志打在 p 节点上，不再加节点；若 rest 有剩余再 +1） | 分裂本身 **+0**（p+余下 = 原标签，字符总数不变！）；rest 剩余部分 +其长度 |
| ④ 插入的串已是路径 | rest 被完全消耗 | 把当前节点 isEndOfWord 置 true | 0 | 0 |

**【必考计算】完整算例（= 例题 5）**：已有 {he, hell, hello, helium, hero}，结构为：
```text
root ── "he"(end) ── "l" ──┬── "l"(end) ── "o"(end)
                           └── "ium"(end)
     └（"he" 的另一子边）── "ro"(end)
```
- 插入 **heli**：走 "he"，rest="li"；子边 {"l","ro"}，与 "l" 完全匹配 → 下降，rest="i"；子边 {"l","ium"}，与 "ium" 公共前缀 "i" 短于 "ium" → **分裂**：`ium` → `i` + 子节点 `um`；rest 恰好被 "i" 消耗完 → isEndOfWord 打在 "i" 节点。Δ节点 = 1，Δ字符 = (1+2)−3 = **0**。
- 插入 **help**：走 "he"→"l"，rest="p"；子边 {"l","i"} 均无公共前缀 → 新建节点 "p"。Δ节点 = 1，Δ字符 = 1。
- 合计 **(2, 1)**。

> 解题口诀：**匹配下降不花钱；分裂加一个节点但字符不变；全新分支节点+1、字符+剩余长度**。

## 3.4 Patricia Trie vs B+ 树对比表（transcript 原表，直接出反选题）

| 维度 | Patricia Trie | B+ 树 |
|---|---|---|
| 插入/查找时间 | **O(L)**（L = 键平均长度，与键总数 N 无关） | **O(log N)**（与 N 有关） |
| 空间 | **O(N·L)**——共享前缀省空间，但**键彼此不相似时每个键都开新分支** | **O(N)**——每节点打包多个键，内存效率高 |
| 目标场景 | **前缀查询**（词典查找、自动补全） | **数值范围查询** |
| 范围查询 | 可以按**字典序遍历**支持，但要访问很多节点，**不高效** | 天生高效（叶子有序链表） |

【易错点】"Patricia trie 总是比 B+ 树省内存"——错，键不相似时更费内存；"trie 查找复杂度 O(log N)"——错，是 O(L)。

# 第 4 章：倒排索引与全文检索（Module 8 + Ch15 Slide 48）

## 4.1 结构

- **倒排索引 (inverted index)**：**词 → 出现位置**的映射。单文档版：word → [positions]（如《战争与和平》里 Russia → 位置 10, 20）。多文档版：**word → (docID → [positions])**。
- BuzzDB 的 C++ 实现是**嵌套 map**：外层 key = 词，value = 内层 map（key = 文档号，value = `vector<int>` 位置表）。底层通常建在**哈希表**上。
- 三个核心函数：
  - `addDocument`：逐词处理（**先转小写**做大小写不敏感匹配），把 (词 → docID → 位置) 加入索引。
  - `getDocuments`：词 → 含该词的 docID 集合（`set<int>`）。
  - `proximitySearch`：**邻近搜索**——两个词在**同一文档**中、位置差的绝对值（`std::abs(pos1 − pos2)`）≤ K 即命中。例：Russia@20、Napoleon@25 → 距离 5，K=10 时命中。
- **布尔查询**：AND/OR = 对 docID 集合求**交/并**。Ch15 版本：每个词存**有序 docID 列表**，多关键词查询做**列表求交**；支持排序还要存 **term frequency、inverse document frequency (TF-IDF)、PageRank** 等信息。

## 4.2 工程问题

- **存储足迹大**（每个词的每次出现都要记位置）→ 用 **delta encoding（差分编码）压缩位置**：存相邻位置的差值而不是绝对值（[1000,1008,1012] → [1000,8,4]），小整数可用更少字节编码。
- 扩展到大语料 → 需要**磁盘存储管理**。

## 4.3 Web 级搜索（例题 8 的完整背景）

- 历史：Stanford Digital Library 项目（Hector Garcia-Molina）→ 学生 Larry Page & Sergey Brin 开发 web 级搜索技术 → Google。
- 两大优化：**sharding（分片）**——索引切成多个 shard 分布到多台服务器；**replication（复制）**——每个 shard 存多副本，负载均衡 + 容错。
- **两种分片方式（必考对比）**：

| | **Document-partitioned（按文档切）** | **Term/word-partitioned（按词切）** |
|---|---|---|
| 做法 | 文档集合切成 shard，每个 shard 对自己的文档建**完整的本地倒排索引** | 词典切开，**某个词的全部 posting 都在一台机器**（Module 8 的示例：shard1 管词 1–100…） |
| 查询 | **广播到所有 shard**，coordinator 归并结果 | 单词查询只碰一个 shard；**多词查询要跨 shard 传输 posting 列表** |
| 更新 | 新文档只影响一个 shard（易） | 新文档的每个词都可能分布在不同 shard（难） |
| 负载 | 天然均衡 | 热门词造成热点 |
| 现实 | **生产系统的主流做法（例题 8 正确答案）** | 教学示例/特定场景 |

- **排序 (ranking)**（PageRank、机器学习模型）与索引过程是**两个独立阶段**：倒排索引先按词命中缩小候选集，排序算法再对候选按相关性排序。【易错点】"排序在倒排索引内部完成"——错。

# 第 5 章：R-Tree（Module 8 + Ch14）

## 5.1 为什么 B+ 树搞不定多维数据

对 (salary, age) 建**复合 B+ 树索引**是把二维空间**线性化**：先按 salary 排、再按 age 排。这**无法表达二维邻近关系**——salary 相近但 age 差很远的点在索引里可能相邻，而空间上真正相近的点却可能离得很远。空间查询（找附近的餐厅）需要**按空间邻近性分组**的结构。

## 5.2 R-Tree 结构

- 出身：**Antonin Guttman 和 Mike Stonebraker，1980 年代，Berkeley**。
- 两种几何对象：**point（点）**（x,y 坐标，如 salary/age、经纬度、图像特征向量）与 **rectangle（矩形，即 MBR/bounding box）**——能包住一组点或子矩形的**最小**边界矩形。
- 三种节点：**叶子**存点（最底层）；**内部节点**存子节点的 MBR；**根**是入口。和 B+ 树一样是**平衡**结构，查找 O(log n)。
- **兄弟/同层的 MBR 允许互相重叠、甚至部分包含**（Ch14："Bounding boxes of children of a node are allowed to overlap"）。
- 【易错点】R-Tree **没有全局全序** → 不存在"按坐标排序的中序遍历"（例题 6 答案）。
- C++：`Point{float x,y}`；`Rectangle{minX,minY,maxX,maxY}` 带两个方法——`contains(point)`（点在矩形内？）与 `intersects(rect)`（两矩形相交？）。

## 5.3 插入与分裂

1. **选路（chooseBestChild）**：把新点视作退化矩形（min=max=点坐标），每层选**"包住它所需扩大量（enlargement）最小"**的孩子 → 保持 MBR 紧凑、少留空白。
2. 递归下到叶子插入；叶子超容量 → **quadratic split（二次分裂）**：
   - **选种子 (chooseSeeds)**：双重循环算所有点对的**欧氏距离**，取**相距最远的两个点**当两个新节点的种子。
   - 其余点逐个分给"使 MBR 扩大量最小"的一侧。
3. 分裂/合并像 B+ 树一样保持平衡。

【易错点】种子是**最远**的一对点（不是最近的）；选子树看**扩大量最小**（不是"面积最小"或"包含点数最少"）。

## 5.4 查询

- **范围查询**（如 salary∈[100K,200K] 且 age∈[40,60]）：从根递归——**内部节点**：只递归进 **MBR 与查询矩形相交** 的孩子；**叶子**：输出被查询矩形 `contains` 的点。→ 只搜相关子树。
- **k 最近邻 (kNN)**：内部节点：算查询点到每个孩子 MBR 的**最小距离**，**按距离排序后近的先递归**；叶子：算查询点到每个点的欧氏距离，压入**按距离排序的优先队列**，**队列超过 k 时弹出最远的** → 结束时队列里就是 k 个最近邻。
- 应用：附近餐厅（范围查询 + 经纬度）、网约车派单（kNN 找最近 k 个司机）、以图搜图（特征向量 + kNN）、开放世界游戏碰撞检测。

## 5.5 ND R-Tree（N 维推广）

- 点 = 坐标**向量**（如 512 维图像特征）；矩形 = **超矩形 (hyperrectangle)**，由 minCoords / maxCoords 两个向量界定。
- **核心设计矛盾**：① 树要平衡（叶子同高 → 遍历浅）；② MBR 要**少重叠、少空白**（重叠多 → 一次查询递归多个子树）。两者要权衡。
- Ch14 补充：R-tree 只对**较小的维度 N** 工作良好（高维会退化，这也是学习索引/专用向量索引存在的原因之一）。

# 第 6 章：学习索引 Learned Index（Module 8）

## 6.1 动机与思想

B+ 树的三个痛点：① 层次结构 → 多层遍历、多次磁盘 I/O；② 每节点大量指针 → 内存开销；③ 刚性划分，不适应数据分布。

**学习索引（2018，Google + Brown，Kraska 等人）**：**把所有内部节点换成机器学习模型**——训练模型直接**预测键在有序数组中的位置**。
- **递归模型索引 (RMI)**：**根模型**看键值决定交给哪个**子模型**（根模型把键域切成若干大段，如 0–250 / 251–900 / 901–1000）；子模型预测键在其数据簇内的位置；**叶层仍是真实的键值对数组**。

## 6.2 线性回归模型（会算！）

模型 = `position = slope × key + intercept`（y = mx + b）。

**【必考计算】训练公式**：
- slope = Σ(keyᵢ − mean_key)(posᵢ − mean_pos) / Σ(keyᵢ − mean_key)²
- intercept = mean_pos − slope × mean_key

transcript 算例：键 100@位置1、200@位置3（等数据）→ slope = 0.025，intercept = −1.75；对 key=120 预测 ≈ 2 ≈ 实际位置。

## 6.3 邻域搜索与根本局限

- 回归**不是 100% 准确**，只给**近似位置** → 预测点周围做**邻域搜索 (neighborhood search)**：设 search radius = r，检查 [pred−r, pred+r] 的槽位。例：pred=10、r=2 → 查位置 8–12。
- **radius 的权衡**：大 → 更可能找到但更慢；小 → 快但可能漏。倾斜数据可考虑动态调整。
- 【最重要的易错点】**radius 内没找到 ≠ 键不存在**——键可能在 radius 之外。**学习索引可能找不到实际存在的键，这是它相对"永远准确"的 B+ 树的根本局限**。

## 6.4 与 B+ 树对比 & 神经网络扩展

| 维度 | B+ 树 | 学习索引 |
|---|---|---|
| 结构 | 刚性、层次化 | 数据自适应、预测式 |
| 查找 | O(log n) 次比较 | 直接预测 + 邻域搜索 → **接近常数时间** |
| 内存 | 每节点多指针，开销大 | 紧凑模型、少指针 → 更省 |
| 准确性 | **总是准确** | 近似；高度散乱的数据上更不准 |

- **神经网络版**：线性回归对**非线性分布**（指数增长的区间、季节性、地理分布）无能为力 → 单隐层网络（输入 1 神经元 = 归一化的 key ÷ max_key，隐层 10 神经元 + **sigmoid** 激活，输出 1 神经元 = 位置）；训练 = 前向传播 + 反向传播降 **MSE（均方误差）**；同样可以组成递归结构（根网络选子模型）。
- 代价：要调**神经元数、学习率、epoch**，且**比线性模型更耗内存**。
- 论文结论：查找从对数级 → 近常数；省内存；即使简单线性模型对点/范围查询也有高精度。

# 第 7 章：查询执行——算子框架、谓词、Select（Module 9）

## 7.1 从硬编码到算子框架

- **硬编码查询**的问题：查询逻辑和存储/索引逻辑深度耦合（如 `select_group_by_sum` 一个函数干完扫描+过滤+分组+求和）——改一个查询要懂整个系统、容易引 bug、难以优化。
- **算子框架 (operator framework)**：每个算子（operator）只负责一种数据操作，像**乐高积木**一样自由组合成复杂查询流水线。
- **统一接口**：每个算子以**一个或多个表为输入，输出一个新表**——输入可以是磁盘上的物理表，也可以是**另一个算子的输出**。这个"表进表出"的标准化接口是可组合性的根源。
- 三大好处（transcript 原话，反选题素材）：**flexibility**（组合算子支持不同查询、无需改算子本身）、**modularity/isolation**（每个算子封装一种功能，改一个不影响其他，便于调试优化）、**reusability**（通用算子实现一次到处用，减少冗余和 bug）。

## 7.2 抽象算子接口（Volcano/iterator 风格）

抽象基类 `Operator` 定义四个方法——**语义必须记准**（getOutput 不推进游标！）：

| 方法 | 语义 |
|---|---|
| `open()` | 初始化算子（分配状态/资源，重置游标） |
| `next()` | **推进到下一个元组**；有元组可用返回 **true**，否则 false |
| `getOutput()` | 返回**当前**元组的字段（不推进游标） |
| `close()` | 清理资源，恢复干净状态 |

**Scan 算子**：从磁盘表读元组。内部维护**当前页号 + 页内槽号**；通过 **buffer manager** 取页（自动处理缓存命中/未命中）；当前页元组耗尽 → 前进到下一页；所有页扫完 → 清空当前元组标志结束。

## 7.3 C++ 抽象基类、继承、多态（必出 1–2 题）

- **抽象基类 (abstract base class)**：含 ≥1 个**纯虚函数**（声明尾部 `= 0`，无实现）的类。**不能实例化**；派生类必须实现全部纯虚函数才能成为具体类。
- **继承 (inheritance)**：派生类获得基类的变量与方法并可扩展（词源：inheritor，"立为继承人"）。
- **多态 (polymorphism)**：基类指针可指向派生类对象；通过基类指针调用虚函数时，**运行期经 vtable 动态分发**到实际对象类型的实现（词源：poly+morph，"多种形态"）。`override` 关键字显式标注覆写。
- 【易错点】（Sheet 01 原题曾考）"`= 0` 使函数编译期绑定、消除虚调用开销"——**错**，纯虚函数照样走运行期 vtable 分发；"抽象类可以直接实例化"——错。
- 算子分类：**UnaryOperator**（一个输入算子：Select、HashAggregation、投影等）；**BinaryOperator**（两个输入：`input_left` + `input_right`，如 Join）。

## 7.4 谓词 (Predicate)

- **谓词** = 对元组求值为 true/false 的条件（如 `salary > 1000`），Select 用它过滤。
- **SimplePredicate 三要素**：左字段、右字段（两个 `unique_ptr<Field>`）+ **PredicateType 枚举**（EQ、NE、GT、GE、LT、LE…）指明比较类型。
- `checkPredicate()` 做**类型相关**的比较；实际比较逻辑抽象成**模板函数** `compare<T>` → 一份代码支持 int/float/string，**类型安全**且**避免复制粘贴导致的 bug**（transcript 明确给这个理由）。
- **两种操作数 (operand)**（例题 7 的考点）：
  - **direct（直接）**：操作数是**常量**，写死在谓词里（静态）。用于"列 vs 常量"（`price < 100`）。
  - **indirect（间接）**：操作数是**元组内的列下标**，求值时到当前元组取值（动态）。用于"**同一元组内两列比较**"（`start_time < end_time`）。
  - 两者可混用；支持两者**提升了表达能力，且不需要新增算子**。
  - 【易错点】"indirect 引用大量用于索引查找并被高度优化"——**错**（例题 7 的 NOT correct 项）。

## 7.5 Select 算子与深浅拷贝

- `Select` 继承 UnaryOperator；持有谓词、`has_next` 标志、`current_output` 向量。`next()` 循环拉取输入元组逐个测谓词，命中即把字段**复制**进 current_output 并返回 true；输入耗尽 → has_next=false、清空输出。
- **`getOutput()` 返回字段的深拷贝 (deep copy)**——保证传给下游算子的数据独立于本算子内部数据。
- **深拷贝 vs 浅拷贝**（Sheet 01 考过一次，Module 9 再次强调，必考）：
  - **深拷贝**：连同堆上动态分配的数据一起复制；副本与原件**互不影响**（改副本的 "Hello"→"Jello" 不影响原件）。
  - **浅拷贝**：只复制成员变量本身（包括**指针的值**），**两个对象指向同一块堆内存** → 改一个另一个跟着变；还会导致 double-free/悬垂指针等内存 bug。
  - BuzzDB 的 `duplicateFields` / Field 拷贝构造做深拷贝，动机：**算子间隔离**——一个算子处理元组时不受另一个算子修改的影响。
- 组合示例：`Scan → Select(field[0] > 2)` —— Select 是 Scan 的**父节点**（数据从下往上流）。

# 第 8 章：高级算子——复杂谓词、HashAggregation、流水线、CreateIndex（Module 10）

## 8.1 IPredicate 接口与任意复杂谓词

需求：`age < 30 AND salary > 1000` 这类多条件过滤。设计：

- **IPredicate 接口**（抽象基类）：唯一要求是实现 `check(tuple) → bool`。
- **SimplePredicate** 实现 IPredicate：单个比较（direct/indirect 操作数 + 比较运算符）。
- **ComplexPredicate** 实现 IPredicate：持有 **`vector<unique_ptr<IPredicate>>`**（每个成员既可以是 SimplePredicate 也可以是**另一个 ComplexPredicate** → 任意嵌套）+ **LogicOperator（AND/OR）**：
  - AND：**所有**子谓词都为 true 才 true；OR：**任一**子谓词 true 即 true。
- 多步组合例：先 `(f0 > 2) AND (f0 < 7)`，再与第三个简单谓词 OR——之所以能这样嵌套，**正因为简单/复杂谓词实现同一接口**。

## 8.2 HashAggregation 算子（例题 4 背景）

对应 SQL：`SELECT c1, SUM(c2) FROM t [WHERE …] GROUP BY c1`。

- 继承 UnaryOperator。两个配置向量：**group-by attributes**（按哪些列分组）+ **aggregate functions**（SUM/COUNT…作用在哪列）。
- **工作流程**：`open()` 建哈希表——键 = 分组列值（组键），值 = 该组的聚合中间值；逐个消费输入元组，`updateAggregate` **动态更新**对应组的聚合值（先检查类型一致性防止类型错误）；输入**全部**处理完后，把 (组键, 聚合值) 拼成输出元组表。`next()` 只是**在聚合结果上移动的游标**。
- **多列分组**：组键 = `vector<Field>`（如 (Category_ID, month) 的每个唯一组合是一组）→ 需要**为字段向量实现哈希器**：逐字段把值**重新解释为字符串**求哈希，再用 **XOR + 位移**把各字段哈希**组合**起来——目标是**让哈希值均匀分布、减少冲突**（不是"保证无冲突"！）。
- 【必考推论】哈希聚合是**阻塞算子**：必须消费完全部输入才能产出第一条结果；**输出顺序由哈希决定，与组键大小顺序无关** → 上层要 ORDER BY 必须插 Sort 算子（或改用有序聚合策略）——这正是例题 4。

## 8.3 算子流水线与 Unix 类比

- 完整例子：`SELECT c1, SUM(c2) FROM t WHERE c1 ∈ (lo, hi) GROUP BY c1` →
  **Scan（buffer manager 读页）→ Select（复杂谓词过滤）→ HashAggregation（分组求和）**。
- **Unix 管道类比**（transcript 花了一整节，值得一题）：
  - 历史：1970 年代，Unix（Ritchie & Thompson，Bell Labs）与关系数据库（Ted Codd，IBM System R）各自独立地对抗"单体软件复杂性"。
  - **每个工具只做好一件事** = 每个算子只做一种操作（grep 过滤 ≈ Select）。
  - `cat file | grep error | sort | uniq -c` = Scan → Select → Sort → GroupBy/Count。
  - **标准化接口**：Unix 工具"文本进文本出" = 算子"表进表出"→ 可任意组合。
  - **可扩展性**：可添加自定义工具 = 可定义自定义算子/函数。

## 8.4 DDL、DML 与 CreateIndex 算子

- **DDL (Data Definition Language)**：定义/修改数据库结构——CREATE/ALTER/DROP，作用于表、**索引**、视图（视图 = 虚拟表）。**DML (Data Manipulation Language)**：查询/修改表中的元组。
- **CreateIndex 算子**：在指定列上建索引。两个要素：**column offset**（对哪一列建索引，如 salary 在 offset 1）+ **索引对象**（BuzzDB 用 hash index）。
- **实现的怪癖（必考）**：**整个建索引过程在 `open()` 里完成**——迭代子算子（如 Scan）的全部元组，按 column offset 抽键、以 (键 → 记录/ID) 插入哈希索引；**`next()` 是空的**（没有逐元组输出）；建好的索引通过 **`getIndex()`** 暴露给其他算子（如 Select）使用。
- 意义：算子框架**统一支撑 DDL 和 DML**；扫描、建索引、查询处理清晰分离。

# 第 9 章：查询处理与代价模型（Ch15）

## 9.1 查询处理三步曲

**① Parsing & translation**（语法检查、翻译成关系代数）→ **② Optimization**（等价表达式 + 每个算子的多种算法 = many plans；**用目录统计信息估代价选最便宜的** evaluation plan）→ **③ Evaluation**（执行引擎跑计划）。

## 9.2 代价度量（所有计算题的地基）

- 用**总资源消耗**（不是响应时间）作代价；忽略 CPU；**不计最终输出写盘**。
- 磁盘代价 = **b × tT + S × tS**（b 次块传输 + S 次寻道）。
  - **tT** = 传一个块的时间（4KB：机械盘 ≈ 0.1ms；SSD ≈ 2–10µs）
  - **tS** = 一次寻道时间（机械盘 ≈ 4ms；SSD ≈ 20–90µs）
  - 记忆点：机械盘 **tS ≫ tT**（4ms vs 0.1ms）→ 顺序读远胜随机读。
- 最坏情形假设：buffer 里啥都没有、只有最少内存。

## 9.3 选择 (Selection) 算法 A1–A10

| 算法 | 场景 | 代价 |
|---|---|---|
| **A1 线性扫描** | 任何条件都行 | br 次传输 + 1 次寻道；键属性等值可停在命中处：平均 br/2 |
| **A2 聚簇索引、键等值** | 取 1 条记录 | **(hᵢ+1) × (tT+tS)**（hᵢ = 索引高度） |
| **A3 聚簇索引、非键等值** | 多条记录**连续存放** | hᵢ×(tT+tS) + tS + **b×tT**（b = 含匹配记录的块数） |
| **A4 二级索引等值** | 键：1 条，(hᵢ+1)(tT+tS)；**非键：n 条记录可能各在一块** | **(hᵢ+n)(tT+tS) —— 可能极贵！n 大时不如线性扫描** |
| **A5 聚簇索引、比较** | σ_A≥v：索引找首条 ≥v 然后顺序扫；σ_A≤v：**直接从头顺序扫，不用索引** | |
| **A6 二级索引、比较** | 扫索引叶子取指针，再逐条取记录——**每条记录一次 I/O，可能不如线性扫描** | |
| A7/A8/A9 合取 | 一个索引选最便宜的 θᵢ 其余内存过滤 / 复合索引 / **多索引取指针交集** | |
| A10 析取 | 所有条件都有索引才可用：**指针并集**；否则线性扫描 | |

- **PostgreSQL 的 bitmap index scan**（弥合二级索引扫描与线性扫描）：**位图每页 1 bit**；先索引扫描把命中记录**所在页**的位置 1，再**按物理顺序线性读所有置位的页**。命中少 → 接近索引扫描；命中多 → 接近线性扫描；**从不显著差于两者中的较优者**。

## 9.4 外部排序 external sort-merge（必考计算）

内存放不下的关系用它排。M = 可用内存页数，br = 关系块数，bb = 每路使用的缓冲块数。

1. **生成初始 run**：每次读 M 块进内存 → 内排 → 写出成一个有序 run。**run 数 N = ⌈br/M⌉**。
2. **归并**：每趟把 **⌊M/bb⌋ − 1** 个 run 归并成一个（留 bb 块做输出缓冲）。**趟数 = ⌈log⌊M/bb⌋−1(br/M)⌉**。

**【必考计算】总块传输 = br × (2 × 趟数 + 1)**（run 生成读+写 = 2br；每趟读+写 = 2br；最后一趟不计写出）。
- 教材例：M=11，90 个 run，bb=1 → fan-in 10，一趟后剩 9 个 run（每个大 10 倍）。
- 完整算例：br=4000，M=40，bb=4 → run 数 = 100；fan-in = ⌊40/4⌋−1 = 9；趟数 = ⌈log₉100⌉ = 3；总传输 = 4000×(2×3+1) = **28,000**。

## 9.5 Join 算法与代价（必考计算）

约定：r 外表（outer）、s 内表（inner）；br/bs = 块数，nr/ns = 元组数。**教材例子**：student nr=5000, br=100；takes ns=10000, bs=400。

| 算法 | 最坏代价（传输 + 寻道） | 关键点 |
|---|---|---|
| **Nested-loop** | **nr×bs + br** 传输，nr+br 寻道 | 逐**元组**配对；任何 join 条件都行；应选**小表做外表**……但真正省的是下一行 |
| **Block nested-loop** | **br×bs + br** 传输，**2×br** 寻道 | 逐**块**配对；内表每块对外表每块读一次 |
| BNLJ + M−2 块优化 | ⌈br/(M−2)⌉×bs + br 传输，2⌈br/(M−2)⌉ 寻道 | 外表一次读 M−2 块 |
| 两表之一全装入内存 | **br + bs** 传输，2 寻道 | 最好情形（小表做内表驻留内存） |
| **Indexed nested-loop** | **br(tT+tS) + nr × c** | c = 内表一次索引查找+取匹配记录的代价；两边都有索引时**元组少的做外表** |
| **Merge join** | **br + bs** 传输 + ⌈br/bb⌉+⌈bs/bb⌉ 寻道（+ 排序代价） | **只适用于等值/自然连接**；需已排序 |
| **Hash join** | **3(br+bs) + 4n_h** 传输 + 2(⌈br/bb⌉+⌈bs/bb⌉) 寻道 | **只适用等值/自然连接**；分区+构建+探测 |

教材数字（要能复算）：NLJ student 外表 = 5000×400+100 = 2,000,100；BNLJ = 100×400+100 = **40,100** 传输 + 200 寻道；indexed NL（takes 有 B+ 树，c=5）= 100 + 5000×5 = **25,100**。

**Hash join 细节**：
- 用 h 把两表按 join 属性分区（r→r₀…rₙ，s→s₀…sₙ）：**rᵢ 只需与 sᵢ 比**。
- **build input = 较小的表 s**（每个 sᵢ 必须装进内存，用**另一个**哈希函数在内存建哈希索引）；**probe input = r**（rᵢ 不必装入内存）。
- 分区数 n = ⌈bs/M⌉ × f（f ≈ 1.2 fudge factor）；**n > M 时要递归分区**（4KB 块 + 12MB 内存可处理 <36GB 的表，很少需要）。
- **倾斜/溢出**：某分区装不下内存（同键值太多/哈希不均）→ 溢出**再分区 (resolution)** 或**避免 (avoidance)**；重复键太多两者都失效 → 退化用 BNLJ。
- 教材算例：instructor(100 块) ⨝ teaches(400 块)，M=20：n=5 分区一趟完成 → 3×(100+400) = **1500** 传输 + 336 寻道。
- **Hybrid hash join**：内存较大时，**build 表的第 0 号分区常驻内存**，probe 表相应分区**直接现场探测不写盘** → 教材例省成 1300；M ≫ √bs 时最有用。

**复杂连接条件**：合取 r ⨝_{θ1∧θ2…} s → 用最便宜的单条件 join，再内存过滤其余条件；析取 → 各单条件 join 的并集（或 NLJ）。空间 join → R-tree 等空间索引 + indexed NL。

## 9.6 其他运算

- **去重**：排序（run 生成与归并中就可提前去重）或哈希（同桶必相邻）。**投影** = 逐元组投影 + 去重。
- **聚合**：类似去重——排序或哈希把同组聚齐再算；**partial aggregation 优化**：run 生成/归并阶段就合并同组（count/min/max/sum 直接保部分值；**avg 保 (sum, count) 最后相除**）。
- **集合运算**（∪∩−）：同一哈希函数分区两表 → 每分区内存哈希索引处理。
- **外连接**：join 后补 null-padding，或改造 merge/hash join（probe 端不匹配直接输出补 null；build 端要**记录哪些 build 元组匹配过**，结束时输出未匹配者）。

## 9.7 表达式求值：物化 vs 流水线（必考概念）

| | **Materialization（物化）** | **Pipelining（流水线）** |
|---|---|---|
| 做法 | 自底向上，每个算子算完把**中间结果写盘**成临时关系，再给上层 | 元组一产生就**直接传给父算子**，不落盘 |
| 适用性 | **永远适用** | 不总是适用（sort、hash join 等阻塞） |
| 代价 | 各算子代价之和 + **中间结果读写盘的代价** | 省掉中间结果 I/O，**更便宜** |
| 优化 | **double buffering**：两个输出缓冲交替（一个在写盘另一个在填）重叠计算与 I/O | |

**流水线两种驱动方式**：
- **Demand-driven（需求驱动 / lazy / pull 模型）**：上层不断向下层"要下一个元组"；每个算子实现为 **iterator：open() / next() / close()**，调用之间**自己维护状态**（这正是 BuzzDB Module 9 的接口！）。
- **Producer-driven（生产者驱动 / eager / push 模型）**：算子**主动**产元组塞进算子间**缓冲区**，缓冲满则等待；系统调度"有输入可处理且输出缓冲有空"的算子。

**阻塞算子 (blocking operations)**：**消费完全部输入才能出第一条结果**——排序、（哈希）聚合、hash join 的 build。但可拆成两个子阶段分别参与流水线（sort = run 生成 + 归并；hash join = 分区 + build-probe）；**pipeline stages**：同一 stage 内的算子并发跑，stage 之间有先后。**Double-pipelined join**：两表的 0 号分区都留内存，元组到达即互相探测、即刻出结果（hybrid hash join 的对称改造）。
**流数据**：continuous queries + 窗口聚合（tumbling window），用 **punctuation** 判断窗口数据齐了。
**内存时代的优化**：查询**编译成机器码**（消除解释开销，JIT/LLVM）；列存 + 向量化；**cache-conscious 算法**——排序 run 取 L3 大小、hash join 把 build 子分区切到 L3 大小、常一起访问的属性排相邻、多线程掩盖 cache miss。

# 第 10 章：并发控制（Ch18）

> 本章与前面章节的连接点：**索引并发（crabbing / B-link）直接建立在 B+ 树之上**；**next-key locking 靠 B+ 树叶子的有序性防幻读**；Sheet 01 已考过 buffer manager 的 latch/pin，本章是其理论续篇。

## 10.1 锁基础与两阶段锁 (2PL)

- 两种锁模式：**S（shared，共享/读）**、**X（exclusive，排他/读写）**。兼容矩阵：S-S 兼容，其余（S-X、X-X）都不兼容。锁不兼容时请求者**等待**直到冲突锁释放。
- **只是加锁并不保证可串行化**（教材给出 unlock 太早导致读到不一致 A+B 的反例）→ 需要**锁协议**限制加/放锁时机。
- **两阶段锁协议 (2PL)**：
  - **增长阶段 (growing)**：只能获得锁，不能释放。
  - **收缩阶段 (shrinking)**：只能释放锁，不能获得。
  - 保证**冲突可串行化**；串行化顺序 = 各事务 **lock point**（获得最后一把锁的时刻）的顺序。
- 【易错点】**2PL 不能防死锁**！也不保证无级联回滚。
- 变体：**Strict 2PL**——**X 锁**持有到提交/中止（保证可恢复、无级联回滚）；**Rigorous 2PL**——**所有锁**持有到提交/中止（串行化顺序 = 提交顺序）。多数数据库实际实现 rigorous 却叫它 2PL。
- 2PL **不是可串行化的必要条件**（存在 2PL 产生不了的可串行化调度）；但没有额外信息时它在"对抗性"意义上是必要的。
- **锁转换**：增长阶段可**升级 (upgrade)** S→X；收缩阶段可**降级 (downgrade)** X→S。
- **锁管理器**：内存中的**锁表**（按数据项哈希），记录已授予的锁和等待队列；新请求排队尾，与前面的都兼容才授予；事务中止时其全部请求被删除。

## 10.2 死锁 (Deadlock)

- 定义：一组事务互相等待对方持有的锁，谁都动不了。**多数锁协议都可能死锁（necessary evil）**。另一个问题是**饿死 (starvation)**（如某事务反复被选为牺牲品）——好的管理器可避免饿死。
- **预防 (prevention)**：
  - **预先声明**：开始前锁住全部所需数据项。
  - **偏序/图协议**：按数据项的偏序加锁。
  - **wait-die（非抢占）**：**老等少；少（请求老的锁时）直接死**（回滚）。年轻事务可能反复 die。
  - **wound-wait（抢占）**：**老伤少（强制回滚年轻者）；少等老**。回滚比 wait-die 少。
  - 两者中被回滚的事务**用原时间戳重启** → 越等越老，最终必然赢 → **不会饿死**。
  - **超时法**：等锁超时就回滚——简单，但可能误杀 + 超时值难定 + 可能饿死。
- **检测 (detection)**：**wait-for graph**（点 = 事务；边 Ti→Tj = Ti 在等 Tj 持有的锁）。**有环 ⟺ 死锁**。周期性跑环检测。
- **恢复 (recovery)**：选**代价最小**的牺牲品回滚；**total rollback**（推倒重来）或 **partial rollback**（只回滚到释放所需锁的程度）；为防饿死可以规定"最老的事务永不做牺牲品"。

## 10.3 图协议（树协议）

- **tree protocol**：数据项组织成树；规则：**只用 X 锁**；第一把锁可加在任何项上；之后**只有持有父节点锁才能锁孩子**；随时可解锁；**解锁过的项不能再锁**。
- 性质：保证冲突可串行化 + **无死锁**（不需要回滚）；可以比 2PL 更早解锁（并发更高）。
- 缺点：**不保证可恢复性/级联自由**（需要额外 commit 依赖机制）；**可能要锁根本不访问的数据项**（额外开销）。与 2PL 互不包含（各有对方做不到的调度）。

## 10.4 多粒度锁 (Multiple Granularity)

- 粒度层级：**database → area → file → record**，显式锁一个节点 = **隐式锁住其全部后代**。粒度细 → 并发高、开销大；粒度粗 → 开销小、并发低。
- **意向锁 (intention locks)**：让高层节点不用逐个检查后代就能直接加 S/X：
  - **IS**：后代将加 S 锁；**IX**：后代将加 X（或 S）锁；**SIX** = 整棵子树 S 锁 + 后代将加 X 锁。
- **兼容矩阵（背！）**：

| | IS | IX | S | SIX | X |
|---|---|---|---|---|---|
| **IS** | ✓ | ✓ | ✓ | ✓ | ✗ |
| **IX** | ✓ | ✓ | ✗ | ✗ | ✗ |
| **S** | ✓ | ✗ | ✓ | ✗ | ✗ |
| **SIX** | ✓ | ✗ | ✗ | ✗ | ✗ |
| **X** | ✗ | ✗ | ✗ | ✗ | ✗ |

- 记忆法：IS 最温和（只跟 X 冲突）；IX 与 IX 兼容（两边都下去锁细粒度，真冲突在下面判）；S 与 IX 冲突（有人要改下面）；SIX 只容 IS；X 谁都不容。
- **加锁规则**：先锁根；锁 S/IS 需父节点有 **IS 或 IX**；锁 X/SIX/IX 需父节点有 **IX 或 SIX**；事务必须两阶段；**解锁必须自底向上**（孩子全解完才能解父）——加锁自顶向下、放锁自底向上。
- **锁升级 (escalation)**：某层锁太多时换成更高层的 S/X。

## 10.5 幻读 (Phantom) 与索引锁

- **幻读现象**：T1 做**谓词读**（`count(*) where dept='Physics'`），T2 同时**插入**一条 Physics 记录——两者没碰任何公共元组却在逻辑上冲突（读的是"关系里有哪些元组"这一信息）。只用元组锁 → 可能产生不可串行化调度。**更新也能造成幻读**（把 Wu 的系改成 Physics）。
- 解决方案递进：
  1. **关系级数据项锁**：扫描者 S 锁、插删者 X 锁——并发太低。
  2. **索引锁协议 (index locking)**：每个关系至少一个索引；查找必须 **S 锁所有访问到的索引叶子**（**哪怕叶子里没有满足条件的元组也要锁**）；插/删/改必须 **X 锁所有受影响的索引叶子**；再叠加 2PL → 防幻读。
  3. **Next-key locking（更高并发）**：锁**所有满足条件的键值 + 下一个键值 (next key)**；查找用 S、插删改用 X。例：范围查 7≤v≤16，叶子有 [3,5,8,11,14,18…] → 锁 8、11、14 **和 18**。
- 【易错点】`select … for update` 能绕过部分 SI 异常，但**不处理幻读/谓词读**。

## 10.6 时间戳排序 (Timestamp Ordering, TSO)

- 每个事务进系统时拿唯一时间戳 TS(Ti)（逻辑计数器或 (墙钟, 计数器)），**时间戳顺序 = 串行化顺序**。
- 每个数据项 Q 维护：**W-TS(Q)**（成功写 Q 的最大时间戳）、**R-TS(Q)**（成功读 Q 的最大时间戳）。
- **读规则**：TS(Ti) < W-TS(Q) → Ti 要读的值已被"未来"覆盖 → **拒绝，回滚 Ti**；否则读并令 R-TS(Q) = max(R-TS, TS(Ti))。
- **写规则**：TS(Ti) < R-TS(Q) → "未来"已经读过旧值 → **拒绝回滚**；TS(Ti) < W-TS(Q) → 写的是过时值 → **拒绝回滚**；否则写并令 W-TS(Q) = TS(Ti)。
- 性质：优先图的边全部从小时间戳指向大时间戳 → 无环 → **可串行化**；**无死锁**（从不等待）；但**可能级联回滚、甚至不可恢复**（需补救：写全部放到末尾原子执行 / 等数据提交后再读 / commit 依赖）。
- **Thomas' Write Rule**：**只改写规则第 2 条**——TS(Ti) < W-TS(Q) 的过时**写**直接**忽略**（不回滚）。允许更多并发，能产生一些**视图可串行化但非冲突可串行化**的调度。【易错点】Thomas 规则只作用于**写**，读规则不变。

## 10.7 验证协议（乐观并发控制，OCC）

- 思想：**用提交时刻作串行化顺序**。事务三阶段（必须按序，但不同事务可交错）：
  1. **读/执行**：只写**本地临时变量**。
  2. **验证**：检查是否与其他事务冲突（读写集 + 时间戳测试）。
  3. **写**：验证通过才把更新落库，否则回滚。
- 三个时间戳：StartTS、**ValidationTS（= 事务的序号 TS）**、FinishTS。
- **验证测试**：对所有 TS(Ti) < TS(Tj) 的 Ti，须满足其一：① FinishTS(Ti) < StartTS(Tj)（完全没并发）；② StartTS(Tj) < FinishTS(Ti) < ValidationTS(Tj) 且 **Ti 的写集 ∩ Tj 的读集 = ∅**。
- 冲突概率低时并发优于锁/TSO；实时系统里表现也好。

## 10.8 多版本并发控制 (MVCC) 与快照隔离 (SI)

- **核心思想**：每次成功的写**创建数据项的新版本**（带时间戳标签）；读操作按事务时间戳**挑合适的版本**返回 → **读永不等待、永不被拒绝**。
- **MV-TSO**：版本 Qk 带 content、W-TS、R-TS。读：返回 W-TS ≤ TS(Ti) 的最新版本（**读总是成功**）。写：若 TS(Ti) < R-TS(Qk) → 回滚（有"未来"事务读过它本应读到 Ti 写的值）；TS(Ti) = W-TS(Qk) → 覆写；否则**创建新版本**。
- **MV2PL**：区分**只读事务**（启动时拿 ts-counter 做时间戳，走多版本读，**完全不加锁**）与**更新事务**（rigorous 2PL；首次写 Q 创建新版本 W-TS=∞；提交时 TS = ts-counter+1，给自己创建的版本盖章，ts-counter++）。
- 实现代价：多版本占空间 → **垃圾回收**（比最老活跃事务还老的非最新版本可删）。
- **快照隔离 (Snapshot Isolation, SI)**：
  - 事务**在开始时拿一份已提交数据的快照**；全程读/改自己的快照（并发事务的更新不可见；自己的更新可见）；提交时写才生效。
  - **First-committer-wins**：提交时若发现**并发事务已提交了对同一数据项的写** → 自己中止。（Oracle 用变体 **first-updater-wins**：写时就加锁检查，早发现早回滚，效果等价。）
  - 优点：**读不阻塞也不被阻塞**；性能接近 read committed；**无脏读、无丢失更新、无不可重复读**。
  - 【最爱考的缺陷】**SI 不保证可串行化**！经典反例 **write skew（写偏斜）**：A=3, B=17；Ti: A:=B，Tj: B:=A 并发 → 两者都读旧快照 → 结果 A=17, B=3（**互换**），任何串行执行都得不到。两个事务改**不同**数据项、各自基于对方修改项的旧值 → SI 检测不到（它只查**写-写**冲突，不查读-写）。插入型偏斜（两个事务都取 max(order)+1 → 撞号）同样是幻读的例子。
  - **SSI (Serializable Snapshot Isolation)**：额外跟踪**读-写依赖**、发现可能成环就回滚 → 真可串行化；**PostgreSQL 9.1+ 实现**（还配合索引锁防幻读）。
  - 【冷知识必背】**Oracle 把隔离级别设为 serializable 时实际给的是 SI**（老版本 PostgreSQL <9.1 也是）。
- **应用层并发控制**：元组带版本号，更新时 `WHERE version = :读到的版本`——乐观并发控制的民间版（Hibernate 用），防丢失更新但不保证可串行化。

## 10.9 弱一致性级别与 SQL 隔离级别

- **Degree-two consistency**：S 锁随时可放、随时可拿（X 锁保持到结束）→ 不保证可串行化。**Cursor stability**：读时逐条锁-读-放。
- SQL 隔离级别（从强到弱）：**serializable**（标准默认）> **repeatable read**（读已提交 + 重复读同值，但**不防幻读**）> **read committed**（≈ degree-two/cursor stability；**多数商用系统的实际默认**）> **read uncommitted**（能读未提交数据）。

## 10.10 索引并发与无锁结构（与 B+ 树的交汇，大概率出题）

- 索引访问极其频繁，对索引节点做 2PL 会把并发掐死。好在**索引不需要可串行化访问**——只要最终落到正确的叶子，内部节点读到的过渡值无所谓。
- **Crabbing protocol（螃蟹协议）**：像螃蟹走路一样交替持锁——
  1. 先 **S 锁根**；
  2. 锁住需要的孩子后**释放父节点的锁**；
  3. 插入/删除时把**叶子升级成 X 锁**；
  4. 分裂/合并需要改父节点时再 **X 锁父节点**。
  - 【易错点】crabbing **不是**无死锁的：**下行的查找**和**上行的分裂**可能互相死锁 → 检测后**中止并重启查找**（不影响事务本身）。
- **B-link tree 协议**：并发更高——**先放父锁再拿子锁**，靠叶子/节点间的 link 指针补救"放锁到拿锁之间世界变了"的问题。
- **主存数据库**可以简化：对整个索引拿**短期锁**（操作级串行化），因为没有磁盘等待，操作很快。
- **Latch-free（无锁）技术**：用 **CAS（compare-and-swap）**原子指令更新共享结构（循环重试直到 CAS 成功）。已知陷阱：**ABA 问题**——P1 记下头节点 N1；P2 删 N1、N2 又把 N1 插回来；P1 的 CAS 看到"头还是 N1"误以为没变 → 链表指向已删除的 N2。
- **在线建索引 (online index creation)**：大表建索引若用 2PL 会阻塞所有更新 → 在**快照**上建索引，同时**记录期间的更新**，随后**追赶 (catch-up)**；接近追平时短暂锁表补完最后一批，把索引挂进 catalog。

## 11.2 全局易错点 Top 20（考前最后过一遍）

1. B+ 树精确查找**必须到叶子**，键等于内部分隔键也不能停（那是 B-tree）。
2. 内部节点**键数 = 孩子数 − 1**；计数题先算孩子。
3. 叶子分裂**复制**分隔键上去；内部分裂**搬移**中位键上去。
4. 根分裂 → 新根 1 个键 2 个孩子，**树高 +1 且所有路径同时加高**。
5. 删除借用 → **父分隔键要更新**；根只剩 1 孩子 → 删根、高度 −1。
6. 序列化时**内存指针必须换成文件偏移**；写指针值毫无意义（unique_ptr 同理）。
7. 二级索引**必须稠密**；稀疏索引只配聚簇文件。
8. 复合索引 (a,b)：a 等值 + b 任意可用；**a 范围 + b 等值不高效**。
9. 哈希索引不支持范围查询（键无序，不是慢在哈希函数）；PostgreSQL 不鼓励 hash index。
10. LSM 删除 = 插入**删除标记**；查询要查**多棵树**（Bloom filter 缓解）。
11. Patricia trie 分裂**不增加字符总数**；trie 复杂度 O(L) 与 N 无关。
12. 倒排索引：生产系统主流是 **document-partitioned**（查询广播+归并）；ranking 与索引是**两个阶段**。
13. R-tree **无全序、无中序遍历**；MBR **允许重叠**；quadratic split 种子 = **最远**点对。
14. 学习索引**可能找不到存在的键**（radius 之外）；B+ 树永远准确。
15. `next()` 推进并返回 bool；`getOutput()` 只取当前元组（Select 里是**深拷贝**）。
16. 纯虚函数 `= 0` ≠ 编译期绑定；虚函数走**运行期 vtable**；模板在**编译期**实例化。
17. HashAggregation 是**阻塞算子**，输出**无序** → ORDER BY 需要 Sort（分组键=排序键时可换有序聚合）。
18. CreateIndex 在 **open() 里建完索引**，next() 为空。
19. 2PL **防不了死锁**；wait-die 老等少、wound-wait 老伤少，重启用**原时间戳**；TSO 无死锁但可能级联；Thomas 规则只忽略过时**写**。
20. SI 有 **write skew**，不可串行化（Oracle 的 serializable 实为 SI）；crabbing 可能死锁（重启查找解决）；`select for update` 不防幻读。
