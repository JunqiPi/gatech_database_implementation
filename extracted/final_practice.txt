1. A column store uses block-wise delta encoding for 64-bit integer columns: within each block, it stores the first value and then encodes differences (deltas) to subsequent values, followed by bit-packing based on the maximum delta in the block.

Which statement about situations where delta encoding is a poor choice is NOT correct?

A. For workloads dominated by random point lookups, delta encoding can be less attractive because decoding may require reconstructing a sequence of values within a block just to access a single position.

B. If the column values in storage order are effectively random (no correlation between neighbors), the deltas are also large and random, so delta encoding yields little or no compression.

C. On pages that are frequently updated in place, delta encoding can be attractive because small changes may require recomputing only a few deltas, so update performance is good along with compression.

D. If data exhibits large periodic jumps (e.g., a counter that frequently resets to zero), a single large delta in a block can force a wide bit-width for all deltas in that block, reducing compression effectiveness.

4. A storage engine considers two designs for a generic B+Tree leaf page that stores key–record pairs.

12345678910111213
// Design A: store records inline in the leaf template 
<typename Key, typename T> struct BPlusLeafInline { 
 Key keys[NUM_SLOTS]; 
 T records[NUM_SLOTS]; // records stored by value 
 // ... metadata ... 
};

// Design B: store pointers to records in a separate heap/segment template 
<typename Key, typename T> struct BPlusLeafPtr { 
  Key keys[NUM_SLOTS]; 
  T* record_ptrs[NUM_SLOTS]; // pointers to records 
  // ... metadata ... 
};
Which statement about the performance and storage implications of these two designs is NOT correct?

A. With large, fixed-size, inline records, each leaf page holds fewer key-record pairs when T is large, which can increase the height of the B+Tree and the number of page I/Os for point and range queries.

B. Storing only pointers in the leaf can reduce write amplification for updates to non-indexed fields of T, because the record can often be updated in place in the heap without moving or rewriting the leaf entry.

C. With pointer-based leaves, more (key, pointer) entries fit into a leaf page when T is large, which can reduce tree height and index I/Os, at the cost of an extra pointer chase (and potential page access) to fetch each record.

D. For small, fixed-size records that fit comfortably in a page, pointer-based leaves are faster for range queries, because the engine only needs to scan the key and pointer arrays and can ignore the actual record contents.
