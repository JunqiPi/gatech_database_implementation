## 📖 三、核心概念精讲

### 3.1 两种存储：易失 vs 持久（高频考点）

| | **DRAM（内存）** | **SSD / HDD（磁盘）** |
|:---|:---|:---|
| 别名 | volatile（易失） | non-volatile / persistent（持久） |
| 断电 | **数据丢失** | **数据保留** |
| 速度 | 快，访问 ≈ 50 纳秒 | 慢，SSD ≈ 50 微秒（**慢约 1000 倍**） |
| 成本 | 贵，≈ $10/GB | 便宜，SSD ≈ $0.10/GB（**便宜约 100 倍**） |
| 用途 | 缓存热数据、查询中间结果 | 数据库主体、事务日志、所有 page |

> 💡 **数据生命周期（两阶段）**：① 事务更新先写**内存**（快）；② commit 后把改动刷到**磁盘**（持久）。利用内存的快 + 磁盘的持久。这就是为什么需要**缓冲管理器**（M5）来桥接两者。

> 🌟 **Paper 4（Umbra）的关联**：DRAM 涨价又涨不动（2TB ≈ $20000），SSD 又快又便宜（2TB ≈ $500，读 3.5GB/s，差 40 倍）。所以现代做法 = **大内存缓冲 + 快 SSD**，"用磁盘系统做出内存级性能"（标题原意）。

### 3.2 存储层级与磁盘性能（ch12）

**存储层级（越往上越快越贵越小）**：

```
寄存器/Cache   1–5 ns        ┐ 易失 (volatile)
主存 DRAM      60–100 ns     ┘   primary
─────────────────────────────
闪存/SSD       20–100 μs     ┐ 持久
磁盘 HDD       5–10 ms       ┘   secondary (on-line)
磁带 Tape      顺序访问       ┘   tertiary (off-line, 归档)
```

**磁盘（HDD）性能三件套**：
- **访问时间 = 寻道时间(seek) + 旋转延迟(rotational latency) + 传输时间**
  - 寻道：移动磁臂到正确磁道，平均 ≈ 最坏的一半，4–10 ms
  - 旋转延迟：等扇区转到磁头下，4–11 ms（取决于转速）
- **IOPS**（每秒随机块读数）：HDD 仅 **50–200 IOPS**；SSD 4KB 随机读 ≈ **10000 IOPS**（并行可到 100000+）。
- **顺序访问 vs 随机访问**：顺序只需第一次寻道，之后连续；随机每次都要寻道 → 慢。
- **MTTF**（平均无故障时间）：3–5 年。AFR（年化故障率）= (365×24)/MTTF ×100%。

**SSD / 闪存要点**：NAND flash，按页读（512B–4KB，20–100μs），随机和顺序读差别不大；**只能写一次，重写前要先擦除**（erase block 256KB–1MB）；FTL（闪存转换层）做逻辑→物理映射；**磨损均衡（wear leveling）**把冷数据放到擦写多的块。

**RAID**（冗余磁盘阵列）：用多盘提速 + 冗余防丢。Level 0=条带化不冗余；Level 1=镜像；Level 5=分布式奇偶校验；Level 6=双校验。

### 3.3 C++ 文件 I/O

- **`std::ifstream`** 读文件、**`std::ofstream`** 写文件、**`std::fstream`** 读写。
- 读之前**先检查文件是否存在**（不存在就报错退出，避免数据损坏）——重要的错误处理。
- `std::ios::in | std::ios::out` 用按位或组合"既读又写"。
- **缓冲 I/O**：写入先进内存缓冲区（优化），`flush()` 强制刷到磁盘（防程序意外终止丢数据）。
- 用 `chrono` 库给操作计时，找性能瓶颈。

---

### 3.4 Field 类：支持多种数据类型（int/float/string）

- **enum（枚举）** `FieldType { INT, FLOAT, STRING }`：命名常量，代码更可读。
- **union（联合体）**：让 int / float / char* **共享同一块内存**，省空间（大小 = 最大成员）。int 和 float 都 4 字节，所以 union 占 4 字节。
- **构造函数重载（constructor overloading）**：一个吃 int、一个吃 float、一个吃 string，根据参数类型自动选。
- **字符串要动态内存**：string 长度不定 → 用 **`new`** 在**堆**上分配 `length+1` 字节（+1 给 `\0` 空终止符）。
- **析构函数（destructor）**：对象销毁时自动调用，负责 `delete` 释放堆内存，防泄漏。**每个 `new` 必须配一个 `delete`**。
- **多态容器**：Field 能装 int/float/string 三种"形态"（polymorphic = 多种形态）。

### 3.5 ⚠️ 裸指针的 4 大坑 → 智能指针（重灾区，必懂）

| 坑 | 是什么 | 后果 |
|:---|:---|:---|
| **内存泄漏 memory leak** | `new` 了忘记 `delete` | 内存越用越多，最终系统变慢/崩溃 |
| **悬空指针 dangling pointer** | 内存已释放，指针还指着它 | 访问 = 数据损坏/崩溃 |
| **重复释放 double free** | 同一块内存 `delete` 两次 | 未定义行为/崩溃 |
| **所有权不清 ownership ambiguity** | 不知道谁负责 `delete` | 多函数共享指针时混乱 |

**解药：智能指针 `std::unique_ptr`**（属于 `<memory>` 库）：
- **自动管理**：指针离开作用域时**自动 `delete`** → 杜绝泄漏（无需手动 delete）。
- **唯一所有权（unique ownership）**：内存恰好被释放一次 → 杜绝 double free。
- reset 或离开作用域时置空 → 不会变悬空指针。
- 用 `std::move` **显式转移所有权** → 解决所有权不清。

> 🔑 **RAII 原则**（Resource Acquisition Is Initialization）：把资源（内存/文件句柄/锁）的生命周期**绑到对象的生命周期**上。对象建→拿资源，对象毁→放资源。智能指针、`lock_guard`、`fstream` 都是 RAII 的例子。

### 3.6 拷贝语义（copy semantics）—— 深拷贝 vs move

- 对象被**按值传递、从函数返回、赋值**时会触发拷贝。
- **拷贝构造函数（copy constructor）**：用一个已有对象**创建**新对象。
- **拷贝赋值运算符（copy assignment operator）**：把一个已有对象的内容**赋给**另一个已有对象。
- **深拷贝（deep copy）**：新对象拥有**自己独立的**字符串副本（而非共享同一块内存）。
  - ⚠️ 深拷贝**不是**为了省内存（恰恰相反，它复制了一份），而是为了**安全**：各自独立、互不影响、销毁一个不影响另一个。
- **`unique_ptr` 不能拷贝**（唯一所有权），但能 **move**（`std::move` 转移所有权，无复制开销）。tuple 类用 `vector<unique_ptr<Field>>`，靠 move 转移。

### 3.7 堆（heap）vs 栈（stack）

| | **堆 Heap** | **栈 Stack** |
|:---|:---|:---|
| 用途 | 动态分配（`new`），大小运行时才定 | 函数局部变量，大小编译期已知 |
| 生命周期 | 持续到显式释放（超出作用域仍在） | 函数返回即自动销毁 |
| 管理 | 程序员管理（或智能指针） | C++ 运行时自动管理 |
| 大小 | 大（受 DRAM 限制） | 小 |
| 速度 | 慢（有碎片管理开销） | 快（连续内存） |

> ⚠️ **大坑**：函数返回一个**栈上**分配的对象的引用/指针 → 该对象已销毁 → **未定义行为**（可能崩溃或悄悄出错）。要持久就用堆（配智能指针）。

### 3.8 Page 类与序列化/反序列化（核心机制）

**为什么要序列化**：内存里的对象有指针、`std::string` 有容量/动态增长——**这些指针存到磁盘毫无意义**（下次运行地址全变）。必须把数据**线性化（linearize）成字节流**才能存磁盘。

- **Page（页）**：磁盘存储的基本单位，通常 **4KB**。BuzzDB 把多个 tuple 打包进固定大小的页（插入前先检查总大小不超 4KB）。
- **序列化（serialization）**：内存对象 → 磁盘字节流。顺序：
  1. 先写**元组总数（num_tuples）**
  2. 每个 tuple：写**字段数（num_fields）**
  3. 每个 field：写**类型（type）+ 数据长度（length）+ 实际数据**
  - **为什么要写 length**：变长字段（如 string）反序列化时**需要知道读多少字节**。
- **反序列化（deserialization）**：磁盘字节流 → 内存对象。读 num_tuples → 每 tuple 读 num_fields → 每 field 读 type、length、data，按 length 动态分配内存读回。
- **`reinterpret_cast`**：把字节指针"重新解释"成另一种类型指针（如 `char*` ↔ `int*`），底层读写字节时用。**不改二进制值，只改解释方式**，要小心用。
- **静态方法 `deserialize`（static method）**：不用先 new 一个 Page 对象，直接从磁盘数据构造页。静态方法属于类整体，无需实例即可调用。

> 🔑 **内存表示 vs 磁盘表示（测验 Q7 考点）**：内存里 `std::string` 用指针/容量动态增长；磁盘上数据被**线性化成 `[length][bytes]` 字节流**，**裸指针既不存也无意义**。

---

### 3.9 删除 + 内存↔磁盘同步（一致性）

- 删除 tuple：按 index 从页（vector）里移除，减少 used size。
- ⚠️ **持久性不匹配（persistence mismatch）**：在**内存**里删了 tuple，但**没写回磁盘** → 再从磁盘读，删除没生效！
- **解法**：内存改动后，**必须触发序列化把页写回磁盘**，保证内存与磁盘一致。
- **核心思想**：已提交事务的每个内存改动都应反映到磁盘，防数据丢失。

## 📄 四、配套论文 / 章节分析（论文是考试重点）

### 📕 Paper 3 — Stonebraker, "Operating System Support for Database Management" (1981)

> **地位**：经典论证——**"操作系统提供的服务，对数据库来说要么太慢、要么不合适，所以 DBMS 得自己造轮子。"** 这正是 BuzzDB 自己写 StorageManager / BufferManager 的理由。

**📐 结构拆解**（逐个 OS 服务批判）：
1. **缓冲池管理（Buffer Pool）**：OS 提供文件缓存（用 LRU），但有 4 个问题——
   - 性能开销大（一次取块要 1800–5000 条指令）
   - **LRU 不适合数据库访问模式**：顺序扫描时该用 "toss-immediately（用完即扔）"，不是 LRU
   - **预取（prefetch）不对**：OS 按文件顺序预取，但 DBMS 知道**下一个真正要读的块**（不一定是文件里的下一块）
   - **崩溃恢复**：DBMS 需要"选择性强制写出（selected force-out）"——commit 标志必须在 intentions list 之后才刷盘，OS 缓冲管理器不提供
2. **文件系统（File System）**：OS 给的是"字符数组文件"，但 DBMS 想要**带键访问的记录管理**。物理连续性（extent-based 优于一块一块散落，否则磁臂乱跑）。三棵树问题（i-node 块树 + 目录树 + DBMS 索引树，合一棵更高效）。
3. **调度/进程/IPC**：process-per-user vs server model。**护航现象（convoy phenomenon）**：持短期锁的进程被调度走，其它进程全堵在锁后。消息开销大（≈5000 指令）。
4. **一致性控制**：OS 能锁文件，但很少有更细粒度（页/记录）锁；commit point、ordering dependency。

**🎯 核心论点**：OS 服务对 DBMS "不太对"，DBMS 普遍**自建用户态缓冲池**绕开这些问题。DBMS 偏爱"小而高效、只提供所需服务"的 OS。

**✅ 优势/价值**：解释了**为什么数据库要自己管缓冲/存储**（贯穿 M3、M5）。"toss-immediately"思想正是 M5 缓冲池 flooding + 2Q 策略的前身。

**📝 可能考法**：为什么 DBMS 不直接用 OS 文件缓存？LRU 对顺序扫描为何差？什么是 convoy 现象？"selected force-out" 与 WAL 的关系。

---

### 📘 Paper 4 — Neumann & Freitag, "Umbra: A Disk-Based System with In-Memory Performance"

> **地位**：Paper 3 的"现代续集"。讲现代 DBMS 怎么造一个**又持久又快**的缓冲管理器。

**📐 结构拆解**：
- **§1 动机**：纯内存系统（HyPer）快但数据超内存就崩；DRAM 贵且涨不动，SSD 便宜又快 → 大内存缓冲 + 快 SSD。
- **§2 缓冲管理器（核心贡献）**：
  - **可变大小页（variable-size pages）**：传统是固定大小页，但大对象（长字符串、字典）塞不进单页很麻烦。可变大小页能原生连续存大对象。用**大小类（size class）**（64KiB 起，按 2 倍增长）。
  - 靠**虚拟内存映射**避免外部碎片（mmap 预留虚拟地址，pread 载入，MADV_DONTNEED 释放物理内存）。
  - **指针混写（pointer swizzling）**：swip = 64 位，要么是内存指针（swizzled）要么是磁盘 PID（unswizzled），避免全局哈希表瓶颈。
  - **版本化闩锁（versioned latches）**：exclusive / shared / **optimistic（乐观）** 三种模式。乐观闩锁记版本号、释放时校验，几乎无竞争。
- **§3 其它**：B+ 树组织关系、PAX 列式叶页布局、字符串处理（16 字节头，≤12 字符内联）、ARIES 恢复。

**🎯 核心论点**：用低开销 + 可变大小页的缓冲管理器，让"磁盘系统达到内存级性能"。实验显示缓冲管理器开销 <6%。

**✅ 优势**：可变大小页简化了整个系统对大对象的处理；乐观闩锁在多读场景几乎零竞争（**对应 M8 的 shared_mutex 思想**）。

**📝 可能考法**：可变大小页 vs 固定大小页的取舍；为什么纯内存系统不经济；乐观/共享/独占三种闩锁的区别（联系 M8）。

### 例题 1（测验 Q1）— CSV 解析为何多读一次
```cpp
bool parse_user_row(const std::string& line) {
  std::stringstream ss(line);
  std::string id, name, loc, extra;
  std::getline(ss, id, ','); std::getline(ss, name, ','); std::getline(ss, loc, ',');
  if (std::getline(ss, extra, ',')) return false; // 多读一次
  return true;
}
```
**题**：读完 3 个必需列后，为何还故意多 `getline` 一次、成功就返回 false？
- ✅ **正确**：**严格校验 schema——检测并拒绝列数比预期多的行**。
- ❌ 干扰项（隐藏 UUID 主键、stringstream 会抛异常、消费 Windows 的 `\r`）都是编造的。
- **考点**：防御式 CSV 解析——多一列就是脏数据，拒绝。

### 例题 2（测验 Q2）— `unique_ptr` 与序列化 ⚠️你做错
```cpp
struct Page { std::unique_ptr<char[]> data; uint32_t len; };
```
**题**：关于 `unique_ptr` 与序列化，哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"把 `unique_ptr` 移动/传进 write 函数，就会序列化它指向的数据。"** ← 错！
- **为什么错**：传 `unique_ptr` 本身**不会**自动序列化它指向的数据。序列化必须**显式写出值**（len + 字节负载），并在加载时重建新缓冲区。
- ✔ 对的说法：序列化必须写 len 和字节并在加载时重建；`unique_ptr` 不约束磁盘格式；序列化裸指针值跨运行无意义。
- **考点**：智能指针只管**内存生命周期**，不等于"会自动存盘"。序列化是另一回事，要手动写字节。

### 例题 3（测验 Q3）— 元数据放在末尾的后果 ⚠️你做错
**题**：页/段格式把"元组数量"元数据写在**所有元组字节之后**（头部没有指向尾部的指针），对反序列化有何影响？
- ✅ **正确**：**读者必须扫描/seek 到末尾才能得知元组数量，使反序列化复杂化。**
- ❌ 别选"反序列化更快（可跳过元数据）""OS 页缓存透明提供""安全性提升"——都错。
- **考点**：**元数据应放在头部**（先读到 num_tuples 才好按数量循环读）。放末尾要么 seek 到尾、要么扫全程，麻烦。这也是为什么 BuzzDB 序列化**先写 num_tuples 在最前面**。

### 例题 4（测验 Q4）— 深拷贝 ⚠️你做错
**题**：Field 的拷贝构造做**深拷贝**内部字符串。哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"深拷贝通过在多个 Field 间共享公共缓冲区来最小化内存占用。"** ← 错！
- **为什么错**：深拷贝恰恰是**不共享**——它给每个对象一份**独立**的副本，所以会**用更多**内存，不是更少。"共享缓冲区"那是**浅拷贝（shallow copy）**。
- ✔ 对的：深拷贝让按值传递安全（无生命周期/别名问题）；每个对象有独立数据防意外共享；避免悬空指针（销毁一个不影响其它副本）。
- **考点**：深拷贝 = 独立副本（更安全、更费内存）；浅拷贝 = 共享指针（省内存、危险）。**别把两者搞反**。

### 例题 5（测验 Q6）— `unique_ptr` 遇异常
```cpp
void risky() {
  auto buf = std::make_unique<char[]>(4096);
  throw std::runtime_error("fail");
}
```
**题**：哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"为避免泄漏，必须在 catch 块里对 buf 调 `delete[]`，否则内存残留。"** ← 错！
- **为什么错**：`unique_ptr` 是 RAII——抛异常时**栈展开自动析构 buf、自动释放** 4096 字节，**根本不需要手动 delete**。
- **考点**：RAII 让异常安全"免费"——局部智能指针在栈展开时自动清理。

### 例题 6（测验 Q7）— 内存表示 vs 磁盘表示 ⚠️你做错
**题**：Document 类内存里用 `std::string`，磁盘上存成 `[length][bytes]`。哪个最准确描述内存 vs 磁盘表示的区别？
- ✅ **正确**：**内存里 `std::string` 用指针/容量动态增长；磁盘上数据被线性化成带长度的字节流，裸指针既不存也无意义。**
- ❌ 别选"磁盘保留文件相对指针以随机访问""序列化器写 string 的指针值并在加载时重建同地址""内存和磁盘都保留指针以便回滚恢复地址"——指针存盘毫无意义。
- **考点**：跨运行地址会变，**指针不能存盘**；必须线性化成字节。这是序列化的根本原因（同 M3 §3.8）。

### 例题 7（测验 Q23）— SSD vs HDD 的 IOPS 比（计算题）
**题**：随机 4KB 读。HDD：寻道+旋转 ≈ 8 ms；SSD 随机读 ≈ 80 µs。单个未完成 I/O 时，SSD vs HDD 的随机读 IOPS 比约为？
- ✅ **正确：≈ 100×（SSD 高约 100 倍）**。
- **算法**：IOPS ∝ 1/延迟。比值 = HDD延迟 / SSD延迟 = 8 ms / 80 µs = 8000 µs / 80 µs = **100**。
- **考点**：单位换算（1 ms = 1000 µs）+ IOPS 与延迟成反比。

### 例题 8（测验 Q32）— 性价比计算 ⚠️你做错
**题**：层级 A：延迟 ≈ 100 ns，成本 $1000/月；层级 B：延迟 ≈ 400 ns，成本 $300/月。吞吐 ∝ 1/延迟，性价比用 $/Mops（每百万次操作每秒的美元，越低越好）。谁性价比更好、约多少？
- ✅ **正确：层级 A；约 $100/Mops**。
- **算法**：
  - A 吞吐 ∝ 1/100ns = 10⁷ ops/s = **10 Mops**。性价比 = $1000 / 10 Mops = **$100/Mops**。
  - B 吞吐 ∝ 1/400ns = 2.5×10⁶ ops/s = **2.5 Mops**。性价比 = $300 / 2.5 Mops = **$120/Mops**。
  - A（$100）< B（$120），**A 更划算**。
- **考点**：吞吐 = 1/延迟，性价比 = 成本/吞吐，**数字越小越好**。你之前可能算反了或选了 B。

### 例题 9（测验 Q25）— 为什么 `num_pages` 要 `std::atomic` ⚠️你做错
```cpp
class StorageManager { std::atomic<uint64_t> num_pages; };
```
**题**：为什么 `num_pages` 要声明成 `std::atomic` 而非普通 int？
- ✅ **正确**：**因为并发线程可能在一个线程扩展文件时，另一些线程正读 `num_pages` 做边界检查。**
- ❌ 干扰项（32 位上 int 上限 4GB、atomic 绕过 friend 权限、OS 要求 atomic 映射 SSD 扇区）都是编造的。
- **考点**：多线程同时读写共享计数器 → 需要原子操作防 data race（联系 M6）。

### 例题 10（测验 Q27）— `from_chars` vs `stoi` ⚠️你做错
```cpp
int parse_id(const std::string& s) {
  int val = 0; std::from_chars(s.data(), s.data()+s.size(), val); return val;
}
```
**题**：用 `std::from_chars` 而非 `std::stoi` 解析整数，哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"`std::stoi` 会通过抛 `std::invalid_argument` 异常安全地拒绝尾随字符（如 '100abc'），更适合严格 CSV 解析。"** ← 错！
- **为什么错**：`std::stoi("100abc")` **不会**抛异常——它会**成功解析出 100 并忽略 "abc"**！只有完全无法解析（如 "abc"）才抛。所以它**不**能严格拒绝尾随字符。
- ✔ 对的：`from_chars` 返回含"首个未解析字符指针"的结构，可严格校验无多余字符；`from_chars` 不抛异常、不分配内存，高性能。
- **考点**：`stoi` 对 "100abc" 是**宽容**的（解析前缀），不适合严格校验；`from_chars` 才能精确知道哪里停下。

### 例题 11（测验 Q28）— 空闲空间图（Free Space Map）⚠️你做错
**题**：有些 DBMS 把空闲空间元数据放在专门的页（如 Postgres 的 Free Space Map）。哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"专门的空闲空间元数据页有助于减少页内碎片和页压缩的需要。"** ← 错！
- **为什么错**：FSM 只是帮你**快速找到哪页有空间插入**，它**不解决页内碎片**——碎片整理（compaction）是页内的事，跟 FSM 无关。
- ✔ 对的：FSM 集中存储避免扫描每个数据页，加速插入选址；重负载下若不缓存/分区会成热点；从数据页移走元数据略增元组密度但插入时要额外 I/O 查 FSM。
- **考点**：FSM 管"哪页有空"（插入选址），**不管页内碎片整理**。

## 🏋️ 六、举一反三 + 新增模拟考题（含答案）

> 🟢基础 🟡进阶 🔴挑战

### A. 选择题

**A1 🟢** 关于 DRAM 和 SSD，下面哪个说法**正确**？
A) DRAM 持久、SSD 易失 B) DRAM 比 SSD 慢但便宜
C) DRAM 快但断电丢数据，SSD 慢但持久 D) 两者速度一样
<details><summary>答案</summary>**C**。DRAM 快(~50ns)、易失、贵；SSD 慢(~50µs)、持久、便宜。</details>

**A2 🟡** 序列化一个含变长字符串字段的 tuple 时，为什么每个字段要写"长度（length）"？
<details><summary>答案</summary>因为反序列化时**需要知道读回多少字节**——变长字段（string）没有固定大小，必须靠 length 才能准确读回。</details>

**A3 🟡** 下面哪个**不是**裸指针的固有问题？
A) 内存泄漏 B) 悬空指针 C) 自动垃圾回收 D) 重复释放
<details><summary>答案</summary>**C**。裸指针**没有**自动 GC——这正是问题之一（要手动管理）。A/B/D 是裸指针的三坑（加"所有权不清"共四坑）。</details>

**A4 🔴** 一块 HDD 随机读延迟 10 ms，一块 SSD 随机读延迟 100 µs。SSD 的随机读 IOPS 约是 HDD 的几倍？
<details><summary>答案</summary>10 ms / 100 µs = 10000 µs / 100 µs = **100 倍**。（IOPS ∝ 1/延迟）</details>

**A5 🔴** 函数 `int& f() { int x = 5; return x; }` 返回后使用返回值，会发生什么？为什么？
<details><summary>答案</summary>**未定义行为**。x 是**栈**上局部变量，函数返回即销毁，返回它的引用 = 悬空引用。要持久应在**堆**上分配（用智能指针）。</details>

### B. 判断题

**B1 🟢** "智能指针 `unique_ptr` 在抛异常时，栈展开会自动释放它管理的内存，无需手动 delete。"
<details><summary>答案</summary>**对**。这是 RAII（测验 Q6）。</details>

**B2 🟡** "把一个 `unique_ptr` 传进 write 函数，就会自动把它指向的数据序列化到磁盘。"
<details><summary>答案</summary>**错**。智能指针只管内存生命周期，序列化必须**手动写出值（length+字节）**（测验 Q2）。</details>

**B3 🟡** "`std::stoi("42abc")` 会抛异常拒绝，因为有尾随字符。"
<details><summary>答案</summary>**错**。它会成功返回 42、忽略 "abc"，不抛异常（测验 Q27）。要严格校验用 `from_chars`。</details>

### C. 简答题

**C1 🟡** 为什么内存里对象的"指针"不能直接存到磁盘？序列化是怎么解决的？
<details><summary>参考答案</summary>因为程序每次运行内存地址都不同，存下来的指针下次运行指向错误位置、毫无意义。序列化把数据**线性化成字节流**（如 `[length][bytes]`），只存值不存指针；反序列化时在新内存里重建对象。</details>

**C2 🔴** Paper 3 为什么说 LRU 对数据库的某些访问模式很差？数据库能怎么改进？
<details><summary>参考答案</summary>顺序扫描时，被扫过的页短期内不会再用，但 LRU 会把它们当"最近用过"留在缓存，挤掉真正的热页。数据库**知道自己的访问模式**，对"扫一遍就不用"的页该用 toss-immediately（用完即扔），只对会重用的页用 LRU——这就是 M5 的 2Q 策略思想。</details>

### D. 应用题

**D1 🔴** 一个页序列化格式为：`[num_tuples][tuple1][tuple2]...`，每个 tuple 为 `[num_fields][field1]...`，每个 field 为 `[type][length][data]`。
(1) 反序列化时第一步读什么？为什么放在最前面好？
(2) 如果把 num_tuples 改放在文件**末尾**，反序列化会有什么麻烦？
<details><summary>参考答案</summary>(1) 先读 num_tuples，这样才知道循环读几个 tuple；放最前面让读者立刻知道总数。(2) 放末尾的话，读者必须先 seek 到末尾或扫完全程才知道有几个 tuple，使反序列化复杂化（测验 Q3）。</details>

## ⭐ 七、易错点 & 速记

| 易错点 | 正确理解 |
|:---|:---|
| 以为传 `unique_ptr` 就会序列化数据 | 不会！序列化要**手动写字节** |
| 深拷贝/浅拷贝搞反 | 深拷贝=独立副本(费内存、安全)；浅拷贝=共享指针(省内存、危险) |
| 以为异常要手动 delete 智能指针 | RAII 自动释放，**不用** delete |
| 以为 `stoi("100abc")` 会抛异常 | 不会，它解析出 100 忽略 abc |
| 以为 FSM 能减少页内碎片 | FSM 只管"哪页有空"，不管碎片整理 |
| 把栈对象引用返回 | 栈对象函数返回即销毁 → 悬空 |
| 元数据放页末尾 | 放**头部**（先读 num_tuples） |
| IOPS 计算 | IOPS ∝ 1/延迟，记得 ms↔µs 换算 |

**🎵 口诀**：
- 裸指针四坑：**"漏、悬、双、权"**（泄漏/悬空/双重释放/所有权不清）
- 序列化：**"先写总数，每字段写'类型+长度+数据'"**
- 存储：**"内存快易失贵，磁盘慢持久廉，差一千倍速、一百倍价"**
- RAII：**"对象生即取资源，对象灭即放资源"**
