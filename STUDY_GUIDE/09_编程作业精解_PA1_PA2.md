## 📦 PA1 — Flat-File 数据库（对应 M1–M4）

### 一、它造了什么

一个**平面文件（flat-file）数据库**，管理三个 CSV：`users / posts / engagements`（就是 M1 社交媒体分析的例子真身）。

**三个数据类**（`User / Post / Engagement`）：
```cpp
class User {
public:
    int id; std::string username; std::string location;
    User(int id, std::string username, std::string location)
        : id(id), username(std::move(username)), location(std::move(location)) {}
    std::string toCSV() const;
};
```
- 注意构造函数用 **`std::move`** 转移字符串所有权（避免拷贝）→ M3 的 move 语义。
- 每个类有 `toCSV()` 把对象**序列化**成 CSV 行 → M3 序列化思想。

**存储结构**：`map<int, unique_ptr<User>>`（id → 对象的智能指针）
- 用 `map`（有序）而非 `unordered_map`：方便按 id 排序输出。→ M7 容器选择。
- 用 `unique_ptr`：自动内存管理，唯一所有权。→ M3 智能指针。

---

### 二、关键操作 + 对应模块

| 操作 | 做什么 | 对应模块/考点 |
|:---|:---|:---|
| `parseUsers/Posts/Engagements` | 读 CSV，跳过表头，**跳过空行/格式错误行**，解析进 map | M3 文件 I/O、CSV 解析 |
| `parseInt` | `stoi(s,&idx); return idx==s.size()` —**严格校验**，拒绝 "100abc" | M3（对应测验 Q27 stoi 陷阱！） |
| `loadFlatFile` | 单线程加载，最后 `scoped_lock` 锁住、`commit` 原子换入 | M2 原子提交 |
| `loadMultipleFlatFilesInParallel` | **每个 CSV 一个线程**并行解析，再统一 commit | M2/M6 多线程 |
| `writeAtomicallyToCSV` | 写**临时文件**→`fs::rename` **原子交换** | M2 原子性、M3 持久化 |
| `updateUserName` | 改名要**重写 users + posts + engagements 三个 CSV** | **M1 flat-file 冗余的代价！** |
| `addEngagementRecord` | 加互动前检查 **postId 和 username 存在**（外键检查） | M1 引用完整性 |
| `getAllEngagementsByLocation` | 按地点统计 like/comment，要先扫 users 找该地点用户名 | M1 flat-file 查询慢（要扫表） |

> 🔑 **PA1 最大的教学点**：`updateUserName` 一个改名操作要重写三个文件、遍历所有 posts/engagements 改用户名——**这就是 M1 说的 flat-file "冗余 + 改名要改 N 处" 的痛点**，亲手体会了为什么需要关系模型（只在 users 改一行）。

---

### 三、PA1 用到的 C++/并发要点（高频考点）

1. **`stoi` 严格校验**：`stoi(s, &idx)` 后检查 `idx == s.size()`，确保整个字符串都是数字（拒绝 "100abc"）。→ 对应测验 Q27（裸 `stoi` 默认是宽容的，要靠 idx 检查才严格）。
2. **原子写文件**：写临时文件 + `rename` = 原子交换。崩溃时要么旧文件完整、要么新文件完整，**不会半截**。→ M2 原子性、持久性。
3. **`scoped_lock`/`mutex`**：commit 时加锁，保证读者**永不看到半更新状态**（一致快照）。→ M2 隔离性、M6 mutex。
4. **`atomic<unsigned long> tempCounter`**：生成唯一临时文件名，并发安全。→ M6 atomic。
5. **并行加载**：三个文件三个线程，`join` 等待，再 commit。→ M6 多线程。

---

### 四、PA1 可能的考法

- **概念**：为什么 flat-file 改用户名代价大？（要重写多个文件、遍历改所有引用）→ 答：冗余，关系模型只需改一行。
- **代码理解**：`parseInt` 为什么检查 `idx == s.size()`？（严格拒绝尾随字符）
- **并发**：为什么 commit 要加锁？（保证读者看到一致快照，不看到半更新）
- **原子写**：为什么写临时文件再 rename，而不直接覆盖原文件？（rename 原子，避免崩溃时文件损坏/半写）
- **外键**：`addEngagementRecord` 为什么先检查 postId/username 存在？（引用完整性，不能有指向不存在用户的互动）

## 🗄️ PA2 — Buffer Manager（对应 M5、M6、M8）

### 一、它造了什么

一个**线程安全的缓冲管理器**，用 **2Q 替换策略** 管理页缓存，支持多线程并发读写。这正是 **M5（缓冲池+2Q）+ M8（细粒度锁）** 的代码实现。

**五个核心类**：

| 类 | 职责 | 对应模块 |
|:---|:---|:---|
| **`Page`** | 4096 字节固定大小页（最基本存储单位） | M3/M4 |
| **`BufferFrame`** | 装**一个**页 + 元数据（page_id、**dirty 脏标志**、`atomic<bool> exclusive_`） | M5 |
| **`BufferManager`** | 控制并发、替换、2Q 策略、fix/unfix 页 | M5 核心 |
| **`PageGuard`** | **RAII 包装**：离开作用域自动 unfix 页、释放锁（**move-only**） | M3/M6 RAII |
| **`FrameLockTable`** | **每帧一把 `shared_mutex`**，细粒度共享/独占锁 | **M8 核心** |
| **`TwoQPolicy`** | FIFO + LRU 两队列，决定驱逐谁 | M5 的 2Q |

---

### 二、核心数据结构（来自 buffer_manager.hpp）

```cpp
class BufferManager {
    static constexpr size_t MAX_PAGES_IN_MEMORY = 10;     // 缓冲池只装 10 页（调试友好，见 M6）
    StorageManager storage_manager_;                       // 底层磁盘读写 (M3/M4)
    std::vector<std::unique_ptr<BufferFrame>> buffer_pool_;// 缓冲池
    std::unordered_map<PageID, FrameID> page_to_frame_;    // 页→帧 快速查找 (M5)
    std::array<std::atomic<int16_t>, MAX_PAGES_IN_MEMORY> use_counters_; // pin 计数(原子!) (M6/M8)
    std::set<PageID> pinned_pages_;                        // 被 pin 的页（不可驱逐）
    FrameLockTable frame_lock_table_;                      // 细粒度每帧锁 (M8)
    std::unique_ptr<Policy> policy_;                       // 多态策略指针 (M5)
    std::mutex buffer_mutex_;                               // 保护类级变量的粗锁
};
```

> 💡 **看这个结构就把模块串起来了**：`unique_ptr`(M3) + `unordered_map` 查找(M5) + `atomic` pin 计数(M6) + `FrameLockTable` 细粒度锁(M8) + 多态 `Policy*`(M5) + `dirty_` 脏标志(M5)。

---

### 三、两个核心方法的流程（高频考点）

**`fix_page(page_id, exclusive)`** —— 固定一个页（返回 PageGuard）：
1. 页**在内存**？→ 更新策略访问信息 → 加锁（shared/exclusive）→ **use_counter +1** → 返回 PageGuard。
2. 页**不在**？→ 找空帧；缓冲池满 → 让策略选驱逐候选 → **脏页先写回磁盘**（独占锁下）→ 从策略移除 → 用 StorageManager 从磁盘加载 → 初始化帧元数据 → 加锁 → use_counter +1 → 返回 PageGuard。

**`unfix_page(frame, is_dirty)`**（私有，由 PageGuard 析构调用）：
1. 若 `is_dirty` → 标记帧为 **dirty**（驱逐时才写盘）。
2. **原子地** use_counter -1。归零 → 该页**可被驱逐**。
3. 通过 FrameLockTable **释放锁**（shared 或 exclusive）。

**2Q 驱逐规则**：
- 优先从 **FIFO 队列**驱逐（read-once 冷页）；FIFO 都在用 → 从 **LRU 队列**驱逐。
- **脏页驱逐前必须写回磁盘**（独占锁下），防丢数据。
- 两队列都没可驱逐页（全被 pin）→ 抛 **`buffer_full_error`**。

---

### 四、PageGuard 的 RAII + move-only（高频考点）

```cpp
class PageGuard {
    BufferManager* bm_; BufferFrame* frame_; bool dirty_;
public:
    ~PageGuard();                                  // 析构自动 unfix_page → 释放锁、减 pin
    PageGuard(const PageGuard&) = delete;          // 禁止拷贝
    PageGuard& operator=(const PageGuard&) = delete;
    PageGuard(PageGuard&& other) noexcept;         // 允许 move
    PageGuard& operator=(PageGuard&& other) noexcept;
    void setDirty();                               // 改了页就标记脏
};
```
- **RAII**：拿到 guard = 页被 fix；guard 离开作用域 = 自动 unfix（释放锁、减 pin count）。即使抛异常也保证释放。→ M3/M6 RAII。
- **Move-only（只移动不拷贝）**：像 `unique_ptr` 一样唯一所有权。move 时要把旧对象的 `frame_` 置空，**防止 moved-from 对象析构时误调 unfix_page**（双重释放）。→ M3 move 语义。

用法：
```cpp
{
    auto guard = bm.fix_page(page_id, /*exclusive=*/false);  // 拿锁+pin
    auto* data = reinterpret_cast<uint64_t*>(guard->page_data.get());  // reinterpret_cast (M4)
    guard.setDirty();   // 若改了页
}  // guard 析构 → 自动 unfix（解锁、减 pin）
```

---

### 五、FrameLockTable 细粒度锁（M8 核心）

- **不能用一把巨锁锁整个缓冲池**（会毁掉并发）。
- 用 `FrameLockTable::lock_shared(FrameID)` / `lock_exclusive(FrameID)` —— **每帧一把 `shared_mutex`**：
  - 读 → 共享锁（多读者并发）；写 → 独占锁（单写者）。→ M8 的 shared_mutex。
- `fix_page` 取帧时按访问类型加对应锁，`unfix_page` 释放。

> 🔑 **PA2 把 M5 和 M8 完美合一**：M5 的 2Q 策略（驱逐）+ M8 的细粒度共享/独占锁（并发）。`use_counters_` 用 `atomic`（M6）防 pin 计数竞态。

---

### 六、PA2 可能的考法

- **fix/unfix 流程**：fix_page 命中和未命中各做什么？unfix_page 三步（标脏、减 pin、解锁）。
- **2Q 驱逐**：先驱逐哪个队列？脏页驱逐前要做什么？全 pin 了抛什么异常？
- **PageGuard**：为什么 move-only？move 时为什么要置空旧对象的 frame_？（防 moved-from 析构误 unfix → 双重释放）→ 联系测验 Q20（释放/竞态）。
- **FrameLockTable**：为什么不用一把全局锁？（毁并发）读写各用什么锁？
- **atomic**：use_counter 为什么用 `atomic<int16_t>`？（多线程并发 fix/unfix 同一页，pin 计数要原子）→ 测验 Q25。
- **dirty 标志**：脏页为什么要在驱逐前写回？（防丢已修改数据）。
