## 0. 一分钟看懂这门课在干嘛

这门课不是教你"怎么用数据库"（写 SQL），而是教你**怎么亲手造一个数据库**。
我们要从零搭一个叫 **BuzzDB** 的数据库系统，一层一层往上盖楼：

```
          ┌─────────────────────────────────────────────┐
   上层    │  查询 / 索引 (Index)        ← M5,M7,M8        │  "怎么快速找到数据"
          ├─────────────────────────────────────────────┤
   中层    │  缓冲管理 (Buffer Manager)  ← M3(M5)          │  "怎么少读慢磁盘"
          │  多线程并发 (Concurrency)   ← M4(M6),M6(M8)   │  "多人同时用不出错"
          ├─────────────────────────────────────────────┤
   底层    │  页 / 槽页 (Page/Slotted)   ← M2(M4)          │  "数据在页里怎么排"
          │  存储管理 (Storage/Disk)    ← M1(M3)          │  "数据怎么存到磁盘"
          ├─────────────────────────────────────────────┤
   地基    │  关系模型 + 事务 (RM+ACID)  ← M1,M2           │  "为什么要有数据库"
          └─────────────────────────────────────────────┘
```

> 💡 **一句话主线**：数据必须存在**慢但持久**的磁盘（disk）上，而 CPU 很快——所以整门课都在解决一个矛盾：**"如何让又慢又笨重的磁盘，用起来像又快又聪明的内存"**。这也正是 Paper 4（Umbra）标题的意思。

## 2. 八个模块的"一句话 + 优势"速览

| Module | 它解决的问题 | 关键武器 | 为什么这么设计（优势） |
|:---:|:---|:---|:---|
| M1 | 用文本文件存数据太烂 | 关系模型(表+主外键) | 消冗余、可索引、并发安全、SQL 声明式查询 |
| M2 | 怎么把"全做或全不做"落地 | 事务 + ACID | 失败可回滚、并发不串味、崩溃不丢数据 |
| M3 | 数据要落到慢磁盘上 | 存储管理器 + 序列化 | 内存指针无意义→线性化成字节流才能持久 |
| M4 | 变长数据在页里乱放会碎 | 槽页 + 槽目录 | 删除/移动元组而 slot id 不变（间接层） |
| M5 | 反复读磁盘太慢 | 缓冲池 + 替换策略 | 把热页缓存在 DRAM，命中即免一次磁盘 I/O |
| M6 | 多核时代单线程浪费 | 多线程 + mutex | 并行吞吐↑，但要锁保护共享状态防 race |
| M7 | 全表扫描找一行太慢 | 哈希索引 | O(1) 定位，避免逐个元组比对 |
| M8 | 多线程同时改哈希表会坏 | 线程安全 + 闩锁 | 细粒度 latch 兼顾正确性与并发度 |

## 5. 推荐复习路线（按"理解依赖"排序，不是按编号）

1. **先打地基**：M1 关系模型 → M2 事务/ACID（理解"为什么要数据库"）
