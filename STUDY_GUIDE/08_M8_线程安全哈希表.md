## 📖 三、核心概念精讲

### 3.1 并行建索引 + 线程不安全（race condition）

- **并行建索引**：单线程逐页建索引太慢。多核上把页**分给多个线程**并行处理（如 7 页 2 线程 → 线程1 处理 3 页、线程2 处理 4 页）。
- **问题——线程不安全**：多线程同时更新索引同一处会**丢数据**。

**哈希表 race condition 例子**（线性探测，hash = key mod 10）：
- 线程1 插 key=15，线程2 插 key=25，**都 hash 到 slot 5**。
```
线程1 探测 slot 5，发现空 ──┐
                          （上下文切换）
线程2 探测 slot 5，也发现空 ──┐
线程1 切回，把 15 存入 slot 5
线程2 切回，把 25 也存入 slot 5  ← 覆盖了 15！数据丢失
```
- **线程安全（thread safety）= 多线程同时访问也不会数据丢失/损坏**。

---

### 3.2 用 mutex 串行化（最粗暴的修法）

- 用一个 **index mutex** + `std::lock_guard`：哪个线程改索引前先拿锁，挡住其它线程。
- 修复后：线程1 拿锁插 15 到 slot 5 → 解锁 → 线程2 拿锁，发现 slot 5 占了 → 探测到 slot 6 插 25。**两个 key 都正确插入，无丢失**。
- 谁先谁后取决于哪个线程先抢到锁，但**两种顺序都正确**（15、25 分别落在 5、6 或 6、5）。

> ✅ 全局锁**保证正确**，但所有线程串行 → **并发差**（回到单线程性能）。

---

### 3.3 ⭐ 细粒度锁（每槽一把锁）+ 为什么 `vector<unique_ptr<mutex>>`

- **细粒度锁（fine-grained locking）**：**每个槽一把 mutex**。线程只锁它要操作的那个槽，其它槽不受影响。
- 例：线程1 插 12（slot 2）、线程2 插 27（slot 7）→ 各锁各的槽，**并行进行**，互不等待。
- 对比：全局锁时，即使操作不同槽也要抢同一把锁 → 退化成单线程。

> ⚠️⚠️ **高频考点：为什么用 `vector<unique_ptr<mutex>>` 而不是 `vector<mutex>`？**
> - **`std::mutex` 不可移动、不可拷贝**（设计如此，防止意外移动正在使用的锁；它是和 OS 紧绑的底层同步原语）。
> - 但 **`std::vector` 扩容时需要把元素移动到新内存** → 要求元素**可移动**。
> - 矛盾！解法：存**指向 mutex 的 `unique_ptr`**。vector 扩容时只移动**指针**，不移动 mutex 本身 → 满足 vector 要求，又保持 mutex 状态一致。

**细粒度锁的取舍**：
- 优点：大幅提高并发（不同槽并行）。
- 缺点：锁多 → 获取/释放开销增加、**每把锁占内存**。
- **要找平衡**：高竞争的部分用细粒度，低竞争的用粗粒度就够。

---

### 3.4 ⭐ shared_mutex（共享锁）—— 读多场景提速

- **问题**：普通 mutex 对一个槽**同时只允许一个线程**，不管读还是写。但**多个读操作本可以安全地同时进行**（读不改数据）。读多时 mutex 浪费并发。
- **`std::shared_mutex`** 区分读和写：
  - **写**：用 **`std::unique_lock`**（独占，exclusive）——同时只一个写者，且写时无读者。
  - **读**：用 **`std::shared_lock`**（共享，shared）——**多个读者可同时持有**，只要没人在写。
- 效果：例如 16 个线程能**同时读**同一个槽（线程安全），读吞吐大增。
- 例：线程1 写 + 线程2、3 读：
  - 普通 mutex：3 个操作必须排队，一次一个。
  - shared_mutex：线程2、3 **同时读**（shared_lock），然后线程1 独占写（unique_lock）。

> 🌟 **Paper 4（Umbra）的关联**：Umbra 的 **versioned latch** 有 exclusive / shared / **optimistic** 三种模式，正是这个思想的进阶版——optimistic（乐观）读甚至不改锁状态，只记版本号，几乎零竞争。

---

### 3.5 三种并发协议对比（模拟器）

用 Python 模拟器（确定性、便于教学）比较**同一组操作**需要的**逻辑时间步**（越少越好）：

| 协议 | 规则 | 逻辑时间步 | 为什么 |
|:---|:---|:---:|:---|
| **全局 mutex** | 整个表一把锁 | **30**（最多） | 所有访问串行，一次一个线程 |
| **每槽 mutex** | 每槽一把锁 | **21** | 不同槽可并行，减少竞争 |
| **每槽 shared_mutex** | 每槽一把共享锁 | **15**（最少） | 不同槽并行 + 同槽多读并发 |

> 🔑 **结论**：粒度越细 + 区分读写 → 并发越高 → 完成同样操作用的时间步越少。**每槽 shared_mutex 在读多负载下最快**。

## 📄 四、配套分析

### 📕 Paper 4 — versioned latch（本模块进阶）
- Umbra 每个 buffer frame 有一个**版本化闩锁**，三种模式：
  - **exclusive（独占）**：像全局 mutex，写时用。
  - **shared（共享）**：多读者并存（对应 shared_lock）。
  - **optimistic（乐观）**：读时**只记版本号、不改锁**，释放时校验版本号是否变了——变了就重试。几乎零竞争，适合多读。
- 这是 M8 的 shared_mutex 思想在真实系统里的高级形态。

### PA2 关联（frame_lock_table）
- PA2 的缓冲管理器要支持并发访问 frame（缓冲帧），用的就是**每帧一把锁**的细粒度思想 + shared/exclusive 区分（读者共享、写者独占）——和本模块完全对应。

## 🧩 五、例题精解

### 例题 1（测验 Q20）— unfix_page 先放锁后查标志的竞态 ⚠️你做错
```cpp
void unfix_page(int frame_id) {
  BufferFrame& frame = buffer_pool[frame_id];
  // 全局 buffer_mutex 在这里被释放了
  if (frame.exclusive) { /* ... 释放独占锁 */ }
}
```
**题**：`unfix_page` 在**释放全局缓冲池锁之后**才检查 frame 的 `exclusive` 标志。关于"为什么危险"，哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"它会立即触发内核级线程 panic，因为 OS 检测到对未 pin 页的无保护并发内存读。"** ← 错！
- **为什么错**：这是**编造的**——OS **不会**因为这种用户态并发读而 panic。真正的危险是**数据竞争导致的逻辑错误/损坏**，而不是内核 panic。
- ✔ 对的（真实危险）：另一线程可能在此刻 `fix_page` 这个帧并把 `exclusive=false`；原线程可能用 `unlock()` 错误地解一个共享锁触发未定义行为；即使 pin count 归零，帧可能被驱逐，另一线程在原线程释放锁前覆盖其元数据。
- **考点**：**释放保护锁后再读共享状态 = 经典 TOCTOU（检查时/使用时）竞态**。OS 不会帮你 panic——后果是悄悄的数据损坏。这就是为什么"检查 + 操作"必须在**同一个锁的保护下**完成。

---

### 例题 2（示例 Q5）— pin 与 latch（也见 M5）
**题**：哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"只持 latch（pin count = 0）就足以防驱逐，从而能安全用裸指针。"** ← 错！
- **考点**：**latch 防并发改，pin 防驱逐**。pin count = 0 的帧随时可能被驱逐，裸指针悬空。两者职责不同、缺一不可。

---

### 例题 3（概念）— 为什么 `vector<mutex>` 编译不过
**题**：为什么哈希表的每槽锁要用 `vector<unique_ptr<mutex>>` 而非 `vector<mutex>`？
- ✅ **答**：`std::mutex` 不可移动、不可拷贝（设计如此）；而 `vector` 扩容要移动元素，要求元素可移动 → 直接放 mutex 编译不过/不安全。改存 `unique_ptr<mutex>`，扩容时只移动指针、不移动 mutex 本身。
- **考点**：容器扩容的可移动性要求 vs mutex 的不可移动性。

## 🏋️ 六、举一反三 + 新增模拟考题（含答案）

> 🟢基础 🟡进阶 🔴挑战

### A. 选择题

**A1 🟢** 两个线程同时往哈希表插入两个 hash 到同一空槽的 key，不加锁会怎样？
A) 两个都正确插入 B) 程序崩溃 C) 后者覆盖前者，丢失一个 key D) OS panic
<details><summary>答案</summary>**C**。两个线程都看到槽空、都写入，后写的覆盖先写的 → 丢数据（race condition）。</details>

**A2 🟡** 细粒度"每槽一锁"相比"全局一锁"的主要优势是？
A) 用更少内存 B) 不同槽的操作可并行，提高并发
C) 完全不需要锁 D) 保证公平
<details><summary>答案</summary>**B**。不同槽并行，避免不相关操作互相等待。代价是锁更多、内存/管理开销大。</details>

**A3 🟡** `shared_mutex` 相比普通 `mutex` 在什么场景下提升最大？
A) 写多读少 B) 读多写少 C) 完全无并发 D) 单线程
<details><summary>答案</summary>**B**。读多时，shared_lock 允许多读者并发，普通 mutex 只能一个一个来。</details>

**A4 🔴** 为什么 `std::vector<std::mutex>` 是个问题？
A) mutex 太大 B) mutex 不可移动/拷贝，但 vector 扩容要移动元素
C) vector 不支持 mutex D) mutex 必须全局
<details><summary>答案</summary>**B**。mutex 不可移动，vector 扩容需移动元素 → 冲突。改用 `vector<unique_ptr<mutex>>`，只移动指针。</details>

### B. 判断题

**B1 🟢** "线程安全意味着多线程同时访问数据结构也不会丢数据或损坏。"
<details><summary>答案</summary>**对**。这是线程安全的定义。</details>

**B2 🟡** "全局一把锁能保证哈希表正确，但并发性能差。"
<details><summary>答案</summary>**对**。正确但串行化，回到单线程性能。</details>

**B3 🟡** "在释放保护锁之后再检查共享状态的标志，是安全的。"
<details><summary>答案</summary>**错**。这是 TOCTOU 竞态——释放锁后状态可能被别的线程改变（测验 Q20）。检查+操作要在同一锁保护下。</details>

**B4 🔴** "用 `shared_lock`（共享）读时，允许多个线程同时读同一个槽。"
<details><summary>答案</summary>**对**。shared_mutex 的共享模式允许多读者并存（只要无写者）。</details>

### C. 简答题

**C1 🟡** 画出两个线程插入 hash 到同一空槽的 key（15、25）丢数据的交错序列，并说明 mutex 怎么修复。
<details><summary>参考答案</summary>T1 探测 slot5 空 → (切换) T2 探测 slot5 空 → T1 存 15 到 slot5 → T2 存 25 到 slot5（覆盖 15）。丢了 15。修复：用 index mutex，T1 拿锁插 15、解锁，T2 再拿锁、发现 slot5 占了、探测到 slot6 插 25。两个都在。</details>

**C2 🔴** 三种并发协议（全局锁、每槽锁、每槽共享锁）在读多负载下，哪个最快？为什么？
<details><summary>参考答案</summary>每槽共享锁最快。全局锁所有访问串行；每槽锁让不同槽并行；每槽共享锁在"不同槽并行"基础上再允许"同槽多读并发"，所以读多时并发度最高、逻辑时间步最少（模拟器：30 > 21 > 15）。</details>

### D. 应用题

**D1 🔴** 一个并发哈希索引，读操作远多于写操作。你会用每槽 `mutex` 还是每槽 `shared_mutex`？写操作和读操作分别用哪种 lock？为什么？
<details><summary>参考答案</summary>用每槽 `shared_mutex`。写用 `std::unique_lock`（独占，保证写时无其它读写），读用 `std::shared_lock`（共享，多读者并发）。因为读多，shared_mutex 让大量读并发进行，吞吐远高于普通 mutex（后者读也要排队）；写仍独占保证正确性。</details>

## ⭐ 七、易错点 & 速记

| 易错点 | 正确理解 |
|:---|:---|
| 以为 race condition 会让 OS panic | 不会，后果是**悄悄的数据损坏/丢失** |
| 释放锁后再检查/操作共享状态 | TOCTOU 竞态，检查+操作要在**同一锁内** |
| `vector<mutex>` | mutex 不可移动 → 用 `vector<unique_ptr<mutex>>` |
| 以为读也要独占锁 | 读用 `shared_lock`（多读并发） |
| 全局锁够用 | 正确但并发差，读多用每槽 shared_mutex |
| pin / latch 混淆 | pin 防驱逐、latch 防并发改 |

**🎵 口诀**：
- 锁粒度：**"全局串行、每槽并行、共享读并发"**
- 锁类型：**"写用 unique_lock 独占，读用 shared_lock 共享"**
- 容器：**"mutex 不可动，vector 装 unique_ptr"**
- 竞态：**"检查与操作同锁内，放锁再看就出事"**
