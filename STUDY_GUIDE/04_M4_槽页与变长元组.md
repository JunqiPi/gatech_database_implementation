## 📖 三、核心概念精讲

### 3.1 基础 Page 类的 3 个毛病（先懂问题）

| 毛病 | 说明 | 类比 |
|:---|:---|:---|
| **找空位要线性扫描** | 插新元组要从头扫整页找空槽 | 在快满的停车场从头找空位 |
| **不支持变长元组** | 定长槽放变长字符串：短的浪费、长的塞不下 | 用同样大的鞋盒装大小不一的鞋 |
| **碎片 + 整理贵** | 反复插删后页像瑞士奶酪全是洞，要周期性 **compaction（压缩）** 把元组挪到一起，开销大 | 整理满是空隙的书架 |

---

### 3.2 ⭐ 槽页（Slotted Page）结构（核心考点）

```
┌─────────────────────────────────────────────────┐
│ Page Header:  [槽数 num_slots] [空闲空间偏移 free_space_offset] │  ← 页头
├─────────────────────────────────────────────────┤
│ Slot Array:   [slot0: offset,length] [slot1: ...] [slot2: ...]  │  ← 槽目录(从前往后长)
│                          ↓ 指向 ↓                                │
│               ...... 空闲空间 ......                              │
├─────────────────────────────────────────────────┤
│ Tuple Data:   [...tuple2...][...tuple1...][...tuple0...]         │  ← 实际数据(从后往前长)
└─────────────────────────────────────────────────┘
```

- **页头（header）**：记 `num_slots`（槽数）+ `free_space_offset`（空闲空间起点，随插删动态更新）。
- **槽目录（slot array）**：每个 **slot = (offset 偏移, length 长度)**，指向元组数据在页内的位置。
- **元组数据**：放在页内任意位置，由槽指向。

> 💡 **核心思想 = 加一层"间接（indirection）"**：上层只认 **slot id**（槽号），不直接认元组的物理地址。元组在页内挪来挪去，只要更新槽里的 offset，slot id 不变。

---

### 3.3 槽页如何逐个解决基础 Page 的毛病

| 基础 Page 毛病 | 槽页解法 |
|:---|:---|
| 找空位线性扫描 | 查页头 + 槽目录直接找到够大的空闲块，**直接定位**插入 |
| 不支持变长元组 | 每个槽指向**任意长度**的元组，最小化内部碎片 |
| 删除留洞 | **逻辑删除**：把槽标记为空闲，**不立即物理搬移**其它元组 |
| 整理贵 | 压缩时把元组挪到一起，**只需更新槽的 offset**，开销小 |
| 直接访问 | 通过 slot id 索引，**O(1) 直接访问**任意元组，无需线性扫描 |

> ⚠️ **测验 Q11 的考点（哪个说法"不对"）**：
> ❌ **"槽目录保证元组能原地增长而无需重新定位，从而减少碎片。"** ← 错！槽页**不**保证原地增长——元组变大放不下时，要**移动**到别处并更新槽的 offset/length。
> ✔ 对的：槽目录支持逻辑删除（标记空闲不立即搬移）；压缩时可移动元组同时保持 slot id 稳定；增加一层间接略增查找成本，但远低于扫描变长记录数组。

### 3.4 多页数据库文件管理

- BuzzDB 用一个含**多个页**的数据库文件支持更多数据。
- 构造时：用 `ifstream` 检查文件是否存在（不存在就用 `ofstream` 创建），再用 `fstream` 以 `ios::in | ios::out`（读写）打开。
- **页偏移（page offset）= page_id × PAGE_SIZE**。例：4KB 页，第 0 页偏移 0、第 1 页偏移 4096、第 2 页偏移 8192……
- **`extend_database_file`**：所有页满了就在文件末尾追加一个空页，支持动态扩展（scalability）。
- **`flush`**：seek 到页偏移 → write 页数据 → flush 清空缓冲 → 数据落盘持久。

> ⚠️ **测验 Q19 考点（持久性与可见性，哪个"不对"）**：
> ❌ **"每次删除都必须立即 fsync 强制刷盘以保证 ACID 正确性，即使事务还没提交。"** ← 错！未提交就强制刷盘不是 ACID 要求。
> ✔ 对的：写回磁盘后未来重载才反映删除；其它事务/进程在写回前看不到改动；内存改动只有写回/刷盘后才持久。

---

### 3.5 从磁盘文件构建索引（reinterpret_cast 的用武之地）

- 遍历文件所有页 → 每页拿到原始字节缓冲 → 用 **`reinterpret_cast`** 把 `char* page_buffer` 当成 `Slot*`（槽数组）来读槽元数据 → 找到非空槽 → 按 offset 取元组数据 → 反序列化 → 加进内存索引。
- **`reinterpret_cast`**：把一种指针**重新解释**成另一种（如 `char*` → `Slot*`），**不改二进制值，只改解释方式**。处理磁盘原始字节时常用，但要小心别破坏数据完整性。

---

### 3.6 C++ 四种 cast（重点 static / reinterpret）

| cast | 用途 | 例子 |
|:---|:---|:---|
| **`static_cast`** | 类型**自然兼容**的转换（最安全） | `float 123.45 → int 123` |
| **`reinterpret_cast`** | 任意指针 ↔ 任意指针，**底层位级重解释** | `char* → Slot*` 读磁盘字节 |
| `dynamic_cast` | （提了一下）运行时多态向下转型 | — |
| `const_cast` | （提了一下）去 const | — |

> ⚠️ **测验 Q13 考点（reinterpret_cast，哪个"不对"）⚠️你做错**：
> ❌ **"`reinterpret_cast` 是把任意指针转成任意指针的可移植、安全机制（只要大小匹配）。"** ← 错！它**既不可移植也不安全**——它做的是危险的位级重解释，平台相关、易破坏数据。
> ✔ 对的：它让危险转换**显式化**（提高可读性、表明程序员担责）；不像 C 风格 cast 那样悄悄组合多种转换；让代码更易审计（reviewer 能一眼认出位级转换）。

---

### 3.7 流（Streams）

- **流（stream）= I/O 的统一抽象**：用同一套操作读写文件/内存/控制台/网络。
- **`fstream`**（文件流）：读写磁盘文件。
- **`stringstream`**（字符串流）：把字符串当流来处理，方便数据↔字符串转换。建索引时用 `istringstream` 把元组字符串反序列化成 tuple 对象。

---

### 3.8 StorageManager 类 + RAII（模块化）

- **目的**：把存储管理职责从主 BuzzDB 类**抽离**出来 → 关注点分离（separation of concerns）→ 提高**模块化（modularity）**。
- 核心方法：`load`（读页）、`flush`（写页）、`extend`（扩文件）。
- **RAII（Resource Acquisition Is Initialization）**：把**文件句柄**的生命周期绑到 StorageManager 对象——构造时打开文件，析构时自动关闭。
  - **为什么重要**：文件句柄是**有限的系统资源**，OS 限制同时打开数。不释放会**句柄耗尽（resource exhaustion）**，谁都打不开新文件。RAII 自动释放，防句柄泄漏。
- RAII 三剑客：`lock_guard`（管 mutex）、`unique_ptr`（管内存）、`fstream`（管文件句柄）。

---

### 3.9 封装与"魔法数字" PAGE_SIZE（测验 Q26 考点）

- 如果 `PAGE_SIZE` 作为**全局**常量散落在 5 个模块里引用，从 4KB 改 8KB 要改 **5 处**。
- 如果 **封装**成 StorageManager 的私有成员，只需改 **1 处**。
- **考点**：封装 = 改动局部化（change localization），降低维护成本。

## 📄 四、配套章节分析

### 📘 ch13（Data Storage Structures）要点

- **定长记录**：记录 i 存在字节 `n×(i-1)`。删除方案：①后面的往前移 ②用最后一条填空 ③**空闲链表（free list）**串起空位。
- **变长记录**：变长属性用**固定大小的 (offset, length)** 表示，实际数据放所有定长属性之后；null 用 **null 位图（null-value bitmap）**。
- **槽页结构（Slide 8，本模块核心）**：头部存"记录数 + 空闲空间末尾 + 每条记录的位置和大小"；记录可在页内移动以保持紧凑；**指针不应直接指向记录，而应指向头部里那条记录的目录项**（= slot 间接层）。
- **记录组织**：堆（heap，哪有空放哪）、顺序（sequential，按搜索键排序）、多表聚簇（multitable clustering，相关记录放同块减少 I/O）、B+ 树、哈希。
- **空闲空间图（free-space map）**：每块一项，记录该块空闲比例，加速找插入位置（同 M3 Q28）。

### 例题 4（测验 Q17）— 定位 I/O 的 API 设计 ⚠️你做错
**题**：考虑用单个定位 I/O 调用 `read_at(offset, buf, len)` 替换 `seekg()+read()`。聚焦 **API 设计**，哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"采用定位 I/O 函数能显著提升性能，因为避免了一串函数调用。"** ← 错！
- **为什么错**：定位 I/O 的好处是 **API 设计更清晰**（offset/length 显式、不依赖共享流状态），**不是为了性能**——省那一两次函数调用对性能微不足道。题目特意强调"聚焦 API 设计"。
- ✔ 对的：两种风格并存会割裂用法，除非强制统一；即使函数变多，语义面会缩小（调用方不再操纵共享流状态，不变量显式）；引入定位 I/O 常导致更多函数变体、更多 API 入口要维护。
- **考点**：定位 I/O 的价值是**正确性/清晰性（显式 offset/length，无共享状态）**，不是性能。

---

### 例题 5（测验 Q30）— 槽页查找延迟计算 ⚠️你做错
**题**：一页平均 64 个元组。设计1（无槽）：连续存，查第 i 个要扫 i 个元组；设计2（有槽）：槽目录常数时间查找。平均扫描成本 0.05 µs/元组；槽查找成本 0.20 µs。哪个设计平均查找延迟更低？
- ✅ **正确：设计 2（有槽）**。
- **算法**：
  - 设计1（无槽）：查第 i 个平均要扫 **平均 (64+1)/2 ≈ 32** 个元组（均匀分布）。平均成本 ≈ 32 × 0.05 µs = **1.6 µs**。
  - 设计2（有槽）：常数 **0.20 µs**。
  - 1.6 µs > 0.20 µs → **设计 2 快得多**。
- ❌ 别选"两者差不多""不知元组大小没法比"——给了每元组扫描成本就能算。
- **考点**：槽目录用一点点固定开销（0.20µs）换掉了线性扫描（平均 32 次）。这正是"间接层"的价值。

### 例题 6（示例 Q2）— 槽页 vs 无槽：要几个 CPU 核（计算题，进阶版）
**题**：8KiB 页，页头 32B，槽项 4B/元组，平均元组负载 128B。
- 设计1（无槽）：连续存，查第 i 个线扫 i 个，扫描成本 0.05 µs/元组。
- 设计2（有槽）：槽目录常数查找 0.20 µs。
- 负载：每秒 200 万次随机查找，均匀分布在一页的元组上。一个核背靠背做查找，忽略 I/O。问各需几个核？

**解**：
1. 先算**一页有多少元组**。无槽设计：8192B 头部 32B 后剩 8160B，每元组 128B → 8160/128 ≈ **63.75 ≈ 64 个元组**（有槽设计每元组还要 4B 槽项 = 132B，8160/132 ≈ 61，但本题按"平均查找一页内元组"取 ≈ 64 估算，与示例答案吻合）。
2. **无槽设计**：均匀随机查找，平均扫 (64)/2 ≈ **32** 个元组 → 每次 32 × 0.05 µs = **1.6 µs**。每秒 200 万次 → 总需 2×10⁶ × 1.6 µs = **3.2 秒的 CPU 时间/秒** → 需 **≈ 3.2 个核**。
3. **有槽设计**：每次固定 0.20 µs → 2×10⁶ × 0.20 µs = **0.4 秒的 CPU 时间/秒** → 需 **≈ 0.40 个核**。
- ✅ **答案：3.2 ; 0.40（选项 C）**。
- **考点**：吞吐 = 每次成本 × QPS；核数 = 总 CPU 时间需求 / 1 秒。槽页把 3.2 核降到 0.4 核——**8 倍**提升。

**A2 🟡** 槽页删除一个元组时，最高效的做法是？

### D. 应用题

**D1 🔴** 一个 8KiB 页，页头 64B，每元组 200B（无槽）。
(1) 这页能放多少元组？
(2) 无槽设计平均查找要扫多少个元组？若每元组扫描 0.05µs，平均查找延迟多少？
(3) 有槽设计固定 0.20µs，每秒 100 万次查找，无槽和有槽各需几个核？
<details><summary>参考答案</summary>
(1) (8192-64)/200 = 8128/200 ≈ **40 个元组**。
(2) 平均扫 40/2 = **20 个**，延迟 20 × 0.05 = **1.0 µs**。
(3) 无槽：10⁶ × 1.0µs = 1.0 s CPU/s → **1 核**；有槽：10⁶ × 0.20µs = 0.2 s CPU/s → **0.2 核**。
</details>

## ⭐ 七、易错点 & 速记

| 易错点 | 正确理解 |
|:---|:---|
| 以为槽页元组能原地增长 | 不能，变大要移动并更新槽 |
| 以为 reinterpret_cast 安全可移植 | 危险、平台相关、位级重解释 |
| 以为定位 I/O 是为性能 | 是为 **API 清晰**（显式 offset/length） |
| 以为删除要立即 fsync | 未提交强制刷盘不是 ACID 要求 |
| 槽查找 vs 线扫算延迟搞错 | 线扫=平均 N/2 × 单次；槽=固定常数 |
| 以为封装靠"约定" | 封装靠**机制**（私有成员），不靠约定 |

**🎵 口诀**：
- 槽页 = **"头记槽数与空闲，槽记偏移与长度，数据任放，删移只改槽"**
- 槽页解三病：**"直接定位、变长可容、压缩只改 offset"**
- cast：**"static 同类安全转，reinterpret 位级重解释（危险）"**
