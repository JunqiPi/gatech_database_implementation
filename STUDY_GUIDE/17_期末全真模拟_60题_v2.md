# ✅ 答案与详解

## Part A · module_12（1–8）

**1. D** — 方向反转。**行存**最擅长"访问完整的行"；**列存**最擅长"访问特定的列"。列存要拼回整行反而要付 **tuple reconstruction** 的代价。

**2. C** — ⭐ 原文的限定是 **"When we have a highly selective filter"**。选择性低时要读回大部分行，列存的优势被元组重建成本吃掉。（手法① `regardless of` = 绝对化）
> B 是对的，值得记住：**这个"先扫过滤列收 offset、再取目标列页"的两阶段做法，就是 C-Store 的 `Select`→bitstring→`Mask` 的手写版**，也是 Final Practice Q7 里说的 late materialization。

**3. D** — ⭐ **byte dictionary 只在"唯一值数量有限"时可用**（要映射进 0–255 的单字节码），百万级不同值直接爆掉；而且它面向 **categorical** 数据。（手法⑤张冠李戴）

**4. D** — ⭐ 原文强调 **"The query result … remains consistent across all the compression algorithms"** —— 这些都是**无损压缩**。
> ⭐ 这组数字最反直觉的地方要记牢：**压缩比更高的 Huffman（2.24 ms）反而比 byte dictionary（0.71 ms）慢 3 倍**，因为**按位解码**才是查询时的瓶颈。**"压缩比最高 ⇒ 查询最快"是错的。**

**5. D** — 恰恰相反：课程演示的是**逐列选不同算法**（timestamp→delta、temperature→shift+bit packing、product ID→byte dictionary），而且方案与参数是**自动逐列选择**的。

**6. D** — ⭐ 原文对 hash join 的说法是 **"Although non-contiguous access can be challenging"**，而且**不连续的查找需要专门的 gather 指令**，绝不是"和顺序扫描一样高效"。（手法⑥半真半假）

**7. D** — ⭐ 原文：**"we handle any leftover elements if our total count isn't a multiple of four in a scalar loop"**，并称"**向量化主体 + 标量尾巴**是 SIMD 算法的常见模式"。

**8. B（2,500,000；16×）** —
```
向量宽度 W = 512 bit / 32 bit = 16
指令数     = 40,000,000 / 16 = 2,500,000
削减倍数   = 16×
```
**诱饵**：**A** 把寄存器当成 256 位（W=8）；**C** 把元素当成 16 位（W=32）；**D** 把元素当成 8 位（W=64）。
⭐ **常用 W 速查**：128 bit(NEON/SSE, `q`)÷32=4｜256 bit(AVX2)÷32=8｜**512 bit(AVX-512)÷32=16**。

## Part B · module_11（9–14）

**9. D** — ⭐ 解析**只解决灵活性**，运行时开销**一点没减**：每个 tuple 仍要穿过整条算子链、仍有 vtable 动态分派。这正是下一节引入查询编译的动机。

**10. D** — ⭐ **正则只在 parse 阶段跑一次**，与 tuple 数量无关。真正的第四个开销是 **memory：算子里频繁创建/销毁临时对象（如指向 field 的 unique_ptr）**。（手法④不存在的机制）

**11. D** — ⭐ 原文：硬编码反序列化 **"is super fast, but also very rigid, unlike the interpreted approach, which is flexible but slow"**。D 把"刚性"说成"灵活、能在运行时适配 schema"，正好反了。

**12. D** — ⭐ 原文明说：**"The cost of frequent recompilations might exceed the performance gains from query compilation."** D 说"重编译便宜、频繁改 schema 也不影响收益"，与原文相反。

**13. D** — ⭐ 顺序反了。正确的算子链是 **Scan（底）→ Select（过滤）→ HashAggregation（顶）**：**先过滤再分组**。把聚合放在 Select 下面既不符合 `execute_query` 的构造顺序，语义上也是先分组后过滤（那是 HAVING 的语义，不是 WHERE）。

**14. B** — `(\d+)` 是 **capturing group**：`\d` 匹配一位数字，`+` 表示一次或多次；捕获的数字标明 **sum 作用在哪一列**。（`\{`/`\}` 才是匹配字面花括号。）

## Part C · 论文（15–24）

**15. D** — ⭐ **查询编译成 LLVM IR、把算子融进紧循环是 P10 HyPer（Neumann）和 `module_11` 的技术**。C-Store（2005）是**解释执行**：10 种算子 + 64K 单列块迭代器，没有代码生成。

**16. B** — ⭐ **PDT（按位置组织差分）是 Vectorwise 的**；A（K-safety + 多 sort order）、C（HWM/LWM/epoch/IV/DRV）、D（Type 2 位图编码）**全是 C-Store**。
> ⭐ **关键辨析：Vectorwise 只存一份数据副本，因此每表只能一个 clustered index，不可能有"多种 sort order 任选"，也没有 K-safety。**

**17. D** — ⭐ **exchange 是唯一的例外**：*"While all other modules are based on demand-driven dataflow, the producer-consumer relationship of exchange uses **data-driven dataflow**."* 而且"消除请求消息的需要"正是**选 data-driven 的理由之一**，D 把因果接反了。

**18. D** — ⭐ **shared-memory 在数据库负载下扩展性最差**（干扰严重，当时上限约 **32 个处理器**）；**shared-nothing 才能到数百上千**（Teradata/Tandem/Intel 已出货 200+）。

**19. D** — ⭐ **RMI 的阶段之间没有任何搜索**，每阶段只是一次模型求值——这正是原文列的第 4 条好处。二分搜索只在**最后**、在叶模型的误差界内使用。

**20. D** — ⭐ **分裂涉及三个页（原页 O、新兄弟 N、父页 P），无法用一次 CAS 装上**；Bw-tree 把 SMO 拆成**一串各自可用一次 CAS 装上的原子动作**，靠 **B-link 的 side pointer** 使 half split 之后索引就已合法。

**21. D** — ⭐ 原文明确说**不能也不该把整个查询编译成一个函数**，两个理由：① LLVM 某处会调 C++ 并交出控制流（如外部排序的归并阶段）；② ⭐ **内联全部逻辑会导致代码指数增长**（外连接在"找到匹配"和"产生 NULL"两种情形都要调用消费者）。正确做法是**在 LLVM 内部定义函数，但保证 hot path 不跨函数边界**。

**22. D** — ⭐ **Vectorwise 只保存一份数据副本，所以每表只允许声明一个 index（相当于 clustered index）**。"每种 sort order 一个 clustered index"是 C-Store 的 overlapping projections，不是 Vectorwise。

**23. D** — ⭐ 论文的结论恰恰相反：**"The linear node-split algorithm proved to be as good as more expensive techniques. It was fast, and the slightly worse quality of the splits did not affect search performance noticeably."**

**24. B** — mapping table + delta + CAS = **Bw-Tree (P5)**；最易混的是 **Umbra (P4)**——Umbra 用 **swip（指针混写）+ 版本化闩锁（独占/共享/乐观）+ 可变大小页**。

## Part D · module_8（25–35）

**25. C** — ⭐ **MBR 必然包含"死空间（dead space）"**：用轴对齐矩形去包不规则、分散的对象，一定会圈进大片没有对象的区域。**死空间正是 R-Tree 的核心弱点**，它导致 MBR 重叠 → 一次搜索要下多棵子树 → 无最坏情况保证 → 高维退化。

**26. B** — ⭐ **自相矛盾**：若重叠减少，访问的分支应**变少**而非变多。真相是**维度升高 → 重叠增加 → 剪枝失效 → 趋向全扫描**（curse of dimensionality）。

**27. C** — ⭐ **R-Tree 没有全序**，不存在"按坐标排序枚举"的中序遍历。（手法⑤把 B+树的性质安给 R-Tree）

**28. D** — ⭐ 字典序是**一维全序**问题，该用 B+树/trie。把每个字符当一维既导致**维度不定**，又碰上**维度灾难**，而且 R-Tree **根本不维护全序**。

**29. C** — ⭐⭐ **最坏情况恰恰是学习索引的软肋**：B+树保证 O(log n) **与分布无关**；学习索引分布越复杂 → 模型误差越大 → 局部搜索窗口越大。**hybrid index 只是把最坏情况"兜到"B 树水平，不是超过它。**
> 💡 **一句话：学习索引赢在【平均】，B+ 树赢在【最坏】。**

**30. D** — ⭐ 手法①绝对化（`removes the possibility`）。线性模型**降低但不消除**过拟合风险；而且学习索引真正的问题是 **underfit**。

**31. D** — ⭐ **知道 min/max error 恰恰就能选出既保证正确又限制代价的窗口**——这正是 RMI 的核心机制：**为最后阶段的每个模型分别存 min/max error**，从而"按 key 用的模型逐个限制搜索空间"。

**32. D** — ⭐ **增加模型复杂度会【增大】内存占用和查找延迟**，这句话本身在物理上讲不通。论文的真实权衡是 **"balance the complexity of the model with its accuracy"**。

**33. D** — ⭐ **Patricia 的边存【子串】**（单字符边那是普通 trie）；分裂只是把一条边拆成前缀边 + 余下边，**不产生字符链**。

**34. D** — ⭐ 方向反了。**先做便宜且选择性高的 (1)（只比文档 ID），再对幸存文档做昂贵的 (2)（读并归并位置列表）**。反过来会对每一篇文档白读位置数据。
> 💡 这与 **Q38 的谓词重排序**、**module_12 的列存晚物化**是同一条思想的三个面。

**35. C** — ⭐ **把 `≤` 偷换成 `=`，还丢了绝对值**。定义是 `|p − q| ≤ k`；按 C 的说法 k=3 时距离为 1 或 2 的文档会被错误拒绝。
> 💡 **验算法**：设 Pos(w1)={5}, Pos(w2)={6}, k=3 → `|5−6|=1 ≤ 3` 合格；但 C 要求 q = 5+3 = 8 ≠ 6 → 被拒 → **与定义矛盾，立刻判死**。

## Part E · module_9/10（36–43）

**36. D** — ⭐ **一个词的陷阱**：end-of-stream 的条件是读完**最后一页的【最后一个】slot**，不是 "first slot"。
> ⚠️ C 是完全正确的工程实践（也是 BuzzDB 的写法），**不要因为它"听起来太普通"就排除它**。

**37. C** — ⭐ **索引查找用的是键值/常量，那是 direct reference**；indirect 的用途是**同一元组内两列比较**（`start_time < end_time`）和动态条件。
> 💡 这题在 Sheet 02 真题里以两种措辞考了 **两次**（Q4、Q7）。

**38. D** — ⭐ **方向反了**：应该把**便宜且选择性高**的谓词放前面。例子里 `price < 100`、`stock > 0` 是廉价整数比较，`classify(text)` 是昂贵的 UDF —— **先跑便宜的淘汰掉大部分元组**，只让少数幸存者付出昂贵代价。
> ⭐ 标准代价模型：按 **选择性 / 代价** 的比值从高到低排。

**39. D** — ⭐⭐ **跨技术归属错配**。模块化的收益机制是**稳定接口 + 运行期组合**，**完全不需要重编译执行器代码**；"重编译低层执行器代码"是 **查询编译（`module_11` / P10 HyPer）**的做法，而它恰恰是要**离开算子框架**来换性能的。**两者是对立取舍，不是互相支持。**

**40. C** — ⭐ **MIN 需要自己的运行最小值**，从 sum 和 count 推不出来。（COUNT←runningCount、SUM←runningSum、**VARIANCE 还需要平方和**。）

**41. D** — ⭐ 题目作用域是「**Hash** Aggregation 算子**内部**的数据结构」。把哈希表换成平衡树，**它就不再是 hash aggregation**，而是基于排序/有序聚合——**另一个算子**。
> ⚠️ 注意与"**规划器可以选用 ordered aggregation 策略替代 Sort**"（这是**对的**）区分：**前者是算子选择层面，后者是算子实现层面。读题先锁定"这句话在讲哪一层"。**

**42. D** — 统一接口的**全部意义**就是"插入新算子不用改邻居的代码"。

**43. D** — ⭐ 放在 `open()` 的**全部意义**就是"只做一次"，`next()` 反而**不再承担**这个代价。

## Part F · B+ 树（44–46）

**44. D** — ⭐ **B+ 树精确查找必须走到叶子**，因为 **payload 只在叶子**。"键等于内部分隔键就可提前终止"是 **B-tree** 的性质。

**45. D** — ⭐ **兄弟指针正是 B+ 树支持范围查询的关键**。回父节点再下降**并不等代价**：要多走 O(log n) 的路径、可能触发额外页访问，而且跨越父节点边界时还要继续上溯。这就是 B+ 树把叶子串成链表的理由。

**46. B（3 层）** —
```
扇出 f = 250 × 0.8 = 200
200¹ = 200        < 800,000
200² = 40,000     < 800,000
200³ = 8,000,000  ≥ 800,000   → 3 层
```
⚠️ **诱饵 A=2**：`log₂₀₀800000 = 2.57` **向下取整**。⭐ **索引层数永远向上取整。**

## Part G · 教材（47–48）

**47. D** — ⭐ **LSM 的写放大恰恰来自反复归并（compaction）**；在读多写少或随机更新的负载下未必优于 B+树。（手法① `for every workload`）

**48. D** — ⭐ **快照隔离有 write skew，不可串行化**（Oracle 的 "serializable" 实为 SI）。

## Part H · 期中范围（49–60）

**49. C** — ⭐⭐ **投影的复合是【交集】不是并集**：`π_X(π_Y(R)) = π_{X ∩ Y}(R)`，而且要求 **X ⊆ Y** 才有定义；因此**也不可交换**。
> 💡 **验算**：`R(A,B)`，X={A}, Y={B} → `π_B(R)` 里**没有 A** → `π_A(π_B(R))` 不合法，立刻判死。

**50. B** — **Closure = 关系算子的输入是关系、输出也是关系** → 可任意嵌套组合。（A 接近 lossless-join decomposition；C 说的是 attribute closure X⁺ —— **closure 在本课有三种同名异义**。）

**51. C** — **Grouping → HAVING filtering → Ordering**。⭐ HAVING 作用在**分组后的组**上，必须先分组；ORDER BY 永远最后。

**52. D** — ⭐ 手法①绝对化（`always`）。**没有 ORDER BY 时顺序不保证**，实际顺序取决于访问路径、缓冲池状态、并行度、优化器当次的计划。

**53. B** — DRAM 每 bit 存在**电容**里，**电容漏电所以必须周期性刷新**（"Dynamic" 就指这个）。**NAND flash 是非易失的浮栅晶体管**，是 SSD 的材料。

**54. D** — ⭐ 页比块小既不减少碎片，也不提升吞吐；它带来 **4× 读放大**，写还要 **read-modify-write**。

**55. D** — ⭐ **槽目录不保证元组能原地增长**：元组变大装不下就得**搬走**，slot 里换成新 offset 或 forwarding pointer。

**56. D** — ⭐ **纯虚 `= 0` 表示"必须被派生类实现"，与绑定时机无关**；通过基类指针调用**走运行期 vtable**。（手法③编译期/运行期偷换）

**57. D** — ⭐ **传/移动 unique_ptr 并不会序列化它指向的数据**；必须写**值**（len + 字节流）并在加载时**重建新缓冲区**。

**58. D** — ⭐ **方向反转**：引用计数/所有权标志是用来 **AVOID（避免）** 深拷贝的（只读时共享、要写时才拷 = **copy-on-write**），不是用来"执行"深拷贝。

**59. D（Index 11）** —
```
h₁(40) = 40 mod 17 = 6            (40 = 2×17 + 6)
h₂(40) = 1 + (40 mod 6) = 1 + 4 = 5   (40 = 6×6 + 4)
探测 (6 + 5i) mod 17：
 i=0 → 6    (X，已占用)
 i=1 → 11   (空) ✓
```
⚠️ **诱饵 A=7**：退化成**线性探测**（6→7）。**B=10**：随手选了另一个已占用槽。**C=12**：h₂ 误算成 6（忘了 `+1` 的位置或把 `40 mod 6` 当成 5）。
⭐ **边界情形也要知道**：若 `k mod 6 == 0` 则 h₂ = 1，**双重哈希此时退化成线性探测**——这是 h₂ 设计不当的典型症状（好的 h₂ 应与 m 互质且避免取 1）。

**60. B** — ⭐ Stonebraker 1981 §2.3 原文：*"this block is **not necessarily the next one in logical file order**. Hence, there is **no way for an OS to implement the correct prefetch strategy**."* —— 论点恰好相反：**DBMS 知道自己下一个要哪块，但那块不一定是文件里的下一块**，所以 OS 的顺序预读对 DBMS 不对路。
