## Q1 · 列存 delta encoding 什么时候不适合（NOT correct）

**题干机制**：块内存第一个值 + 后续存 delta，然后**按块内最大 delta 做 bit-packing**。

**答案：C**

| 选项 | 判定 | 理由 |
|:--|:--:|:---|
| A. 随机点查为主时不划算，因为解码可能要重建块内一串值才能访问单个位置 | ✅ 真 | delta 是**链式**的，第 k 个值 = 首值 + 前 k 个 delta 之和 → **随机访问必须顺序重放** |
| B. 存储顺序上的值本质随机（邻居无相关性）时，delta 也大而随机，压缩收益几乎为零 | ✅ 真 | delta encoding 的前提就是**邻居相关**（如递增 timestamp） |
| **C. 在频繁原地更新的页上 delta encoding 很有吸引力，因为小改动只需重算少数几个 delta，更新性能好且兼得压缩** | ❌ **假 → 答案** | 改一个值会**打断 delta 链**：后面所有 delta 可能都要重算；更糟的是若新的最大 delta 变大，**整块的 bit-width 都要变，要重新 bit-pack 整块**。delta+bit-packing 是**读优化**表示，对原地更新极不友好 |
| D. 数据有大的周期性跳变（如计数器频繁归零）时，块内**一个**大 delta 会迫使该块**所有** delta 用宽 bit-width，削弱压缩 | ✅ 真 | 直接由题干"按块内最大 delta 做 bit-packing"推出 |

**手法识别**：C 用的是 **手法②方向反转 + 手法⑥半真半假**——"只需重算少数几个 delta"听起来合理，但方向完全反了。而且题目问"**poor choice** 的情形"，C 却说"attractive"，**在题干框架下也自相矛盾**。
**映射**：🆕`module_12` 压缩一节（delta encoding + bit packing） + **P12 C-Store Type 3 编码（block-oriented delta）** + **P11 Vectorwise（只用解压极快的方案）**。
> ⭐ **顺带记一个交叉点**：C-Store 之所以要 **WS/RS 两层 + tuple mover**，根本原因就是 C 选项描述的那件事做不到——**压缩排序的 RS 段不能原地更新**。这题和 office hour 的 C-Store 更新架构题是同一个知识点的两面。

## Q2 · B+ 树层数计算

**题干**：12,000 个不同键；每个非根节点最多 **100 个孩子**；平均 **75% 满**。问 root-to-leaf **含两端**的层数。

**答案：D（3 层）**

**推导（方法一，自底向上数）**：
```
有效扇出 fanout = 100 × 75% = 75
叶子层：每叶约装 75 个键 → 需要叶子数 = 12,000 / 75 = 160 个叶子
上一层：160 个叶子 / 75 个孩子每节点 = 2.13 → 需要 3 个内部节点
再上一层：3 个节点 → 1 个根装得下（3 ≤ 75）✓
层数 = 根(1) + 内部(1) + 叶子(1) = 3
```
**推导（方法二，容量上界法，更快）**：
```
h 层能装的最大键数 ≈ fanout^h = 75^h
75^1 = 75          < 12,000  ✗
75^2 = 5,625       < 12,000  ✗   ← 2 层装不下！
75^3 = 421,875     ≥ 12,000  ✓
→ h = ⌈log₇₅ 12,000⌉ = ⌈2.18⌉ = 3
```

**诱饵怎么造的**：
- **C = 2** ← 典型"**半步错误**"：算出 `log₇₅ 12,000 = 2.18` 后**向下取整**。⚠️ 索引层数永远是**向上取整**。或者忘了乘 75% 而觉得 100² = 10,000 差不多够（其实 10,000 < 12,000 也不够）。
- **A = 4** ← 多算一层，例如把"叶子层"和"数据层"分开数，或把 75% 用错方向（100/0.75 = 133 反而更浅）。
- **B = 1** ← 完全没算。

**映射**：`module_7`（B+树）+ ch14。**这题的模板要背下来**：`层数 = ⌈log_(扇出) N⌉`，扇出 = 最大孩子数 × 填充率。

## Q3 · 双重哈希探测走位

**题干**：m = 11，h1(k) = k mod 11，h2(k) = 1 + (k mod 5)；占用情况 `X E E E E X E E X E E`（即 **0、5、8 已占**）；插入 k = 27。

**答案：A（Index 3）**

**推导（把每一步写出来，考场上就这么算）**：
```
h1(27) = 27 mod 11 = 5        (27 = 2×11 + 5)
h2(27) = 1 + (27 mod 5) = 1 + 2 = 3

探测序列 (h1 + i·h2) mod 11：
 i=0 → (5 + 0) mod 11 = 5   → X 占用
 i=1 → (5 + 3) mod 11 = 8   → X 占用
 i=2 → (5 + 6) mod 11 = 0   → X 占用
 i=3 → (5 + 9) mod 11 = 3   → E 空 ✓ 插入 index 3
```

**诱饵怎么造的**：
- **C = 6** ← 把双重哈希**当成线性探测**（5 → 6）。这是最经典的半步错误。
- **B = 9** ← 从最后一个被占的槽 8 开始线性 +1。
- **D = 1** ← 步长算错（如 h2 漏掉 +1，得 h2 = 2，序列 5→7 就停在 7，也不是 1；或用了别的错误组合）。

**⚠️ 这题的元信息比答案更重要**：double hashing 属于 `module_5`（**期中已考过的范围**），却被官方选进 Final Practice。
→ **结论：20% 的"期中已考"部分，出题人优先选可以出计算题的 topic**（哈希探测、B+树计数、IOPS、槽页布局、缓冲替换命中率）。**别以为期中考过的就不看了——把"可计算的"那部分再过一遍。**

**映射**：`module_5` 哈希索引（double hashing）。

## Q4 · B+ 树叶页：inline 记录 vs 指针（NOT correct）

**题干**：两个模板设计。A：`T records[NUM_SLOTS]`（记录按值内联）；B：`T* record_ptrs[NUM_SLOTS]`（指针指向单独的堆/段）。

**答案：D**

| 选项 | 判定 | 理由 |
|:--|:--:|:---|
| A. T 很大时每个叶页装的键-记录对更少 → 树更高 → 点查和范围查的页 I/O 更多 | ✅ 真 | 内联大记录直接吃掉叶页空间，**扇出下降 → 高度上升** |
| B. 只存指针能减少"对 T 的非索引字段更新"的写放大，因为记录常可在堆里原地更新而不必移动或重写叶项 | ✅ 真 | 叶子里的 (key, ptr) 不变 → 不用碰索引页 |
| C. 指针叶在 T 很大时每页装更多 (key, pointer) 项 → 树更矮、索引 I/O 更少，代价是每条记录多一次指针追逐（可能多一次页访问） | ✅ 真 | 标准权衡的正面表述 |
| **D. 对能舒服装进一页的小定长记录，指针叶的范围查询更快，因为引擎只需扫键数组和指针数组、可以忽略实际记录内容** | ❌ **假 → 答案** | **范围查询是要把记录返回的**，不可能"忽略记录内容"；指针叶意味着**每条命中记录都要一次指针追逐**（可能是一次随机页访问）。小定长记录恰恰是 **inline 更优**的场景——叶页内**顺序局部性好，扫完键就顺手拿到记录** |

**手法识别**：**手法⑥半真半假**——前半句"只需扫键和指针数组"在**统计类查询（如 COUNT）**下成立，但被偷换成了"范围查询更快"这个更强的结论。
**映射**：`module_7` B+树 + C++ 模板 + ch13 存储结构。
> ⭐ **交叉点**：这就是 Sheet 02 例题 1 里"叶子存 record ID 还是完整元组"的加强版，也是 **P12 C-Store 里 storage key 不物理存储（从位置推算）** 的对照面。

## Q5 · 二分查找中点表达式

**题干**：`l`、`h` 是 **32 位整数**，表示当前 low/high 下标（含两端）。哪个 `mid` 表达式更好？

**答案：B（`mid = l + (h - l) / 2;`）**

**为什么**：
- `A. (l + h) / 2` —— 当 `l + h > INT_MAX`（≈ 21.4 亿）时**整数溢出**，结果变成负数 → 数组越界 / 死循环。这是著名的 **JDK binary search bug（2006 年 Joshua Bloch 公布，Java 库里潜伏了 9 年）**。
- `B` —— `h - l` 一定非负且 ≤ 数组长度，**不可能溢出**，数学上又等价于 `(l+h)/2`（向下取整）。✅
- `C. (l + h) / 2 - 1` —— 既没解决溢出，还把中点**系统性偏移了 1**，会跳过元素、破坏正确性。
- `D. (l + h + 1) / 2` —— 溢出风险**更大**（多加 1），且这是**向上取整**的中点；只在特定的"避免死循环"二分变体里才需要，这里不是。

**手法识别**：**手法④"不存在/不适用的机制"的变体**——C 和 D 看起来像是"某种调优"，实则无来由。
**映射**：C++ 代码题 + `module_7`（B+树**节点内**二分查找）。
> ⭐ **配套记住**：BuzzDB 在节点内查键用 `std::lower_bound` / `std::upper_bound`（Sheet 02 分析已列为必考 C++ 点）。`lower_bound` 返回**第一个 ≥ key** 的位置，`upper_bound` 返回**第一个 > key** 的位置。

## Q6 · Volcano 逐元组 vs 向量化：吞吐量提升几倍 ⭐⭐

**题干成本模型**：
- Volcano `next()`：**80 ns 迭代器/控制开销 + 20 ns 谓词求值，每元组**。
- 向量化 `nextBatch()`（1000 元组/批）：**200 ns 控制开销每批 + 20 ns 谓词求值每元组**。

**答案：B（约 5X）**

**推导**：
```
Volcano  ：每元组 = 80 + 20 = 100 ns          → 吞吐 = 1/100ns = 1.0 × 10⁷ tuples/s
向量化   ：每批   = 200 + 1000×20 = 20,200 ns
           每元组 = 20,200 / 1000 = 20.2 ns    → 吞吐 ≈ 4.95 × 10⁷ tuples/s

加速比 = 100 / 20.2 = 4.95 ≈ 5X
```

**⭐ 这题真正在考的洞察（比答案重要）**：
> **只有 iterator/control overhead 被批量摊薄了（80 → 0.2 ns/元组），谓词求值的 20 ns/元组一分不减。**
> 所以加速比的**理论上限 = 100 / 20 = 5X**，无论 batch 多大都突破不了。

这正是 **P11 Vectorwise「向量化 dramatically reduces the interpretation overhead」** 与 **P10 HyPer「向量化 offers excellent performance, but still does not reach the speed of hand-written code」** 的量化版本：
- **向量化摊薄的是"解释/控制"开销** → 上限由"真正的计算"决定；
- **P10 编译执行**进一步把"真正的计算"也优化了（数据留在寄存器、消除虚调用、分支布局），所以能再快 2–4 倍。

**诱饵怎么造的**：
- **D = 10X** ← 只看开销的降幅（80 → 0.2 是 400 倍）却算错总账，或把谓词成本也当成被摊薄的。
- **A = 3X** ← 批大小或开销代入错。
- **C = 差不多** ← 认为"反正都要算谓词"。

**映射**：**P9 Volcano（iterator/demand-driven）** + **P11 Vectorwise（向量化）** + **P10 HyPer（编译）** + 🆕`module_12` 向量化一节 + 🆕`module_11` 查询解释的开销来源。**这是全卷最"跨材料"的一题。**

## Q7 · 哪一项 NOT 是 C-Store 的核心设计技术 ⭐⭐

**答案：D**

| 选项 | 判定 | 理由 |
|:--|:--:|:---|

### ❌ 期中 Q4 · 逗号分隔的多值列（M1 / ch2 / P1）

### ❌ 期中 Q5 · Stonebraker 1981（P3 OS Support）NOT correct

> **题干**：Which of these statements is **NOT correct** based on Stonebraker's 1981 paper?
> **你选**：To make an OS-provided buffer cache attractive to a DBMS, the access overhead must drop to **a few hundred instructions**.
> **正确（即那句错的）**：**The next block a DBMS needs is typically the next logical file block, so a sequential prefetch is an efficient strategy.**

**⭐ 原文依据（我逐字核对了 `extracted/paper3.md`）**：

正确答案为什么是错的 —— `paper3.md` §2.3 Prefetch（第 224–237 行）：
> *"Although UNIX correctly prefetches pages when sequential access is detected, there are **important instances in which it fails**. Except in rare cases INGRES at (or very shortly after) the beginning of its examination of a block **knows exactly which block it will access next. Unfortunately, this block is not necessarily the next one in logical file order. Hence, there is no way for an OS to implement the correct prefetch strategy.**"*

→ 论文的论点恰好相反：**DBMS 知道自己下一个要哪一块，但那一块不一定是文件里的下一个逻辑块**（例如沿 B 树指针走、按排序顺序读），所以 **OS 的顺序预读对 DBMS 是错的策略**。这正是"DBMS 要自建缓冲池"的四大理由之一。

> *"for an (OS) provided buffer pool manager to be attractive, the access overhead **must be cut to a few hundred instructions**."*

**根因分类**：⚠️⚠️ **【根因 B】在论文类 NOT-correct 题里，把"带具体数字/具体名词的陈述"当成最可疑的，反而放过了"方向反转"的那句。**

### ❌ 期中 Q6 · SELECT 无 ORDER BY 的输出顺序（M1 / ch2）

### ❌ 期中 Q22 · DRAM 为什么是易失性的（M3 / ch12）

> **题干**：Why is DRAM considered volatile memory?
> **你选**：It is built using NAND flash technology
> **正确**：**It uses capacitors that leak charge over time**

**为什么错**：
- **DRAM** = Dynamic RAM。每个 bit 存在一个**电容（capacitor）**里，电容会**漏电**，所以必须**周期性刷新（refresh，典型 64 ms 一轮）**；**断电即刻丢失** → 这就是 volatile 的物理原因。"Dynamic"这个词本身指的就是"需要不断刷新"。
- **NAND flash** 是**非易失（non-volatile）**的，用**浮栅晶体管（floating-gate transistor）**把电荷困住，断电也保留 —— 它是 **SSD** 的材料，**与 DRAM 无关**。你的选项把两种介质完全搞混了，而且逻辑上自相矛盾（NAND 是非易失的，不可能成为"易失"的原因）。

**根因分类**：⚠️ **【根因 D】硬件/物理层的事实性知识点是薄弱区。**（与 Q19、Q28 同属一类。）

> 📌 **补一张最小必背表**：
> | 介质 | 易失性 | 物理机制 | 用在哪 |
> |:--|:--|:--|:--|
> | **SRAM** | 易失 | 触发器（6 晶体管锁存），**不需刷新**，最快最贵 | CPU cache |
> | **DRAM** | **易失** | **电容 + 需周期刷新**，电容漏电 | 主存 / 缓冲池 |
> | **NAND Flash** | **非易失** | **浮栅晶体管**困住电荷；**写前需擦除**，随机写慢于顺序写 | SSD |
> | **磁盘 (HDD)** | 非易失 | 磁化盘片 + 机械寻道 | 冷数据 |

### ❌ 期中 Q25 · GROUP BY / HAVING / ORDER BY 的求值顺序（M1 / ch2）

> **题干**：What is the correct order of evaluation for relational operators in SQL (for GROUP BY, HAVING, ORDER BY)?
> **你选**：HAVING filtering → Grouping → Ordering
> **正确**：**Grouping → HAVING filtering → Ordering**

**为什么错**：**HAVING 是作用在"分组之后的组"上的过滤器**，所以**必须先分组才能 HAVING**（`HAVING SUM(x) > 100` 里的 `SUM(x)` 只有分组后才存在）。而 `ORDER BY` 作用在**最终结果集**上，永远在最后。

**必背的完整 SQL 逻辑求值顺序**：
```
FROM / JOIN  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT (投影/别名)  →  DISTINCT  →  ORDER BY  →  LIMIT/OFFSET
                 ↑                        ↑
            过滤【行】               过滤【组】
```
> 💡 **一句话记住区别**：**WHERE 过滤行（分组前），HAVING 过滤组（分组后），ORDER BY 永远最后。**
> 💡 **副作用**：因为 `SELECT` 的别名在 `WHERE/GROUP BY/HAVING` 之后才产生，所以标准 SQL 里**不能在 WHERE 里用 SELECT 定义的别名**，但**可以在 ORDER BY 里用**。

**根因分类**：⚠️ **【根因 E】关系代数 / SQL 语义的"顺序与定义"类知识点不牢。**（与 Q6、Q33、Q35 同属一类。）

### ❌ 期中 Q28 · DB 页比磁盘块小时的影响（M3 / ch12）

> **题干**：If DB page size is **smaller** than disk block size (e.g., 1 KB page vs 4 KB block), what is the impact?
> **你选**：Disk fragmentation is minimized
> **正确**：**Performance decreases due to read amplification**

**为什么错**：磁盘/SSD 的**最小可传输单位是块**。要读一个 1 KB 的 DB 页，硬件必须**把整个 4 KB 块读上来**，其中 **3 KB 是浪费的** → 这就是 **read amplification（读放大）= 4×**。
- 写更糟：改一个 1 KB 页要 **read-modify-write** 整个 4 KB 块 → **写放大**。
- "碎片最小化"不成立：更小的页反而意味着**更多的页、更多元数据、更差的顺序性**。

> 📌 **把三种"放大"一起记牢（期末很可能考）**：
> | 术语 | 定义 | 典型起因 |
> |:--|:--|:--|
> | **Read amplification（读放大）** | 实际读的字节 / 真正需要的字节 | **页 < 块**；LSM 树要查多层；Bw-tree 的 delta 分散在 flash 上要全读回来 |
> | **Write amplification（写放大）** | 实际写的字节 / 逻辑写的字节 | **页 < 块**（read-modify-write）；日志结构存储的 GC 搬运活数据；flash 的擦除块粒度 |
> | **Space amplification（空间放大）** | 实际占的空间 / 逻辑数据大小 | 旧版本未回收、B+树节点半满、C-Store 的 overlapping projections（**故意的**） |
>
> ⭐ **交叉点**：**P5 Bw-Tree 的"增量刷盘减少写放大，代价是读放大"** 正是这组概念的论文级应用——它靠 **flash 极高的随机读性能**来偿还读放大。

**根因分类**：⚠️ **【根因 A + D 复现】**选了"听起来是好处"的选项（fragmentation minimized），且硬件层事实不牢。

### ❌ 期中 Q33 · 关系模型的数学基础（ch2）NOT correct ⭐ 最难的一题

> **题干**：With respect to the relational model and its mathematical foundations, which statement is **NOT correct**?
> **你选**：A domain is a mathematical set of atomic values with at least equality defined; a tuple is a function from attribute names to values in their respective domains.
> **正确（即那句错的）**：**The projection operator π is idempotent and commutative in the sense that for any attribute sets X and Y: π_X(π_Y(R)) = π_Y(π_X(R)) = π_{X ∪ Y}(R).**

**为什么那句是错的（两处都错）**：
1. ⭐ **投影的复合给出的是"交集"，不是"并集"**：
   ```
   π_X(π_Y(R)) = π_{X ∩ Y}(R)        ← 交集！
   ```
   直觉：`π_Y` 先把关系削到只剩 Y 里的属性，之后 `π_X` **不可能变出 Y 里没有的属性**。投影只会**越投越少**，绝不可能通过嵌套得到"并集"（那需要凭空造出属性）。
2. ⭐ **要"有定义"还需要前提 `X ⊆ Y`**：若 X 里有不属于 Y 的属性，`π_X(π_Y(R))` **根本不合法**（那些属性已经不存在了）。因此"for **any** attribute sets X and Y"就是错的——**手法①绝对化**。
3. **交换性也不成立**：`π_X(π_Y(R))` 与 `π_Y(π_X(R))` 一个要求 `X ⊆ Y`、另一个要求 `Y ⊆ X`，一般来说两者不能同时合法。

**你选的那句为什么是对的**：这是关系模型的标准形式化定义 ——
- **domain（域）** = 原子值的集合，**至少定义了相等比较**（这样才能做选择、连接、去重）；
- **tuple（元组）** = 从**属性名**到**各自域中的值**的一个**函数**（这也正是"关系的属性无序、靠名字引用"的形式化根据）。

另两个正确选项也值得记：
- *"a relation is a **subset of a Cartesian product of domains**; attributes are **named roles over domains**, so **the same domain can appear more than once under different attribute names**"* —— 例：`Flight(origin: City, destination: City)`，同一个域 City 出现两次，靠属性名区分角色。
- *"Under **set semantics**, projection may require **duplicate elimination**; thus **projecting away all attributes of every candidate key can collapse distinct tuples**, so **keys are not guaranteed to be preserved by projection**."* —— 例：`R(id, city)` 有 3 行不同 id 但都是 Atlanta，`π_city(R)` 在集合语义下只剩 1 行。

**根因分类**：⚠️ **【根因 E 复现】+ 【根因 B 复现】**——你选了一句**教科书标准定义**当作错误项，因为它"术语密度高、像是被编出来的"；而真正错的是一个**带公式的形式化陈述**，需要你真的验算 `π` 的复合语义。

> 💡 **应对这类"带公式的关系代数性质题"的通用方法：拿一个 2 行 2 列的最小例子代进去验算。**
> `R(A, B) = {(1, x), (2, y)}`，X = {A}，Y = {B}：
> - `π_A(π_B(R))` → `π_B(R) = {(x), (y)}`，里面**没有 A** → **不合法**，立刻判死。
> - 若改 X = {A}，Y = {A, B}：`π_A(π_{A,B}(R)) = π_A(R) = {(1),(2)}` = `π_{A ∩ {A,B}}` = `π_A` ✓ **是交集，不是并集**。

### ❌ 期中 Q35 · 关系代数的 closure（ch2）

> **题干**：Which statement about **closure** in relational algebra is true?
> **你选**：Closure prevents loss of information during joins
> **正确**：**Closure means relational operators always produce a relation**

**为什么错**：**Closure（闭合性 / 封闭性）** = 关系代数的运算**输入是关系、输出也是关系**，因此**运算可以任意嵌套组合**（这正是 P8 DeWitt & Gray 说"关系查询天然适合并行、可组合成 dataflow graph"的根据，也是 P9 Volcano 的 iterator 能任意拼接的根据）。

> ⚠️ **"closure" 在本课里有三个同名异义**，务必分清：

> | **Attribute closure X⁺** | 范式化 / 函数依赖 | 由 X 通过 FD 能推出的全部属性 |

## 2.3 ⭐⭐⭐ 从你的错误模式提炼的 6 条应试行为规则

**规则 1 · 绝对化词无条件预警（治根因 C）**
看到 `always / never / must / immediately / guarantees / entirely / only / exclusively`，**不管题型是"which is NOT correct"还是"will X happen"还是"which is true"**，先把该选项标成高度可疑。Q6 的 `always` 就写在脸上。

**规则 2 · 论文 NOT-correct 题：反过来用"具体性"判断（治根因 B，最高价值）**

- 🔑 **操作方法**：先找**哪一句在做"因果或方向性断言"**（because / so / therefore / thus / hence），**验它的方向**，而不是去质疑那些细节数字。

**规则 3 · 选"最不炫技的实话"（治根因 A）**
当一个选项是"朴素的工程现实/负面后果"，其余是"漂亮的机制解释"时，**朴素那个通常是答案**。
对照：Q4 正解"making querying less efficient"、Q19 正解"to run on low-memory systems by default"、Q28 正解"performance decreases due to read amplification"。

**规则 4 · 关系代数带公式的性质题：代最小例子验算（治根因 E）**
用 2 行 × 2 列的关系代进去，30 秒就能证伪。**尤其检查算子复合是"交"还是"并"、是否需要子集前提、是否真的可交换。**

**规则 5 · 同名异义先归属再作答（治根因 F）**
`closure`、`projection`、`delta`、`merge`、`flow control`、`partitioning` 在本课里都有 ≥2 个含义。**先确定题目在哪个语境（关系代数？范式化？C-Store？Volcano？），再选。**
（完整的同名异义表见 `精讲版/论文重点_P5-P12_...md` **表 E**。）

**规则 6 · 计算题写出中间量再看选项（新增，针对期末计算题占比暴涨）**
Final Practice 有 43% 是计算题，且诱饵都是**半步错误**。所以：**先独立算完、写下中间量（扇出、探测序列、每元组 ns），再去比对选项**。绝不要先扫一眼选项再"凑"——那正好落进半步错误的圈套。
三个必背模板：
- **B+ 树层数** = `⌈log_(扇出) N⌉`，扇出 = 最大孩子数 × 填充率；**向上取整**。
- **双重哈希** = `(h1(k) + i·h2(k)) mod m`，**i 从 0 开始**，逐个写出直到遇到空槽。
- **执行模型加速比** = `(每元组总成本_旧) / (每元组总成本_新)`；**只有控制开销被批量摊薄，计算开销不变** → 加速上限 = `总成本 / 计算成本`。

## 3.2 第 1 节：Query Parsing（查询解析）

### What（是什么）
✅ **EN**: *"This approach to extracting details from the query string is known as **query parsing**."*
💡 用**正则表达式（regex, regular expression）**从 SQL 查询**字符串**里抽出各个成分，存进一个结构体，再据此**动态搭建算子链**。

### Why（为什么要它）
之前 BuzzDB 的查询是**硬编码成函数**的（用算子框架手写）。改一个查询就要重写代码。解析让"**只给一个字符串就能执行查询**"成为可能 → **提升查询处理的灵活性**。

### How（怎么做）

**① 四个正则，抽四类信息**（数量要记住：**4 个**）

| # | 正则用途 |
|:--|:---|
| 1 | 提取**被选属性的下标** |
| 2 | 识别 **sum 操作** |
| 3 | 定位 **group by 子句**并提取相关属性下标 |
| 4 | （更复杂的一个）提取并**验证 where 子句**上的谓词 |

**② 结果装进 `QueryComponents` struct（6 个字段，爱考）**

| 字段 | 类型 | 含义 |
|:---|:---|:---|
| `select_attributes` | **vector** | 被检索列的**下标** |
| `sum_operation` | **bool** | 是否含 sum |
| `sum_attribute_index` | 索引 | 对**哪一个**属性求和 |
| `group_by` | **bool** | 是否有 group by 子句 |
| `group_by_attribute_index` | 索引 | 按哪个属性分组 |
| `where_condition` | — | 验证 where 子句的**存在性与边界（bounds）** |

> ✅ **EN**: *"the query components struct contains **all the necessary components to execute SQL queries**."*
> 另有 `pretty_print` 函数把这些成分**结构化输出**，便于一眼验证查询结构与条件。

**③ regex 语法点（transcript 明确讲了，可能出小题）**
以 `sum` 的正则为例：
- `sum` —— **字面匹配**文本 "sum"
- `\{` `\}` —— 匹配**字面花括号**
- `(\d+)` —— **capturing group（捕获组）**；`\d` = 一位**数字**，`+` = 前一元素出现**一次或多次**
- → 捕获花括号里的数字（例子里是 **3**），**这个数字标明 sum 作用在哪一列**

**④ `execute_query`：从 struct 到算子链（顺序要记住）**
```
① 从基本的 scan 操作开始（scan 用 buffer manager 扫表的所有列）
② 有 where 子句 → 每个条件建一个 simple predicate 对象
                 → 用 complex predicate 组合成逻辑 AND
                 → 把组合谓词嵌进 select 算子
③ 有 sum / group by → 配置聚合函数与分组属性
                     → 实例化 hash aggregation 算子
④ 执行：从 root 算子 open 开始，不断 fetch 并打印满足条件的 tuple
```
✅ **EN（执行的递归结构）**: *"The root operator **recursively calls its child operator and so on until we hit a leaf operator with no children like the scan operator**."*

**⑤ 完整例子（三层算子链，必须能画出来）**
```
        hash aggregation   ← 按 column 2 分组，对 column 1 求和
              ↑
           select          ← 按 column 1 的值过滤，选 2–6
              ↑
            scan           ← 用 buffer manager 扫表的所有列
```

❌ **Trap**: *"Query parsing eliminates the per-tuple function call overhead of the operator framework."* —— **错**，解析只解决**灵活性**，**开销一点没少**（下一节就是讲这个）。

## 3.3 ⭐⭐ 第 2 节：Query Interpretation 的 4 个开销来源（最可能考的一条）

✅ **EN**: *"While the query interpretation approach is **very flexible, it is also slow**."*

**术语先分清**：
- **Query interpretation（查询解释）** = 现在的方式 = **parse SQL → 生成 query execution plan（算子链/树）→ 执行**。函数 `query_interpretation` 内部就是调 `parse_query` + `execute_query`。

**四个开销（三个 compute + 一个 memory，分类要记准）**：

| # | 类别 | 开销 | 原文要点 |
|:--|:---|:---|:---|
| **1** | compute | **每个 tuple 要穿过多个算子，产生若干次函数调用** | *"This overhead can significantly affect performance when the query must be executed on **millions of tuples**."* |
| **2** | compute | **每个 tuple 要用"通用 schema 假设"做反序列化（deserialize）** | 泛化的反序列化路径 |
| **3** | compute | **多态的动态函数分派（dynamic dispatch）** | *"as we are using **pointers to abstract classes** for operators. This dispatch requires an **additional lookup in a virtual table (vtable)**"* |
| **4** | **memory** | **算子里频繁创建/销毁临时对象** | *"such as **unique pointers to fields**"* |

> ⭐ **这四条与 P10（Neumann/HyPer）的批判逐条对应**——期末最可能考的交叉点：
> | module_11 的开销 | P10 的对应论述 |
> |:---|:---|
> | ① 每 tuple 穿过多算子、若干函数调用 | *"the next function will be called for every single tuple … **millions of times**"* |
> | ③ 虚表查找的动态分派 | *"the call to next is usually a **virtual call** … degrades the **branch prediction**"* |
> | ② 通用 schema 反序列化 | *"poor code locality and **complex book-keeping**"*（压缩表扫描要记住流位置再跳到解压代码） |
> | ④ 临时对象的内存开销 | P10 的 **pipeline breaker 定义**：把元组**赶出 CPU 寄存器**就算破坏流水线 |

## 3.4 ⭐⭐ Query Compilation（查询编译）：定义、做法、优缺点

### What
✅ **EN**: *"**Query compilation** consists of translating the SQL query string to a **hard coded C function** and then **generating assembly code** from that function."*
→ 数据库**直接跑机器码，绕过查询解释的开销**。

### How（做法的关键细节，都可能出题）
✅ **EN**: *"The query compilation function **moves away from the operator framework** and goes towards a **more hard coded approach**. It **directly runs all the operations from scanning through aggregation in a single function**."*
1. **直接用 buffer manager 遍历表的所有页**，处理页内所有 slot 的 tuple；
2. 到一个 tuple slot 后，**把 tuple data 当作 raw character string（原始字符串）**；
3. **直接把第一个 field 从 raw string 反序列化成整数** —— ⭐ *"This kind of **hard coded deserialization is super fast, but also very rigid**, unlike the interpreted approach, which is **flexible but slow**."*
4. 按 **lower bound / upper bound** 过滤；
5. 通过过滤则**更新该 field 值的 group sum**；
6. 最后打印所有 group sum。

### 优点（2 条）
✅ **EN**: *"(1) compiled queries **eliminate the need for interpreting each tuple and passing them through several operators**, thereby **saving compute and memory resources**. (2) as compiled queries **run on bare metal**, they run significantly faster."*

### ⭐ 必背数字
✅ **EN**: *"for this illustrative **grouping based aggregation** query in BuzzDB, the **compiled query is 30 times faster** than the interpreted query."*

### 缺点（2 条，⭐ 极可能作为"NOT correct"的正确项出现）
✅ **EN**:
1. *"the **compilation process itself can be time consuming**. **If the execution time of the query is short, then the total time to compile and run it might actually be longer than just interpreting it.**"*
2. *"compiled queries are **[less] flexible** compared to interpreted queries. Once a query is compiled into machine code, **it is not possible to easily adjust the compiled query if the table schema changes**. There might be a need to **recompile** the query. **The cost of frequent recompilations might exceed the performance gains** from query compilation."*

> ⚠️ **转录里第二条被口误说成 "compiled queries are flexible compared to interpreted queries"，从上下文（"Once compiled … not possible to easily adjust … need to recompile"）看应为 "less flexible"**。考试按 **"编译后灵活性更差"** 记。

### 📊 解释 vs 编译 对比表（必背）

| 维度 | Query Interpretation | Query Compilation |
|:---|:---|:---|
| 流程 | parse → 算子链 → 逐 tuple 走算子 | parse → 硬编码 C 函数 → 汇编/机器码 → 直接跑 |
| 是否用算子框架 | ✅ 用 | ❌ **离开算子框架，单个函数干完** |
| 反序列化 | **通用 schema 假设**，灵活但慢 | **硬编码**，超快但**刚性** |
| 函数调用 | 每 tuple 多次 + **vtable 动态分派** | 基本没有 |
| 灵活性 | ⭐ **高** | ⭐ **低**（schema 变了要重编译） |
| 速度 | 慢 | ⭐ **快 30×**（本例） |
| 何时反而更差 | — | ⭐ **查询执行时间很短时**，编译+运行 > 直接解释 |

## 3.5 ⭐ module_11 与 P10 的关键差异（高危考点）

| | 🆕 module_11（BuzzDB） | P10（Neumann / HyPer） |
|:---|:---|:---|
| 编译目标 | **先生成 C 函数，再生成汇编** | ⭐ **直接生成 LLVM IR，用 LLVM JIT** |
| 为什么这样选 | 课程教学，展示"硬编码有多快" | ⭐ **P10 明确否决了 C++ 路线**：*"an optimizing C++ compiler is really slow — compiling a complex query could take **multiple seconds**"*；且 *"C++ does not offer total control over the generated code — in particular **overflow flags** are unavailable"* |
| 编译耗时 | 承认"编译本身耗时"是缺点 | ⭐ LLVM **只需几毫秒**（Table 1：16.53 s → **0.81 s**；Table 2 Q1：1556 ms → **16 ms**） |
| 数据流方向 | 硬编码的单个循环 | ⭐ **push-based（数据被推向消费者）**，不是 pull |
| 组织原则 | 一个函数干完 | ⭐ **data-centric（不是 operator-centric）**，**数据尽量留在 CPU 寄存器**；**pipeline breaker 之间** 才落内存 |
| C++ 的角色 | 生成的就是 C | ⭐ **C++ 是预编译的"齿轮"，LLVM 是动态生成的"链条"**；**hot path 必须纯 LLVM** |

> 🎯 **期末如果问"编译执行的缺点"**：module_11 给的是**编译耗时 + 不灵活**；**P10 恰恰是来解决"编译耗时"的**（用 LLVM 而非 C++）。**两者别混。**

## 4.1 第 1 节：列存 vs 行存

### 案例设定（数字要记住）
- 数据集：**weather**，列 = **timestamp, temperature, humidity, wind speed**（4 列）
- 查询：**timestamp 5 到 75 之间的平均温度**（只需 timestamp + temperature 两列）
- 合成数据：**100 万行、4 列**，存成 **4 KB 页**
- 分布：**timestamp 顺序递增**；**temperature 用正态分布**围绕均值波动；**humidity 与 wind speed 用均匀分布**

### ⭐ 页数对比（必背）
| 格式 | 读取页数 | 原因 |
|:---|:--:|:---|
| **行存** | **7 页** | 记录一条接一条存 → **被迫读入无关的 humidity 和 wind speed 列** |
| **列存** | **4 页** | 每列存在**单独一组页**（page1 = 记录 1–40 的 timestamp，page2 = 记录 1–40 的 temperature…）→ **只访问需要的两列** |

### ⭐⭐ 四维对比表（transcript 原表，几乎必考）

| 维度 | 行存 (Row / NSM) | 列存 (Columnar / DSM) |
|:---|:---|:---|
| **存储** | 一行的所有列**存在一起** | **每列存在单独的文件里** |
| **理想负载** | **事务型（transactional）**，频繁访问**完整记录** | **分析型（analytical）**，通常只需**列的子集** |
| **最佳访问模式** | 访问**完整的行** | 访问**特定的列** |
| **压缩潜力** | ⭐ **有限**，因为**一行内的值类型各不相同** | ⭐ **高得多**，因为**每列是单一数据类型** |

### ⭐ 列存查询的执行方式（这是 late materialization 的教学版，重要）
✅ **EN**: *"We first read through the **timestamp pages**. Each timestamp value is checked against the given time range… **If the record qualifies, we save the satisfying record's offset in a map.** We then **retrieve only the necessary temperature pages using the offsets that we previously collected.**"*

💡 **两阶段：先扫过滤列拿到 offset 列表 → 再只取需要的目标列页**。
> ⭐ **交叉点**：这与 **P12 C-Store 的 `Select` 返回 bitstring + `Mask` 算子** 是同一个思想；也就是 Final Practice Q7 选项 A 说的 **late materialization（延迟物化）**。**module_12 讲的是它的手写版，C-Store 讲的是它的算子化版。**

### ⭐ 必背性能数字
✅ **EN**: *"When we have a **highly selective filter**, running the same query using columnar storage format is **30 times faster** than with row storage format. This is mainly because we read **four times fewer pages** from disk."*

> ⚠️ **注意逻辑**：**页数只少 4 倍，端到端却快 30 倍** —— 因为除了 I/O，还省了缓冲池空间、减少了内存带宽占用。**"30× 的前提是 highly selective filter"这个限定条件很可能是陷阱点**（❌ Trap: *"Columnar storage is 30× faster for all queries."*）。

### 收尾金句（可能作为概念题）
✅ **EN**: *"this lesson highlights the **tight connection between the storage manager and the query execution engine** of a database system."*

## 4.2 ⭐⭐ 第 2 节：压缩四算法（最可能出计算/匹配题）

### 为什么列存更适合压缩
✅ **EN**: *"Row storage **mixes different data types in each row**, making it difficult to find repeating patterns that compression algorithms can exploit… In contrast, columnar storage **keeps all the values of a single column together**… In this way, **columnar storage improves data similarity, making compression more effective**."*
- 补充理由：**每列单一数据类型 + 高数据冗余度**（product ID 在百万行里反复出现；温度读数集中在小范围）→ **高压缩比**。
- ⭐ **压缩的第二重收益**：*"columnar compression also allows **more data to fit in the in-memory buffer pool**, significantly reducing disk IO operations."*

### ⭐⭐ 四种算法对照表（必背，注意"数值型 vs 类别型"的二分）

| 算法 | 适用数据类型 | 机制 | 关键细节 |
|:---|:---|:---|:---|
| **① Delta encoding** | **numeric（数值）**，值**增量式变化** | 存**第一个完整值** + 后续存与**前一个值的差（delta）** | delta 通常小得多，**需要更少的 bit**。典型用于 **timestamp** |
| **② Bit packing** | **numeric**，**取值范围小** | **只分配必要的 bit 数** | ⭐ 算例：温度 35/40/45/50 落在 **6 bit 范围（0–63）**；原本整数占 **4 字节 = 32 bit**，改用 **6 bit** |
| **③ Huffman encoding** | **categorical（类别）**，如字符串 | ⭐ **基于频率**：**高频值给短码，低频值给长码** | ⭐ 算例：product ID `111111` 出现 **100 次** → 码 **`0`**；`444444` 出现 **10 次** → 码 **`111`**。建树时**高频元素留在树的上层，低频不断被合并到更深层** |
| **④ Byte dictionary encoding** | **categorical**，⭐ **唯一值数量有限** | 把类别值替换成**紧凑的单字节码（0–255）** | 压缩时遍历列：已在字典里就用其编码值；不在就分配**新的唯一字节值**并更新**反向字典（reverse dictionary）**用于解码 |

> 💡 **术语定义要记准**：**numeric data** = 可度量的值（timestamp、temperature）；**categorical data** = 离散标签（product ID、country name）。
> ❌ **Trap**（张冠李戴型）：*"Huffman encoding is well suited for incrementally changing numeric data."* —— **错**，那是 delta encoding；Huffman 是**基于频率、面向类别数据**的。

### Bit packing 的实现要点（代码题素材）
- `bit_pack`：先算**总共需要的 bit 数**，再定**需要多少字节**；然后逐个整数**抽出其 bit，用位运算顺序打包进 byte vector**。
- `extract_value`（解压）：按 **index 和 bit width** 算**起始 bit 位置**；逐 bit 检查 packed data 中该位是否置位；置位则在结果里**设置对应位**，重建原整数。

### ⭐⭐ 压缩方案的查询性能对比（必背三个数字）
> 前提：查询结果（total sales）在所有算法下**完全一致**（保证正确性）。

| 方案 | 查询耗时 | 原因 |
|:---|---:|:---|
| **无压缩** | **7.79 ms** | 原始 product ID 需要**完整字符串比较** |
| **Huffman** | **2.24 ms** | 用了短二进制码，**但仍需按位解码，带来额外开销** |
| ⭐ **Byte dictionary** | ⭐ **0.71 ms（最快）** | product ID 换成**单字节值**，比较极快 |

✅ **EN（结论句）**: *"This highlights how compression **not only reduces storage space but also improves query efficiency**."*
> ⚠️ **这里的排序很反直觉、极适合出题**：**压缩比更高的 Huffman 反而比 byte dictionary 慢**，因为**解码成本**才是查询时的瓶颈。
> ❌ **Trap**: *"The compression scheme with the highest compression ratio always gives the fastest queries."* —— **错**（手法①绝对化 + 与本数据矛盾）。

### weather 数据集上的组合应用（爱考"哪列用哪种"）
| 列 | 压缩方式 | 实现细节 |
|:---|:---|:---|
| **timestamp** | **Delta encoding** | 初始化 delta 向量，**第一个值设为原始 timestamp**，用 **`std::adjacent_difference`** 计算差值 |
| **temperature** | ⭐ **先 shift（减最小值）再 Bit packing** | 用 **`std::min_element`** 找最小温度，**`std::transform`** 把所有值减去最小值→**收缩取值范围**；再 bit pack。⭐ **4 bit 就够小范围温度数据** |

- 压缩后的列存进**独立的二进制文件**；查询时**加回 delta** 重建 timestamp，**用位运算从 packed 值中 extract** 重建 temperature。

### ⭐⭐ 三档存储格式性能对比（必背，Final Practice 风格的数字题素材）
| 存储格式 | 查询耗时 |
|:---|---:|
| **行存**（扫整行） | **17.57 ms** |
| **列存** | **5.13 ms** |
| ⭐ **压缩列存** | ⭐ **4.08 ms** |

✅ **EN**: *"using compressed columnar storage, we further reduce query time to 4.08 milliseconds as **fewer bytes need to be read from disk and decompressed efficiently**."*

## 4.3 ⭐⭐⭐ 第 3 节：向量化执行 + SIMD（与 Final Practice Q6 直接对应）

### tuple-at-a-time 的三个问题（必背）
✅ **EN**: *"Traditional execution processes each tuple at a time, incurring a lot of overhead…"*
1. **每个 tuple 都触发不同关系算子之间的函数调用**；
2. **CPU 无法充分利用它"一次处理多个 tuple"的能力**；
3. ⭐ **这种逐元组处理常导致 CPU pipeline stall（流水线停顿）和 cache miss**。

### vector-at-a-time 的收益
✅ **EN**: *"**Batching reduces function call overhead because we only transition between operators once per batch rather than once per tuple.**"*
> ⭐ **这一句就是 Final Practice Q6 的原理**：**被摊薄的只有"算子间转换/控制"的开销**（80 ns → 0.2 ns），**谓词求值的 20 ns/元组不变** → **加速上限 = 100/20 = 5×**。

### SIMD 的数据库用例（3 个，爱考）
1. **过滤落在范围内的行**；
2. **聚合**（sum、average）；
3. ⭐ **解码压缩数据**（如 **bit-packed 列**）—— 注意这条把 §4.2 和 §4.3 串起来了。

### 核心 SIMD 操作（3 类）
① **加载数据向量**；② **应用 mask（掩码）**来过滤/选择元素；③ **horizontal reduction（水平归约）**累加部分和。

### ⭐ 过滤 timestamp 的完整例子（ARM NEON 命名，指令名可能出题）
```
vld1q_s32   → 把 4 个连续的 32 位整数载入 SIMD 寄存器
vcgeq_s32   → 向量比较：≥ start_timestamp        ┐ 各产生一个 mask
vcleq_s32   → 向量比较：≤ end_timestamp          ┘
vandq       → 按位 AND 合并两个 mask → 得到"落在范围内"的 mask
```
✅ **EN**: *"This vectorized approach **replaces a loop of scalar comparisons**, allowing the CPU to handle **four timestamps per instruction**."*

**具体数值例子（要能复现）**：载入 **18, 40, 25, 15**；条件 `> 20` 且 `< 30`；`vand` 合并后 → ⭐ **唯一合格的整数是 25**。

### ⭐⭐ 求平均温度的 SIMD 流程（"用 mask 代替分支"的关键技巧）
```
① vload 整数 / vload_f32：各载入 4 个 32 位值（timestamp 与 temperature 分别一个寄存器）
② 两次向量比较（≥start、≤end）→ 两个 mask → 用 AND 合并
③ 把 mask 转成 float 向量，用 vmulq 与 temperature 向量逐元素相乘
   → ⭐ 范围外元素变成 0，范围内保留原温度值
④ 用 vaddq 把 masked 温度加到"运行中的 sum 向量"
⑤ 做 horizontal reduction（如 vaddvq）从向量得到标量和
⑥ ⭐ 用标量循环处理剩余元素（总数不是 4 的倍数时）
```
✅ **EN（③④ 的意义）**: *"This approach **seamlessly integrates conditional filtering without resorting to branch instructions**."*
✅ **EN（⑥ 的意义）**: *"Combining the vectorized portion with a simple scalar tail case is a **common pattern for SIMD algorithms**."*

### ⭐⭐ SIMD 的三大优势（分类记，每条都可能单独出题）

| # | 优势 | 原文要点 |
|:--|:---|:---|
| **1** | **指令数减少** | ⭐ *"If you have **N** data points … with a vector of width **W**, you only need **N/W instructions**."* 减少指令数**不仅加快执行，还降低指令解码和调度的开销** |
| **2** | **内存访问更规整** | 数据存在**连续数组**里，**列式格式尤其**契合；**向量加载与 cache line 对齐**得好，CPU 取回**与 SIMD 寄存器宽度匹配的整条 cache line**，**充分利用每次内存传输**。相比之下 ⭐ **分散的或行式的访问导致 cache line 只被部分利用、更多 cache miss** → **列存 + SIMD = 高效利用内存子系统** |
| **3** | **最小化分支** | ⭐ *"SIMD minimizes branching by applying **one instruction uniformly across an entire vector**."* 标量代码频繁分支在**预测错误时造成 pipeline stall**；**向量化代码依赖 mask 而不是分支**，缓解停顿、保持流水线繁忙 |

### ⭐ SIMD 发展史（年代/名称题素材）
| 时期 | 技术 | 要点 |
|:---|:---|:---|
| 早期超算 | **ILLIAC IV** | 科学负载（**矩阵乘法**）受益于向量化 |
| **1980s–1990s** | 多媒体与图形 | ⭐ **Intel MMX，1996 年**推出，为桌面 CPU 加入**并行整数运算**指令（例：给图像整体**加亮度**） |
| **2000 年代早期** | **Intel SSE** / **ARM NEON** | SIMD 成为通用 CPU 的固定配置；⭐ **都扩展到 128 位**；支持**浮点** → 音视频处理到游戏物理 |
| **2010 年起** | ⭐ **Intel AVX-512** | SIMD 寄存器推到 ⭐ **512 位** |
| 现代 | ⭐ **Apache Arrow** | 按**列式数据存储格式**设计，体现软件如何**大规模利用 SIMD**；分析引擎常规用 SIMD 做**列式扫描、聚合、压缩** |

### ⭐ SoA（Structure of Arrays）与命名约定
- **SoA（数组结构体）**：把 timestamp 和 temperature 拆成**独立数组** → **每列数据在内存中连续，完美适合向量加载**；⭐ **把数组按 SIMD 友好的边界对齐还能防止未对齐访问（misaligned access）**。
- **命名约定**：指令名指明 **① 操作类型**（and / multiply…）+ **② 数据类型**（integer / float）+ **③ 向量宽度**。
  - `vld1q_s32` = 载入 **4 个 32 位有符号整数**的向量
  - `vaddq_f32` = **4 个 float** 的浮点加法
  - ⭐ **`Q` 通常表示 quad-word 操作即 128 位**，虽然更新的 SIMD 扩展扩到 **256 或 512 位**

### ⭐ SIMD 加速 hash join（进阶，可能出"哪一步需要特殊指令"）
```
① 载入一批 probe key 进 SIMD 寄存器
② 并行算 hash（用乘法和位移操作）确定要查哪些 slot
③ ⭐ 从哈希表 gather（聚集）值 —— 因为查找是【不连续的】，
   通常需要专门的 gather 指令
④ 用向量比较指令比对载入的 key 与表项，找出匹配
```
✅ **EN**: *"Although **non-contiguous access can be challenging**, well designed data layouts can still harness SIMD to boost hash join performance."*

### 小结句（概念题）
✅ **EN**: *"The SIMD instructions **reduce the number of CPU cycles needed per operation** and **improve the utilization of the CPU cache and memory bandwidth**."*

## 5.3 三个计算模板（写在草稿纸上）

```
① B+ 树层数 = ⌈log_f N⌉        f = 最大孩子数 × 填充率     【向上取整】
   例：N=12,000，f=100×0.75=75 → ⌈log₇₅ 12000⌉ = ⌈2.18⌉ = 3

② 双重哈希 probe = (h1(k) + i·h2(k)) mod m      i = 0, 1, 2, …
   逐个写出直到遇到空槽；别退化成线性探测

③ 执行模型加速比 = 每元组总成本_旧 / 每元组总成本_新
   向量化：新成本 = 控制开销/批大小 + 计算开销
   ⭐ 上限 = 总成本 / 计算成本（控制开销被摊薄，计算开销不变）
   例：(80+20) / (200/1000 + 20) = 100/20.2 ≈ 5×，上限 100/20 = 5×
```

**Q1.** Which statement about BuzzDB's query parsing is **NOT** correct?
A. Four regular expressions are used: for selected attribute indices, for a sum operation, for a group by clause, and a more complex one for the where clause.
B. The extracted details are stored in a `QueryComponents` struct that includes booleans for `sum_operation` and `group_by`.
C. In the sum regex, `(\d+)` is a capturing group where `\d` matches a digit and `+` means one or more occurrences; it captures which column the sum applies to.
D. **Query parsing removes the per-tuple function-call overhead because the operator chain is built once, before execution.**

<details><summary>答案</summary>

**D 不正确。** 解析只解决**灵活性**问题，**运行时开销一点没减**——每个 tuple 仍然要穿过整条算子链、仍然有 vtable 动态分派。这正是下一节要引入 query compilation 的动机。（**手法⑥半真半假**：算子链确实"建一次"，但被偷换成"消除了逐元组开销"。）
</details>

**Q2.** Which of the following is **NOT** one of the sources of CPU/memory overhead in query interpretation identified in BuzzDB?
A. Each tuple must pass through multiple operators with several function calls.
B. Each tuple must be deserialized using a generic schema assumption.
C. Dynamic function dispatch in polymorphism requires an additional lookup in a virtual table.

**Q3.** 计算题。A filter operator processes 5,000,000 tuples. Volcano-style `next()` costs 60 ns of control overhead + 15 ns of predicate evaluation per tuple. A vectorized `nextBatch()` costs 500 ns of control overhead per batch of 500 tuples + 15 ns of predicate evaluation per tuple. What is the approximate speedup, and what is the theoretical upper bound of the speedup as batch size grows?
A. About 4.7X now; theoretical upper bound 5X
B. About 4.7X now; the speedup is unbounded as batch size grows
C. About 60X now; theoretical upper bound 75X
D. About 3.75X now; theoretical upper bound 3.75X

<details><summary>答案</summary>

**A。** 推导：
```
Volcano ：60 + 15 = 75 ns/元组
向量化  ：控制开销摊薄 = 500 ns / 500 元组 = 1 ns/元组
          每元组总成本 = 1 + 15 = 16 ns
加速比 = 75 / 16 ≈ 4.7×
上限   = 75 / 15 = 5×      （批 →∞ 时控制开销 →0，只剩计算开销）
```
- **B 错**：⭐ **加速比有硬上限**，因为**谓词求值的 15 ns/元组一分不减**。
- **C 错**：只比了控制开销（60 vs 1），忘了计算开销仍在。
- **D 错**：把 `500/500` 算成 `500/1000` 之类的半步错误。
> 💡 批大小 500 已经把控制开销摊到 1 ns，**离上限只差 6%**——说明**批大小的边际收益衰减极快**，这也是 P11 Vectorwise 用 1024 而不是 100 万作为向量长度的原因（还要能装进 CPU cache）。
> ⚠️ 元组总数 **5,000,000 是无关信息**——出题人常放干扰数据，别被带着去算总时间。
</details>

**Q4.** Which statement about query compilation in BuzzDB is **NOT** correct?
A. It translates the SQL query string to a hard-coded C function and then generates assembly code from it.
B. It moves away from the operator framework and runs everything from scanning through aggregation in a single function.
C. It refers to the tuple data as a raw character string and directly deserializes the first field to an integer — fast but very rigid.
D. **Because the compiled code runs on bare metal, compiling and running a query is always faster than interpreting it.**

<details><summary>答案</summary>

**D 不正确（两处错）。** ① `always` 是**手法①绝对化**；② 原文明确反驳：*"**If the execution time of the query is short, then the total time to compile and run it might actually be longer than just interpreting it.**"* 另一个缺点是**灵活性差**——schema 变了要重编译，**频繁重编译的代价可能超过收益**。
（顺带记住数字：本例 grouping-based aggregation 查询，**编译版比解释版快 30 倍**。）
</details>

**Q5.** 归属题。Which technique is used by **Neumann's HyPer (P10)** but **NOT** by BuzzDB's query compilation as described in the course?
A. Translating a query into executable machine code.
B. **Generating LLVM IR and using an optimizing JIT, explicitly to avoid the multi-second compile times of a C/C++ compiler.**
C. Bypassing the overhead of interpreting each tuple.
D. Hard-coded deserialization of fields.

<details><summary>答案</summary>

**B。** BuzzDB 的路线是 **"SQL → 硬编码 C 函数 → 汇编"**；P10 **明确否决了 C++ 路线**——*"an optimizing C++ compiler is really slow — compiling a complex query could take **multiple seconds**"*，且 *"C++ does not offer total control over the generated code — in particular **overflow flags** are unavailable"* → 改用 **LLVM**（几毫秒；TPC-C 脚本编译 16.53 s → **0.81 s**）。
⭐ 另外 P10 独有而 module_11 没讲的：**push-based（不是 pull）**、**data-centric（不是 operator-centric）**、**pipeline breaker 的寄存器级定义**、**C++ 齿轮 + LLVM 链条的混合执行**。
</details>

**Q7.** Match each compression algorithm to its ideal data. Which pairing is **INCORRECT**?
A. Delta encoding — numeric data whose values change incrementally.
B. Bit packing — numeric data with a small range of values.
C. **Huffman encoding — numeric data with sequentially increasing values.**
D. Byte dictionary encoding — categorical data with a limited number of unique values.

<details><summary>答案</summary>

**C 不正确。** **Huffman 是基于频率的、面向 categorical data（如字符串/product ID）**：高频值给短码、低频值给长码。"顺序递增的数值"是 **delta encoding** 的场景。（**手法⑤张冠李戴**。）
</details>

**Q8.** 计算题。A temperature column contains values in the range 35–50 °C (integers). Currently each value is stored as a 4-byte integer. Two optimizations are applied: (1) subtract the minimum value from every entry; (2) bit-pack the shifted values. What is the minimum bit width needed after shifting, and what is the compression ratio versus the 4-byte baseline?
A. 6 bits; about 5.3×
B. **4 bits; 8×**
C. 4 bits; 4×
D. 6 bits; 8×

<details><summary>答案</summary>

**B。** 推导：
```
shift 后的范围 = 50 − 35 = 15，即需要表示 0..15
需要的 bit 数 = ⌈log₂(16)⌉ = 4 bits          （2⁴ = 16 ≥ 16 ✓，2³ = 8 < 16 ✗）
压缩比 = 32 bit / 4 bit = 8×
```
⭐ **对应 transcript 原话**：*"By subtracting the minimum temperature, we **shrink the range** … **four bits is enough for temperature data in a small range**."*
**诱饵 A/D = 6 bits** ← 那是 transcript 里**另一个**例子的答案（温度 35/40/45/50 **不做 shift**，直接落在 0–63 的 **6 bit** 范围）。⭐ **这就是典型的"半步错误"：漏掉了 shift 这一步。**
</details>

**Q9.** The course compares query performance across compression schemes on product IDs. Which statement is **NOT** correct?
A. Without compression the query takes 7.79 ms because raw product IDs require full string comparisons.
B. Huffman encoding reduces it to 2.24 ms but still requires bitwise decoding, which adds overhead.
C. Byte dictionary encoding is fastest at 0.71 ms because product IDs are replaced with single-byte values.
D. **The query result differs slightly across schemes, which is the accuracy cost of compression.**

<details><summary>答案</summary>

**D 不正确。** 原文强调 ⭐ *"The query result, total sales, **remains consistent across all the compression algorithms, ensuring accuracy in results**."* —— 这些都是**无损（lossless）**压缩。
⭐ **顺带记住这组数字反直觉的地方**：**压缩比更高的 Huffman 反而比 byte dictionary 慢**，因为**解码成本**是查询时的瓶颈 → "压缩比最高 ⇒ 查询最快"是错的。
</details>

**Q10.** 计算题。A scan must evaluate a range predicate over 4,000,000 32-bit integers. A scalar implementation needs 1 instruction per element. Using a 128-bit SIMD register, how many instructions are needed for the comparison step, and by what factor is the instruction count reduced?
A. 1,000,000 instructions; 4× reduction
B. 500,000 instructions; 8× reduction
C. 4,000,000 instructions; no reduction in instruction count
D. 2,000,000 instructions; 2× reduction

<details><summary>答案</summary>

**A。** 推导：
```
向量宽度 W = 128 bit / 32 bit = 4 个元素
指令数 = N / W = 4,000,000 / 4 = 1,000,000
削减倍数 = 4×
```
⭐ **公式来自 transcript 原话**：*"If you have **N** data points … with a vector of width **W** and vectorized execution, you only need **N/W instructions**."*
**诱饵 B = 8×** ← 误用 **256 位**寄存器（AVX2）或把元素当成 16 位。⚠️ 题干说的是 **128 位（NEON/SSE 的 Q 寄存器）+ 32 位元素 → W = 4**。
> 💡 顺带记住 **Q = quad-word = 128 位**（`vld1q_s32` 里的那个 q），更新的扩展才到 256（AVX2）/ 512（AVX-512）位。
</details>

A. The ideal workload for row storage is transactional, where entire records are accessed frequently.

**Q18.** 计算题。A table has 8,000,000 rows and 5 columns, each column value 8 bytes, stored in 4 KB pages. A query reads 2 of the 5 columns with no compression. Approximately how many pages does a full scan touch under row storage vs. pure columnar storage, and what is the ratio?
A. 78,125 vs 31,250; ratio 2.5×
B. 78,125 vs 15,625; ratio 5×
C. 156,250 vs 62,500; ratio 2.5×
D. 39,062 vs 15,625; ratio 2.5×

<details><summary>答案</summary>

**A。** 推导：
```
每页容量 = 4096 B / 8 B = 512 个值

行存：必须读【所有 5 列】= 8,000,000 × 5 = 40,000,000 个值
      页数 = 40,000,000 / 512 = 78,125 页

列存：只读【2 列】= 8,000,000 × 2 = 16,000,000 个值
      页数 = 16,000,000 / 512 = 31,250 页

比值 = 78,125 / 31,250 = 2.5×   （= 5 列 / 2 列）
```
⭐ **通用结论要记住**：在**无压缩、定长、每列独立成页**的前提下，**纯列存全扫的页数比 = 总列数 / 需要的列数**。
**诱饵**：**B = 5×** ← 误算成"总列数 / 1"（只算了 1 列）；**C** ← 每页容量按 256 个值算（把 8 字节当 16 字节）；**D** ← 只算了列存那一侧、行存也按 2 列算。
> ⚠️ **别用这个公式去套课程 weather 例子的 7 页 vs 4 页**——那组数字来自幻灯片里具体的页分配图（每页装记录 1–40 的某一列），带了**记录分块的粒度效应**，不是纯粹的 `4/2` 比值。**考试里给了页大小和值宽度就用公式算；只给图就数图。**
</details>

**Q19.** Which statement about the relationship between `module_11` (compilation) and `module_12` (vectorization) is **NOT** correct?
A. Both aim to reduce the per-tuple overhead of the interpreted operator framework.
B. Vectorization amortizes the operator-transition overhead over a batch, while compilation eliminates the operator boundaries entirely.
C. SIMD can also be used to accelerate the decoding of compressed data such as bit-packed columns.

**Q20.** 场景综合题。An analytics team stores a fact table whose `event_time` column increases monotonically, a `sensor_reading` column confined to a narrow numeric range, and a `region_code` column with only 12 distinct string values. They run highly selective range scans on `event_time` and aggregate `sensor_reading`. Which configuration is **best supported** by the course material?
A. Row storage with Huffman encoding on all three columns, plus tuple-at-a-time execution.
B. **Columnar storage with delta encoding on `event_time`, shift + bit packing on `sensor_reading`, byte dictionary encoding on `region_code`, and SIMD-based vectorized scans over the contiguous column arrays.**
C. Columnar storage with a single byte dictionary encoding applied uniformly to all columns, plus compiled queries to avoid recompilation costs.
D. Row storage with bit packing, relying on read amplification being negligible because the page size matches the disk block size.

<details><summary>答案与逐项辨析</summary>

**B。** 逐个匹配课程给出的规则：
- `event_time` **单调递增** → ⭐ **delta encoding**（numeric，增量式变化）；
- `sensor_reading` **窄数值范围** → ⭐ **先 shift 收缩范围，再 bit packing**（transcript 对 temperature 列就是这么做的，4 bit 够用）；
- `region_code` **只有 12 个不同的字符串值** → ⭐ **byte dictionary encoding**（categorical + 唯一值有限；实测 **0.71 ms**，比 Huffman 的 2.24 ms 更快，因为单字节比较无需按位解码）；
- **高选择性范围扫描 + 聚合** → ⭐ **列存（30× / 读 4 倍更少的页）+ SIMD**（过滤范围、聚合、解码 bit-packed 列正是 SIMD 的三个数据库用例；SoA 连续数组完美适合向量加载）。

**其他三项为什么不对**：
- **A**：行存 + 逐元组执行，把课程的两条主线全反了；且 **Huffman 用在 numeric 递增列上是张冠李戴**。
- **C**：⭐ **byte dictionary 只在"唯一值数量有限"时有用** —— 用在 `event_time`（百万个唯一值）上会直接爆掉 256 个字节码的空间；而且"编译查询以避免重编译成本"是自相矛盾（**编译才带来重编译成本**）。
- **D**：**页 = 块时读放大恰好不是问题**，但题干场景要的是"只读两列"，行存做不到；bit packing 也救不了"必须读入无关列"。
</details>
