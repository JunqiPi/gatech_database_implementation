## 📖 三、核心概念精讲

### 3.1 BuzzDB 的最小骨架

| 概念 | 是什么 | 类比 |
|:---|:---|:---|
| **tuple（元组）** | 表里的一行/一条记录。最初只是一个 key-value 对 | 一张卡片：`(客户ID, 金额)` |
| **`std::vector`** | 会自动扩容的动态数组，BuzzDB 用它**存所有 tuple**（就是那张"表"） | 可伸缩的书架 |
| **`std::map`** | 关联容器，key→value，**键唯一且按序排列**。BuzzDB 用它当**索引** | 手机通讯录（名字→号码，按字母排） |

- BuzzDB 的索引声明成 `map<int, vector<int>>`：一个 key 关联**多个** value。例如 key 1 → [100, 200]。
- **`insert`**：往 vector 加 tuple，同时**更新 map 索引**（保证快速按 key 检索）。
- **聚合查询 `select_group_by_sum`**：遍历 index 里每个 key，把它关联的 value 求和。等价于 SQL 的 `GROUP BY + SUM`。

> 💡 **一句话**：`vector` = 表本身；`map` = 索引。这俩 C++ 容器就是最早期 BuzzDB 的全部。

---

### 3.2 类（class）与封装（encapsulation）—— C++ 的核心

- **类 = 对象的蓝图**：把"数据 + 操作这些数据的函数"打包在一起（如 `Book` 类有 `title/author` 变量 + `display_info()` 方法）。
- **封装（encapsulation）**：用 `public`（外部可访问）/`private`（仅类内可访问）控制访问。
  - 好处：隐藏内部实现细节，只暴露受控接口 → 可以改内部而不影响外部 → **模块化（modularity）**。

> 🔑 **封装的考点**（测验 Q8、Q26 都考这个）：把数据库拆成小类（StorageManager、BufferManager…），每个类管自己的数据。改一个类的内部不会牵连其它类。

---

### 3.3 为什么用 C++ 而不是 Python（高频考点）

| 维度 | C++ | Python |
|:---|:---|:---|
| **执行方式** | 编译型，直接编成机器码 | 解释型，运行时逐句解释 |
| **性能** | 算 1 亿整数和 ≈ 100 微秒 | 同样 ≈ 5.24 秒（**慢约 5 万倍**！） |
| **类型** | **静态类型（static typing）**，编译期就知道类型 | 动态类型，运行时才定 |
| **内存** | 精细控制（智能指针、手动管理） | 自动 GC，控制力弱 |
| **硬件** | 可多线程、贴近硬件调优 | 受限 |

- **静态类型的好处（测验 Q34）**：类型在**编译期已知** → 能catch早期类型错误（把字符串赋给 int 直接编译报错）+ 能做**代码特化**（如定长 tuple 布局 fixed-width tuple layouts），性能更好。
- 类比：C++ 之于 Python 的速度差，就像"亚特兰大飞纽约 2 小时" vs "飞冥王星 9.5 年"。

> ⚠️ **易错（Q34）**：别选"动态类型更安全"——恰恰相反，静态类型在编译期就拦住类型错误，更安全、更快。

### 3.4 事务（Transaction）—— 本模块的灵魂

**定义**：事务是**一组操作，被当成一个不可分割的整体单元**来处理。

- 查询（select/group-by/sum）只**读**数据，不改；要**改**数据就得用事务。
- SQL 里事务用 `BEGIN TRANSACTION` 开始，`COMMIT` 提交（只有全部成功才执行）。
- 经典例子：**转账**——A 扣 $100、B 加 $100，必须**一起成功或一起失败**，绝不能只扣不加。

---

### 3.5 ⭐⭐ ACID 四性质（必背！整个期中最高频考点）

用**转账**一个例子串起来记：

| 字母 | 名字 | 大白话 | 转账中保证 | 实现机制 |
|:---:|:---|:---|:---|:---|
| **A** | 原子性 Atomicity | **全做或全不做**，不留半截 | A 扣了钱，B 必加；中途失败则整体回滚 | 日志 + 回滚（rollback） |
| **C** | 一致性 Consistency | 从一个**合法状态**到另一个合法状态 | 转账前后总额不变（守恒） | 约束 + 应用逻辑 |
| **I** | 隔离性 Isolation | 并发事务**互不串味**，看不到对方中间态 | 两个柜员同时存款，不会互相覆盖 | 并发控制（锁） |
| **D** | 持久性 Durability | 一旦提交，**崩溃/断电也不丢** | 取了现金，记录绝不消失 | **写前日志 WAL** |

> 🎵 **记忆口诀**：**"原子全有或全无，一致状态守合法，隔离并发不串味，持久提交不会丢"**。

#### 逐个深挖（每个都有对应考题）：

**A — 原子性（测验 Q14 / 示例 Q1）**
- 保证：转账两笔**要么都生效，要么都不生效**；若中止，不留任何部分效果。
- ⚠️ 别和 C/I/D 混：原子性**不**保证"余额始终非负"（那是 C），**不**保证"别人看不到中间态"（那是 I），**不**保证"提交后崩溃不丢"（那是 D）。

**I — 隔离性（测验 Q29）**：两个柜员例子
- 柜员1 存 $500、柜员2 存 $300，初始 $1000，正确结果应是 $1800。
- 没有隔离：两人都读到 $1000，各自算，后提交的覆盖先提交的 → 错成 $1500 或 $1300。
- **缺乏隔离会出现的异常**：脏读（dirty read）、不可重复读（non-repeatable read）、丢失更新（lost update）、幻读（phantom read）。

**D — 持久性（测验 Q31）**：取现金例子
- 银行把钱给了你，即使数据库随后崩溃，"扣 $500"这条记录**绝不能消失**。
- 实现靠 **写前日志（Write-Ahead Logging, WAL）**：先把事务细节写到**磁盘上的日志**，再标记 commit。崩溃后用日志重建已提交状态。

> 📌 ACID 一词由 Andreas Reuter 等人 1983 年提出（概念 1970 年代就有）。

> 🌟 **Paper 2 的关联**：2000 年代 NoSQL 喊"ACID 没必要、太慢，用弱一致性 BASE 就行"；结果十年后**几乎所有 NoSQL 都把 ACID 事务加了回来**（MongoDB、Cassandra、DynamoDB）。Google 2012 年用 Spanner 抛弃最终一致性、改回真事务时说得最直白。→ **ACID 是刚需，绕不过去**。

### 📗 Paper 2 在本模块的相关部分（ACID 的回归）

**🎯 与 M2 相关的核心论点**：
- NoSQL（文档数据库）当年的两大营销话术：①"SQL 和 join 太慢，用低层 record-at-a-time 接口" ②"ACID 没必要，用弱一致性 BASE"。

**✅ 启示/优势**：说明 ACID 不是"老古董"，而是多用户、易出故障环境下**保证正确性**的根本框架（测验 Q33）。

- **事务管理组件（Slide 27）**：事务 = 完成单一逻辑功能的一组操作；**并发控制管理器**保证并发事务间的一致性。
- **DBMS 要解决的问题里就有原子性 + 并发访问（Slide 7）**——M2 正是这两点的展开。

**题**：转账（debit A, credit B），atomicity 保证什么？

### 例题 2（测验 Q31）— 持久性
**题**：转账的 durability 最佳描述是？
- ✅ **正确**：**一旦提交，崩溃或断电后效果仍然存在**。
- ❌ 别选"和其它事务隔离执行"（I）、"余额瞬间反映真实状态"（C 的味道）、"两笔一起成功或都不"（A）。

---

### 例题 3（测验 Q33）— 为什么多用户 DBMS 需要 ACID
- ✅ **正确**：在并发与故障下**保证可预测行为、维护正确性与数据完整性**。
- ❌ 别选"限制并发防过载""让系统更轻量更快""强制优化器选最优计划"——这些都不是 ACID 的目的。

---

### 例题 4（测验 Q29）— 无隔离会怎样
**题**：两个事务无隔离地并发读写同一行，会发生什么？
- ✅ **正确**：可能出现**脏读、不可重复读、丢失更新、幻读**等现象。
- ❌ 别选"原子性被破坏""写入变不持久""死锁变不可能"——这些张冠李戴。
- **考点**：隔离性缺失 → 并发异常（4 种现象要记住）。

---

### 例题 5（测验 Q34）— 静态 vs 动态类型 ⚠️你做错
**题**：静/动态类型对 DB 引擎实现最相关的根本区别？
- ✅ **正确**：**静态类型在编译期把类型绑定到变量/表达式**，从而能做**代码特化（如定长 tuple 布局）**。
- ❌ 你可能选了别的。错误项：静态类型运行时可改类型（错，那是动态）、动态类型更安全（错）、静态类型不支持泛型（错，模板就是泛型）。
- **为什么重要**：编译期知道类型 → 编译器能生成最优的、针对具体类型特化的机器码（数据库追求极致性能）。

---

### 例题 6（测验 Q22）— 关于 mutex 哪个不对（属于 M6，但常和并发一起考）
**题**：关于 mutex，哪个说法**不对**？
- ✅ **正确（即"不对"的）**：**"mutex 保证所有线程访问资源的公平性。"** ← mutex **不保证公平**！
- ✔ 对的：mutex 为临界区提供互斥；RAII 包装（`lock_guard`）减少异常路径漏解锁；误用 mutex 作用域会导致死锁/竞争。
- **考点**：mutex 只保证"同时只有一个进" ≠ "排队公平"。（详见 M6）

---

### 例题 7（示例 Q4）— `unique_ptr` 与异常栈展开（C++ RAII，承上启下到 M3）
**题**：
```cpp
void bulkLoad(int n) {
  std::vector<std::unique_ptr<char[]>> pages;
  for (int i = 1; i <= n; ++i) {
    pages.push_back(std::make_unique<char[]>(PAGE_SIZE));
    if (i == n / 2) throw std::runtime_error("Disk full!");  // i==5 时抛出
  }
}
```
调用 `bulkLoad(10)`，异常栈展开时释放了**几个**页？
- ✅ **正确：5 个**（选项 B）。
- **推理**：循环 i=1..5。i=5 时（n/2=5）`push_back` 已经把第 5 个页加进 vector 后才抛异常。此时 vector 里有 **5 个** `unique_ptr`。抛异常 → 栈展开 → `pages`（vector）析构 → 它持有的 5 个 `unique_ptr` 全部析构 → 释放 5 个页。
- **考点**：**RAII**——异常发生时，局部对象（含 vector 及其 `unique_ptr` 元素）自动析构、自动释放内存，**不需要手动 delete**。

## 🏋️ 六、举一反三 + 新增模拟考题（含答案）

> 🟢基础 🟡进阶 🔴挑战

### A. 选择题

**A1 🟢** 下面哪个操作**需要**用事务（transaction）来保证安全？
A) `SELECT name FROM users` B) `SELECT COUNT(*) FROM posts`
C) 从账户 A 转 $100 到账户 B D) 按 location 分组统计用户数
<details><summary>答案</summary>**C**。只读查询（A/B/D）不改数据，不需要事务保护；转账要改两行，必须事务保证原子性。</details>

**A2 🟡** ACID 中，哪个性质**直接**靠"写前日志（WAL）"实现？
A) 原子性 B) 一致性 C) 隔离性 D) 持久性
<details><summary>答案</summary>**D 持久性**。先把改动写到磁盘日志再 commit，崩溃后用日志重建。（原子性也会用到日志做回滚，但题目问"提交后不丢"=持久性。）</details>

**A3 🟡** BuzzDB 用 `std::map<int, std::vector<int>>` 当索引。下面哪个说法**正确**？
A) map 的 key 可以重复 B) 一个 key 只能关联一个 value
C) map 的 key 唯一且有序，一个 key 可关联多个 value D) map 底层是哈希表
<details><summary>答案</summary>**C**。`std::map` key 唯一、按序（红黑树），值类型是 `vector<int>` 所以一个 key 可挂多个值。底层是平衡 BST 不是哈希表（那是 `unordered_map`）。</details>

**A4 🔴** 关于"为什么 BuzzDB 用 C++ 而不是 Python"，下面哪个**不是**主要原因？
A) C++ 编译成机器码，性能远高于解释执行的 Python
B) C++ 静态类型可在编译期捕获类型错误并做代码特化
C) C++ 能精细控制内存和多线程，贴近硬件调优
D) C++ 自动垃圾回收，开发者完全不用操心内存
<details><summary>答案</summary>**D**。C++ **没有**自动 GC，内存要靠智能指针/RAII 管理。A/B/C 都是真原因。</details>

### B. 判断题

**B1 🟢** "隔离性（Isolation）保证一旦事务提交，崩溃后数据也不丢失。"
<details><summary>答案</summary>**错**。那是持久性（Durability）。隔离性管的是"并发事务互不干扰"。</details>

**B2 🟡** "封装（encapsulation）让我们能改一个类的内部实现而不破坏调用它的代码，只要接口不变。"
<details><summary>答案</summary>**对**。这正是封装/模块化的核心价值（测验 Q8）。</details>

### C. 简答题

**C1 🟡** 用转账例子，分别用一句话说明 A、I、D 三个性质各保证了什么。
<details><summary>参考答案</summary>原子性 A：扣款和入账一起成功或一起失败，不会只扣不入。隔离性 I：另一个并发转账看不到本次转账的中间状态，不会互相覆盖。持久性 D：转账一旦提交，即使立刻断电，记录也不丢。</details>

**C2 🔴** Paper 2 说 NoSQL 经历了怎样的"ACID 态度转变"？这说明了什么？
<details><summary>参考答案</summary>NoSQL 早期主张"ACID 没必要、用弱一致性 BASE 更快"，但后来几乎都加回了 ACID 事务（MongoDB、Cassandra、DynamoDB），口号也从"不要 SQL"变成"Not only SQL"。说明 ACID 在真实多用户应用里是刚需，绕不过去——这也是"风水轮流转"主题的一个例证。</details>

### D. 应用题

**D1 🔴** 调用 `bulkLoad(8)`（结构同例题 7，`n/2=4`），异常栈展开会释放几个 `unique_ptr<char[]>`？若把 `unique_ptr` 换成裸 `new char[PAGE_SIZE]` 且不 catch，会怎样？
<details><summary>参考答案</summary>(1) i=1..4，i=4 时 push 完第 4 个后抛异常，vector 有 **4 个** unique_ptr，全部自动释放。(2) 裸指针不会被自动释放 → **内存泄漏**（4 个页的内存丢了），这正是 RAII/智能指针要解决的问题。</details>

## ⭐ 七、易错点 & 速记

| 易错点 | 正确理解 |
|:---|:---|
| ACID 四个字母张冠李戴 | A=全有全无、C=合法态、I=不串味、D=提交不丢 |
| 以为动态类型更安全 | **静态类型**编译期拦错，更安全更快 |
| 以为 mutex 保证公平 | mutex 只互斥，**不保证公平排队**（M6） |
| 以为 `std::map` 是哈希表 | map=平衡 BST(有序)；`unordered_map`=哈希表 |
| 以为持久性靠隔离实现 | 持久性靠 **WAL 写前日志** |
| 异常时担心内存泄漏 | RAII/智能指针在栈展开时**自动释放** |

**🎵 口诀**：**"原子全无或全有，一致合法，隔离不串，持久不丢；C++ 快、静态稳、控硬件"**
