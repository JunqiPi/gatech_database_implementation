## 🧊 关键术语秒懂（英文 = 中文 = 大白话）

- **latch（闩锁）** ≠ **lock（锁）**。latch 保护**内存数据结构**（短、物理级，如保护一个页面不被同时改）；lock 保护**事务的逻辑数据**（长、到事务结束）。🔵 latch = 修车时压住引擎盖的支架；lock = 车库门锁。
- **CAS = Compare-And-Swap（比较并交换）**：原子指令，"如果地址 L 上的值还等于旧值，就写入新值"。硬件保证不会被打断。🔵 抢座位：只有第一个人能坐下，其他人失败重试。
- **latch-free（无闩锁）**：不用 latch，靠 CAS 装线程永不阻塞。**注意：latch-free ≠ 无冲突**，冲突时是**重试**而不是等待。
- **MBR = Minimum Bounding Rectangle（最小外包矩形）**：包住一个空间对象的最小矩形。R-tree 索引的就是 MBR，不是对象本身。
- **CDF = Cumulative Distribution Function（累积分布函数）**：F(x) = P(X ≤ x)。学习索引的核心：**位置 = F(key) × N**。
- **RMI = Recursive Model Index（递归模型索引）**：分阶段的模型层级，上一阶段输出用来**挑下一阶段的模型**，最后一阶段预测位置。
- **speedup（加速比）**：问题规模不变，硬件翻 N 倍 → 时间变 1/N。**scaleup（扩展比）**：问题和硬件同时翻 N 倍 → 时间不变。
- **shared-nothing（无共享）**：每个处理器有自己的内存和磁盘，只通过消息通信。**shared-disk（共享磁盘）**：各自内存，共享所有盘。**shared-memory（共享内存）**：共享一块全局内存和所有盘。
- **iterator model / Volcano model（迭代器模型）**：每个算子提供 `open / next / close`；上层反复调 `next` **拉（pull）**一条元组。又叫 **demand-driven dataflow（需求驱动数据流）/ lazy evaluation（惰性求值）**。
- **push-based（推模型）**：反过来，下层算子把元组**推**给上层的 `consume`。又叫 **data-driven dataflow / eager evaluation（急切求值）**。
- **pipeline breaker（流水线阻断算子）**：会把元组**从 CPU 寄存器里赶出去**的算子（Neumann 的定义）；**full pipeline breaker** 会把该侧全部输入物化（如 sort、hash join 的 build 侧、aggregation）。
- **vectorized execution（向量化执行）**：一次 `next` 返回**一批（一个 vector，如 1024 条）**值而不是一条，摊薄解释开销并能用 SIMD。
- **SIMD = Single Instruction Multiple Data**：一条指令处理多个数据。
- **PAX = Partition Attributes Across**：页内按列分区——**页级别是行存（一页装一批完整元组），页内部按列聚簇**。兼顾 I/O 和 cache。
- **NSM = N-ary Storage Model（行存）**；**DSM = Decomposition Storage Model（列存）**。
- **LSM-tree = Log-Structured Merge-Tree**：写进内存小结构，后台批量归并进大的只读结构。C-Store 的 tuple mover 就是这个思路。
- **K-safety**：即使 K 个节点挂掉，数据仍可完整重建。
- **snapshot isolation（快照隔离）**：只读事务读某个过去时刻的一致快照，**不加锁**。
- **write amplification（写放大）**：日志结构存储里，垃圾回收要搬运还活着的数据，导致实际写入量 > 逻辑写入量。

# 🔥 Part 0 · 教授 Office Hour 原题（已确认考点，必背）

> 来源：`raw/Raw_papers/questions_about_the_paper_in_office_hour.txt`。
> **这 5 题直接暴露了教授的出题重心：P7 学习索引（2 题）、P8 并行数据库（1 题）、P12 C-Store（2 题）。**
> 每题都是 **"Which statement is correct?"** 型（3 选 1，2 个假选项），与 Sheet 01/02 的 "Which is NOT correct" 互为镜像——**假选项的制造手法完全一致**。

### Q1 · 学习范围索引的本质（→ P7）

> **Which statement is correct?**
> A. In learned range indexes, the model must predict the **exact** record location.
> B. In learned range indexes, a key requirement is that keys are **uniformly distributed**.
> **C. In learned range indexes, the model approximates the key's position in sorted order.** ✅

💡 **为什么 C 对**：学习范围索引（如 Kraska 的 RMI）学的是键的 **CDF（累积分布函数）**。给一个 key，模型预测它在**有序数组中的近似位置**，然后在**误差界（min/max error）内做局部搜索**（二分/指数搜索）找到精确记录。
❌ **A 错在哪（手法：绝对化 "must" + 抬高要求）**：模型**不需要**预测精确位置，只要够近就行；预测自带误差界，精确位置靠界内搜索找到。**正是这种"容忍近似"才让学习索引实用。**
❌ **B 错在哪（手法：无中生有的前提条件）**：**没有**"键必须均匀分布"的要求。恰恰相反——如果键完全均匀，你根本不需要学习模型，简单的**线性插值**就够了。学 CDF 的全部意义就是**处理任意的、非均匀的键分布**。

### Q2 · RMI 的结构（→ P7）

> **Which statement is correct for a recursive model index (RMI)?**
> **A. In an RMI, one model's output is used to select a model in the next stage and the last stage predicts the record position.** ✅
> B. In an RMI, every stage performs a **binary search** before deciding which model to evaluate next.
> C. In an RMI, all models at the same stage must cover **equal-sized key ranges**, as in B-tree nodes.

💡 **为什么 A 对**：RMI 是**分阶段（stages）的模型层级**。根模型接收 key，其**输出用于挑选下一阶段要评估哪个模型**；逐级向下，**最后一阶段（叶）模型预测记录位置**，然后在该模型的误差界内做局部搜索定位精确记录。
❌ **B 错在哪（手法：张冠李戴 + 机制错位）**：**阶段之间没有任何搜索**，每一阶段只是一次**模型求值**（一个小线性模型或神经网络）。这正是 RMI 遍历快的原因（原文明确列为 RMI 的第 4 条好处："There is no search process required in-between the stages"）。二分搜索**只在最后**、在叶模型的误差界内使用。
❌ **C 错在哪（手法：把 B-tree 的性质安给 RMI）**：与 B-tree 节点不同，**同一阶段的模型不需要覆盖等大的键范围**。键空间是按上层模型的**预测**划分的，覆盖范围随数据分布自适应——有的模型覆盖极多键，有的极少。**这是特性不是缺陷**：简单区域一个模型管一大片，复杂区域用更细粒度的模型。（原文："each model does not necessarily cover the same amount of records like B-Trees do"。）

### Q3 · Speedup vs Scaleup（→ P8）

> **Which statement is correct?**
> A. Parallel database systems achieve **near-linear speedup when using shared memory**.
> **B. Speedup means the system runs the same job N times faster on N times more hardware, while scaleup means it runs an N times larger job in the same time.** ✅
> C.（把 speedup 和 scaleup 的定义**对调**）

💡 **为什么 B 对**（DeWitt & Gray 的经典定义）：
- **Speedup（加速比）**：**固定问题规模，增长硬件**。linear speedup = N 倍硬件把**同一个作业**跑快 N 倍。公式：`Speedup = 小系统耗时 / 大系统耗时`，等于 N 即线性。
- **Scaleup（扩展比）**：**问题和硬件一起增长**。linear scaleup = N 倍硬件在**同样的时间**内跑完 N 倍大的作业。公式：`Scaleup = 小系统跑小问题耗时 / 大系统跑大问题耗时`，等于 **1** 即线性。
❌ **C 错在哪（手法：方向反转）**：纯粹把两个定义调了个个儿。
❌ **A 错在哪（手法：张冠李戴到错误架构）**：**shared-memory 架构在并行架构里恰恰扩展性最差**。共享内存总线/互连网络上的竞争把可扩展性限制在相对少的处理器（原文：**最大的 shared-memory 多处理器当时限制在约 32 个处理器**，而 Teradata/Tandem/Intel 都出货过 **200+ 处理器**的系统）。**near-linear speedup/scaleup 是 shared-nothing 的招牌**——它给每个节点自己的 CPU、内存、磁盘，把干扰降到最低，因此成为大型并行数据库系统的主导设计。

### Q4 · C-Store 的物理存储单位（→ P12）

> **Which statement is correct?**（选项 A = "overlapping projections with varied sort orders"）✅

💡 **为什么 A 对**：C-Store 的物理存储单位是 **projection（投影）**：一组来自某张表的列（还可以包含通过**外键 n:1 关系**连过来的其他表的列），**按列存储**，并**按某个 sort key 排序**。一张表由**一个或多个 projection** 表示，**同一个列可以出现在多个 projection 里，且各自排序不同**。这种冗余是**故意的**：查询优化器挑排序顺序最合适的那个 projection；多余的副本同时提供**恢复能力（K-safety）**。一组 **covering set of projections** 加上 **join indexes** 让系统能在需要时重建完整元组。
❌ **B 错在哪**：C-Store 的 projection 是**物理存储结构**，**不是**行存之上的逻辑视图。**底下根本没有行存布局**——每个 projection 的列就是磁盘上真正存的东西，每列一个压缩文件。（读写走"小的写优化 store + 读优化列 store"，但**两者都是列组织的**。）
❌ **C 错在哪（两处都反了）**：C-Store **拥抱**冗余存储（同一列存在多个 projection 里）；而且**排序让压缩更有效，不是更无效**——排过序（或次级排序）的列会出现长串相等/有序的值，能用 **RLE（run-length encoding）**、**delta encoding** 这类激进方案。"以多种 sort order 存储且压缩"之所以划算，正是因为列压缩效果太好——**用便宜的磁盘空间换查询性能**。

### Q5 · C-Store 的更新架构（→ P12）

> **Which statement is correct with respect to C-Store's update architecture?**
> A. Updates are applied **directly inside compressed RS segments**, and readers wait while those segments are recompressed.
> **B. Inserts go to the write-optimized WS, while the tuple mover later merges WS data into the read-optimized RS in bulk.** ✅
> C. C-Store uses a **single mutable column store**, so the tuple mover is needed only for backup and recovery.

💡 **为什么 B 对**：C-Store 把存储拆成两层：
- **WS（Writeable Store，可写存储）**：小的、写优化的组件，吸收**所有插入**（以及更新的插入那一半）。**它也是列组织的**，但**不压缩**，为高效修改而设计（建在 BerkeleyDB 的 B-tree 上）。
- **RS（Read-optimized Store，读优化存储）**：大的、**重压缩**、**已排序**的列存，绝大部分数据住在这里；从事务角度看基本是只读/追加的。
- **删除**用**删除标记（deletion marker / DRV）**处理而**不是原地改 RS**；**更新 = 删除 + 插入**。
- **tuple mover** 在后台运行，周期性地把成批元组从 WS **批量迁移**到 RS（**merge-out process，MOP**，类似 **LSM-tree** 的归并）。
- 查询**透明地同时读 WS 和 RS** 并合并结果（用 snapshot isolation 依据 IV/DRV 过滤掉不可见元组）。
❌ **A 错在哪**：在压缩、已排序的 RS 段里做**原地更新**代价极高——每次写都要解压、移位、重压缩，还要阻塞读者。**WS/RS 分层存在的全部理由就是避免这件事**：写永远不直接碰 RS，重压缩的工作由 tuple mover **批量、异步**完成。
❌ **C 错在哪**：C-Store **刻意不用单一可变存储**，两层设计是其更新架构的核心。而且 **tuple mover 的职责是数据迁移（WS → RS），不是备份**；C-Store 的恢复靠 **K-safety**——从其他站点上冗余的 projection 重建失败站点的数据。

# 📕 Paper 5 — The Bw-Tree: A B-tree for New Hardware Platforms（2013）

> **主旨**：硬件变了（多核 + flash），B-tree 的实现也该变。Bw-tree 用 **latch-free（无闩锁）+ delta 更新（不原地改）+ log-structured 存储** 三板斧，拿到极高性能。
> **它是什么**：一个 **ARS = Atomic Record Store（原子记录存储）**——支持按 key 读写单条记录，并支持 key 顺序范围访问。可独立使用、可做 Deuteronomy 的 data component、也可嵌进传统数据库。

### 重点1 · 硬件动机（why 的起点）
✅ **EN:** *"Multi-core CPUs mandate high concurrency, but as concurrency increases **latches are more likely to block**, limiting scalability; and good multi-core performance depends on high CPU cache hit ratios, so **updating memory in place causes cache invalidations**."*
💡 **中文（两条并列动机，务必分清）：**
1. **并发问题** → 用 **latch-free** 解决：线程**从不 yield、从不因冲突改道**。
2. **CPU cache 问题** → 用 **delta 更新（不原地改）** 解决：原地改会让**其他线程缓存的 cache line 失效**；delta 保留了旧页状态，之前缓存的行仍然有效。
- **flash 动机**：磁盘延迟"像往返冥王星"，但更要命的是 **IOPS 低**。flash 的 IOPS 高、成本低。但 flash 有怪癖：**读（随机和顺序都）快，写前需要擦除周期，所以随机写比顺序写慢**（2011 年即使高端 FusionIO，顺序写也比随机写快 3 倍）。→ Bw-tree **自己在存储层做 log structuring**，不依赖 SSD 的 FTL。
❌ **Trap:** *"Flash SSDs have uniformly fast reads and writes, so log structuring is unnecessary."* —— 错，随机写慢是核心动机。

### 重点2 · Mapping Table（最核心的结构）⭐
✅ **EN:** *"The Bw-tree is organized around a **mapping table** that maps a logical page identifier (**PID**) to either a **flash offset** or a **memory pointer**, thus **virtualizing both the location and the size of pages**."*
💡 **中文（what / why / how）：**
- **what**：一张表，把**逻辑页号 PID** → **物理地址**（要么是内存指针，要么是 flash 上的偏移量）。
- **how**：**Bw-tree 节点之间的所有链接（向下的 search pointer、侧向的 side link）都是 PID，不是物理指针。**
- **why（三重收益，考点密集）**：
  1. mapping table **切断了"物理位置"和"节点间链接"的联系** → 节点的物理位置可以**每次更新、每次写盘都变**，而**不需要把位置变化一路传播到树根**（否则每改一个叶子就要改父、祖父……直到 root）。
  2. 这种 **"relocation tolerance（可重定位性）"** 直接使能了**内存中的 delta 更新**和**稳定存储上的 log structuring**。
  3. 页是**逻辑的**，**不占固定物理位置、也没有固定大小** → **elastic pages（弹性页）**：页多大不是硬限制，"page" 是**策略而非要求**，方便时才分裂。
❌ **Trap:** *"All links between Bw-tree nodes are physical memory pointers for speed."* —— **错，全是 PID**。这是最爱考的一条。
❌ **Trap:** *"The indirection through a mapping table is unique to the Bw-tree."* —— 错，原文明说 *"this indirection technique is not unique to our approach"*，Bw-tree 只是把它当作多项创新的**基础**。

### 重点3 · Delta Updating + CAS（怎么做到 latch-free）⭐
✅ **EN:** *"Page state changes are done by creating a **delta record** describing the change and **prepending** it to the existing page state; the new address is installed into the page's slot in the mapping table using an atomic **compare-and-swap (CAS)**. This is **the only way** to update a page in the Bw-tree, and is **uniform across all operations** that modify a page."*
💡 **中文（步骤化）：**
1. 从 mapping table 读出页 P 的当前地址；
2. 新建 delta 记录 D，让 D（物理地）指向 P；
3. 用 **CAS** 把 mapping table 里的地址从 P 换成 D。**成功 → D 成为页的新地址；失败 → 重试。**
- 竞争时**只有一个 updater 能赢**，其他必须重试（retry 协议因操作而异）。
- **既用于数据变更**（插入记录）**也用于管理变更**（页分裂、页刷盘）。
- **叶层 delta 有三种：insert、modify、delete。** delete delta 只含要删除记录的 key；insert/update delta 含新负载。所有更新 delta **都带一个由客户端提供的 LSN**。
- **页搜索**：先遍历 delta chain，**在链中第一次遇到 search key 就停**——若该 delta 是 insert/update 则搜索成功返回记录，若是 delete 则搜索失败；链中没有该 key 才对 base page 做**二分搜索**。
❌ **Trap:** *"Bw-tree nodes are updated in place under a short-term latch."* —— 错，**从不原地更新**。
❌ **Trap:** *"A delta record is appended to the end of the page."* —— 错，是 **prepend（前置）**；每次成功更新形成 delta chain 的新"根"。

### 重点4 · Page Consolidation（页整合）
✅ **EN:** *"Search performance degrades if delta chains grow too long; a thread that notices the chain has exceeded a system threshold performs **consolidation** — creating a new base page containing all entries from the old base page as modified by the delta chain (deleted records discarded) — and installs it with a CAS. **If the CAS fails, the thread abandons the operation and does not retry.**"*
💡 **中文：** 链太长搜索就慢，所以**偶尔**整合成一个新的 base page。
- **触发**：访问线程在页搜索时发现 delta chain 超阈值，**先完成自己的读/写操作，再做整合**。
- **失败不重试**：因为后续会有别的线程成功整合，重试是浪费。（对比：**记录更新失败要重试**。）
- 旧页状态（delta chain + base page）**整体交给 epoch 机制做垃圾回收**。
- **实验数据（Fig.5）**：delta chain 阈值太小 → 频繁整合，开销吃掉性能。Xbox 负载（100 字节大记录）**超过 4 个 delta** 搜索就变差（大记录塞不下 L1）；synthetic 负载（8 字节小键）**可以到 8 个 delta**（更利于预取和缓存）。
❌ **Trap:** *"A failed consolidation must be retried until it succeeds."* —— 错。

### 重点5 · Epoch-based Garbage Collection（epoch 垃圾回收）
✅ **EN:** *"A latch-free environment does not permit exclusive access, so one or more readers can be active in a page state even as it is being updated; memory is reclaimed using an **epoch** mechanism — objects deallocated in epoch E can be recycled only after **all threads enrolled in epoch E have exited (drained)**."*
💡 **中文（why 要 epoch）：** latch-free 意味着**你正在换掉的旧页，可能还有别的线程在读**。不能直接 free，否则就是悬垂指针。
- 线程要保护它正在用的对象时**加入一个 epoch**；依赖结束时**退出**。典型时长 = 一次操作（insert / next-record）。
- 逻辑：登记在 epoch E 的线程**可能**见过在 E 中被释放的对象的更早版本，但**不可能**见过在 E−1 中被释放的对象（因为它那时还没开始依赖区间）。所以 **E 中所有线程都退出后，E 中释放的对象就能安全回收**。
- ⭐ **epoch 同时保护两样东西：页内存 和 已删除的 PID。**
❌ **Trap:** *"Reference counting is used to reclaim page memory."* —— 错，是 epoch。

### 重点6 · Structure Modification Operations（SMO：分裂与合并）⭐⭐
✅ **EN:** *"A page split changes **more than one page** (the original O, the new sibling N, and the parent P), so it **cannot be installed with a single CAS**. The Bw-tree breaks an SMO into a **sequence of atomic actions, each installable via a CAS**, using a **B-link** design; a thread that encounters a partial SMO **must complete it before proceeding with its own operation**."*

💡 **Split（分裂）三步走 —— 背下来：**
| 步 | 动作 | 是否需要 CAS |
|:--|:---|:--|
| 0 | 向 cache layer 申请新节点 Q 的 mapping table 槽位；选分裂键 K_P；用 P 中 key > K_P 的记录建 Q 的 base page；Q 带一个指向 P 原右兄弟 R 的 side link | **不需要 CAS**（Q 此时只对分裂线程可见） |
| 1 | **half split**：给 P **前置一个 split delta**，含 (1) 分隔键 K_P（使 P 中 > K_P 的记录失效）+ (2) 指向新兄弟 Q 的**逻辑 side pointer** | ✅ CAS |
| 2 | **parent update**：给父节点 O **前置一个 index entry delta**，含 (1) K_P、(2) 指向 Q 的逻辑指针、(3) K_Q（Q 的分隔键，原先是指向 P 的分隔键） | ✅ CAS |

- ⭐ **为什么第 1 步之后索引就已经是合法的**（即使父节点还没有 Q 的索引项）：**B-link 的 side link 保证了一棵有效搜索树**。所有落在 Q 里的 key 会先走到 P，在 P 上遇到 split delta 后，若 search key > K_P 就**沿 side link 走到 Q**；key < K_P 的搜索留在 P。
- ⭐ **同时存 K_P 和 K_Q 是一项搜索加速优化**：搜索索引节点时要遍历 delta chain，若找到一个 boundary key delta 满足 `K_P < v ≤ K_Q`，**搜索立刻结束**并沿逻辑指针下到 Q；否则继续进 base page 做二分。
- **找父节点**：记住下行路径上的 PID，多数情况下记住的父就是对的。偶尔父已被合并掉——**epoch 机制保证父 PID 不会是悬垂引用**，能看到"已删除"状态，于是上溯到祖父再重新下行找"还活着"的父。

💡 **Merge（合并）四步走 —— 比 split 更复杂，需要更多原子动作：**
| 步 | 动作 |
|:--|:---|
| 1 | **Marking for Delete**：给要被移除的节点 R 前置 **remove node delta**，**停止对 R 的一切后续使用**。遇到它的线程要去**左兄弟 L** 读写原属 R 的内容。 |
| 2 | **Merging Children**：给左兄弟 L 前置 **node merge delta**，它**物理地（内存地址）指向 R 的内容**；R 的存储所有权转移给 L（remove node delta 本身除外），**只在 L 被整合时才回收**。⭐ 这把原本**线性的 delta chain 变成了一棵树**。搜索 L 变成树搜索，node merge delta 里含分隔键指引到正确节点。 |
| 3 | **Parent Update**：给 R 的父节点 P 前置 **index term delete delta**，说明 R 被删除、且 L 现在包含原属 R 的键空间；显式写出 L 的新范围（low key = L 原 low key，high key = R 原 high key）。 |
| 4 | index term delete delta 一贴出，**通往 R 的所有路径都被堵死**，此时开始回收 R 的 PID——把 PID 放进当前活跃 epoch 的 pending delete 列表。 |

- ⭐ **SMO 的串行化（考点）**：Bw-tree 假设**冲突的数据更新由系统别处的并发控制阻止**（锁管理器 / 事务组件），但**"Bw-tree 内部"必须正确串行化：数据更新 vs SMO、SMO vs SMO**。
  - 无闩锁 → 无法阻止线程"撞见未完成的 SMO"（像看到未提交状态）。
  - **对策：撞见者必须先完成并提交它遇到的那个 SMO，然后才能 (1) 贴自己的更新 或 (2) 继续自己的 SMO。** 这迫使未完成的 SMO **"提交"并串行化在被打断的动作之前**。
  - **删除也一样**：删 R 时要去左兄弟 L 贴 merge delta，若发现 **L 正在被删除**（更早的未完成系统事务），则**必须先完成 L 的删除，再完成 R 的删除**。可能形成 SMO 的"栈"，但这种情况罕见，递归实现即可。
❌ **Trap:** *"A page split is installed atomically with a single CAS."* —— **错**，至少两次 CAS。
❌ **Trap:** *"A thread that encounters an in-progress SMO waits until it completes."* —— **错**，**从不等待**，而是**帮忙完成它**。

### 重点7 · Log-Structured Store（LSS）与增量刷盘
✅ **EN:** *"When flushing a page, the LSS need only flush the **deltas** representing changes made since the page's previous flush; this dramatically reduces data written per flush, increases the number of pages fitting in the flush buffer, and **reduces write amplification**. The penalty is on reads: the discontinuous parts of a page must all be read back."*
💡 **中文：**
- **顺序批量写**：页被成批顺序写出，大幅减少独立写 I/O 次数。
- **增量刷盘**：只刷 **LSN 在"上次刷过的最大 LSN"和"当前 ESL"之间**的 delta 记录。**flush delta record** 记录本次刷了什么、新 flash 偏移量在哪，用 CAS 装进 mapping table。
- **两大好处**：(1) 一个 flush buffer 能容纳跨页的**更多更新**，提高每页写效率；(2) **cleaner（垃圾回收器）不用那么累**，因为存储消耗得慢 → 降低每页清理成本、**降低写放大**。
- **读的代价**：页的不连续片段都要读回来才能还原页——**这里正好靠 flash 极高的随机读性能补偿**。
- cleaning（清理旧日志区）时，**LSS 把页和它的 delta 变成连续的**以改善访问性能。
- flush buffer 阈值当前设为 **1MB**；用 **ping-pong（双）缓冲**配异步 I/O，一个在写时准备下一批。
❌ **Trap:** *"Incremental flushing increases write amplification."* —— 反了，是**减少**。

### 重点8 · WAL 协调（ESL / RSSP）—— 不阻塞的写前日志
✅ **EN:** *"Unconventionally, the Bw-tree **does not block page flushes to enforce WAL**. Because recent updates are separate deltas, records on a page with LSNs **larger than the latest ESL** (End of Stable Log) are simply **excluded** from the page when flushed. **Non-blocking is not possible with a conventional update-in-place approach using a single page-wide LSN.**"*
💡 **中文（术语 → 大白话）：**
- **LSN**：更新在事务日志上的序号，由上层 **TC（transactional component 事务组件）**生成。
- **ESL = End of Stable Log**：一个 LSN，所有比它小的 LSN **肯定**已在稳定日志里。TC 周期性把最新 ESL 发给 **DC（data component 数据组件）**。
- **WAL 因果性要求**：**DC 不得把 LSN > 最新 ESL 的操作变持久**，即 DC 要"落后于"TC。
- ⭐ **Bw-tree 的巧解**：因为最近更新是**独立的 delta**，刷盘时**直接把 LSN > ESL 的记录挑出去不刷**，所以**永远不需要阻塞刷盘**。传统"原地更新 + 一个页级 LSN"做不到这一点（整页只有一个 LSN，要么全刷要么全不刷）。
- 为支持这个非阻塞行为，**page consolidation 被限制为只包含 LSN ≤ ESL 的 update delta**。
- **RSSP = Redo-Scan-Start-Point**：TC 想推进 RSSP 以截断日志时，向 DC 提议一个 RSSP，DC 必须把每页上 **LSN < RSSP** 的记录刷稳后才确认。**这类刷盘永远不会被阻塞**（cache manager 可以排除 LSN > ESL 的记录）。
- **SMO 用 system transaction 包起来**写入 LSS，保证恢复时每个 SMO 可视为原子；且**在确知本线程"赢得"了装 SMO delta 的竞赛之前，不提交这个系统事务** → 允许并发 SMO，但**最多只有一个能提交**。
❌ **Trap:** *"Page flushes must block until the corresponding log records are stable."* —— 传统系统是这样，**Bw-tree 不是**。

### 重点9 · 性能结果（数字要有印象）
| 对比 | 结果 |
|:---|:---|
| Bw-tree vs BerkeleyDB（B-tree 模式，非事务，页级 latch） | Xbox **18.7×**（10.4M vs 555K ops/s）；Deduplication **8.6×**；Synthetic **5.8×** |
| Bw-tree vs latch-free skip list | Synthetic **3.7×**（3.83M vs 1.02M）；只读 **4.4×**（5.71M vs 1.30M） |
| CPU 利用率 | Bw-tree **≈99%**，BerkeleyDB **≈60%** |
| Cache（只读负载，VTune） | Bw-tree **≈90%** 的内存读命中 L1/L2；skip list **≈75%** |
| latch-free 更新失败率 | **记录更新 < 0.02%**（三个负载）；**split/consolidate ≈1.25%**（Xbox/Dedup），**8.88%**（Synthetic，最坏情况） |
| 搜索路径覆盖的节点占比 | Bw-tree 内部节点 **≤1%** 的占用内存；skip list **≈50%** 的节点 |

✅ **EN（两个原因，标准答案）:** *"(1) **Latch-freedom**: no thread blocks on updates or reads, while BerkeleyDB uses page-level latching that blocks readers during updates. (2) **CPU cache efficiency**: delta records update immutable base pages, so other threads' CPU caches are rarely invalidated, whereas an in-place insert into a B-tree page moves on average half the elements and invalidates multiple cache lines."*
💡 **为什么 Bw-tree 比 skip list 缓存友好**：skip list **每次比较前都要追一个物理指针**跳到下一个"塔"或链表记录，分支预测失败时 CPU 缓存行为很不稳定；Bw-tree 大部分时间在**一块连续内存里的 base page 上做二分搜索**，**指针追逐少得多**。
❌ **Trap:** *"The synthetic workload's high split failure rate (8.88%) indicates the Bw-tree design is unsound."* —— 错，原文说这是**最坏情况**且**可接受**：synthetic 记录极小，准备并装一个记录 update delta 极快，所以更贵的 split 操作在同一页上装 delta 失败概率高。

# 📗 Paper 6 — R-Trees: A Dynamic Index Structure for Spatial Searching（Guttman, 1984）

> **主旨**：空间对象**有大小**（不是点），传统一维索引不适用。R-tree 用**最小外包矩形（MBR）**做索引项，是 B-tree 在多维的类比。

### 重点1 · 为什么传统索引不行（动机，考"排除法"）
✅ **EN:** *"Structures based on **exact matching** of values, such as **hash tables**, are not useful because a **range search** is required; structures using **one-dimensional ordering** of key values, such as **B-trees and ISAM indexes**, do not work because the search space is **multi-dimensional**."*
💡 **中文：** 空间搜索是**范围搜索**（哈希只能精确匹配）；空间是**多维**的（B-tree/ISAM 只能一维排序）。
- 其他被点名淘汰的方案（都可能做假选项）：
  - **Cell methods（单元格法）**：不适合动态结构，因为**单元格边界必须事先决定**。
  - **Quad trees、k-d trees**：**没有考虑二级存储的分页**。
  - **K-D-B trees**：为分页内存设计，但**只对点数据有用**。
  - **Index intervals**：**不能用于多维**。
  - **Corner stitching**：假设**同质主存**，对**超大数据集的随机搜索不高效**。
  - **Grid files**：把每个非点对象**映射成高维空间中的一个点**来处理。
❌ **Trap:** *"Quad trees are the natural disk-based alternative because they page well."* —— 错，quad tree/k-d tree **不考虑分页**。

### 重点2 · 结构定义（六条性质，逐字考）⭐
✅ **EN:** *"An R-tree is a **height-balanced** tree similar to a B-tree, with index records in its **leaf nodes containing pointers to data objects**. Nodes correspond to disk pages. The index is **completely dynamic**; inserts and deletes can be intermixed with searches and **no periodic reorganization is required**."*
- **叶节点项**：`(I, tuple-identifier)`，I 是被索引空间对象的 **n 维外包矩形**，形如 I = (I₀, I₁, …, I_{n−1})，每个 Iᵢ = [a, b] 是闭区间（可以有一端或两端为无穷，表示对象无限延伸）。
- **非叶节点项**：`(I, child-pointer)`，**I 覆盖下层节点所有项的矩形**。

**六条性质（M = 一个节点最多的项数，m ≤ M/2 = 最少项数）：**
1. 每个**叶节点**含 **m 到 M** 条索引记录，**除非它是根**。
2. 叶节点的每条 `(I, tuple-identifier)`，**I 是在空间上包含该数据对象的最小矩形**。
3. 每个**非叶节点**有 **m 到 M** 个孩子，**除非它是根**。
4. 非叶节点的每个 `(I, child-pointer)`，**I 是在空间上包含孩子节点中所有矩形的最小矩形**。
5. **根节点至少有两个孩子，除非它是叶子。**
6. **所有叶子在同一层。**

**高度与空间**：含 N 条索引记录的 R-tree 高度**至多 ⌈log_m N⌉ − 1**（分支因子至少 m）；根以外所有节点的**最坏情况空间利用率 = m/M**。节点通常项数多于 m，会**降低树高、改善空间利用率**。节点若有 3–4 条以上的项，树就非常宽，**几乎所有空间都用在存索引记录的叶节点上**。
❌ **Trap:** *"Rectangles of sibling nodes in an R-tree must not overlap."* —— **错，R-tree 允许重叠**（这正是它与 K-D-B tree 等的关键区别，也是它没有好的最坏情况保证的原因）。
❌ **Trap:** *"An R-tree requires periodic reorganization."* —— 错，**完全动态、不需要**。

### 重点3 · Search（为什么没有好的最坏情况保证）⭐
✅ **EN:** *"The search algorithm descends the tree from the root in a manner similar to a B-tree. However, **more than one subtree under a node visited may need to be searched**, hence **it is not possible to guarantee good worst-case performance**."*
💡 **中文（算法 Search，给定根 T 和搜索矩形 S）：**
- **S1 [Search subtrees]**：若 T 不是叶子，检查每个项 E 看 **E.I 是否与 S 重叠**；**对所有重叠的项**，在 E.p 指向的子树上递归调用 Search。
- **S2 [Search leaf node]**：若 T 是叶子，检查所有项 E 看 E.I 是否与 S 重叠；若重叠，E 是**合格记录**。
- ⭐ **重点**：因为矩形可以重叠，**一次搜索可能要下到多棵子树**（B-tree 只走一条路）→ **最坏情况无法保证**。但对大多数数据，更新算法把树维护成"搜索算法能排除大片无关区域、只检查搜索区附近数据"的形态。
- **其他搜索变体**：找"完全被搜索区包含的对象"、"包含搜索区的对象"，都是本算法的直接变形；**FindLeaf** 用于删除时定位已知项；**range deletion** 也支持得很好。
❌ **Trap:** *"An R-tree search visits exactly one path from root to leaf, like a B-tree."* —— 错。

### 重点4 · Insert / ChooseLeaf（"最小面积增量"准则）⭐
✅ **EN:** *"**ChooseLeaf** selects, at each level, the entry whose rectangle **needs least enlargement** to include the new entry's rectangle, **resolving ties by choosing the entry with the rectangle of smallest area**."*
💡 **中文（Insert 四步）：**
- **I1**：调 **ChooseLeaf** 选叶节点 L 放 E。
- **I2**：L 有空位就装；否则调 **SplitNode** 得到 L 和 LL。
- **I3**：调 **AdjustTree**（从 L 上溯到根，**调整覆盖矩形**，必要时向上传播分裂）。
- **I4**：若分裂传播导致根分裂，**建一个新根**，孩子是分裂出的两个节点。
- **AdjustTree 细节**：AT3 把父项 E_N.I **调整为紧紧包住 N 中所有项的矩形**；AT4 若 N 有分裂产生的伙伴 NN，就造一个新项 E_NN（指向 NN、矩形包住 NN 的所有矩形）加进父节点 P，**P 没空位就 SplitNode**。
❌ **Trap:** *"ChooseLeaf picks the child whose rectangle has the smallest area."* —— **半真半假的经典陷阱**：**首要准则是"面积增量最小"，"面积最小"只是平局时的次准则**。

### 重点5 · Delete / CondenseTree（**再插入**，不是合并）⭐⭐
✅ **EN:** *"The procedure for disposing of under-full nodes **differs from the corresponding operation on a B-tree, in which two or more adjacent nodes are merged**. R-trees instead **re-insert** the orphaned entries."*
💡 **中文（Delete 四步 + CondenseTree）：**
- **D1** FindLeaf 定位含 E 的叶节点 L（找不到就停）→ **D2** 从 L 删除 E → **D3** 调 **CondenseTree(L)** → **D4** 若调整后根只有一个孩子，**把该孩子变成新根（树变矮）**。
- **CondenseTree**：把项数太少的节点**整个消除**（放进集合 Q），把它的项**重新插入**；沿路径调整所有覆盖矩形（**尽量缩小**）。
  - **CT6 [Re-insert orphaned entries]**：⭐ **从被消除的叶节点来的项按 Algorithm Insert 插回树的叶层；但从更高层节点来的项必须被放到树中更高的位置**，这样它们的从属子树的叶子才能和主树的叶子在同一层。
- ⭐ **为什么选"再插入"而不是"和兄弟合并"（两个理由，考点）：**
  1. **达到同样效果且更容易实现**——可以直接复用 Insert 例程。效率也应当相当，因为**再插入期间需要的页通常就是前面搜索访问过的页，已经在内存里**。
  2. **再插入会渐进式地refine（精炼）树的空间结构**，防止"每个项被永久地固定在同一个父节点下"可能导致的**逐渐劣化**。
- 注：B-tree 式的合并对 R-tree **也是可行**的（虽然没有 B-tree 意义上的"相邻"）：**过空节点可以与"面积增加最少的那个兄弟"合并**，或把孤儿项**分配给多个兄弟节点**。两种方法都可能引起节点分裂。
- **更新**：若元组更新后覆盖矩形改变，其索引记录必须**删除、更新、再插入**，才能找到正确位置。
❌ **Trap:** *"Under-full R-tree nodes are merged with an adjacent sibling, exactly as in a B-tree."* —— 错，**Guttman 选的是 re-insertion**。

### 重点6 · Node Splitting（三种算法）⭐
✅ **EN:** *"The division should be done in a way that makes it **as unlikely as possible that both new nodes will need to be examined on subsequent searches**. Since the decision whether to visit a node depends on whether its covering rectangle overlaps the search area, **the total area of the two covering rectangles after a split should be minimized**."*

| 算法 | 代价 | 做法 |
|:---|:---|:---|
| **Exhaustive（穷举）** | **随页大小指数增长** | 生成所有可能分组挑最好。M=50 时可能的分裂数极大（约 2^M），**太慢，只用作对照标准** |
| **Quadratic（二次）** | **M 的平方，维数的线性** | **PickSeeds**：对每对项 E₁、E₂ 组成包住两者的矩形 J，算 **d = area(J) − area(E₁.I) − area(E₂.I)**，**选 d 最大的一对**做两组的首元素（"放一起最浪费面积的那对"）。**PickNext**：对每个未分组的 E 算加入 Group 1 需要的面积增量 d₁ 和加入 Group 2 的 d₂，**选 \|d₁ − d₂\| 最大的项**（"最偏心的那个先分"），把它加到**覆盖矩形需要扩大最少**的那组。平局依次按：面积更小的组 → 项数更少的组 → 任意。 |
| **Linear（线性）** | **M 的线性，维数的线性** | 与 Quadratic 完全相同，**只换 PickSeeds**，且 **PickNext 随便挑一个剩余项**。**LinearPickSeeds**：沿每一维找"**low side 最高**"的项和"**high side 最低**"的项，记录**分离度**；用整个集合在该维上的**宽度归一化**；选**归一化分离度最大**的那一对。 |

- **QS2 提前终止条件**：若某一组项太少，以至于剩下的全部必须给它才能达到最小项数 m，**就全给它并停止**。
❌ **Trap:** *"PickSeeds chooses the two entries that are farthest apart in Euclidean distance."* —— 错，是**"放在一起最浪费面积"**（d 最大）。
❌ **Trap:** *"The linear split algorithm produces noticeably worse search performance."* —— **错**，见下条结论。

### 重点7 · 实验与结论（记结论，别记曲线）
- 环境：C / Unix / VAX 11/780；**二维数据**（结构与算法适用于任意维）；数据是 **RISC-II 芯片的 VLSI 布局数据**，电路单元 **CENTRAL 含 1057 个矩形**。
- 页大小 128/256/512/1024/2048 字节 → **M = 6/12/25/50/102**；m 测了 **M/2、M/3、2**。
- 测试流程：建树（测最后 10% 记录的插入）→ **100 次随机搜索，每次取回约 5% 的数据** → 再读一遍输入，**删除每第十条**（散布的 10% 删除）。

✅ **EN（结论 1，最重要）:** *"The **linear** node-split algorithm proved to be **as good as more expensive techniques**. It was fast, and the **slightly worse quality of the splits did not affect search performance noticeably**."*
✅ **EN（结论 2）:** *"Insert and delete cost is **independent of tree width but is affected by tree height**, which grows slowly with the number of data items."*
✅ **EN（结论 3）:** *"R-trees would be **easy to add to any relational database system that supported conventional access methods** (e.g., INGRES, System-R), and would work especially well in conjunction with **abstract data types and abstract indexes**."*
- 其他可考的细节：
  - **搜索性能对分裂算法和填充率的选择非常不敏感**——穷举法产生略好的结构（触碰页更少、CPU 更低），但**大多数组合都在最好值的 10% 以内**。
  - **更严格的填充要求 → 索引更小**。最稀疏的索引比最密的多占约 **50%** 空间，但 1/2 满和 1/3 满的结果彼此在 **15%** 以内。
  - **删除代价受最小填充要求强烈影响**：填充要求越严，节点越常变得过空、且过空时项更多，再插入更频繁，分裂也更频繁。
  - **线性算法的 CPU 时间几乎不随页大小增长** → 说明**节点分裂只占插入代价的一小部分**。
  - 空间：linear-2 配置约 **40 字节/数据项**（纯索引记录本身 20 字节）；quadratic-1/3 约 **33 字节/项**。
  - 结论中还提到：**用更小的节点，R-tree 也能作为主存索引**——CPU 性能相当，但没有 I/O 代价。

# 📘 Paper 7 — The Case for Learned Index Structures（Kraska 等, SIGMOD 2018）⭐⭐

> **主旨（第一句话就是全文论点）**：**Indexes are models（索引就是模型）**。
> - **B-Tree-Index** = 把 key 映射到**有序数组**中记录位置的模型；
> - **Hash-Index** = 把 key 映射到**无序数组**中记录位置的模型；
> - **BitMap-Index** = 指示一条数据记录是否存在的模型。
> 既然如此，**所有现有索引结构都能被换成别的模型**（包括深度学习模型）→ **learned indexes（学习索引）**。

### 重点0 · 论文的定位（不要说过头，考"作者到底主张什么"）
✅ **EN:** *"It is important to note that we **do not argue to completely replace traditional index structures** with learned indexes. Rather, the main contribution is to **outline and evaluate the potential** of a novel approach that **complements existing work**."*
✅ **EN（关键洞察）:** *"Many data structures can be **decomposed into a learned model and an auxiliary structure** to provide the same semantic guarantees. The power comes from the fact that **continuous functions describing the data distribution can be used to build more efficient data structures or algorithms**."*
💡 **中文：** 作者说的是"**这是个有潜力的新方向**"，不是"B-tree 该退休了"。而且实验只在**只读分析型负载**上做，**写密集负载仍是开放问题**。这是一篇 **exploratory research paper（探索性研究论文）**。
❌ **Trap:** *"The paper demonstrates that learned indexes should replace all B-Trees in production systems."* —— 错，作者明确不这么主张。

### 重点1 · 为什么通用索引"浪费"了（动机）
✅ **EN:** *"All existing indexes remain **general purpose** data structures; they **assume nothing about the data distribution** and do not take advantage of common patterns in real world data."*
💡 **中文（那个必背的例子）：** 若要为**连续整数键 1 到 100M** 建索引，**没人会用 B-Tree**——**键本身就能当偏移量**，查找从 **O(log n) 变成 O(1)**，索引内存从 **O(n) 变成 O(1)**。
- 推广：**知道确切的数据分布，几乎任何索引结构都能被高度优化**。
- 现实中数据不会完美符合已知模式，而为每个场景手工造专用方案的**工程成本太高** → **用 ML 自动合成专用索引结构，工程成本低**。
❌ **Trap:** *"Learned indexes only help when the data follows a known closed-form distribution."* —— 错，机器学习的美妙之处正是**能学各种分布、混合分布和数据怪癖**。

### 重点2 · B-Tree 就是模型（把 B-Tree 翻译成 ML 语言）⭐
✅ **EN:** *"A B-Tree is a model — in ML terminology, a **regression tree** — that maps a key to a position with a **min-error of 0 and a max-error of the page-size**, with a guarantee that the key can be found in that region if it exists."*
💡 **中文（逐条对照，考点密集）：**
| B-Tree 概念 | ML 说法 |
|:---|:---|
| 索引每页的第一个 key（不是每个 key） | 模型的训练/压缩 |
| 从 key 到位置的映射 | 回归（regression） |
| 保证在 [pos, pos+pagesize] 内找到 | **min-error = 0，max-error = page-size** |
| 插入新数据后**再平衡（rebalance）** | **重训练（re-train）** |
- ⭐ **两个关键放松（why 换模型是可行的）：**
  1. **B-Tree 的强误差保证只对"已存储的键"成立，不对所有可能的键成立。** 对**单调（monotonic）模型**，我们只需对每个 key 跑一遍模型、记下**最坏的高估和低估**，就得到 min/max error。（模型必须单调，才能对"不存在于集合中的查找键"也保证 min/max error。）
  2. **更重要的是：强误差界甚至根本不需要。** 数据本来就是有序的（为了支持范围查询），**任何误差都能靠预测值附近的局部搜索（如指数搜索）纠正** → **因此连非单调模型都可以用**。
- 所以：**B-Tree 可以被任意回归模型替换**（线性回归、神经网络……）。
❌ **Trap:** *"Replacing a B-Tree with a model requires the model to be monotonic."* —— **错**，单调只是"想直接用 min/max error 保证的话"才需要；**用指数搜索/自动调整搜索区间就不需要**。

### 重点3 · Range Index Models are CDF Models（全文最核心的等式）⭐⭐
✅ **EN:** *"A model that predicts the position given a key inside a sorted array effectively **approximates the cumulative distribution function (CDF)**: **p = F(Key) × N**, where p is the position estimate, F(Key) is the estimated CDF (the likelihood to observe a key ≤ the look-up key), and N is the total number of keys."*
💡 **中文（这个观察打开了四扇门，原文逐条列出）：**
1. **索引这件事字面上就是在"学一个数据分布"**。B-Tree 通过建回归树来"学"分布；线性回归模型通过最小化平方误差来学分布。
2. **估计数据集的分布是个成熟问题**，学习索引可以直接受益于几十年的研究。
3. **学 CDF 在优化其他索引结构和算法时也是关键**（后面 hash / Bloom / 排序都用它）。
4. **理论 CDF 与经验 CDF 的逼近程度有很长的研究历史**，为理论分析提供了立足点。
- ⭐ **理论结论（附录 A）**：`E[(F(x) − F̂_N(x))²] = F(x)(1−F(x))/N`，推得**预测位置的平均误差以 O(√N) 增长**。**这种对常数大小模型的次线性误差伸缩，优于常数大小 B-Tree 的线性伸缩。**
❌ **Trap:** *"For point queries the data must also be sorted for the CDF model to work."* —— 错，**点查询不关心记录顺序**；只有范围查询才必须按查找键排序。

### 重点4 · 朴素做法为什么失败（三个原因，必背）⭐
> 实验：200M 条 web-server 日志记录，用 Tensorflow 训了一个**两层全连接、每层 32 神经元、ReLU 激活**的网络，时间戳作特征、有序数组中的位置作标签。
> 结果：**≈1250 次预测/秒，即执行模型 ≈80,000 纳秒**（还不含搜索时间）。对照：**B-Tree 遍历 ≈300ns，全量二分搜索 ≈900ns**。

✅ **EN（三条原因）:**
1. *"**Tensorflow was designed to efficiently run larger models, not small models**, and thus has a significant invocation overhead, especially with Python as the front-end."*
2. *"**B-Trees, or decision trees in general, are really good at overfitting the data with a few operations** as they recursively divide the space using simple if-statements. In contrast, other models can be significantly more efficient to approximate **the general shape of a CDF**, but have problems being accurate **at the individual data instance level**."*
3. *"**B-Trees are extremely cache- and operation-efficient** as they keep the top nodes always in cache. In contrast, standard neural nets require **all weights** to compute a prediction, which has a high cost in the number of multiplications."*
💡 **中文（第 2 条是全文枢纽——"last mile 问题"）：** 从顶层看 CDF 曲线很光滑很规整；**放大到单条记录，越看越不规则**（一个著名的统计效应）。所以神经网络/多项式回归**很擅长把位置从"整个数据集"缩到"几千的范围"**，但**要把误差从几千再降到几百的"最后一英里"，单个神经网络需要显著更多的空间和 CPU 时间**。
- ⭐ **这正是 RMI 被发明出来的理由。**

### 重点5 · 我们能负担多复杂的模型？（那个算术，很爱考）
✅ **EN:** *"Consider a B-Tree indexing 100M records with a **page-size of 100**: it has a **precision gain of 1/100 per node** and needs to traverse **log₁₀₀N** nodes. Traversing a single B-Tree page with binary search takes roughly **50 cycles** and is notoriously hard to parallelize. A modern CPU can do **8–16 SIMD operations per cycle**. Thus, **a model will be faster as long as it has a better precision gain than 1/100 per 50 × 8 = 400 arithmetic operations.**"*
💡 **中文：** 每个 B-Tree 节点把空间从 100M → 1M → 10k → …，即**每个节点带来 1/100 的精度增益，代价约 50 个周期**。**同样 50 个周期，CPU 能做 400 次算术运算。** 所以只要模型能用 ≤400 次运算带来比 1/100 更好的精度增益，就更快。
- 而且这个算法**还假设所有 B-Tree 页都在 cache 里**；**一次 cache miss 要多花 50–100 个周期**，因此实际上允许更复杂的模型。
- **GPU/TPU 展望**：NVIDIA Tesla V100 能做 120 TeraFlops 低精度深度学习运算（**≈60,000 次运算/周期**）→ **30 个周期就能执行 100 万次神经网络运算**。但**本文全部实验只在 CPU 上做**，以便在没有硬件变化的影响下研究"用 ML 替换/增强索引"的含义。
❌ **Trap:** *"The paper's experiments rely on GPUs/TPUs to beat B-Trees."* —— **错**，"this paper focuses entirely on CPUs"。

### 重点6 · RMI = The Recursive Model Index（结构 + 四大好处）⭐⭐
✅ **EN:** *"We build a **hierarchy of models**, where at each stage the model takes the key as an input and **based on it picks another model**, until the final stage predicts the position."*
- 形式化：阶段 ℓ 有 M_ℓ 个模型；阶段 0 训 f₀(x) ≈ y；阶段 ℓ 的第 k 个模型 f_ℓ^(k) 用损失 L_ℓ = Σ(f_ℓ^(⌊M_ℓ f_{ℓ−1}(x)/N⌋)(x) − y)² 训练。**逐阶段（stage-wise）训练，不是端到端**（原文注：端到端会更好，是 future work）。

💡 **RMI 的四大好处（原文编号，逐条考）：**
1. **It separates model size and complexity from execution cost.**（把模型规模/复杂度和执行代价解耦——总模型可以很大，但一次查找只走一条链）
2. **It leverages the fact that it is easy to learn the overall shape of the data distribution.**
3. **It effectively divides the space into smaller sub-ranges, like a B-Tree, to make it easier to achieve the required "last mile" accuracy with fewer operations.**
4. ⭐ **There is no search process required in-between the stages.** 上一阶段模型的输出**直接用来挑下一阶段的模型**。这不仅减少了管理结构的指令数，**还允许把整个索引表示成一次稀疏矩阵乘法交给 TPU/GPU**。

⭐ **RMI 与 B-Tree 的三点不同（office hour 已考，必背）：**
| | B-Tree | RMI |
|:---|:---|:---|
| 结构 | 一定是树 | **不一定是树**——同一阶段的不同模型**可以指向下一阶段的同一个模型** |
| 每个节点/模型覆盖的记录数 | 固定（page-size=100 就覆盖 ≤100 条） | **不必相同**，随数据分布自适应 |
| 阶段间的动作 | 页内二分搜索 | **只有模型求值，无搜索** |
- **另注**：取决于所用模型，**阶段之间的预测不一定能解释为位置估计**，更应看作"**挑一个对某些键更懂行的专家**"（mixture of experts 思想）。

### 重点7 · Hybrid Indexes（混合索引：把最坏情况兜住）⭐
✅ **EN:** *"Hybrid indexes allow us to **bound the worst case performance of learned indexes to the performance of B-Trees**. In the case of an extremely difficult to learn data distribution, **all models would be automatically replaced by B-Trees**, making it virtually an entire B-Tree."*
💡 **中文（Algorithm 1 的第 11–14 行）：** 训练完最后一阶段后，对每个叶模型算误差；**若 `max_abs_err > threshold`，就把这个 NN 模型换成一棵在该子集上训练的 B-Tree。**
- 模型混搭：**顶层用小的 ReLU 神经网络**（能学各种复杂分布），**底层用成千上万个简单线性回归模型**（空间和执行时间都便宜）；**数据特别难学时底层直接用 B-Tree**。
- 本文只用两类模型：**0 到 2 个全连接隐藏层、宽度最多 32 神经元的 ReLU 神经网络**，和 **B-Tree（决策树）**。⭐ **注意：0 隐藏层的 NN 等价于线性回归。**
- **每个最后阶段的模型单独存 standard error、min-error、max-error** → **可以按 key 用的模型逐个限制搜索空间**。
- 参数（阶段数、每模型隐藏层数等）目前用**简单的 grid search** 调。
❌ **Trap:** *"A learned index has no worst-case guarantee at all."* —— 有条件地错：**hybrid index 明确把最坏情况兜到 B-Tree 水平**。

### 重点8 · 搜索策略与单调性
✅ **EN:** *"**Model Biased Search** is our default strategy — it varies from traditional binary search **only in that the first middle point is set to the value predicted by the model**. **Biased Quaternary Search** takes three split points instead of one, defined as **pos − σ, pos, pos + σ**."*
💡 **中文：**
- **为什么学习索引在搜索上有优势**：模型预测的是 **key 的位置**，而不只是 key 所在的**区域（页）**。
- **四元搜索（quaternary search）**：一次取 3 个分裂点，指望**硬件一次把 3 个数据点都预取进来**；数据不在 cache 时性能更好。初始三点定在 pos−σ、pos、pos+σ，即"**先赌预测是准的，把注意力集中在位置估计附近，然后再退回常规四元搜索**"。
- **单调性问题**：实验用 min/max error 作搜索区间。**这保证能找到所有已存在的键；但对不存在的键，若 RMI 模型不单调，可能返回错误的上界/下界。** 三种对策：
  1. **强制 RMI 单调**（ML 上有研究）；
  2. **自动调整搜索区间**——若找到的上/下界正好在 min/max error 定义的边界上，就**增量扩大搜索区**；
  3. **用指数搜索（exponential search）**——若误差服从正态分布，平均而言与其他策略一样好，**而且不需要存任何 min/max error**。
❌ **Trap:** *"Binary search is replaced entirely in learned indexes."* —— 错，仍在**误差界内**用（只是起点被模型偏置）。

### 重点9 · 范围索引结果（数量级要记住）
| 对比 | 结论 |
|:---|:---|
| 学习索引 vs 读优化 B-Tree（3 个整数数据集，2 阶段 RMI，第 2 阶段 10k/50k/100k/200k 模型） | **快 1.5–3×，同时小最多两个数量级**（参考点是 page size 128 的 B-Tree——它给 B-Tree 最好的查找性能） |
| 数据集 | **Weblogs**（200M 条时间戳，**对学习索引近乎最坏情况**：课表/周末/假期/午休/院系活动/学期休假造成极复杂时间模式，出了名地难学）；**Maps**（≈200M 用户维护地物的经度，**相对线性、不规则少**）；**Lognormal**（合成，190M 唯一值，μ=0, σ=2，高度非线性，测重尾分布） |
| 模型选择的经验 | **第一阶段：简单（0 隐藏层）到半复杂（2 隐藏层、8 或 16 宽）最好；第二阶段：简单线性模型性能最好**（最后一英里不值得跑复杂模型，且线性模型能被最优地学出来） |
| 第二阶段用 10,000+ 个模型 | **令人印象深刻**——证明第一阶段模型能做出比 B-Tree 单个节点大得多的精度跳跃 |
| 字符串数据集（10M 个非连续 document-id） | **加速不如整数明显**：模型执行代价相对高；但**字符串搜索更贵，所以更高精度更划算 → hybrid index 有帮助**；搜索策略差异变大：1 隐藏层 NN + 偏置二分搜索 **1102ns**，同模型 + **偏置四元搜索仅 658ns** |

- **其他基线对比（Figure 5，Lognormal + 8 字节指针负载）**：
  - **Histogram（直方图）**：原则上可作 CDF 模型，但**要低误差逼近就需要大量桶，搜直方图本身就贵**；处理数据倾斜要变长桶边界，**显而易见的解法就退化成 B-Tree**，故不再讨论。
  - **Lookup-Table（查找表）**：固定大小和结构（如每槽指向另外 64 个槽），**因固定大小可用 AVX 高度优化**。测的是 3 阶段查找表。
  - **FAST**：高度 SIMD 优化的结构，但**总要按 2 的幂分配内存**才能用无分支 SIMD 指令，**导致索引显著变大**。
  - **定高 B-Tree + 插值搜索**：树总大小设为 1.5MB，与学习模型相当。
  - **结论**：*"learned indexes provide the best overall performance while saving significant amount of memory"*，但作者**绝不宣称学习索引在大小或速度上总是最优**。
- **字符串处理**：把 n 长的字符串当作特征向量 x ∈ Rⁿ，**xᵢ 是 ASCII（或 Unicode）十进制值**；设最大输入长度 N，因为数据按字典序排好，**先截断到长度 N 再 tokenize**；n < N 时 xᵢ = 0（i > n）。**线性模型 w·x+b 的乘加次数随 N 线性增长；哪怕单隐藏层宽 h 的前馈网络也是 O(hN)。**
❌ **Trap:** *"The Weblogs dataset is the easiest case for learned indexes."* —— **反了**，是**近乎最坏情况**。

### 重点10 · Point Index（学习哈希函数）
✅ **EN:** *"We can scale the CDF by the targeted size M of the Hash-map and use **h(K) = F(K) × M** as our hash-function. **If the model F perfectly learned the empirical CDF of the keys, no conflicts would exist.** The hash-function is **orthogonal to the actual Hash-map architecture** and can be combined with separate chaining or any other type."*
💡 **中文：**
- **冲突的量级**：100M 条记录 + 100M 槽 + 均匀随机哈希 → 类似**生日悖论**，**期望约 33% 或 3300 万个槽发生冲突**。
- ⭐ **注意与范围索引的区别**：这里**不追求紧凑存储或严格有序**，只求少冲突。
- **结果**：学习模型在三个数据集上**把冲突减少最多 77%**，执行时间与 Figure 4 的模型执行时间相同（**约 25–40ns**）。
- **收益取决于两个因素**：(1) 模型多准确地表示了观察到的 CDF——**若数据由均匀分布生成，简单线性模型能学到分布，但得到的哈希函数不会比任何足够随机的哈希函数更好**；(2) **Hash map 架构**（实现细节、负载、冲突解决策略、分配多少额外内存）。
- **实测（附录 B/C）**：separate chaining + 20 字节记录时，学习哈希函数**把浪费的存储减少最多 80%，延迟只增加 13ns**（不是 40ns——因为**更少冲突也意味着更少 cache miss**）。附录 C：AVX Cuckoo（32 位值）31ns / 99%；AVX Cuckoo（20 字节记录）43ns / 99%；商用 Cuckoo（20 字节）90ns / 95%；**in-place chained + 学习哈希 35ns / 100% 利用率**。
- **什么时候不划算**：**键小、值小或无值时，传统哈希函数 + Cuckoo hashing 大概就很好**；**负载大或分布式哈希表时，避免冲突收益更大**。⭐ **最大潜力在分布式场景**：如 NAM-DB 用哈希函数经 **RDMA** 查远程机器的数据，**每次冲突要多一次微秒级的 RDMA 请求**，模型执行时间可忽略，**即使小幅降低冲突率也显著提升整体性能**。
- **与 perfect hashing（完美哈希）的区别**：完美哈希也试图避免冲突，但**其函数的大小随数据规模增长**；**学习哈希函数可以与数据规模无关**（例：对 0 到 200M 间每隔一个的整数，一个线性模型零冲突且与数据量无关）。而且**完美哈希对 B-Tree 或 Bloom filter 没用**。
❌ **Trap:** *"Learned hash functions always outperform Cuckoo hashing."* —— 错，**取决于架构、负载大小和实现**。

### 重点11 · Existence Index（学习 Bloom filter）
✅ **EN:** *"A good hash function for a **point index** is one with **few collisions among keys**, whereas a good hash function for a **Bloom filter** would be one that has **lots of collisions among keys and lots of collisions among non-keys, but few collisions of keys and non-keys**."*
💡 **中文（两种做法）：**

**(a) 分类问题 + 溢出 Bloom filter（5.1.1）**
- 学一个二分类模型 f(x) ∈ [0,1]（字符串可用 **RNN / CNN**），用 **log loss** 训练；选阈值 **τ**，f(x) ≥ τ 就认为 key 存在。
- 问题：模型会有**非零的 FPR 和 FNR**；而存在索引**必须 FNR = 0**。
- ⭐ **对策：建一个 overflow Bloom filter（溢出 Bloom 过滤器）**，装的是 **K_τ = {x ∈ K | f(x) < τ}**，即**模型判错的那些假阴性**。查询流程：**若 f(x) ≥ τ 就认为存在；否则查溢出 Bloom filter。**
- 总 FPR：**FPR_O = FPR_τ + (1 − FPR_τ) × FPR_B**；简化设 FPR_τ = FPR_B = p*/2 使 FPR_O ≤ p*。
- ⭐ **溢出 Bloom filter 的大小随 FNR 伸缩**（Bloom filter 大小随键集大小伸缩）。
- **实测（Google transparency report 的 1.7M 条钓鱼 URL）**：普通 Bloom filter 要 **2.04MB**（1% FPR）；16 维 GRU + 每字符 32 维嵌入的模型只有 **0.0259MB**；设 τ 使验证集 FPR = 0.5%（FNR = 55%）→ 模型 + 溢出 filter 共 **1.31MB，省 36%**。若要总 FPR 0.1%，FNR = 76%，从 3.06MB 降到 **2.59MB，省 15%**。
- **协变量偏移（covariate shift）实验**：验证/测试集只用随机 URL → **省 60%**；只用白名单 URL → **省 21%**。
- ⭐ **一个漂亮的性质**：**模型不需要用和 Bloom filter 相同的特征**——可以加 WHOIS 数据、IP 信息等，**提高准确率、减小 filter 大小，同时保持"无假阴性"**。

**(b) Model-Hashes（5.1.2 + 附录 E）**
- 把分类器输出**离散化**当作 Bloom filter 里的**一个额外哈希函数**：`M[⌊m·f(x)⌋] = 1`。
- 总 FPR = **FPR_m × FPR_B**。
- **实测更好**：p* = 0.1% 时 m = 1,000,000，总大小 2.21MB，**省 27.4%**（对比 (a) 的 15%）；p* = 1% 时总大小 1.19MB，**省 41%**（对比 (a) 的 36%）。但结果依赖离散化方案，值得进一步分析。
- ⭐ **FPR 定义的差别（易考）**：传统 Bloom filter 对**任何事先选定的查询集合**保证 FNR = 0 和特定 FPR；本文**换了个说法**——在**保持 FNR = 0** 的前提下，**对"现实查询"提供特定 FPR**，即在**留出的查询数据集上**度量 FPR（ML 系统的常规做法）。前提假设是"能观察到查询分布（如历史日志）"。
❌ **Trap:** *"A learned Bloom filter may return false negatives."* —— **错**，溢出 Bloom filter 就是为了**保证 FNR = 0**。

### 重点12 · 插入/更新与结论（future work，也考）
✅ **EN（append 场景）:** *"If the model generalizes and learns the patterns which also hold for future data, **updating the index structure becomes an O(1) operation** — a simple append with no change of the model itself — **whereas a B-Tree requires O(log n) operations to keep balance**."*
💡 **中文：** 两类插入：**(1) append（追加）** 和 **(2) 中间插入**（如在订单表上按 customer-id 维护二级索引）。
- append 场景（如 web 日志时间戳索引）**几乎全是递增追加** → 若模型泛化得好，**更新是 O(1)**。中间插入也能类似论证，但**可能需要移动数据或在数据中预留空间**。
- ⭐ **两个开放问题**：(1) **泛化能力与"最后一英里"性能之间存在有趣的权衡**——最后一英里预测越准，模型越可能是**过拟合**、越不能泛化到新数据；(2) **分布变化了怎么办？能否检测？能否像 B-Tree 那样保证 O(log n)？**
- ⭐ **永远存在的简单退路**：**delta-index（增量索引）**——所有插入放进缓冲区，不时与主结构合并并可能重训模型。**这已被广泛使用**（如 Bigtable）。
- **分页（Paging）问题**：数据若被分成放在磁盘不同区域的大页，**pos = Pr(X < Key) × N 就不再成立**。三种对策：(1) 利用 RMI 结构本身分区，微调训练以**最小化模型覆盖区域的重叠**，并**复制可能被多个模型访问的记录**；(2) 加一张 **<first_key, disk-position> 的转换表**（页很大时效果最好；用预测位置 + min/max error 可以减少从大页里读的字节数）；(3) 模型复杂时**直接学页的实际指针**（若文件系统对磁盘块有系统化编号）。
- **结论里的 future work**：其他 ML 模型；**多维索引**（"最激动人心的方向"）；**Beyond Indexing: Learned Algorithms**——⭐ **CDF 模型还能加速排序和连接**：用 CDF 模型把记录大致排好，再用插入排序纠正近乎完美有序的数据；GPU/TPU（唯一障碍是 **2–3 微秒的调用延迟**，可用批处理摊薄）。

# 📙 Paper 8 — Parallel Database Systems: The Future of High Performance Database Processing（DeWitt & Gray, CACM 1992）⭐⭐

> **主旨（摘要一句话）**：*"Parallel database machine architectures have **evolved from the use of exotic hardware to a software parallel dataflow architecture based on conventional shared-nothing hardware**."*
> **一句话结论**：**专用数据库机（exotic hardware）失败了；用普通硬件搭的并行数据库系统大获成功。**

### 重点1 · 为什么并行数据库成功了（关系模型的意外红利）⭐
✅ **EN:** *"**Relational queries are ideally suited to parallel execution**; they consist of **uniform operations applied to uniform streams of data**. Each operator produces a new relation, so the operators can be composed into highly parallel **dataflow graphs**."*
✅ **EN（金句）:** *"**Parallelism is an unanticipated benefit of the relational model.**"*
💡 **中文：**
- 1983 年关系数据库刚上市；今天（1992）它主宰市场。关系查询由**作用在均匀数据流上的均匀操作**组成，每个算子产出新关系 → **可组合成高度并行的数据流图**。
- **两种并行方式**：
  - **pipelined parallelism（流水线并行）**：把一个算子的输出**流进**另一个算子的输入，两者串联同时工作。
  - **partitioned parallelism（分区并行）**：把输入数据**分区到多个处理器和内存**，一个算子拆成许多**独立的**算子各处理一部分。
- **SQL 数据模型原本是为提高程序员生产力**（非过程化语言）提出的；**data independence 是附带好处**（程序不指定"怎么执行"，schema 演化后仍能运行）；**并行是意外之喜**（非过程化语言给了执行上的巨大自由度）。
- ⭐ **老软件是使用并行的最大障碍**：为单处理器写的老软件放到任何多处理器上都得不到 speedup/scaleup，必须重写。**数据库应用是一个独特的例外**——多数数据库程序用 ANSI/ISO 标准化的 SQL 写成，**可以把为单处理器写的标准 SQL 应用原封不动地在 shared-nothing 数据库机上并行执行**。
❌ **Trap:** *"Parallelism was an explicit design goal of the relational model."* —— 错，是 **unanticipated benefit**。

### 重点2 · Speedup 与 Scaleup（office hour 已考）⭐⭐
✅ **EN:** *"(1) **linear speedup**: twice as much hardware can perform the task in **half the elapsed time**; (2) **linear scaleup**: twice as much hardware can perform **twice as large a task** in **the same elapsed time**."*

| | 公式 | 线性的判据 | 变什么 |
|:---|:---|:---|:---|
| **Speedup** | `小系统耗时 / 大系统耗时` | **= N** | **固定问题规模，增长系统** |
| **Scaleup** | `小系统跑小问题耗时 / 大系统跑大问题耗时` | **= 1** | **系统与问题同时增长** |

- ⭐ **两种 scaleup（爱考的细分）：**
  - **transaction scaleup（事务扩展）**：作业由**许多小的独立请求**组成（多个客户端操作共享数据库）→ N 倍客户端、N 倍请求、N 倍大的数据库。**这是事务处理系统和分时系统的典型形态，也是 TPC 用来扩展其事务处理基准的方式。** ⭐ **transaction scaleup 特别适合并行系统**，因为每个事务通常是能在独立处理器上跑的小的独立作业。
  - **batch scaleup（批量扩展）**：扩展任务是**单个大作业**（数据库查询、科学模拟的典型形态）→ 用 N 倍大的计算机解 N 倍大的问题。**对数据库系统，batch scaleup 意味着"在 N 倍大的数据库上跑同一个查询"；对科学问题，意味着"在 N 倍细的网格或 N 倍长的模拟上做同一个计算"。**
- ⭐ **near-linear（近线性）这个词的由来（脚注 4）**：**有些算子的执行代价是超线性的**。例如排序 n 元组的代价是 **n log(n)**。当 n 是数十亿时，扩大一千倍会使 n log(n) 增加 **3000** 倍。**这个在三个数量级扩展中 30% 的线性偏离，正当化了 "near-linear scaleup" 这个说法。**
❌ **Trap:** *"Linear scaleup means the scaleup metric evaluates to N."* —— 错，**scaleup 线性时该式 = 1**。

### 重点3 · 线性 speedup/scaleup 的三大障碍（"triple threats"）⭐⭐
✅ **EN:** *"The generic barriers to linear speedup and linear scaleup are the **triple threats** of: **startup**, **interference**, and **skew**."*
| 障碍 | 原文定义 | 大白话 |
|:---|:---|:---|
| **startup（启动）** | *"The time needed to start a parallel operation. If **thousands of processes must be started**, this can easily **dominate the actual computation time**."* | 起进程比干活还久。🔵 组织一千人开会，光点名就点了一上午。 |
| **interference（干扰）** | *"The **slowdown each new process imposes on all others** when accessing shared resources."* | 大家抢同一份资源互相拖慢。 |
| **skew（倾斜）** | *"As the number of parallel steps increases, the **average size of each step decreases, but the variance can well exceed the mean**. The service time of a job is the service time of **the slowest step**. When the variance dominates the mean, increased parallelism improves elapsed time only slightly."* | **整体耗时由最慢那一步决定**；步子切得太碎时，方差压过均值，再加并行也没用。 |

- ⭐ **干扰的数量化（必背的例子）**：*"If this slowdown (interference) is **1%**, then the **maximum speedup is 37** and a **thousand-processor system has 4% of the effective power of a single processor system**."*
- Figure 2 的三条曲线：左 = 理想线性；中 = 加硬件完全没有加速；右 = 三大威胁——**初期 startup 代价主导，随进程数增加 interference 上升，最终作业被切得太细，服务时间的方差（skew）导致减速**。
❌ **Trap:** *"Skew only matters for data placement, not for execution time."* —— 错，论文明确区分 **data skew（数据倾斜）** 和 **execution skew（执行倾斜）**，后者直接决定耗时。

### 重点4 · 三种硬件架构（Stonebraker 分类法）⭐⭐
✅ **EN:**
- **shared-memory:** *"All processors share direct access to a common global memory and to all disks."* 典型：IBM/370、Digital VAX、Sequent Symmetry。
- **shared-disks:** *"Each processor has a **private memory** but has **direct access to all disks**."* 典型：IBM Sysplex、原始的 Digital VAXcluster。
- **shared-nothing:** *"**Each memory and disk is owned by some processor** that acts as a server for that data."* 典型：Teradata、Tandem、nCUBE。

✅ **EN（shared-nothing 为什么赢，金句）:** *"The other architectures **move large quantities of data through the interconnection network**. The **shared-nothing design moves only questions and answers through the network.** Raw memory accesses and raw disk accesses are performed **locally** in a processor, and **only the filtered (reduced) data is passed** to the client program."*
💡 **中文（逐条对比，考点极密）：**

| | shared-memory | shared-disk | **shared-nothing** |
|:---|:---|:---|:---|
| 内存 | 全局共享 | 各自私有 | **各自私有** |
| 磁盘 | 全部共享 | **全部可直接寻址** | **每块盘归某个处理器所有** |
| 网络上传的是什么 | 大量数据 | **大量物理数据页 + 预约消息** | ⭐ **只有"问题和答案"** |
| 扩展上限 | ⭐ **当时最大约 32 个处理器** | 难扩展到几千处理器/磁盘 | ⭐ **数百乃至数千处理器**（Teradata/Tandem/Intel 已出货 200+；Intel 在做 2000 节点 Hypercube） |
| 主要问题 | **interference 是大问题**；互连网络带宽必须等于所有处理器和磁盘带宽之和；给每个处理器配大私有 cache 后，**测量显示装载和刷新这些 cache 严重降低处理器性能** | **读写共享数据库时非常低效**：处理器要更新数据必须先取得当前副本、并**声明更新意图**，等**所有其他处理器确认**后才能读改写回。所有优化最终都在**交换预约消息和大的物理数据页** | 干扰最小 |
| 演化趋势 | 用 **affinity scheduling（亲和调度）**减少干扰——**这本身就是数据分区，是朝 shared-nothing 演化的一步**。但"分区一个共享内存系统"会带来 shared-nothing 的 skew 和负载均衡问题，**却享受不到更简单硬件互连的好处** | 给数据加**处理器亲和性**，其他处理器发消息给管理该数据的服务器 —— **又是朝分区数据模型和 shared-nothing 演化** | — |

- ⭐ **shared-disk 的适用面**：*"If the disk interconnection network can scale to thousands of discs and processors, then a shared-disk design is **adequate for large read-only databases and for databases where there is no concurrent sharing**."*（**只读或无并发共享**时够用。）
- ⭐ **总结句**：*"Given such results, database machine designers see **little justification for the hardware and software complexity** associated with shared-memory and shared-disk designs."*
- **注（脚注 5）**：**SIMD 机器**（如 Connection Machine、MASSPAR、ILLIAC IV）**被排除在讨论外**，因为**在数据库领域鲜有成功**；SIMD 似乎适合模拟、模式匹配和数学搜索，**不适合数据库系统那种多用户、I/O 密集、数据流的范式**。
- **互连网络实现多样**：Teradata 用冗余树形网络（**Y-net**）；Tandem 用三层双工网络（簇内两层 + 连接簇的环）；Arbre/Bubba/Gamma **不依赖底层互连**，只要求任意两节点能通信（Gamma 跑在 Intel Hypercube 上；Arbre 原型用 IBM 4381 点对点网络）。
❌ **Trap:** *"Shared-memory scales best because processors can exchange data without messages."* —— **错**，恰恰扩展性最差。
❌ **Trap:** *"Affinity scheduling on a shared-memory machine avoids the skew problems of shared-nothing."* —— **错**，它**带来了** shared-nothing 的 skew 和负载均衡问题，却没有更简单硬件互连的好处。

### 重点5 · 三种数据分区策略（必背表）⭐⭐
✅ **EN:** *"**Round-robin** partitioning maps the i'th tuple to disk **i mod n**. **Hash** partitioning maps each tuple to a disk location based on a hash function. **Range** partitioning maps contiguous attribute ranges of a relation to various disks."*

| 策略 | 适合什么 | 弱点 | 谁在用 |
|:---|:---|:---|:---|
| **Round-robin（轮转）** | ⭐ *"excellent if **all applications want to access the relation by sequentially scanning all of it** on each query"*（分区版的 entry-sequence 文件） | ⭐ **应用经常想做 associative access（关联访问）**（找某属性值等于某值的所有元组），轮转做不到 | — |
| **Hash（哈希）** | ⭐ *"ideally suited for applications that want **only sequential and associative access**"*；对特定属性值的关联访问**可以定向到单块盘**，**免去在多块盘上启动查询的开销** | ⭐ **哈希是把数据随机化而不是聚簇化** | Arbre、Bubba、Gamma、Teradata |
| **Range（范围）** | ⭐ *"good for sequential and associative access, and is **also good for clustering data**"*；把属性相似的元组**聚在同一分区**；名字来自典型的 SQL 范围查询（`latitude BETWEEN 37° AND 39°`） | ⭐ **风险是 data skew（所有数据落到一个分区）和 execution skew（所有执行发生在一个分区）**；hashing 和 round-robin **不太容易有这些倾斜问题** | Arbre、Bubba、Gamma、Oracle、Tandem |

- ⭐ **范围分区可以通过"挑非均匀分布的分区标准"来最小化倾斜**。**Bubba 用了这个思路：建分区时考虑每个元组的访问频率（heat 热度）**，目标是**平衡每个分区被访问的频率（temperature 温度）而不是每块盘上的实际元组数（volume 体积）**。（🔵 heat/temperature/volume 这组词非常爱考。）
- **聚簇（clustering）是高度应用相关的**：电话簿里的 Smith 若常按字母序访问就该按此序存页并把这些页聚在磁盘上以支持顺序预取；地理数据库里附近街道的元组该聚在一起；库存应用里发票明细行该和发票元组聚在一起。
- ⭐ **分区度不是越高越好**：*"Increasing the degree of partitioning usually reduces the response time for an individual query and increases the overall throughput. For **sequential scans**, response time decreases because **more processors and disks** are used. For **associative scans**, response time improves because **fewer tuples are stored at each node and hence the size of the index that must be searched decreases**. **There is a point beyond which further partitioning actually increases the response time** — this occurs when **the cost of starting a query on a node becomes a significant fraction of the actual execution time**."*（**这就是 startup 障碍在分区上的体现。**）
- 数据分区还提供了**优于 RAID 式系统的 I/O 带宽，且不需要任何专用硬件**。
❌ **Trap:** *"Hash partitioning is best for range queries because tuples with nearby values land on the same disk."* —— **错**，那是 range partitioning；hash **随机化**数据。

### 重点6 · Split 与 Merge 算子（并行数据流的两个"胶水"）⭐
✅ **EN:** *"The basic idea is to use **parallel data streams instead of writing new parallel operators**. This approach enables the use of **unmodified, existing sequential routines** to execute the relational operators in parallel."*
- **merge operator（归并算子）**：**把几路并行数据流合成一条顺序流**，喂给算子的一个输入端口。
- **split operator（分裂算子）**：**把一个算子产生的元组流分区或复制**成多路独立流。*"A split operator defines a **mapping from one or more attribute values of the output tuples to a set of destination processes**."*
  - split 表的形式（Figure 9）：`"A-H" → (cpu #5, Process #3, Port #0)`，即 **谓词 → (CPU 号, 进程号, 端口号)**。
  - ⭐ **端口号区分左右输入**：关系 A 的 scan 送到 join 进程的 **Port #0**，关系 B 的 scan 送到 **Port #1**。
  - **其他 split 算子可以复制输入流、或按 round-robin 分区、或按 hash 分区。分区函数可以是任意程序。**
- ⭐ **split 和 merge 内建了流控和缓冲**：*"When a split-operator's output buffers fill, it **stalls the relational operator** until the data target requests more output."* —— 这**防止某个算子在计算中跑得太靠前**。
- **粒度是策略**：为简化，例子里每个进程一个算子，但**完全可以把几个算子放进一个进程以获得更粗粒度的并行**。根本思想是**造一个自定步调（self-pacing）的数据流图，并把它分布在 shared-nothing 机器上使干扰最小**。
- ⭐ **Gamma、Volcano、Tandem 都用这个方法**，好处包括：**系统里新加的任何算子都自动获得并行能力**，以及**支持多种并行**。
❌ **Trap:** *"Each relational operator must be rewritten in a parallel version."* —— **错**，split/merge 的全部意义就是**复用未修改的顺序例程**。

### 重点7 · 流水线并行的三个局限（必背）⭐
✅ **EN:** *"The benefits of pipeline parallelism are limited because of three factors: (1) **Relational pipelines are rarely very long — a chain of length ten is unusual.** (2) **Some relational operators do not emit their first output until they have consumed all their inputs** — **aggregate and sort operators** have this property; one cannot pipeline these operators. (3) **Often, the execution cost of one operator is much greater than the others** (this is an example of **skew**)."*
✅ **EN（结论）:** *"**Partitioned execution offers much better opportunities for speedup and scaleup.** By taking the large relational operators and partitioning their inputs and outputs, it is possible to use **divide-and-conquer** to turn one big job into many independent little ones. **Partitioned data is the key to partitioned execution.**"*
❌ **Trap:** *"Pipelined parallelism is the primary source of speedup in parallel database systems."* —— **错**，是 **partitioned parallelism**。

### 重点8 · 并行连接算法：sort-merge vs hash join ⭐
✅ **EN:** *"**Sort-merge join** has an **n log(n)** execution cost. It works well in a parallel dataflow environment **unless there is data skew**; in case of data skew, some sort partitions may be much larger than others, which in turn creates **execution skew** and limits speedup and scaleup. **These skew problems do not appear in centralized sort-merge joins.**"*
✅ **EN:** *"**Hash-join** has **linear execution cost** rather than n log(n), and it is **more resistant to data skew**. It is **superior to sort-merge join unless the input streams are already in sorted order**."*
💡 **中文（hash join 怎么做）：** 关系 A 和 B 先**按连接属性哈希分区**；A 的一个哈希分区被**哈希进内存**；扫描 B 的对应分区，每条元组与 A 分区的**内存哈希表**比对；匹配则送到输出流。**每一对哈希分区都这样比较。**
- ⭐ **hash join 把一个大 join 拆成许多小 join**。若哈希函数好且数据倾斜不太糟，**桶大小的方差就小**，此时 hash-join 是**线性时间、线性 speedup 和 scaleup**的连接算法。
- ⭐ **病态倾斜（pathological skew）**：*"When **many or all tuples have the same attribute value**, one bucket may contain all the tuples. In these cases **no algorithm is known to speedup or scaleup**."*（**这是"没有已知算法"的情形，很爱考。**）
❌ **Trap:** *"Hash join is always superior to sort-merge join."* —— **错**，**输入已经有序时 sort-merge 更优**。

### 重点9 · 四个代表系统（各记 2–3 个独有特征）
| 系统 | 独有特征（考"张冠李戴"） |
|:---|:---|
| **Teradata**（1978 起） | 处理器分两类：**IFP（Interface Processor）**负责与主机通信、查询解析优化、协调 AMP；**AMP（Access Module Processor）**负责执行查询。互连为**双冗余树形 Y-net**。⭐ **每个关系在 AMP 子集上哈希分区**：插入时对**主键**应用哈希函数选 AMP，元组到达 AMP 后**第二个哈希函数**决定它在片段中的位置，**片段内元组按哈希键序**。支持**哈希二级索引**。⭐ **join 用并行 sort-merge 算法**；⭐ **不用流水线并行——查询执行时每个算子在所有参与节点上跑到完成，才启动下一个算子** |
| **Tandem NonStop SQL** | 处理器簇经 **4 路光纤环**互连。⭐ **应用与数据库服务器跑在同一处理器和操作系统上，没有前端/后端之分**。配置为**每 MIPS 一块盘**（10 MIPS 处理器约 10 块盘），**盘通常双工（duplexed）**。⭐ **在盘服务器上用 SQL 谓词过滤和处理元组、大块预取**以最小化共享互连网络流量。支持 **entry-sequenced、relative、B-tree** 组织；⭐ **只支持 B-tree 二级索引**；⭐ 提供 **nested / sort-merge / hash join**。⭐ **主要为 OLTP 设计**；OLTP 的主要并行特性是**并行索引更新**——SQL 关系典型有 **5 个索引（10 个也不罕见）**，索引加快读但拖慢写；**并行维护索引可使多索引的维护时间几乎保持恒定** |
| **Gamma** | 跑在 **32 节点 Intel iPSC/2 Hypercube**，每节点一块盘。⭐ 除 round-robin、range、hash 外还提供 **hybrid-range partitioning（混合范围分区）**，结合哈希和范围分区的优点。分区后提供**聚簇和非聚簇索引**，可建在**分区属性或非分区属性**上；索引实现为 **B-tree 或哈希表**。用 **split/merge** 同时实现并行和流水线；支持 **sort-merge 和三种不同的哈希连接方法** |
| **Bubba** | 跑在 **40 节点 FLEX/32 多处理器 + 40 块盘**。⭐ **虽然硬件是 shared-memory，Bubba 被设计成 shared-nothing 系统，共享内存只用于消息传递**。节点分三组：Interface Processors、**Intelligent Repositories**（存储与查询执行）、**Checkpoint/Logging Repositories**。⭐ **用 FAD 而不是 SQL** 作接口语言——FAD 是扩展关系型的持久编程语言，支持复杂对象（含共享子对象）、面向集合的数据操作原语。**FAD 编译器负责根据数据对象的分区方式检测可并行执行的操作**；⭐ **编译并行化 FAD 程序比并行化关系查询困难得多**。⭐ 另一独特点：**single-level store（单级存储）**——每个节点的持久数据库被映射到该节点上每个进程的**虚拟内存地址空间**，而不是传统的文件和页 |
| **SDC（Super Database Computer，东京大学）** | ⭐ **软硬件结合**的对照案例。基本单元 **PM（processing module）** = 一个或多个共享内存的处理器 + **专用高速排序引擎（当时 3MB/s）** + 磁盘子系统。PM 簇经 **omega network** 互连，提供**非阻塞 N×N 互连**和一些**动态路由以最小化哈希连接期间的倾斜数据分布**。设计目标扩展到数千 PM，故**对数据倾斜问题投入大量关注**。数据按**哈希**分区。⭐ **SDC 是 shared-nothing 设计 + 软件数据流架构**（符合"当前并行数据库机使用常规硬件"的论断），但 **omega 网络和硬件排序器的专用设计明确与"专用硬件不是好投资"的论点矛盾** |

- **其他系统**：XPRS 和 Volcano 实现在**共享内存多处理器**上，XPRS 独特之处在于其设计**利用了海量共享内存**；Arbre；IBM Research 的 PERSIST 项目。⭐ **Oracle 实现在 64 节点 nCUBE shared-nothing 系统上，是第一个在工业标准 TPC-B 基准上演示超过每秒 1000 事务的系统**。**NCR 宣布 3600/3700 产品线**，用 shared-nothing 架构跑 System V R4 Unix on Intel 486/586；3600 用向 Teradata 授权的增强 Y-Net，3700 基于 NCR 与 Teradata 联合开发的新多级互连网络；两个软件方案：Teradata 软件移植到 Unix（面向决策支持）、基于 Sybase DBMS 并行化（面向事务处理）。

### 重点10 · Grosch 定律不再适用（结论性论断）⭐
✅ **EN:** *"**Grosch's law no longer applies to database and transaction processing problems. There is no economy of scale. At best, one can expect linear speedup and scaleup** of performance and price/performance."*
💡 **中文：** 1960 年代 Herb Grosch 观察到计算存在**规模经济**——贵的计算机比便宜的强得多，产生**超线性**的 speedup 和 scaleup。
- 当时定价反映了这个观点：**主机 $25,000/MIPS、$1,000/MB RAM**；**微处理器 $250/MIPS、$100/MB RAM**（相差 100 倍和 10 倍）。
- 把成百上千台小系统组合起来，**能用远低于一台中等主机的钱造出极强的数据库机**。
- 具体证据：**Tandem 在 TPC-A 上远超最大的主机且线性扩展，price/performance 比可比主机便宜 3 倍**；**Oracle on nCUBE 有最高的 TPC-B 数字**；**Gamma、Tandem、Teradata 在复杂关系数据库基准上都演示了线性 speedup 和 scaleup**。
❌ **Trap:** *"Economies of scale make large mainframes the best price/performance choice for large databases."* —— **错，正是被本文推翻的论断。**

### 重点11 · 未解决的研究问题（5 个，可能考"哪个是开放问题"）
1. **Mixing Batch and OLTP Queries（混合批量与 OLTP 查询）**
   - **锁问题**：大的关系查询**获取大量锁并长时间持有**，阻止简单在线事务并发更新。两种现有解法：(a) 给 ad-hoc 查询一个**模糊快照（fuzzy picture）**，浏览时不加锁——这种 **"dirty-read"** 方案**对某些应用不可接受**；(b) **versioning（版本化）机制**——读者看到一致的**旧**版本，更新者可创建对象的新版本。
   - **优先级调度问题**：批作业倾向于**垄断处理器、淹没内存 cache、对 I/O 子系统提出大量需求**。⭐ **priority inversion（优先级反转）问题**：低优先级客户向高优先级服务器发请求；服务器必须以高优先级运行（它管理关键资源）；于是**低优先级客户的工作在被高优先级服务器服务时，实际上被提升到了高优先级**。已有若干 ad-hoc 尝试，但**还需要相当多的工作**。
2. **Parallel Query Optimization（并行查询优化）**：单处理器的关系查询代价模型现在**理解得比较透**，但仍**依赖顶多算是猜测的代价估计器**。有些系统**在运行时根据实际可用物理内存和中间结果的基数动态选择计划**。⭐ **至今没有查询优化器同时考虑每个算子的所有并行算法和所有查询树组织形式。** 另一个问题是**高度倾斜的值分布**导致中间关系大小的高方差 → **既造成糟糕的计划代价估计，也造成次线性 speedup**。
3. **Application Program Parallelism（应用程序并行）**：并行数据库系统只在**数据库系统内部**提供并行；**缺少让应用程序利用这些并行的工具**。虽然自动并行化 Cobol 程序可能不可行，但**需要便于写显式并行应用程序的库包**。⭐ **理想情况下 SPLIT 和 MERGE 算子应被打包，让应用也能受益。**
4. **Physical Database Design（物理数据库设计）**：需要工具帮 DBA 在众多索引和分区组合中选择。输入应包括**负载中的查询描述、执行频率、关系的统计信息、处理器和磁盘的描述**；输出应建议**每个关系的分区策略和要建的索引**。⭐ **当前算法用单个属性的值分区**——例如地理记录按经度或纬度分区；**按经度分区能把经度范围选择局部化到少数节点，但纬度上的选择必须发给所有节点**。**这在小配置里可接受，在有数千处理器的系统里不可接受。需要更多关于多维分区和搜索算法的研究。**
5. **On-line Data Reorganization and Utilities（在线重组与工具）**：以每秒 1MB 装载/重组/转储 1TB 数据库要**十二个日夜**。工具本身必须并行化，而且**数据在工具运行时必须仍然可用**。⭐ **这类算法的基本性质：online（不使数据不可用）、incremental（在大数据库的一部分上操作）、parallel（利用并行处理器）、recoverable（允许操作被取消并回到旧状态）。**
- **结论里还留了一句**：*"Some application domains are **not well supported by the relational data model**. It appears that a new class of database systems based on an **object-oriented data model** are needed."*

# 📓 Paper 9 — Encapsulation of Parallelism in the Volcano Query Processing System（Graefe, SIGMOD 1990）

> **主旨**：把**所有并行性问题封装进一个算子（exchange）**，使得**所有其他算子都可以当作"单进程"来写**，却能在高度并行环境中不加修改地运行。
> **规模感**：Volcano 全系统**不到两打核心模块、约 15,000 行 C 代码**；exchange 是**在其他查询处理模块全部写完之后**才设计实现的。

### 重点1 · Volcano 的基础：iterator + open/next/close + streams ⭐
✅ **EN:** *"**All algebra operators are implemented as iterators**, i.e., they support a simple **open–next–close** protocol similar to conventional file scans. The tree-structured query evaluation plan is used to execute queries by **demand-driven dataflow**."*
💡 **中文（几个必背的构件）：**
- **state record（状态记录）**：每个算法关联一个，装算法的参数。
- **support functions（支持函数）**：记录上的所有操作（比较、哈希）**由放在 state record 里、作为参数传给 iterator 的支持函数完成** → ⭐ **查询处理模块不需要知道数据对象的内部结构、也不受其约束**（这是可扩展性的来源）。
- **QEP 结构**：input pointer 指向的结构含**四个指针** = open、next、close 三个过程入口 + 一个 state record。
- ⭐ **anonymous inputs / streams（匿名输入 / 流）**：*"An operator **does not need to know what kind of operator produces its input**, and whether its input comes from a complex query tree or from a simple file scan."* **这正是后面 exchange 能被插到任意位置而上下算子毫无察觉的根本原因。**
- **执行流程**：对最上层算子 **open** → 递归实例化所有 state record（如分配哈希表）并 open 所有输入；反复 **next** 直到返回 **end-of-stream**；**close** 递归关闭。
- **next 的返回值**是 **NEXT_RECORD** 结构 = **记录标识符 + 缓冲池中的记录地址**，且该记录在缓冲区中被 **pinned/fixed（钉住）**。
- ⭐ **fix/unfix 协议**：*"Each record pinned in the buffer is **owned by exactly one operator at any point in time**."* 算子可持有、可 unfix（谓词失败时）、可传给下个算子。**像 join 这样创建新记录的操作必须先把新记录 fix 在缓冲区再往下传，并且要 unfix 它的输入记录。**
- **virtual devices（虚拟设备）**用于中间结果：页**只存在于缓冲区**，unfix 时丢弃；好处是**能给中间结果记录分配唯一 RID**，让所有算子**像对待真实磁盘设备一样**管理它们。
❌ **Trap:** *"Volcano operators must know whether their input comes from a scan or from a subtree."* —— 错，**anonymous inputs**。

### 重点2 · Bracket Model vs Operator Model（全文的骨架对比）⭐⭐
| | **Bracket Model（GAMMA、Bubba）** | **Operator Model（Volcano）** |
|:---|:---|:---|
| 形态 | 一个 **generic process template（通用进程模板）**能收发数据，**任一时刻只执行恰好一个算子** | 一个 **exchange iterator**，对上下算子**使用并提供标准 iterator 接口** |
| 谁控制执行 | 模板代码调用算子，**由算子控制执行**；网络 I/O 作为服务提供给算子 | 所有控制问题**局部化在 exchange 一个算子里** |
| 输入数上限 | ⭐ **最多 2 个活跃输入**（因为大多数系统只有一元和二元算子） | ⭐ **单个进程可以有任意多个输入** |
| 调度器 | ⭐ **每个控制点都要被创建，通常需要一个独立的 scheduler process**；每次扩展算子集都要额外开发软件 → **不适合可扩展系统** | ⭐ **不需要独立 scheduler**，调度（初始化、流控、最终清理）是算子的一部分，在标准 open-next-close 范式内完成 |
| 数据传递 | ⭐ **network I/O 是获取输入、交付输出的唯一手段**（scan/store 除外）→ **传一个数据项总要走昂贵的 IPC 系统调用，即使整个查询在单机上求值** | ⭐ **不要求算子用 IPC 交换数据** → **每个进程可以执行复杂查询计划的任意子树** |
| 加新算子 | 要**修改 scheduler 和 template process** 两个模块 | ⭐ **exchange 不需要任何修改** |
| 移植到新环境 | 要改**两个**模块（template process + scheduler） | ⭐ 只要改**一个**模块（exchange iterator） |

- ⭐ **反例佐证**：Wisconsin Benchmark 的三路连接 **"joinCselAselB"** 两次二路连接用**同一连接属性**，本不需要在节点间重分区；但 bracket model 里 **IPC 及其开销是强制的而非可选的**。
❌ **Trap:** *"In the bracket model a process template can run several operators concurrently."* —— 错，**任一时刻恰好一个**。

### 重点3 · Exchange 是一个 iterator（最容易被忽略却最爱考）⭐⭐
✅ **EN:** *"Notice that it is **an iterator with open, next, and close procedures**; therefore, it can be **inserted at any one place or at multiple places in a complex query tree**."*
💡 **中文：** 这一句是 exchange 全部威力的来源。因为它对上下都长得像普通 iterator：
- 上面的算子（消费者侧）以为自己在调普通 iterator 的 next；
- 下面的算子（生产者侧）以为自己被普通 iterator 驱动；
- **两边都不知道跨了进程边界。**
❌ **Trap:** *"The exchange module is a special scheduler process outside the operator tree."* —— **错，它就在算子树里，是个普通 iterator。**

### 重点4 · 三种并行的分类（必背表）⭐⭐
| 并行类型 | 定义 | 属于哪一大类 | 怎么实现 |
|:---|:---|:---|:---|
| **Vertical parallelism（垂直并行）** | **进程之间的 pipelining（流水线）** | **inter-operator（算子间）** | exchange 的 **open** 在共享内存里建 **port**，然后 **fork** 出子进程 |
| **Bushy parallelism（浓密树并行）** | **不同 CPU 执行复杂查询树的不同子树** | **inter-operator（算子间）** | 在查询树里插一两个 exchange。例：并行地排序 merge-join 的两个输入——父进程 fork 出产生第一路有序输入的子进程后**立即转向第二个 sort** |
| **Intra-operator parallelism（算子内并行）** | **多个 CPU 对一个数据集/中间结果的不同子集执行同一个算子** | **intra-operator（算子内）** | ⭐ **需要 data partitioning**：已存数据集用**多个文件（最好在不同设备上）**；中间结果用**一个 port 里的多个 queue**，每个消费者一个输入队列；生产者用 **support function** 决定记录进哪个队列 → **可实现 round-robin、key-range、hash 分区** |
| （第四种）**Inter-query parallelism（查询间并行）** | DBMS 并发处理多个查询 | — | ⭐ **当前版本的 Volcano 不支持** |

- **父子角色**：⭐ **父进程 = consumer（消费者），子进程 = producer（生产者）。** 子进程用 UNIX **fork** 创建，是父进程的**精确复制**，exchange 随后在父/子中走不同路径。
  - 消费者侧：`open_exchange` 建完子进程即完成；`next_exchange` **等数据经 port 到达，一次返回一条记录**；`close_exchange` 通知生产者可以关闭、等确认、返回。
  - 生产者侧：exchange 成为其下查询树的 **driver**，对输入调 open/next/close。
- **packets（包）**：next 的输出被收集进包（NEXT_RECORD 数组）。⭐ **packet size 是 exchange state record 里的参数，可设在 1 到 32,000 条记录之间。** 包满了就插进 port 的链表并用**信号量**通知消费者。**包中的记录被 fix 在共享缓冲区，必须由消费算子 unfix。**
❌ **Trap:** *"Bushy parallelism is a form of intra-operator parallelism."* —— **错**，bushy 和 vertical 都是 **inter-operator**。

### 重点5 · demand-driven ↔ data-driven 的范式转换（最核心考点）⭐⭐
✅ **EN:** *"While **all other modules are based on demand-driven dataflow (iterators, lazy evaluation)**, the producer-consumer relationship of exchange uses **data-driven dataflow (eager evaluation)**."*
💡 **两个原因（原文逐条）：**
1. **打算把 exchange 也用于 horizontal parallelism，而水平并行用 data-driven dataflow 更容易实现。**
2. ⭐ **该方案消除了 request messages（请求消息）的需要。** 带请求消息的方案（如用信号量）在共享内存机器上性能大概可接受，但**会造成不必要的控制开销和延迟**。作者相信极高并行度和高性能查询求值需要"共享内存机器的紧耦合网络（如 hypercube）"，故采用**已在 shared-nothing 数据库机上被证明有效**的数据交换范式。
- ⭐ **exchange 的封装里"包含了 demand-driven（进程内）与 data-driven（进程间）之间的转换"** —— 这是摘要就点明的贡献之一。
❌ **Trap:** *"All Volcano operators, including exchange, use demand-driven dataflow."* —— **错，exchange 是唯一的例外。**

### 重点6 · Flow Control / Back Pressure（流控/背压）⭐
✅ **EN:** *"A **run-time switch** of exchange enables **flow control** or **back pressure** using an additional semaphore. If the producer is significantly faster than the consumer, the producer may **pin a significant portion of the buffer**, thus impeding overall system performance."*
💡 **机制：** 启用后，**生产者向 port 插入新包后必须请求流控信号量；消费者从 port 取走一个包后释放流控信号量**。⭐ **流控信号量的初值（例如 4）决定了生产者可以领先消费者多少个包。**
- ⭐⭐ **flow control ≠ demand-driven dataflow（原文明确区分，极易混）：**
  1. **流控允许生产者与消费者在同步上有一些 "slack"（松弛），因而是真正的重叠执行**；而 **demand-driven dataflow 是相当刚性的请求-交付结构，消费者要等生产者产出下一个输出**。
  2. **data-driven dataflow 更容易与水平并行和分区高效结合。**
❌ **Trap:** *"Enabling flow control turns the exchange operator back into demand-driven dataflow."* —— **错**，这是原文专门澄清的一点。

### 重点7 · 进程创建与关闭（细节考点）
- **master / slave**：一组进程并行执行某算子（子树）时，其中一个是 **master**。查询树被 open 时只有一个进程在跑，它自然是 master；**master fork 出子进程时，子进程成为它那一组内的 master**。master producer 的**第一个动作是调用支持函数确定需要多少 slave**，若生产者操作要并行，再 fork 其余生产者进程。
- ⭐ **Gerber 指出集中式 fork 在高并行度下次优** → 改成 **propagation tree scheme（传播树方案）**后**观察到显著性能提升**：master fork 一个 slave，然后这两个各 fork 一个，然后四个各 fork 一个……（该方案在**二进制 hypercube 的广播通信与同步**中非常有效）。
- ⭐ **primed processes（预热进程）**：即使优化了 fork，开销仍不可忽略。作者考虑用"一直存在、等待工作包"的进程（**许多商业数据库系统在用**）；因为**编译代码（支持函数）的可移植分发不简单**，该改动被推迟。
- **fork 完后进程间无需进一步同步，两个例外**：(1) 访问**共享数据结构**（port、缓冲表）时要获取**持续一次链表插入时长的 short-term locks**；(2) 一个生产者组**同时也是消费者组**时（垂直流水线中至少两个 exchange、三个进程组），**这些进程要同步两次**，在很短的间隔中该组 master 创建一个服务全组的 port。
- **关闭**：close 请求向下传播到第一个 exchange 时，master consumer 的 `close_exchange` 用信号量通知所有生产者可以关闭；若生产者同时也是消费者，其组 master 再通知它的生产者……→ ⭐ **所有算子被有序关闭，整个查询求值是 self-scheduling（自调度）的。**
- **例子的数字**（4.3 节，A / BC / D 三组，A₀ 一个 + BC₀₋₂ 三个 + D₀₋₃ 四个 = **8 个进程**）：每个 D 进程中的 Y 给**每个 BC 进程**的最后一个包打 end-of-stream 标签 → 共 **3×4 = 12** 个打标包；**BC 中的 Y 收到 4 个标签**（= 生产者/D 进程数）后判定输入耗尽；**A₀ 中的 X 收到 3 个标签**（= BC 进程数）后向 A 指示 end-of-stream。

### 重点8 · Exchange 的三个变体
1. **replicate / broadcast（广播给所有消费者）**：动机是 **hash-division** 的一种分区方法要求**除数被复制**给被除数的每个分区；以及 **Baru 的并行连接算法**中一个关系不动、另一个送过所有处理器。⭐ **不需要拷贝记录**——它们驻留在共享缓冲池，**只要在缓冲池里多次 pin**，让每个消费者都能像自己是唯一使用者那样 unpin。**实现该特性后，并行化 hash-division 程序只花了约三小时。**
2. **merge 相关**：⭐ **与其他算子不同，merge iterator 需要按生产者区分输入记录**（join 不在乎输入记录在哪产生，所有输入可汇入单一流；**merge 必须区分才能正确归并多个有序流**）。为此 exchange 被改造成能**按生产者分开保存输入记录**，`next_exchange` 的**第三个参数**用于把所需生产者告诉 exchange。**merge iterator 由 sort 模块很容易派生**——它用**单层归并**而非 sort 的级联归并，**它的输入是一个 exchange**。这些改动支持**多级归并树**，**归并路径自动选择使每层负载尽量均匀**。
   - ⭐ **一个反直觉的发现**：并行排序实验中，处理器数 = 磁盘数时用**每 CPU 两个进程**（一个 scan+分区、一个 sort）→ **创建并运行"比处理器还多的进程"带来显著代价**，因为进程竞争 CPU 需要 OS 调度；在"中央运行队列允许进程自由迁移 + 每 CPU 带大 cache"的环境下，**频繁的 cache migration（缓存迁移）增加了显著成本**。
3. **exchange 位于算子树中间（不 fork 进程）**：为此把进程数**减半**，变成**每磁盘一个进程**。此模式下 exchange 被 open 时**不 fork 任何进程**，只建通信 port；**next 向输入树请求记录，可能把它们送给组内其他进程，直到找到属于自己分区的记录**。⭐ **这种模式还使 flow control 变得多余（obsolete）**：一个进程只有在"没有可给消费者的输入"时才运行生产者，所以若生产者有超跑消费者的危险，**没有任何生产者算子会被调度**。（**是否 fork 新进程是一个运行时开关。**）

### 重点9 · 性能数据（结论比数字更重要）
- **环境**：Sequent Symmetry，**12 颗 Intel 16 MHz 80386**，**shared-memory**，每 CPU **64 KB cache**、约 **4 MIPS**；**DYNIX** 操作系统**在所有处理器上执行系统调用**。
- **基线**：创建 100,000 条记录并释放 = **20.28 秒**；exchange 切到"不建进程"模式（每条记录多 3 次过程调用）= **28.00 秒** → ⭐ **每条记录每个 exchange 算子的开销 = 25.73 μsec**。
- ⭐ **exchange 真的建进程（4 进程流水线）：启用流控 16.21 秒，禁用流控 16.16 秒——都比单进程的 20.28 秒还短**，说明**用 exchange 做数据传输非常快，流水线式多进程执行是值得的**。
- **Table 1（包大小的影响）**：1 条/包 = **176.4 秒**，2 条 = **97.6 秒**（⭐ **几乎减半**），5 = 45.27，10 = 27.67，20 = 20.15，50 = **15.71**，100 = 13.76，200 = 12.87，250 = **12.73 秒**。
- **回归**：截距（基线时间）**12.18 秒**，斜率 **0.001654 秒/包**，相关性 **> 0.99**；考虑跨三个进程边界、其中两个边界上有 3 生产者 3 消费者 → 估计 **1654 μsec / 1.667 = 992 μsec 每包每进程边界**。
- ✅ **两个结论（原文）**：(1) **若数据传输开销小，即使对非常简单的查询计划，vertical parallelism 也能带来收益。** (2) **由于 packet size 可设为任意值，Volcano exchange iterator 的开销可以忽略不计。**
❌ **Trap:** *"Exchange adds significant overhead that must be traded against parallelism."* —— 错，**开销可忽略**（前提是包大小别设成 1）。

### 重点10 · 结论金句
✅ **EN:** *"**Volcano is the first implemented query evaluation system that combines extensibility and parallelism.** Encapsulating all parallelism issues into one module was essential to making this combination possible. The encapsulation of parallelism in Volcano allows for **new query processing algorithms to be coded for single-process execution but run in a highly parallel environment without modifications**."*
✅ **EN（六条优势，见重点2 表格 + 下面两条）:** *"(5) A single process can have **any number of inputs**, not just one or two. (6) The operator can be implemented in such a way that it can **multiplex a single process between a producer and a consumer** — in some respects, it efficiently implements application-specific **co-routines or threads**."*

# 📔 Paper 10 — Efficiently Compiling Efficient Query Plans for Modern Hardware（Neumann, VLDB 2011 / HyPer）

> **主旨**：内存变大后，查询性能越来越由**查询处理本身的原始 CPU 代价**决定。经典 iterator 模型简单灵活但在现代 CPU 上很差。本文提出**把查询编译成紧凑高效机器码**的策略，性能常常**媲美手写 C++**。

### 重点1 · 三条设计原则（论文自己列的，必背）⭐⭐
✅ **EN:**
1. *"**Processing is data centric and not operator centric.** Data is processed such that we can **keep it in CPU registers as long as possible**. **Operator boundaries are blurred** to achieve this goal."*
2. *"**Data is not pulled by operators but pushed towards the operators.** This results in much better **code and data locality**."*
3. *"Queries are compiled into **native machine code** using the optimizing **LLVM** compiler framework."*
💡 **中文口诀：数据中心（不是算子中心）、推（不是拉）、编译成机器码（不是解释）。**

### 重点2 · iterator 模型为什么在现代 CPU 上差（三条）⭐
✅ **EN:** *"(1) The **next** function will be called **for every single tuple** produced as intermediate or final result, i.e., **millions of times**. (2) The call to next is usually a **virtual call or a call via a function pointer** — even more expensive than a regular call and **degrades the branch prediction** of modern CPUs. (3) This model often results in **poor code locality and complex book-keeping**."*
💡 **中文（第 3 条的例子要记）**：一个对压缩关系的简单表扫描——因为元组必须**一次产出一条**，表扫描算子必须**记住当前元组在压缩流中的位置**，并在被要 next 时**跳到相应的解压代码**。
- ⭐ **iterator 模型来自"查询处理由 I/O 主导、CPU 消耗不重要"的年代。**
- **现有的补救及其代价**：
  - **block-oriented processing（块处理）**：一次 next 产出多条元组，摊薄调用成本 → ⭐ **但它消除了 iterator 模型的一大强项：pipelining（流水线）**。pipelining 指**算子能把数据传给父算子而不拷贝或以其他方式物化**。**产出多条元组时这种纯流水线一般用不了，因为元组必须被物化到某处才可访问。**
  - **物化的好处**是允许**向量化操作**，但**缺少流水线很不幸，因为它消耗更多内存带宽**。
  - **MonetDB 走到另一个极端：物化所有中间结果**，消除了反复调用输入算子的需要；简化了算子交互且有其他好处，但**代价显著**。
  - **MonetDB/X100（后来演化成 VectorWise）选了中间路线：传递大的数据向量、在每个 chunk 上向量化求值** → 性能优异，**但仍达不到手写代码的速度**。
- ⭐ **Figure 1 的观察**：*"a **hand-written program clearly outperforms even very fast vectorized systems**"*。作者说这在某种意义上是预料之中的（人能用 DBMS 永远想不到的技巧），**但图中的查询只是一个简单聚合查询（TPC-H Q1），本该只有一种合理的求值方式 → 现有查询求值方案显然是次优的。**
❌ **Trap:** *"Block-oriented processing preserves the pipelining advantage of the iterator model."* —— **错，正好牺牲了它。**

### 重点3 · Pipeline Breaker 的定义（比标准定义更严格）⭐⭐
✅ **EN:** *"We give a definition of pipeline-breaker that is **more restrictive than in standard database systems**: An algebraic operator is a **pipeline breaker** for a given input side if it **takes an incoming tuple out of the CPU registers**. It is a **full pipeline breaker** if it **materializes all incoming tuples from this side** before continuing processing."*
💡 **中文（务必和课本定义区分）：**
- **课本/标准定义**：pipeline breaker = 需要看完全部输入才能产出第一条输出的算子（sort、聚合）。
- ⭐ **Neumann 的定义把门槛降到"离开 CPU 寄存器"** —— 也就是说 **把数据溢出到内存就算破坏流水线**。
- 作者也承认这个定义"略显含糊"（单条元组可能就大到装不下寄存器），但**要点就是：把数据溢出到内存视为破坏流水线的操作；查询处理期间，所有数据都应尽可能久地留在 CPU 寄存器里。**
- ⭐ **由此推出的批判**：*"any iterator-style processing paradigm that **pulls** data up from the input operators **risks breaking the pipeline**, as, by offering an iterator-based view, it has to offer a **linearized access interface** to the output of an arbitrarily complex relational operator."*
❌ **Trap:** *"Under Neumann's definition, a selection operator is a pipeline breaker."* —— 错，**selection 是流水线算子**（元组留在寄存器里）。

### 重点4 · Push 模型与执行的组织方式 ⭐
✅ **EN:** *"Instead of pulling tuples up, we **push them towards the consumer operators**. While pushing tuples, we **continue pushing until we reach the next pipeline-breaker**. As a consequence, **data is always pushed from one pipeline-breaker into another pipeline-breaker.** Operators in-between leave the tuples in CPU registers and are therefore very cheap to compute."*
💡 **中文（两个额外好处）：**
- **在 push 架构里，复杂的控制流逻辑往往在紧循环之外，这降低了寄存器压力。**
- **因为典型的 pipeline breaker 本来就要物化元组，所以生成的执行计划把内存访问次数降到最少。**
- ⭐ **运行例子（Figure 2–4）必须能复述**：查询 `select * from R1, R3, (select R2.z, count(*) from R2 where R2.y=3 group by R2.z) R2 where R1.x=7 and R1.a=R3.b and R2.z=R3.c`，编译后的伪代码是**四个片段**：
  1. `for each tuple t in R1: if t.x=7 → materialize t in hash table of ⋈_{a=b}`
  2. `for each tuple t in R2: if t.y=3 → aggregate t in hash table of Γ_z`
  3. `for each tuple t in Γ_z → materialize t in hash table of ⋈_{z=c}`
  4. `for each tuple t3 in R3: for each match t2 in ⋈_{z=c}[t3.c]: for each match t1 in ⋈_{a=b}[t3.b]: output t1∘t2∘t3`
  - ⭐ **四个片段各自强流水线**：只在"取新元组"或"物化结果"时访问内存；**代码局部性极好，小的代码片段在紧循环里处理大量数据**。

### 重点5 · produce / consume 接口（"只是心智模型"）⭐
✅ **EN:** *"Conceptually each operator offers two functions: **produce()** and **consume(attributes, source)**. … However, **this produce/consume interface is only a mental model. These functions do not exist explicitly**, they are only used by the code generation."*
💡 **中文（流程）：** 调 ⋈_{a=b}.produce → 它调 σ_{x=7}.produce 去填哈希表 → σ 调 R1.produce → R1 是叶子，扫描关系，对每条元组加载所需属性并调 `σ_{x=7}.consume(attributes, R1)` → σ 过滤，通过则调 `⋈_{a=b}.consume(attributes, σ)` → join 看到元组来自左侧，于是存进哈希表 → R1 的元组产完后控制流回到 join，join 调 ⋈_{c=z}.produce 拿探测侧的元组……
- ⭐ **编译时机**：SQL 查询**照常**被解析、翻译成代数、代数表达式被优化；**只有在这之后才偏离标准方案**——最终代数计划**不是被翻译成可执行的物理代数，而是被编译成一个命令式程序**，而**只有这个编译步骤在内部使用 produce/consume 接口**。
- ⭐ **算子边界模糊是优势不是限制**：*"It is important to note that this is **an advantage, not a limitation** of the approach! The iterator model has a nice, simple interface, but it pays for this by using **virtual function calls and frequent memory accesses**. By exposing the operator structure, we can generate **near optimal assembly code**."* 需要的抽象**只存在于查询编译器里**；生成的代码暴露所有细节（为了效率），**但这没关系，因为代码反正是生成的**。
- **代码片段结构很不规则**：例如二元 pipeline breaker 物化左侧输入与物化右侧输入非常不同。**在 iterator 模型里一切都是一个简单的 next 调用；这里复杂的算子逻辑直接影响代码生成。**
❌ **Trap:** *"HyPer's operators implement produce() and consume() as virtual methods at runtime."* —— **错，它们不存在，只用于代码生成。**

### 重点6 · 为什么用 LLVM 而不是 C++ ⭐⭐
✅ **EN:** *"First, an optimizing **C++ compiler is really slow** — compiling a complex query could take **multiple seconds**. Second, **C++ does not offer total control over the generated code**, which can lead to suboptimal performance; in particular, **overflow flags etc. are unavailable**."*
✅ **EN（LLVM 的好处）:** *"LLVM **hides the problem of register allocation** by offering an **unbounded number of registers** (albeit in **Single Static Assignment (SSA)** form) … the LLVM assembler is **portable across machine architectures** … the LLVM assembler is **strongly typed**, which caught many bugs … and LLVM is a **full strength optimizing compiler** which usually requires only a **few milliseconds** for query compilation."*
💡 **中文：** 所以可以**假装每个元组属性都有一个 CPU 寄存器**，大大简化生活。
- ⭐ **混合执行模型（Figure 6 的齿轮/链条比喻，很爱考）：**
  - **C++ 是"齿轮（cogwheels）"**：复杂部分（复杂数据结构管理、溢出到磁盘、索引结构）用 C++ 写，**预编译好**。
  - **LLVM 是"链条（chain）"**：把不同算子连接起来的代码是**动态生成**的 LLVM。
  - **两者能直接互相调用**（C++ 方法可从 LLVM 直接调，反之亦然；对编译器来说没区别——都产生本地机器码，都有强类型原型），**没有性能惩罚，也不需要额外的 wrapper**。
- ⭐⭐ **黄金法则**：*"For optimal performance it is important that **the hot path, i.e., the code that is executed for 99% of the tuples, is pure LLVM**. Calling C++ from time to time (e.g., when switching to a new page) is fine … but the bulk of the processing has to be done in LLVM."* **调外部函数时所有寄存器都要溢出到内存**——绝对值上很便宜（溢到栈上，通常在 cache 里），**但做几百万次就明显了**。
- ⭐ **为什么不把整个查询编译成一个函数（两个理由）**：
  1. **务实的理由**：LLVM 代码某处很可能调 C++ 代码，由后者接管控制流（如外部排序算子用 LLVM 产生初始归并段，但归并阶段大概从 C++ 控制）。
  2. ⭐ **把完整查询逻辑内联进一个函数会导致代码指数增长**。例如**外连接会在两种情形下调用其消费者**（找到匹配时、产生 NULL 值时）；若两处都直接包含消费者代码，**一串外连接就会导致代码指数增长**。因此要**在 LLVM 内部定义函数**。**同样要保证 hot path 不跨越函数边界**——**一个流水线片段应该产生一段紧凑的 LLVM 代码。**

### 重点7 · 性能调优的两个瓶颈（哈希 + 分支）⭐
✅ **EN（哈希）:** *"For TPC-H Query 1 … more than **50% of the time of our initial plan was spent on hashing**, even though we only hash two simple values."*
✅ **EN（分支）:** *"On modern CPUs, branches are **very cheap as long as the branch prediction works**, i.e., as long as the branches are taken either **nearly never or nearly always**. A branch that is taken with a probability of **50%** however **ruins the branch prediction and is very expensive**."*
💡 **中文（必背的代码改写例子）：**
```c
// ❌ 预测不友好：while 混了两件事
Entry* iter = hashTable[hash];
while (iter) { ... ; iter = iter->next; }

// ✅ 预测友好：拆成"存不存在"（几乎总为真）和"到没到链尾"（几乎总为假）
Entry* iter = hashTable[hash];
if (iter) do { ... ; iter = iter->next; } while (iter);
```
⭐ **原因**：第一种把两件事混了——**"这个哈希值到底有没有条目"（因为哈希表是填满的，几乎总为真）** 和 **"是否到了冲突链末尾"（因为冲突链很短，几乎总为假）**。⭐ **实验中仅仅改变分支结构就把哈希表查找改善了 20% 以上。**
- **其他调优规则**：所有元组属性放在（虚拟）CPU 寄存器；**字符串保存"长度 + 指向字符串的指针"两个寄存器**；⭐ **尽可能晚地加载属性**——要用它的那一刻，或因为反正要访问对应内存而免费拿到时；但**当这些值在关键路径上时（如用哈希值访问哈希表），提早一点计算以隐藏计算延迟是有意义的**。
- **代码生成器的规模**：*"the code generation for all algebraic operators required for **SQL-92** consists of about **11,000 lines of code**, which is **not a lot**."*
❌ **Trap:** *"Branches should be minimized because every branch is expensive."* —— **半真半假**：分支预测有效时**非常便宜**；真正贵的是 **50% 概率的分支**。

### 重点8 · 并行化（SIMD + 多核）
✅ **EN:** *"Traditional **block-wise processing** has the great disadvantage of **creating additional memory accesses**. However, processing more than one tuple at once is indeed a very good idea, **as long as we can keep the whole block in registers** — in particular when using **SIMD registers** this is often the case."*
💡 **中文（一次处理多条元组的两个好处）：**
1. 能用现代 CPU 的 **SIMD 指令**，大幅加速；
2. ⭐ **能延迟分支**——谓词可以**先求值再组合，不必立刻执行分支**。
- ⭐ **这种"把值打包进（大）寄存器"的块处理天然契合本框架**，因为算子总是**把寄存器值传给消费者**；**LLVM 直接允许把 SIMD 值建模为 vector 类型**，因此对整体代码生成框架的影响相对很小。
- **两种并行的分类**：⭐ **SIMD 是一种 inter-tuple parallelism（元组间并行）**，即一条指令处理多条元组；**第二种与现代 CPU 相关的是 multi-core processing（多核）**。
- **多核**：几乎所有数据库系统都会用多核做 **inter-query parallelism（查询间并行）**；但核数增加后 **intra-query parallelism（查询内并行）**变得更重要。原则上这是研究得很透的问题，通常靠**分区算子的输入、独立处理每个分区、再合并各分区结果**解决。
- ⭐ **对本代码生成框架，这种并行几乎不需要代码改动**：代码**总是在数据片段（fragments）上操作，在紧循环里处理并物化进下一个 pipeline breaker**。通常片段由存储系统决定，**但它们同样可以来自一个并行化决策**，只需一些额外逻辑合并各自的结果。
- ⭐ **但作者提醒**：*"the **'parallelizing decision' in itself is a difficult problem**! **Splitting and merging data streams is expensive**, and the optimizer has to be careful about introducing parallelism. This is beyond the scope of this paper."*

### 重点9 · 实验结果（数字要有印象）
**OLTP（Table 1，TPC-C，12 warehouses，单线程无客户等待）：**
| | HyPer + C++ | HyPer + LLVM |
|:---|---:|---:|
| TPC-C [tps] | 161,794 | **169,491** |
| total compile time [s] | 16.53 | **0.81** |
- ⭐ **性能差别很小**（多数 TPC-C 事务简单、触碰 < 30 条元组），**但编译时间差了 10 倍以上，且 C++ 版性能还（略）差——这是本文编译技术的有力论据**。

**OLAP（Table 2，TPC-CH 查询，预备语句，热执行时间，单位 ms）：**
| | Q1 | Q2 | Q3 | Q4 | Q5 |
|:---|---:|---:|---:|---:|---:|
| **HyPer + C++** | 142 | 374 | 141 | 203 | 1416 |
| *（编译时间）* | *1556* | *2367* | *1976* | *2214* | *2592* |

- **DB X 明显更慢不奇怪**（通用的基于磁盘的系统，尽管这里数据在内存且测热执行时间）。**HyPer + LLVM 常比其他系统再快 2–4 倍**。
- ⭐ **C++ 后端 vs LLVM 后端的对比最有意思**：C++ 版本相当快，**但 LLVM 生成的紧凑代码显著更快**。**Q5 由 join 主导，差别不那么明显；但其他查询、尤其是聚合查询 Q1，差别很大**——Q1 原则上非常简单（一个扫描 + 一个聚合），**对应的 C++ 代码看上去非常自然高效，但就是竞争不过"尽力把一切留在寄存器里"的 LLVM 版本**。

**代码质量（Table 3，callgrind/valgrind 二进制插桩，LLVM vs MonetDB）：**
- ⭐ **分支数**：LLVM 版**远少于** MonetDB（如 Q5：1140 万 vs 3.34 亿）。**不奇怪——我们试图把"直到下一个 pipeline breaker"的所有代码生成为一段线性代码片段。**
- ⭐ **分支误预测**：LLVM 显著更低（Q5：**639** vs 672 万）。**唯一的例外是 Q2**，但这是 HyPer 的次优行为而非 LLVM 的问题（**HyPer 当前对溢出到磁盘非常悲观，大量拷贝字符串，造成 60% 以上的误预测；MonetDB 避免了这些拷贝**）。**有趣的是 MonetDB 的相对误预测率相当好**（符合其架构预期），**但它执行的分支总数太多，因此误预测也多**。
- ⭐ **cache**：多数查询 D1 和 L2d 数字非常接近，意味着**数据若不在 L1 大概也不在 L2**——**对非常大的哈希表这是预期行为**。LLVM 的 cache miss 比 MonetDB 少**最多 10 倍**。
- ⭐ **指令数**：LLVM 生成的代码**紧凑得多**（Q5：1.59 亿 vs 20.89 亿）。**某种程度上这源于 MonetDB 总是在 BAT（Binary Association Tables）上操作，因此必须多次触碰元组。**

### 重点10 · 结论
✅ **EN:** *"By compiling queries into machine code using the optimizing LLVM compiler, the DBMS can achieve a query processing efficiency that **rivals hand-written C++ code**. … By relying on **mainstream compilation frameworks**, the DBMS **automatically benefits from future compiler and processor improvements without re-engineering the query engine**."*
💡 **中文（最后一句是与"把优化塞进查询引擎自己"路线的关键对比）：** 用成熟编译框架，**未来编译器、代码优化和硬件的改进你都白拿**；而**把处理优化集成进查询引擎自身的路线，必须手工更新自己的系统**。

# 📒 Paper 11 — Vectorwise: Beyond Column Stores（Zukowski & Boncz, IEEE Data Eng. Bull. 2012）

> **主旨（标题即结论）**：**"Beyond Column Stores" —— 高性能远远不只是列存。**
> ✅ **EN（核心 take-away）:** *"The **novelty in Vectorwise is much more than just column-storage**: it boasts many query processing innovations in its **vectorized execution model**, and an **adaptive mixed row/column data storage model with indexing support** tailored to analytical workloads."*
> ✅ **EN（另一个 take-away）:** *"There is a **long road from research prototype to commercial product**, though database research continues to achieve a strong innovative influence on product development."*

### 重点1 · 血统与架构分层（爱考"哪部分来自哪里"）
- **时间线**：2003 年 CWI（以 **MonetDB** 项目闻名）的一组研究者发明了新的查询处理模型 → 成为 **X100 项目**的基础 → 2008 年 CWI 剥离该项目成立 **Vectorwise BV** → 与 Actian 的 **Ingres** 结合 → 两年后交付集成产品 → Vectorwise 被收购成为 **Actian** 的一部分。**Vectorwise 1.0 于 2010 年 6 月发布，2.0 于 2011 年 11 月发布。**
- ⭐ **架构分层**：
  - **上层来自 Ingres**：数据库管理工具、连接 API、**SQL 解析**、**基于直方图统计的基于代价的查询优化器**。
  - **下层来自 X100**：**尖端的查询执行与数据存储**。
❌ **Trap:** *"Vectorwise's query optimizer was developed as part of the X100 project."* —— 错，**优化器来自 Ingres 上层**。

### 重点2 · 存储：基于 PAX 的广义行/列存储 ⭐⭐
✅ **EN:** *"Vectorwise stores data using a **generalized row/column storage based on PAX**. A table is stored in **multiple PAX partitions, each of which contains a group of columns**. This allows providing both **'DSM/PAX'** (each column in a separate PAX group) and **'NSM/PAX'** (all columns in one PAX group), **as well as all options in between**."*
💡 **中文（这是"不只是列存"的第一层含义）：**
- 从 **IO 角度**定义：**只含一个列数据的磁盘块叫 DSM/PAX，含所有列的叫 NSM/PAX**（后者就是 [Ailamaki] 论文里说的 PAX）。
- **分组可以用 DDL 显式控制，没写就自调优（self-tuned）。**
- ⭐ **三条自动 PAX 策略（很爱考的细节）：**
  1. **nullable 列**：Vectorwise 内部把可空列表示成**一个装值的列 + 一个标记是否为 NULL 的布尔列**。**动机是查询处理效率**——逐元组测 NULL 会因**难以预测的分支指令**拖慢谓词求值，而且 **NULL 的存在妨碍使用 SIMD 指令**。很多时候 NULL 测试可以跳过、查询可以完全忽略 NULL 列，所以分开表示有意义。**每个可空属性把值列和 NULL 列放在同一个 PAX 分区。**
  2. **复合（多列）主键自动放在同一分区。**
  3. ⭐ **小表用 NSM/PAX（单个 PAX 分区）**，因为 DSM 表示会**每列一个（几乎）空的磁盘块，浪费大量空间**。**这种空块开销在 Vectorwise 里比传统系统更高，因为 Vectorwise 用相对大的块——磁盘上通常 512KB，SSD 上 32KB。**
  4. **超宽表用更高级的 PAX 分组算法**自动把某些列聚在一起。⭐ **限制 PAX 组数量的理由在于表扫描所需的缓冲内存**：每个 PAX 组、每个物理磁盘设备、每个 PAX 分区，扫描都要分配多个块；**实践中最宽的表（数百列）否则会导致单次扫描就需要好几 GB。**
❌ **Trap:** *"Vectorwise stores every column in its own PAX partition (pure DSM)."* —— **错**，是**自适应的混合**，从纯 DSM 到纯 NSM 连续可调。

### 重点3 · 压缩（"不做压缩执行"的理由，后来又部分做了）⭐
✅ **EN:** *"Vectorwise **only uses compression schemes that allow very high decompression ratios, with a cost of only a few cycles per tuple**. Thanks to the very low overhead of decompression, it is possible to **store data compressed in buffer pool and decompress immediately before query processing**. This allows **increasing the effective size of the buffer pool**, further reducing the need for IO."*
💡 **中文：** 压缩方案与参数都是**自动选择、自动调优**的。
- ⭐ **为什么最初刻意不做 compressed execution（在压缩数据上直接算）**：*"it can **complicate the query executor**, and our **extremely high decompression speed and fast vectorized execution limits the benefit** of compressed execution in many common cases."*
- ⭐ **后来又做了简单形式，因为有些情形收益极高**：
  - **在 RLE 上做聚合**（可以少一个数量级的工作量）；
  - **对字典压缩的字符串做操作**（把字符串比较变成**便宜得多的整数比较甚至 SIMD 比较**）。
❌ **Trap:** *"Vectorwise decompresses data when reading it from disk into the buffer pool."* —— **错**，**数据在缓冲池里保持压缩**，**查询处理前一刻才解压**。

### 重点4 · 索引：一个 clustered index + MinMax ⭐
✅ **EN（clustered index）:** *"Vectorwise allows users in its DDL to declare **one index per table**; this simply means that the **physical tuple order becomes determined by the index keys** rather than insertion order. As Vectorwise keeps a **single copy of all data**, only one such index declaration is allowed per table."*
- **主要好处是把索引键上的范围谓词下推（push-down of range-predicates）。**
- ⭐ **索引建在外键上时处理特殊**：**元组顺序从被引用表派生**，这**加速了这两张表之间的外键连接**。
- **未来方向**：多维索引，让表在多个维度上**共聚簇（co-clustered）**，加速多种选择谓词以及共聚簇表之间的外键连接。

✅ **EN（MinMax）:** *"Vectorwise automatically keeps so-called **MinMax indices on all columns**. MinMax indices, based on the idea of **small materialized aggregates**, store **simple metadata about the values in a given range of records, such as Min and Max values**. They allow **quick elimination of ranges of records** during scan operations."*
- ⭐ **MinMax 在查询重写（query rewriting）阶段被大量参考**；**只有当属性值与元组位置之间存在相关性时才能有效消除 IO**。
- ⭐ **数据仓库里事实表的顺序常与时间相关，所以日期/时间列通常存在这种相关性**；**用有序表（clustered index）是"位置与列键值相关"的直接来源**。
- **重写器（rewriter）会用 MinMax 索引，对任何位置相关的列，用范围选择去限制表扫描。**
❌ **Trap:** *"Vectorwise supports multiple secondary B-tree indexes per table."* —— **错，每表只有一个（clustered），另加所有列上自动的 MinMax。**

### 重点5 · Cooperative Scans / ABM（提出了但产品里换掉了）⭐
✅ **EN:** *"The X100 project originally proposed **cooperative scans**, where table scans **accept data out-of-order**, and an **Active Buffer Manager (ABM)** determines the order to fetch tuples **at runtime, depending on the interest of all concurrent queries**, optimizing both average query latency and throughput. The **ABM is a quite complex component** that influences the system architecture considerably, such that **in the product version we have switched to a less radical, but still highly effective variant of intelligent data buffering**."*
💡 **中文：** IO 与缓冲池层的目标是**为并发的扫描密集型查询（分析负载的典型）提供最优性能**。cooperative scans 的思路是让多个并发扫描**共享 IO**——但 ABM 太复杂、对系统架构影响太大，**产品里换成了不那么激进但同样有效的"智能数据缓冲"**。
❌ **Trap:** *"The Active Buffer Manager is a core component of the shipping Vectorwise product."* —— **错，产品里换掉了。**

### 重点6 · 更新：Positional Delta Trees（PDT）⭐⭐
✅ **EN:** *"High-performance updates use a **differential update mechanism based on Positional Delta Trees (PDT)**. A **three-level design** — one **very small PDT private to the transaction**, one **shared CPU-cache resident PDT**, and one potentially large **RAM-resident PDT** — offers **snapshot isolation without slowing down read-only queries in any way**."*
✅ **EN（PDT 的关键特性）:** *"The crucial feature of PDTs as differential structure is that they **organize differences by position rather than by key value**, and therefore **the task of merging in differences during a table scan has virtually no cost**, as it **does not involve costly key comparisons (nor key scans)**."*
💡 **中文：** 这是与 C-Store WS/RS 的直接对比点——**都是"差分/两层"思想，但组织差分的维度不同**：
| | C-Store | Vectorwise |
|:---|:---|:---|
| 差分结构 | **WS（写优化列存 + B-tree，按 storage key / sort key 组织）** | **PDT（按位置组织）** |
| 合并时机 | **tuple mover 后台批量 merge-out（MOP）** | **扫描时即时合并** |
| 合并代价 | 批量重写 RS 段 | ⭐ **几乎为零**（无键比较、无键扫描） |
| 层数 | 两层（WS / RS） | ⭐ **三层 PDT**（事务私有的极小 / 共享的 CPU-cache 常驻 / 可能很大的 RAM 常驻） |
❌ **Trap:** *"PDTs organize differences by key value, like a B-tree delta."* —— **错，by position（按位置）是关键。**

### 重点7 · 向量化执行模型及其演进 ⭐⭐
✅ **EN:** *"The core technology behind the high processing speeds is its **vectorized processing model**. It **dramatically reduces the interpretation overhead** typically found in **tuple-at-a-time** processing systems. Additionally, it **exposes possibilities of exploiting performance-critical features of modern CPUs like super-scalar execution and SIMD instructions**. Finally, thanks to its focus on **storing data in the CPU cache**, **main-memory traffic is reduced**, which is especially important in modern multi-core systems."*
💡 **中文（三个好处逐条：解释开销↓、超标量+SIMD、内存流量↓）。**
- ⭐ **后续改进（四条编号 + 三条补充，爱考"哪一条是 Vectorwise 做的"）：**
  1. **lazy vectorized expression evaluation（惰性向量化表达式求值）**；
  2. **根据环境选择不同的函数实现**；
  3. ⭐ **把 selection 往上推（pushing UP selections），如果这能启用更多的 SIMD 谓词求值**（⚠️ **注意方向：是"上推"不是常规优化里的"下推"**）；
  4. **NULL 处理优化**。
  - ⭐ **补充 A（很重要）**：*"strict adherence to a **vertical (columnar) layout in all operations was dropped**, and now Vectorwise **uses an NSM record layout during the execution** for (parts of) tuples where the access pattern makes this more beneficial (**mostly in hash tables**)."* —— **执行期也不是纯列式了。**
  - **补充 B**：加入了 ⭐ **基于 exchange 算子的 Volcano 式并行**，让 Vectorwise 能高效扩展到多核。
  - **补充 C**：许多内部操作被改进，例如**用高效的 Bloom filter 加速连接处理**；与 **Intel 合作**使用新 CPU 特性如**大 TLB 页**、用 **SSE4.2 指令**优化文本数据处理。
- ⭐ **执行路线图（roadmap）**：**在压缩数据上执行**；以及 ⭐ **智能地使用 JIT（just-in-time）编译复杂谓词——只在真正比向量化执行更划算的情形下用**。（**注意这个措辞：不是"用 JIT 取代向量化"，而是"选择性地混合"** —— 正好与 P10 的编译路线形成对照。）另有引入 **MPP 集群能力**的项目在进行中，使 Vectorwise 可用于 scale-out 架构。
❌ **Trap:** *"Vectorwise plans to replace vectorized execution with JIT compilation."* —— **错，是"只在有收益的情形下"选择性使用。**

### 重点8 · 客户反应与采用挑战（软性内容，可能出"以下哪项不是"）
- ⭐ **性能太好导致的误会**：*"In a number of cases, the improvement was so large **customers believed the system must be doing some sort of query result caching (which it does not)**."*
- ⭐ **高性能让客户采用了以前不可能的做法（五条，注意 2 和 3 是相反的）：**
  1. **Removing indices（去掉索引）**——高效的内存和磁盘扫描性能 + 优化的过滤，比以前用索引还快；
  2. **Normalizing tables（规范化）**——快速数据变换让大批量规范化成为可能，提升性能并减少存储量；
  3. ⭐ **De-normalizing tables（反规范化）**——**与上一条相反**：有些用户觉得反规范化表的性能绰绰有余，**因为 schema 更简单、装载更容易**而更喜欢这种方式；
  4. **Running on the raw data（直接在原始数据上跑）**——避免昂贵的数据预计算；
  5. **Full data reloads（全量重载）**——高装载性能让"全量重载"成为可行方法。
- **采用挑战**：
  - **离线数据迁移相对容易**（手工或 ETL 工具）；**从事务系统在线传输数据挑战更大**；**不同 SQL 方言 + 大量非标准函数的迁移相对简单但费力**；⭐ **最难的问题是存在 DBMS 里的应用逻辑（如 PL/SQL）——从使用这种方式的复杂系统迁移极其耗人力**。
  - ⭐ **设计假设被打破**：Vectorwise 最初设计时假设**数据装载相对少**；但用户习惯了高处理速度后，要求在**更新鲜的数据**上用，**包括亚秒级的数据装载延迟**。为此 Vectorwise 迅速改进了**增量装载与数据更新能力，并提供完整 ACID 属性**；Actian 另外提供 **Vectorstream**——一个使超低延迟数据装载进 Vectorwise 的独立产品/服务。
  - **复杂数据库 schema**：数百个数据库、数千张表、数千个属性的场景对系统能力构成压力，需要 schema 重组和大量系统改进。
- **生态与认证**：与 Pentaho、Jaspersoft、SAP Business Objects、MicroStrategy、IBM Cognos、Tableau、Yellowfin 认证；发布了功能完整的 **Windows 版本**，成为**极少数支持该平台的分析型 DBMS 之一**。
- **基准成绩**：截至 **2012 年 3 月 18 日，Vectorwise 保持单节点 100GB 到 1TB TPC-H 的领先地位**（Figure 2 的 1TB 结果：Vectorwise 2011-05-03，32 核 1TB RAM，**436,788 QphH，$0.88/QphH**——是图中最高吞吐和最低单价）。
- **研究项目**：向学术机构提供源码研究许可（CWI、Ilmenau、Tübingen、Edinburgh 大学、巴塞罗那超算中心）；Actian 资助博士生；与阿姆斯特丹自由大学、华沙大学合作的硕士项目已完成的题目包括：**Volcano 式多核并行**、**谓词的 JIT 编译**、**压缩数据上执行的非侵入式机制**、**中间结果的物化与缓存（把 Recycler 思想用于流水线执行）**、**让并发查询协作而非争抢 IO 的缓冲管理策略**（比所谓 Cooperative Scans 更少侵入系统）、以及 **XML 存储与处理**。

# 📚 Paper 12 — C-Store: A Column-oriented DBMS（Stonebraker 等, VLDB 2005）⭐⭐

> **主旨（摘要第一句）**：*"This paper presents the design of a **read-optimized** relational DBMS that **contrasts sharply with most current systems, which are write-optimized**."*
> **一句话记住定位**：行存 = **write-optimized**（一次磁盘写就把一条记录所有字段推出去，OLTP 特别有效）；C-Store = **read-optimized**（面向大量数据的即席查询）。

### 重点0 · 六大创新（论文自己列的清单，最可能整段考）⭐⭐
✅ **EN:**
1. *"A **hybrid architecture** with a **WS** component optimized for frequent insert and update and an **RS** component optimized for query performance."*
2. *"**Redundant storage** of elements of a table in several **overlapping projections in different orders**, so that a query can be solved using **the most advantageous projection**."*
3. *"**Heavily compressed columns** using one of several coding schemes."*
4. *"A **column-oriented optimizer and executor**, with **different primitives** than in a row-oriented system."*
5. *"**High availability and improved performance through K-safety** using a sufficient number of overlapping projections."*
6. *"The use of **snapshot isolation to avoid 2PC and locking for queries**."*
- ⭐ **作者的自我定位（爱考的谦逊句）**：*"while many of these topics have parallels with things that have been **studied in isolation** in the past, it is **their combination in a real system** that makes C-Store interesting and unique."*
- **结论里的清单（措辞略不同，也要认）**：列存表示 + 配套执行引擎；允许在列存上做事务的**混合架构**；通过**编码数据值和 dense-packing** 节省磁盘存储表示；**由表的重叠 projection 组成的数据模型**（不同于"表 + 二级索引 + 投影"的标准套餐）；为 **shared nothing** 环境优化的设计；⭐ **没有 redo log、没有两阶段提交的分布式事务**；**高效的快照隔离**。

### 重点1 · 用 CPU 换磁盘带宽（贯穿全文的经济学）⭐
✅ **EN:** *"**CPUs are getting faster at a much greater rate than disk bandwidth is increasing.** Hence, it makes sense to **trade CPU cycles, which are abundant, for disk bandwidth, which is not.** This tradeoff appears especially profitable in a **read-mostly** environment."*
💡 **中文（列存用 CPU 换带宽的两种方式，原文明确的"two ways"）：**
1. ⭐ **coding（编码）**：把数据元素编码成更紧凑的形式。**必背例子**：存"客户居住的州"，**美国的州可以编码成 6 bit**，而两字符缩写要 **16 bit**，州名的变长字符串要多得多。
2. ⭐ **densepack（密集打包）**：*"in a column store it is straightforward to **pack N values, each K bits long, into N × K bits**."*（行存要按字节/字边界补齐 padding。）
- ⭐ 并且：*"it is also desirable to have the **DBMS query executor operate on the compressed representation whenever possible** to avoid the cost of decompression, **at least until values need to be presented to an application**."*
- ⭐ **传统关系 DBMS 的做法正好相反**：*"Current relational DBMSs were designed to **pad attributes to byte or word boundaries** and to **store values in their native data format**. It was thought that it was too expensive to shift data values onto byte or word boundaries in main memory for processing."*（**这个"曾经认为"现在被 CPU/磁盘的速度差反转了。**）
❌ **Trap:** *"C-Store decompresses all columns before query execution to keep the executor simple."* —— **错**，尽可能在压缩表示上直接算。

### 重点2 · Projection = 物理存储单位（office hour 已考）⭐⭐
✅ **EN:** *"C-Store supports the **standard relational logical data model** … **Data in C-Store is not physically stored using this logical data model.** Whereas most row stores implement physical tables directly and then add various indexes to speed access, **C-Store implements only projections.**"*
💡 **中文（定义要背准，四个要点）：**
1. **anchored（锚定）**：一个 C-Store projection **锚定在一张给定的逻辑表 T 上**，含 T 的**一个或多个属性**。
2. ⭐ **可含其他表的列**：*"a projection can contain **any number of other attributes from other tables**, as long as there is a **sequence of n:1 (i.e., foreign key) relationships** from the anchor table to the table containing an attribute."*
3. **构造方式**：从 T 投影出感兴趣的属性，**保留任何重复行**，再做相应的**基于值的外键连接**取来非锚定表的属性。⭐ **因此一个 projection 与其锚定表有相同的行数。**
4. ⭐ **术语警告（原文自己提醒）**：*"we use the term projection **slightly differently than is common practice**, as we **do not store the base table(s) from which the projection is derived**."*（**底下没有基表！**）
- **记法**：第 i 个 projection 写作 tᵢ 后跟字段名；来自其他表的属性**前缀该逻辑表名**；**排序顺序用竖线 `|` 追加在后面**。
- ⭐ **必背例子**（EMP(name, age, salary, dept)、DEPT(dname, floor)）：
  ```
  EMP1 (name, age | age)
  EMP2 (dept, age, DEPT.floor | DEPT.floor)
  EMP3 (name, salary | salary)
  DEPT1(dname, floor | floor)
  ```
  注意 **EMP2 里的 DEPT.floor 就是"通过外键连过来的其他表的列"**。
- **列式存储**：*"Tuples in a projection are **stored column-wise**. Hence, if there are K attributes in a projection, there will be **K data structures, each storing a single column, each of which is sorted on the same sort key**."* ⭐ **sort key 可以是 projection 中的任意一列或多列；元组按 key 从左到右的顺序排序。**
- **segment（段）**：*"every projection is **horizontally partitioned into 1 or more segments**, which are given a segment identifier, **Sid > 0**."* ⭐ **C-Store 只支持在 projection 的 sort key 上做基于值的分区**；每个段关联该 projection sort key 的一个键范围，**所有键范围的集合划分整个键空间**。
- ⭐ **covering set（覆盖集合）**：*"to answer any SQL query in C-Store, there must be a **covering set of projections** for every table in the database such that **every column in every table is stored in at least one projection**."*
❌ **Trap:** *"A projection in C-Store may contain arbitrary joins between tables."* —— 错，只允许**从锚定表出发的 n:1（外键）关系序列**。
❌ **Trap:** *"C-Store stores base tables plus projections."* —— **错，只存 projection。**

### 重点3 · Storage Keys 与 Join Indices（怎么把元组拼回来）⭐⭐
✅ **EN（Storage Keys）:** *"Each segment associates every data value of every column with a **storage key, SK**. Values from different columns in the same segment with **matching storage keys belong to the same logical row**. Storage keys are numbered 1, 2, 3, … **in RS and are not physically stored, but are inferred from a tuple's physical position** in the column. Storage keys are **physically present in WS** and are represented as integers **larger than the largest integer storage key for any segment in RS**."*
💡 **中文（RS vs WS 的关键差别之一）：**
| | RS | WS |
|:---|:---|:---|
| storage key | ⭐ **不物理存储**，从元组在列中的**物理位置（序号）推算** | ⭐ **显式物理存储**，是整数 |
| 取值范围 | 1, 2, 3, … | ⭐ **大于 RS 中任何段的最大整数 storage key** |

✅ **EN（Join Indices）:** *"If T1 and T2 are two projections that cover a table T, a **join index from the M segments in T1 to the N segments in T2** is logically a collection of **M tables, one per segment S of T1**, consisting of rows of the form **(s: SID in T2, k: Storage Key in Segment s)**. Since all join indexes are between projections **anchored at the same table**, this is **always a one-to-one mapping**."*
💡 **中文（两种理解方式 + 一个必背例子）：**
- **理解 1**：T1 某段中某元组的 join index 项，含 **T2 中对应（连接）元组的段 ID 和 storage key**。
- ⭐ **理解 2（更好的直觉）**：*"An alternative view of a join index is that it takes T1, sorted in some order O, and **logically resorts it into the order O' of T2**."*
- ⭐ **必背例子（Figure 2）**：EMP3 的第一项 (Bob, 10K) 对应 EMP1 的**第二项**，所以 **join index 的第一项 storage key = 2**。
- ⭐ **path（路径）**：要从 T1…Tk 的段重建 T，**必须能找到一条通过若干 join index 的路径**，把 T 的每个属性映射到某个共同排序顺序 O*。**path = 从某个 projection Tᵢ 指定的排序顺序出发、经过零个或多个中间 join index、以按 O* 排序的 projection 结束的一组 join index。**
  - 例：要从 Example 2 的 projection 重建 EMP 表，**至少需要两个 join index**。若选 age 作共同排序顺序，可以建两个索引把 EMP2 和 EMP3 映射到 EMP1 的顺序；**或者**建一个把 EMP2 映射到 EMP3、一个把 EMP3 映射到 EMP1。
- ⭐⭐ **为什么实践中要少用 join index（极高频考点）**：*"In practice, we expect to **store each column in several projections**, thereby allowing us to **maintain relatively few join indices**. This is because **join indexes are very expensive to store and maintain in the presence of updates**, since **every modification to a projection requires every join index that points into or out of it to be updated as well**."*
  → 💡 **一句话：宁可多存几份冗余列，也不要多建 join index。**
❌ **Trap:** *"Join indexes are cheap because they only store integers."* —— **错，在有更新时存储和维护都非常昂贵。**
❌ **Trap:** *"A join index may map between projections anchored at different tables."* —— **错，必须锚定在同一张表**（所以才是一对一映射）。

### 重点4 · RS 的四种编码方案（一定要背表）⭐⭐
> **选哪种取决于两个维度**：(a) **ordering（排序性）**——该列是**按自己的值排序（self-order）**，还是按同 projection 中**某个其他列的值排序（foreign-order）**；(b) **distinct values 的比例（多还是少）**。

| 类型 | 条件 | 表示形式 | 例子 | 辅助索引 |
|:---|:---|:---|:---|:---|
| **Type 1** | **Self-order, few distinct values** | **三元组序列 (v, f, n)**：v 是列中的值，**f 是 v 首次出现的位置**，**n 是 v 出现的次数** | 4 出现在位置 **12–18** → **(4, 12, 7)** | ⭐ **在 value 字段上建 clustered B-tree 索引**。因为 **RS 没有在线更新，索引可以 densepack 不留空位**；配大磁盘块（**64–128K**），**索引高度可以保持很小（2 或更少）** |
| **Type 2** | **Foreign-order, few distinct values** | **二元组序列 (v, b)**：v 是值，**b 是位图，指示该值出现在哪些位置** | 整数列 `0,0,1,1,2,1,0,2,1` → **(0, 110000100)、(1, 001101001)、(2, 000010010)** | ⭐ **每个位图很稀疏，所以做 run-length encoding 省空间**；为高效找第 i 个值，包含 **"offset indexes"——把列中的位置映射到该位置所含值的 B-tree** |
| **Type 3** | **Self-order, many distinct values** | ⭐ **每个值表示为与前一个值的 delta（差值）**。**块导向（block-oriented）形式**：每个块的**第一项是真实值及其 storage key**，**后续每个值是与前一个值的 delta** | `1,4,7,7,8,12` → **`1,3,3,0,1,4`** | ⭐ **块级的 densepack B-tree**。原文注：**这与 VSAM 编码 B-tree 索引键的方式相似** |
| **Type 4** | **Foreign-order, many distinct values** | ⭐ **值不编码（leave the values unencoded）**——"我们仍在研究这种情况可能的压缩技术" | — | **densepack B-tree 仍可用于索引** |

- ⭐ **常考的对应关系**：Type 1 ↔ 自序 + 少值（RLE 式三元组）；Type 2 ↔ 外序 + 少值（**位图**）；Type 3 ↔ 自序 + 多值（**delta**）；Type 4 ↔ 外序 + 多值（**不编码**）。
- ⭐ **Type 2 的代价（在优化器一节被点出）**：*"operators that take **Type 2 data as input require much larger memory buffer space (one page of memory for each possible value in the column)** than any of the other three types of compression."*
❌ **Trap:** *"Type 2 encoding uses run-length triples (v, f, n)."* —— **错，那是 Type 1；Type 2 是位图。**
❌ **Trap:** *"Type 3 (delta) encoding stores one starting value for the entire column."* —— **错，是 block-oriented，每个块的第一项才是真实值。**

### 重点5 · WS 的实现（与 RS 的对照）⭐
✅ **EN:** *"**In order to avoid writing two optimizers, WS is also a column store and implements the identical physical DBMS design as RS.** Hence, the same projections and join indexes are present in WS. **However, the storage representation is drastically different because WS must be efficiently updatable transactionally.**"*
💡 **中文（WS 的具体表示）：**
- ⭐ **不压缩**：*"Since we assume that **WS is trivial in size relative to RS**, we make **no effort to compress data values**; instead we represent all data directly."*
- ⭐ **用 B-tree 维护逻辑 sort-key 顺序**（建在 **BerkeleyDB** 的 B-tree 之上）：
  - **每个列**表示成 **(v, sk) 对的集合**，v 是列中的值，sk 是对应的 storage key；**每对存在一棵按第二个字段（sk）建的常规 B-tree 里**。
  - **每个 projection 的 sort key 另外**表示成 **(s, sk) 对**，s 是 sort key 值，sk 是 s **首次出现**的 storage key；**这个结构表示成按 sort key 字段建的常规 B-tree**。
  - ⭐ **用 sort key 搜索的两步**：**先用后者的 B-tree 找到感兴趣的 storage key，再用前者那组 B-tree 找到记录的其他字段。**
- ⭐ **1:1 映射**：*"For simplicity and scalability, **WS is horizontally partitioned in the same way as RS**. Hence, there is a **1:1 mapping between RS segments and WS segments**. A **(sid, storage_key) pair identifies a record in either of these containers**."*
- ⭐ **join index 的完整描述**：*"Every projection is represented as a **collection of pairs of segments, one in WS and one in RS**. For each record in the '**sender**', we must store the sid and storage key of a corresponding record in the '**receiver**'." 且 "each (sid, storage key) pair is **a pointer to a record which can be in either the RS or WS**."*
- **性能考虑**：*"every insert to a projection results in a **collection of physical inserts on different disk pages, one per column per projection**. To avoid poor performance, we plan to utilize a **very large main memory buffer pool** … we expect '**hot' WS data structures to be largely main memory resident.**"*
- **存储管理**：一个 **storage allocator** 自动把段分配到网格节点。约束：⭐ **(a) 一个 projection 的单个段里所有列必须共置（co-located）；(b) join index 应与其 "sender" 段共置；(c) 每个 WS 段与含相同键范围的 RS 段共置。** *"Our analysis shows that a **raw device offers little benefit relative to today's file systems**. Hence, **big columns (megabytes) are stored in individual files** in the underlying operating system."*
❌ **Trap:** *"WS is a row store, which is why it supports efficient updates."* —— **错，WS 也是列存**（原文理由：**为了避免写两个优化器**）。

### 重点6 · Updates 与 Snapshot Isolation（office hour 已考）⭐⭐
✅ **EN:** *"**Inserts are sent to WS**, while **deletes must be marked in RS for later purging by the tuple mover**. **Updates are implemented as an insert and a delete.**"*
✅ **EN（为什么不用常规锁）:** *"C-Store expects **large numbers of ad-hoc queries with large read sets interspersed with a smaller number of OLTP transactions covering few records**. **If C-Store used conventional locking, then substantial lock contention would likely be observed, leading to very poor performance.** Instead, C-Store **isolates read-only transactions using snapshot isolation**."*
💡 **中文（快照隔离的机制，术语必须记准）：**
- **historical mode（历史模式）**：只读查询选一个**小于最近提交事务时间戳**的时间戳 **T**，查询在语义上被保证产生"历史上那个时刻"的正确答案。
- ⭐ **HWM = high water mark（高水位）**：**快照隔离能运行的"过去最近的时刻"**。
- ⭐ **LWM = low water mark（低水位）**：**只读事务能运行的最早有效时刻**。*"If we let read-only transactions set their effective time arbitrarily, then we would have to support **general time travel, an onerously expensive task**."*
- ⭐ **不能原地更新**：*"To provide snapshot isolation, **we cannot perform updates in place**. Instead, an update is turned into an insert and a delete. Hence, **a record is visible if it was inserted before ET and deleted after ET.**"*
- ⭐ **epoch（时代）作为时间戳单位**：为了不占太多空间，用**粗粒度的 "epochs"** 作时间戳单位。
- ⭐ **两个向量（必背）：**
  | 向量 | 全称 | 内容 | 存哪里 |
  |:---|:---|:---|:---|
  | **IV** | **insertion vector（插入向量）** | 每条记录**被插入时所处的 epoch** | ⭐ **WS 的每个 projection 段**。**tuple mover 被编程保证 RS 中没有记录是在 LWM 之后插入的，因此 RS 不需要维护 IV** |
  | **DRV** | **deleted record vector（删除记录向量）** | 每个 projection 记录一项：**未删除 = 0；否则 = 被删除时的 epoch** | ⭐ **存在 WS 里**（因为必须可更新）。**DRV 非常稀疏（大部分是 0），所以可用前面的 Type 2 算法紧凑编码** |
- **运行时系统查 IV 和 DRV，为每个查询**逐记录**做可见性计算。**
- ⭐ **HWM 的维护协议（TA 协议，步骤要能复述）：**
  1. 指定一个站点为 **TA = timestamp authority（时间戳权威）**，负责给其他站点分配时间戳。
  2. 把时间划分为若干 epoch；**epoch number = 自"时间开始"以来流逝的 epoch 数**。**epoch 相对较长（例如若干秒），确切时长因部署而异。** 初始 **HWM = epoch 0，current epoch 从 1 开始**。
  3. TA 周期性决定推进到下一个 epoch：向每个站点发 **end of epoch** 消息；各站点把 current epoch 从 e 增到 e+1，**使新到达的事务以时间戳 e+1 运行**。
  4. 每个站点**等待所有在 epoch e（或更早）开始的事务完成**，然后向 TA 发 **epoch complete** 消息。
  5. TA 收到**所有站点**对 epoch e 的 epoch complete 后，**把 HWM 设为 e**，并把该值发给每个站点。
  6. TA 广播新 HWM 值 e 后，**只读事务可以开始读 epoch e 或更早的数据，并确信这些数据已提交**。
  - ⭐ **Figure 3 的关键注解**：*"Note that although **T4 is still executing when the HWM is incremented, read-only transactions will not see its updates because it is running in epoch e+1.**"*
  - **为让用户能引用真实世界时间**，维护一张 **epoch number → 时间**的映射表，查询从"最接近用户指定时间的 epoch"开始。
  - ⭐ **epoch 回绕**：为避免 epoch 号无界增长占额外空间，计划**"reclaim"不再需要的 epoch**——通过**像 TCP 那样"wrapping"时间戳**复用旧 epoch 号。多数仓库应用记录保留固定时长（如 2 年），所以**只需跟踪任何 DRV 中最老的 epoch，确保绕过零不会覆盖**。对无法有效回绕的环境，只能**加大 epoch 的 "wrap length" 或加大 epoch 的尺寸**。
❌ **Trap:** *"C-Store performs updates in place in WS to keep the deleted record vector small."* —— **错，快照隔离要求不能原地更新。**
❌ **Trap:** *"RS maintains an insertion vector so read-only queries can filter it."* —— **错，RS 不需要 IV**（tuple mover 保证 RS 里没有 LWM 之后插入的记录）。

### 重点7 · 读写事务的并发控制与提交（不用 2PC！）⭐⭐
✅ **EN:** *"**Read-write transactions use strict two-phase locking** for concurrency control. Each site sets locks on data objects that the runtime system reads or writes, thereby implementing a **distributed lock table** as in most distributed databases. **Standard write-ahead logging is employed for recovery purposes; we use a NO-FORCE, STEAL policy** but differ from the traditional implementation in that **we only log UNDO records, performing REDO as described in Section 6.3**, and **we do not use strict two-phase commit, avoiding the PREPARE phase**."*
💡 **中文（三个关键差异，全是高频考点）：**
1. ⭐ **只记 UNDO 日志，不记 REDO 日志**。REDO 靠"从其他站点上的其他 projection 复制状态"完成（见恢复一节）。
2. ⭐ **不用严格两阶段提交，省掉 PREPARE 阶段**：每个事务有一个 **master**，负责把事务对应的工作单元分配给合适的站点、并决定事务的最终提交状态。**master 收到 COMMIT 语句时，等所有 worker 完成所有未完成动作，然后向每个站点发 commit（或 abort）消息。** 站点收到 commit 后即可释放该事务的所有锁并删除该事务的 UNDO 日志。
   - ⭐ **代价（原文明说）**：*"This means it is possible for a site the master has told to commit to **crash before writing any updates or log records related to a transaction to stable storage**. In such cases, the failed site will **recover its state, which will reflect updates from the committed transaction, from other projections on other sites in the system during recovery.**"*
3. **死锁用超时解决**（abort 其中一个死锁事务的标准技术）。
- ⭐ **回滚用 logical logging**：*"When a transaction is aborted … it is undone by **scanning backwards in the UNDO log**, which contains one entry for each **logical** update to a segment. We use **logical logging (as in ARIES)**, since **physical logging would result in many log records, due to the nature of the data structures in WS**."*（**WS 每次插入会在很多不同磁盘页上产生物理插入，物理日志会爆炸。**）
- ⭐ **NO-FORCE, STEAL 是什么**（术语补充）：**NO-FORCE** = 提交时不强制把脏页刷盘（靠日志保证）；**STEAL** = 允许把未提交事务的脏页换出到磁盘。
❌ **Trap:** *"C-Store logs both UNDO and REDO records for read-write transactions."* —— **错，只记 UNDO。**
❌ **Trap:** *"C-Store uses two-phase commit for distributed transactions."* —— **错，省掉了 PREPARE 阶段。**

### 重点8 · Recovery（三种情形 + WS 恢复的查询）⭐
✅ **EN:** *"A crashed site recovers by **running a query (copying state) from other projections**. Recall that C-Store maintains **K-safety**; i.e. sufficient projections and join indexes are maintained, so that **K sites can fail within the time to recover, t**, and the system will be able to maintain transactional consistency."*
💡 **中文（三种情形，逐条）：**
| 情形 | 处理 |
|:---|:---|
| **1. 失败站点无数据丢失** | **执行网络中别处为它排队的更新**即可"roll forward"。⭐ *"Since we anticipate read-mostly environments, this roll forward operation should not be onerous. Hence, **recovery from the most common type of crash is straightforward.**"* |
| **2. 灾难性失败（RS 和 WS 都毁了）** | **只能从系统中其他 projection 和 join index 重建两个段**。⭐ 唯一需要的额外功能是**能从远程站点取回辅助数据结构（IV、DRV）**。恢复后还要跑排队的更新。 |
| **3. WS 毁了但 RS 完好** | ⭐ *"Since **RS is written only by the tuple mover**, we expect it will typically **escape damage**. Hence, we discuss this **common case** in detail."* |

- ⭐ **情形 3 的恢复（6.3.1，那段 SQL 要能读懂）**：
  - tuple mover 保证**每个 WS 段 S 含有所有插入时间戳晚于某个时刻 t_lastmove(S) 的元组**，t_lastmove(S) 代表 S 对应的 RS 段中任何记录的**最近插入时间**。
  - 恢复站点 r 先检查集合 C 中**每个含有 S_r 的 sort key 的 projection**，寻找一组"覆盖键范围 K 且每段满足 **t_lastmove(S) ≤ t_lastmove(S_r)**"的列。若成功，就跑形如下面的查询：
    ```sql
    SELECT desired_fields, insertion_epoch, deletion_epoch
    FROM   recovery_segment
    WHERE  insertion_epoch > t_lastmove(S_r)
      AND  insertion_epoch <= HWM
      AND  deletion_epoch = 0
       OR  deletion_epoch >= LWM
      AND  sort_key in K
    ```
  - 只要查询返回 storage key，**段中其他字段就能顺着相应的 join index 找到**。**只要存在一组覆盖 S_r 键范围的段，这个技术就能把 S_r 恢复到当前 HWM**；再跑排队的更新就完成了。
  - ⭐ **失败情形**：若**不存在具备所需性质的覆盖**，说明 **S_r 中的一些元组已经被搬到远程站点的 RS 里了**。虽然仍能查询远程站点，**但要在"不取回 RS 中所有东西再与本地 RS 段做差"的前提下识别出想要的元组很有挑战——而那显然是昂贵的操作**。
  - ⭐ **对策（若这种情况变常见）**：*"we can **force the tuple mover to log, for each tuple it moves, the storage key in RS that corresponds to the storage key and epoch number of the tuple before it was moved from WS**. This log can be **truncated to the timestamp of the oldest tuple still in the WS on any site**."* 这样恢复站点就能用**远程 WS 段 + tuple mover 日志**解上面的查询，**即使 t_lastmove(S) 晚于 t_lastmove(S_r)**。
  - 还要**重建本地存储的 join index 的 WS 部分**（即 S_r 是 "sender" 的那些）：这只需**查询远程的 "receiver"**，它们在生成元组时就能计算 join index，**把 join index 的 WS 分区随恢复的列一起传过来**。
❌ **Trap:** *"Recovery in C-Store replays a redo log."* —— **错，靠从其他 projection 复制状态。**

### 重点9 · Tuple Mover（MOP，office hour 已考）⭐⭐
✅ **EN:** *"The job of the tuple mover is to **move blocks of tuples in a WS segment to the corresponding RS segment, updating any join indexes in the process**. It operates as a **background task** looking for **worthy segment pairs**. When it finds one, it performs a **merge-out process, MOP** on this (RS, WS) segment pair."*
💡 **中文（MOP 的完整流程，必背）：**
1. **MOP 找出所选 WS 段中插入时间 ≤ LWM 的所有记录**，分成两组：
   - ⭐ **在 LWM 或之前被删除的 → 丢弃**（因为**用户不可能在"它们还存在"的时刻跑查询**）；
   - **未被删除的、或在 LWM 之后被删除的 → 搬到 RS**。
2. **MOP 创建一个新的 RS 段 RS′**。
3. 然后**读入 RS 段各列的块，删除 DRV 值 ≤ LWM 的 RS 项，并合并进 WS 的列值**；合并后的数据写出到新的 RS′ 段，**RS′ 随合并进行而增长**。
4. ⭐ **RS′ 中记录的最近插入时间成为该段新的 t_lastmove，且总是 ≤ LWM。**
5. ⭐ **old-master/new-master 方法比 update-in-place 更高效，因为基本上所有数据对象都会移动。**
6. ⭐ **记录在 RS′ 中获得新的 storage key，因此需要维护 join index；由于 RS 项也可能被删除，DRV 的维护也是强制的。**
7. **一旦 RS′ 含有所有 WS 数据、且 join index 在 RS′ 上被修改好，系统就从 RS 切换（cut over）到 RS′，旧 RS 占的磁盘空间即可释放。**
- ⭐ **LWM 的推进**：*"Periodically the timestamp authority sends out to each site a new LWM epoch number. Hence, **LWM 'chases' HWM**, and **the delta between them is chosen to mediate between the needs of users who want historical access and the WS space constraints.**"*（**LWM 追着 HWM 跑；两者的间距是"历史访问需求"与"WS 空间约束"之间的权衡。**）
- ⭐ **LSM 关联（摘要/引言就点了）**：*"In order to support a high-speed tuple mover, we use a **variant of the LSM-tree concept**, which supports a **merge out process** that moves tuples from WS to RS in bulk by an efficient method of **merging ordered WS data objects with large RS blocks, resulting in a new copy of RS that is installed when the operation completes.**"*
❌ **Trap:** *"The tuple mover moves all records in the WS segment, regardless of timestamp."* —— **错，只处理插入时间 ≤ LWM 的记录。**
❌ **Trap:** *"MOP updates RS segments in place to avoid rewriting them."* —— **错，是 old-master/new-master（写出全新的 RS′ 再切换）。**

### 重点10 · 查询执行：10 种算子 + 三种数据类型 ⭐⭐
✅ **EN:** *"There are **10 node types** and each accepts operands or produces results of type **projection (Proj)**, **column (Col)**, or **bitstring (Bits)**. In addition, C-Store query operators accept **predicates (Pred)**, **join indexes (JI)**, **attribute names (Att)**, and **expressions (Exp)** as arguments."*
- **projection** = **一组基数相同、顺序相同的列**；**bitstring** = **一串 0/1，指示相关值是否出现在被描述的记录子集中**。
- ⭐ *"**Join indexes and bitstrings are simply special types of columns.** Thus, they also can be included in projections and used as inputs to operators where appropriate."*

| # | 算子 | 作用 |
|:--|:---|:---|
| 1 | **Decompress** | 把压缩列转成**未压缩（Type 4）**表示 |
| 2 | **Select** | 等价于关系代数的选择 σ，⭐ **但不产生输入的限制，而是产生结果的 bitstring 表示** |
| 3 | **Mask** | 接受 bitstring B 和 projection Cs，⭐ **只发出 B 中对应位为 1 的那些值** |
| 4 | **Project** | 等价于关系代数的投影 π |
| 5 | **Sort** | 按 projection 中某个列子集（sort columns）对 projection 的所有列排序 |
| 6 | **Aggregation Operators** | 在指定列上计算 SQL 式聚合，**并按某个 projection 中的值标识的每个组分别计算** |
| 7 | **Concat** | 把**一个或多个按相同顺序排序的 projection** 合并成单个 projection |
| 8 | **Permute** | ⭐ **按某个 join index 定义的顺序置换一个 projection** |
| 9 | **Join** | 按关联两个 projection 的谓词做连接 |
| 10 | **Bitstring Operators** | **BAnd**（两个 bitstring 按位与）、**BOr**（按位或）、**BNot**（补） |

- ⭐ **计划形态与 64K 块迭代器（很爱考的细节）**：*"A C-Store query plan consists of a **tree of the operators** listed above, with **access methods at the leaves** and **iterators serving as the interface** between connected nodes. Each non-leaf plan node consumes the data produced by its children via a **modified version of the standard iterator interface** via calls of '**get_next**.' **To reduce communication overhead (i.e., number of calls of get_next) between plan nodes, C-Store iterators return 64K blocks from a single column.** This approach **preserves the benefit of using iterators (coupling data flow with control flow), while changing the granularity of data flow to better match the column-based model.**"*
  → 💡 **这就是"块/向量化迭代器"的一个早期实例——与 P11 Vectorwise 的向量化模型、P10 的批处理讨论直接呼应。**
❌ **Trap:** *"C-Store's Select operator returns the qualifying tuples directly."* —— **错，返回 bitstring。**
❌ **Trap:** *"C-Store abandons the iterator interface entirely."* —— **错，保留了迭代器，只是把粒度改成 64K 单列块。**

### 重点11 · 查询优化（两处与传统不同）⭐
✅ **EN:** *"We plan to use a **Selinger-style optimizer** that uses **cost-based estimation** for plan construction. We anticipate using a **two-phase optimizer** to limit the complexity of the plan search space. **Query optimization in this setting differs from traditional query optimization in at least two respects: (1) the need to consider compressed representations of data, and (2) the decisions about when to mask a projection using a bitstring.**"*
💡 **中文：**
1. ⭐ **压缩表示的代价建模**：*"C-Store operators have the capability to **operate on both compressed and uncompressed input**. … **the ability to process compressed data is the key to the performance benefits of C-Store.** An operator's execution cost (both in terms of I/O and memory buffer requirements) **is dependent on the compression type of the input.**"*
   - **例子（必背）**：**在 Type 2 数据上做 Select**（外序/少值，存成 delta 编码的位图，每个值一个位图）**可以只从磁盘读那些值匹配谓词的位图**——**尽管列本身没有排序**！但**接受 Type 2 数据作输入的算子需要大得多的内存缓冲空间（列中每个可能值一页内存）**。⭐ **所以代价模型必须对输入和输出列的表示形式敏感。**
2. ⭐ **Mask 的放置位置**：*"in some cases it is desirable to **push the Mask early in the plan** (e.g., to avoid producing a bitstring while performing selection over Type 2 compressed data) while in other cases it is best to **delay masking until a point where it is possible to feed a bitstring to the next operator** in the plan (e.g., **COUNT**) that can **produce results solely by processing the bitstring**."*
- ⭐ **优化器最大的决策**：*"The major optimizer decision is **which set of projections to use for a given query**. Obviously, it will be time consuming to construct a plan for each possibility and then select the best one. **Our focus will be on pruning this search space.**"*
❌ **Trap:** *"C-Store's optimizer treats all compressed columns as equally cheap to scan."* —— **错，代价依赖压缩类型。**

### 重点13 · Related Work（"C-Store 到底新在哪"）⭐
✅ **EN（数据立方体 vs C-Store 的定位）:** *"Precomputation of aggregates as well as more general materialized views is **especially effective when a prespecified set of queries is run at regular intervals**. On the other hand, **when the workload cannot be anticipated in advance, it is difficult to decide what to precompute. C-Store is aimed entirely at this latter problem.**"*
✅ **EN（vs data mirrors）:** *"Including two differently architected DBMSs in a single system has been studied before in **data mirrors**. However, the goal of data mirrors was to **achieve better query performance than either of the two underlying systems alone in a warehouse environment**. In contrast, **our goal is to simultaneously achieve good performance on update workloads and ad-hoc queries.** Consequently, C-Store **differs dramatically from a data mirror in its design.**"*
✅ **EN（vs 其他列存）:** *"Storing data via columns has been implemented in several systems, including **Sybase IQ, Addamark, Bubba, Monet, and KDB**. Of these, **Monet is probably closest to C-Store in design philosophy**. However, these systems typically **store data in entry sequence** and **do not have our hybrid architecture nor our model of overlapping materialized projections.**"*
- **vs inverted organization**：*"C-Store uses this sort of organization **in WS** but extends the architecture with **RS and a tuple mover**."*
- **压缩上的定位**：*"Our observation that **it is possible to operate directly on compressed data has been made before**."*（**这一点不是 C-Store 首创**，作者诚实标注。）
- ⭐ **总结句**：*"materialized views, snapshot isolation, transaction management, and high availability have also been extensively studied. **The contribution of C-Store is an innovative combination of these techniques** that simultaneously provides **improved performance, K-safety, efficient retrieval, and high performance transactions.**"*
❌ **Trap:** *"C-Store was the first system to store data by column."* —— **错，Sybase IQ、Monet、KDB 等在前；C-Store 的贡献是"组合"。**
❌ **Trap:** *"C-Store targets workloads where the query set is known in advance."* —— **错，正好相反——它针对的是"负载无法事先预知"的问题。**

### 重点14 · K-safety 与 shared-nothing 设计
✅ **EN:** *"We propose to **horizontally partition data across the disks of the various nodes in a 'shared nothing' architecture**. … We call a system that **tolerates K failures K-safe**. C-Store will be **configurable to support a range of values of K**."*
💡 **中文：**
- **动机**：*"Many warehouse systems maintain **two copies of their data because the cost of recovery via DBMS log processing on a very large (terabyte) data set is prohibitive.** This option is rendered increasingly attractive by the **declining cost per byte of disks**."*
- ⭐ **关键洞察**：*"there is **no requirement that one store multiple copies in the exact same way**. C-Store allows redundant objects to be stored in **different sort orders**, providing **higher retrieval performance in addition to high availability**."*（**冗余不只是保险，还是性能资产。**）
- **一般化**：*"storing overlapping projections further improves performance, **as long as redundancy is crafted so that all data can be accessed even if one of the G sites fails**."*
- **失败处理**：*"When a failure occurs, C-Store simply **continues with K-1 safety** until the failure is repaired."*
- ⭐ **物理设计问题的完整表述**：*"the C-Store physical DBMS design problem is to determine **the collection of projections, segments, sort keys, and join indices** to create for the collection of logical tables in a database. This physical schema must give **K-safety** as well as **the best overall performance for a given training workload**, provided by the C-Store administrator, subject to requiring **no more than a given space budget, B**."*
  - **C-Store 可以被指示记录所有查询的日志，周期性用作训练负载**；⭐ *"Because there are **not enough skilled DBAs to go around**, we are writing an **automatic schema design tool**."*
- **网格假设**：*"any new DBMS architecture should assume a **grid environment** in which there are **G nodes (computers), each with private disk and private memory**. Grid computers in the near future may have **tens to hundreds of nodes**."* ⭐ **intra-query parallelism 靠存储数据结构的水平分区来促进，跟随 Gamma 的路线。**

| 假选项 | 真相 |
|:---|:---|
| "RMI 同一阶段的模型必须覆盖**等大键范围**，像 B-tree 节点" | 不必等大，随分布自适应 |
| "**shared-memory** 达到 near-linear speedup" | ⭐ 是 **shared-nothing** 的招牌；shared-memory 扩展性最差（约 32 处理器上限） |
| "**hash 分区**适合范围查询，值相近的元组落同一盘" | 那是 **range 分区**；hash **随机化**数据 |
| "R-tree 过空节点与相邻兄弟**合并**，与 B-tree 完全一样" | ⭐ Guttman 选的是 **re-insertion** |
| "ChooseLeaf 挑**面积最小**的孩子" | ⭐ 首要准则是 **面积增量最小**，面积最小只是平局次准则 |

### ⑤ 半真半假（东西存在，但作用/细节说错）
| 假选项 | 真相 |
|:---|:---|
| "tuple mover 的作用是**备份与恢复**" | ⭐ 作用是**数据迁移 WS → RS**；恢复靠 **K-safety** |
| "join index 便宜，因为只存整数" | ⭐ **有更新时存储和维护都非常昂贵** → 宁可多存冗余列 |
| "Active Buffer Manager 是出货产品的核心组件" | ⭐ **产品里换成了更温和的智能数据缓冲** |
| "MOP 原地更新 RS 段以避免重写" | ⭐ **old-master/new-master**：写出全新 RS′ 再切换 |
| "RS 维护 insertion vector 供只读查询过滤" | ⭐ **RS 不需要 IV**（tuple mover 保证 RS 无 LWM 之后插入的记录） |
| "flow control 让 exchange 变回 demand-driven dataflow" | ⭐ 原文专门澄清两者不同（**slack → 真正重叠执行**） |
| "PDT 按**键值**组织差分" | ⭐ **按位置（by position）**，这是零成本合并的关键 |
| "分支越少越好，每个分支都很贵" | ⭐ 预测有效时**非常便宜**；真正贵的是 **50% 概率的分支** |
| "C-Store 是第一个按列存数据的系统" | ⭐ Sybase IQ / Monet / KDB 在前；C-Store 的贡献是**组合** |
| "C-Store 针对查询集合事先已知的负载" | ⭐ 正好相反：**针对负载无法事先预知的问题**（这是它与 data cube / 预计算路线的分界） |

### ⑥ 一步之遥的"超纲常识"（出题人爱考的"transcript 外一小步"）
- **latch vs lock**：latch 保护内存结构（短、物理），lock 保护事务数据（长、逻辑）。**Bw-tree 是 latch-free，不是 lock-free 的事务**——它明确假设"冲突的数据更新由系统别处的并发控制阻止"。
- **NO-FORCE / STEAL**（P12 提到但没解释）：NO-FORCE = 提交不强制刷脏页；STEAL = 允许换出未提交事务的脏页。
- **SSA（Single Static Assignment）**（P10 提到）：LLVM 的无界寄存器是 SSA 形式的（每个虚拟寄存器只被赋值一次）。
- **BAT（Binary Association Table）**（P10 提到）：MonetDB 的基本存储单元 = (oid, value) 二元关系；**这是它"必须多次触碰元组"的根源**。
- **write amplification（写放大）**：日志结构存储的固有代价，GC 搬运活数据造成实际写 > 逻辑写；**也磨损 flash**。
- **priority inversion（优先级反转）**（P8 的开放问题）：低优先级客户请求高优先级服务器，工作实际被提升到高优先级。

### Q1（P5）Which statement is **NOT** correct about the Bw-tree mapping table?

### Q2（P5）A thread performing a page consolidation finds that its CAS on the mapping table fails. What does it do?
A. Retries the CAS until it succeeds.
B. **Abandons the operation by deallocating the new page and does not retry.**
C. Falls back to acquiring a latch on the page.
D. Triggers a page split instead.

<details><summary>答案</summary>

**B。** 原文：*"If this CAS fails, the thread abandons the operation by deallocating the new page. **The thread does not retry**, as a subsequent thread will eventually perform a successful consolidation."*
⭐ **对比记忆**：**记录更新（insert/modify/delete）失败要重试；consolidation 失败不重试。** C 更是双重错误（Bw-tree 全程 latch-free）。

### Q3（P5）多步推理。A thread traverses the Bw-tree and encounters a page P whose delta chain contains a **split delta** with separator key K_P = 500, but the parent node O has **no index entry** for the new sibling Q. The thread is searching for key 750. Which sequence is correct?
A. The search fails because the index is in an inconsistent state.
B. The thread must wait for the split to complete, then re-traverse from the root.
C. **The thread follows the side link to Q (since 750 > 500); additionally, if it is an updater or another SMO that would traverse the side pointer, it must first complete the SMO by posting the index entry delta to the parent.**
D. The thread posts the index entry delta to O, then restarts its search from the root.

<details><summary>答案</summary>

**C。** 两个知识点合成：
1. **half split 之后索引就已经合法**——B-link 的 side link 保证了有效搜索树；key > K_P 的搜索沿 side link 走到 Q。
2. **SMO 的串行化规则**：*"when an updater or another SMO would traverse a side pointer to reach the correct page, it **must complete the split SMO by posting the new index term delta to the parent. Only then can it continue on to its own activity.**"*
- A 错（索引是合法的）；B 错（**从不等待**）；D 半对但"restart from the root"是多加的机制（原文说记住下行路径的 PID，多数时候记住的父就是对的）。
</details>

### Q7（P6）多步计算。An R-tree is built with page size 1024 bytes. Each 2-D entry needs 4 numbers × 4 bytes + a 4-byte pointer. Given the paper's own footnote reasoning, what are M and the worst-case space utilization for non-root nodes when m = M/3?

### Q9（P7）Which statement is correct about the min-/max-error guarantees of a learned range index?
A. The strong min-/max-error guarantee of a B-Tree holds for **all possible keys**, so a learned model must match that.
B. **The B-Tree only provides the guarantee over the stored keys; moreover, strong error bounds are not even needed because any error can be corrected by a local search around the prediction, which even allows non-monotonic models.**

<details><summary>答案</summary>

<details><summary>答案</summary>

**B。** 原文原句。
- C 是原文专门澄清的错误：*"flow control and demand-driven dataflow are **not the same**"*——**流控允许"slack"、是真正的重叠执行**，而 demand-driven 是刚性的请求-交付结构。
- D 方向错：选 data-driven 的两个理由是 ⭐ **(1) 打算把 exchange 也用于 horizontal parallelism，而水平并行用 data-driven 更容易实现；(2) 消除了 request messages 的需要。** 且原文还说 **data-driven dataflow 更容易与水平并行和分区高效结合**。
</details>

### Q19（P9）多步计算。In the Volcano example of Section 4.3, a plan runs in three process groups: A (1 process), BC (3 processes), D (4 processes), with exchange X between A and B, and exchange Y between C and D. How many end-of-stream-tagged packets does Y produce in total, and how many tags does the Y copy in **each** BC process count before declaring end-of-stream?
A. 12 total; each BC process counts 3
B. **12 total; each BC process counts 4**
C. 7 total; each BC process counts 4
D. 12 total; each BC process counts 12

<details><summary>答案</summary>

**B。** 原文：*"In each D process, Y flags its last packets to each of the BC processes (i.e., **a total of 3×4 = 12** flagged packets)"*；*"The copies of the Y operator in the BC processes count the number of tagged packets; **after four tags (the number of producers or D processes)**, they have exhausted their inputs."*
⭐ **A 是最毒的诱饵**：3 是 **A₀ 中的 X 需要收到的标签数**（= BC 进程数）。**记法：某个 exchange 的消费者侧要数的标签数 = 它的生产者进程数。**
</details>

### Q20（P9）Which statement is **NOT** correct about the exchange operator's variants?
A. It can be directed to replicate/broadcast all records to all consumers, after pinning them multiple times in the buffer pool — **without copying the records**.
B. The merge iterator, unlike other operators, requires input records to be **distinguished by their producer**.
C. When exchange sits in the middle of a process's operator tree, it forks no processes at open and merely establishes a communication port — a mode that also makes **flow control obsolete**.
D. **Creating two processes per CPU (one to scan/partition, one to sort) was found to be optimal because it overlaps I/O with computation.**

<details><summary>答案</summary>

**D 不正确（结论反了）。** 原文：*"We realized that **creating and running more processes than processors inflicted a significant cost**, since these processes competed for the CPU's and therefore required operating system scheduling. … in our environment with a central run queue allowing processes to migrate freely and a large cache associated with each CPU, **the frequent cache migration adds a significant cost.**"* → 于是**把进程数减半，变成每磁盘一个进程**（这也正是变体 C 被开发出来的原因）。
</details>

### Q21（P10）Under Neumann's definition, which of the following is **NOT** a pipeline breaker?
A. The build side of a hash join.
B. A sort operator.
C. A hash-based aggregation.
D. **A selection (σ) operator.**

<details><summary>答案</summary>

**D。** 定义：*"An algebraic operator is a pipeline breaker for a given input side if it **takes an incoming tuple out of the CPU registers**."* Selection 只是判断谓词并让元组**继续留在寄存器里**往上推 → **不是 pipeline breaker**。
⭐ A、B、C 都要**物化**（把元组写进内存中的哈希表/排序缓冲）→ 是（full）pipeline breaker。
</details>

### Q22（P10）Which statement is correct about why Neumann chose LLVM over generating C++?
A. C++ compilers produce slower machine code than the LLVM JIT in all cases.
B. **An optimizing C++ compiler is really slow (multiple seconds per complex query), and C++ does not offer total control over the generated code — in particular overflow flags are unavailable.**
C. LLVM lets the query engine avoid calling C++ code entirely.
D. LLVM assembler is untyped, which makes code generation simpler.

<details><summary>答案</summary>

**B。** 原文两条理由原句。
- A 过头了（原文说 LLVM 版**显著更快**，但理由是"紧凑代码 + 一切留在寄存器"，不是"C++ 编译器永远产生更慢的码"；TPC-C 上两者性能差别很小）；
- C 错——⭐ **混合执行模型是核心**：**C++ 是预编译的"齿轮"，LLVM 是动态生成的"链条"**，两者**直接互调无性能惩罚**；
- D 反了——⭐ *"the LLVM assembler is **strongly typed**, which caught many bugs that were hidden in our original textual C++ code generation."*
</details>

### Q23（P10）Which statement is **NOT** correct about compiling a query into machine code in HyPer?
A. It is neither possible nor desirable to compile a complex query into a single function.
B. Inlining the complete query logic into a single function can lead to exponential growth in code, e.g., because outer joins call their consumers in two different situations.
C. A pipelining fragment of the algebraic expression should result in one compact LLVM code fragment, and the hot path must not cross a function boundary.
D. **Because all code is generated, the produce()/consume() functions are compiled into the final machine code as virtual calls.**

<details><summary>答案</summary>

**D 不正确。** 原文：*"this produce/consume interface is **only a mental model. These functions do not exist explicitly**, they are only used by the code generation."* **消除虚函数调用正是本方法的目的**，把它们编译进去是自相矛盾的。

### Q24（P11）Which statement is **NOT** correct about Vectorwise's storage?
A. A table is stored in multiple PAX partitions, each containing a group of columns, giving everything from DSM/PAX to NSM/PAX.
B. Nullable columns are represented as a value column plus a boolean NULL column, stored **in the same PAX partition**, because NULL testing hurts branch prediction and prevents SIMD.
C. NSM/PAX is used for small tables because a DSM representation would waste space with one nearly-empty disk block per column.
D. **The PAX grouping must always be specified explicitly via DDL; there is no automatic policy.**

<details><summary>答案</summary>

**D 不正确。** 原文：*"The exact grouping of a given table in PAX partitions **can be controlled by explicit DDL, but in absence of this, it is self-tuned**."* 论文还列了三条自动策略（nullable 列、复合主键同分区、小表用 NSM/PAX）和超宽表的高级分组算法。
⭐ **附加**：限制 PAX 组数量的理由是**表扫描所需的缓冲内存**——最宽的表（数百列）否则单次扫描要好几 GB。
</details>

### Q25（P11）Which statement is correct about MinMax indices in Vectorwise?
A. They are optional and must be declared in DDL, one per table.
B. **They are kept automatically on all columns, store simple metadata such as Min and Max for a range of records, are heavily consulted during query rewriting, and are effective only if there are correlations between attribute values and tuple position.**
C. They replace the clustered index and provide exact-match lookup.
D. They are based on Positional Delta Trees.

<details><summary>答案</summary>

**B。** 原文原句合成（"based on the idea of **small materialized aggregates**"）。
- A 混淆了两种索引：⭐ **"每表一个"说的是 clustered index；MinMax 是所有列上自动的**；
- C 错（MinMax 做的是**快速消除记录范围**，不是精确查找）；
- D 张冠李戴（**PDT 是更新机制**）。
⭐ **为什么"位置相关性"是前提**：数据仓库里事实表顺序常与时间相关，所以日期/时间列有这种相关性；**用有序表（clustered index）本身就是"位置与列键值相关"的直接来源**。
</details>

### Q26（P12）Which statement is **NOT** correct about C-Store's encoding schemes?
A. Type 1 (self-order, few distinct values) uses triples (v, f, n) where f is the first position of v and n is the number of occurrences.
B. Type 2 (foreign-order, few distinct values) uses pairs (v, b) where b is a bitmap, run-length encoded because each bitmap is sparse.
C. Type 3 (self-order, many distinct values) is a **block-oriented** delta scheme: the first entry of every block is an actual value with its storage key, and every subsequent value is a delta.
D. **Type 4 (foreign-order, many distinct values) uses dictionary compression with an offset index.**

<details><summary>答案</summary>

**D 不正确。** 原文：*"Type 4: Foreign-order, many distinct values: If there are a large number of values, then it probably makes sense to **leave the values unencoded**. However, we are **still investigating** possible compression techniques for this situation. A densepack B-tree can still be used for the indexing."*
⭐ **"offset indexes" 是 Type 2 的**（把列中的位置映射到该位置所含值的 B-tree）。（**手法：张冠李戴 + 无中生有的机制**。）
</details>

### Q27（P12）多步推理。A read-only query in C-Store runs at effective time ET. Which combination correctly describes how visibility is determined?
A. Consult the RS insertion vector and the WS deleted record vector.
B. **Consult the WS insertion vector (IV) and the deleted record vector (DRV); RS needs no IV because the tuple mover guarantees no records in RS were inserted after the LWM.**
C. Consult a global transaction table maintained by the timestamp authority.
D. Acquire shared locks on the projections being read, then read the latest committed version.

<details><summary>答案</summary>

**B。** 原文：*"we maintain an **insertion vector (IV) for each projection segment in WS** … **We program the tuple mover to ensure that no records in RS were inserted after the LWM. Hence, RS need not maintain an insertion vector.** In addition, we maintain a **deleted record vector (DRV) for each projection** … We **store the DRV in the WS**, since it must be updatable. The runtime system can now consult IV and DRV to make the visibility calculation for each query **on a record-by-record basis**."*
- A 错（RS 没有 IV）；C 无中生有（TA 只管 epoch/HWM/LWM）；D 错（⭐ **snapshot isolation 的全部意义就是"不需要设任何锁"**）。
</details>

### Q28（P12）Which statement is **NOT** correct about the tuple mover's merge-out process (MOP)?
A. It finds all records in the chosen WS segment with an insertion time at or before the LWM.
B. Records deleted at or before the LWM are **discarded**, because the user cannot run queries as of a time when they existed.
C. It creates a new RS segment RS′ and the system cuts over from RS to RS′ once join indexes are modified on RS′.
D. **Because records keep their storage keys when moved into RS′, no join index maintenance is required.**

<details><summary>答案</summary>

**D 不正确（两处都反了）。** 原文：*"notice that **records receive new storage keys in RS′, thereby requiring join index maintenance**. Since RS items may also be deleted, **maintenance of the DRV is also mandatory**."*
⭐ **配套记忆**：*"This **old-master/new-master** approach will be **more efficient than an update-in-place strategy**, since essentially **all data objects will move**."*
</details>

### Q29（P12）Which statement is correct about C-Store's transaction management?
A. Read-write transactions use snapshot isolation; read-only queries use strict two-phase locking.
B. **Read-write transactions use strict two-phase locking and log only UNDO records; distributed commit omits the PREPARE phase of 2PC.**
C. C-Store logs both UNDO and REDO records and uses a FORCE, NO-STEAL buffer policy.
D. Deadlocks are prevented by a wait-for graph maintained at the timestamp authority.

<details><summary>答案</summary>

**B。** 原文：*"Read-write transactions use **strict two-phase locking** … we use a **NO-FORCE, STEAL** policy but differ … in that **we only log UNDO records, performing REDO as described in Section 6.3**, and **we do not use strict two-phase commit, avoiding the PREPARE phase**."*
- A **方向反转**（是**只读用快照隔离、读写用 2PL**）；C 两处都反（**只记 UNDO**；**NO-FORCE, STEAL**）；D 错（⭐ *"We resolve deadlock via **timeouts** through the standard technique of aborting one of the deadlocked transactions."*）。
⭐ **省掉 PREPARE 的代价要能说出来**：*"it is possible for a site the master has told to commit to crash before writing any updates or log records to stable storage. In such cases, the failed site will **recover its state from other projections on other sites**."*
</details>

### Q30（跨论文，场景权衡）A data-warehouse team runs unpredictable ad-hoc analytical queries with occasional small online updates, on a cluster of commodity nodes, and wants both high availability and the ability to answer queries using the most advantageous sort order. According to the papers, which combination of design decisions is **best supported**?
A. Row store + shared-disk architecture + precomputed data cubes + strict 2PC.
B. **Column store with overlapping projections in multiple sort orders + shared-nothing horizontal partitioning + K-safety + snapshot isolation for read-only queries + a write-optimized store drained by a background tuple mover.**
C. Column store with a single copy of the data + one clustered index per table + PDT-based differential updates + MPP.
D. In-memory row store + LLVM-compiled push-based execution + inter-query parallelism only.

<details><summary>答案与逐项辨析</summary>

**B（= C-Store 的设计）。** 场景里的每个关键词都对应 C-Store 的一项设计：
- "**unpredictable ad-hoc**" → ⭐ C-Store 的 related work 明确说 *"when the workload cannot be anticipated in advance, it is difficult to decide what to precompute. **C-Store is aimed entirely at this latter problem.**"*
- "**most advantageous sort order**" → **overlapping projections in different sort orders**；
- "**commodity nodes + high availability**" → **shared-nothing 水平分区 + K-safety**；
- "**occasional small online updates**" → **WS + tuple mover**，只读查询用 **snapshot isolation** 避免锁竞争。

**为什么其他三项不是"最佳支持"：**
- **A**：行存是 write-optimized（P12）；**shared-disk 对"读写共享数据库"的应用很低效**（P8）；**预计算数据立方体只在查询集合事先已知时特别有效**（P12 related work）；C-Store 明确**避免 2PC**。
- **C** 是 **Vectorwise 的设计（P11）**，本身完全合理，但**只保存一份数据副本**，因此 ⭐ **"每表只能声明一个 clustered index"，无法提供"多种 sort order 任选"**，论文里也没有 K-safety 这类高可用机制。**这是"半真半假 + 张冠李戴"型的强诱饵。**
- **D**：**HyPer 的 LLVM push 执行（P10）是执行层的正解**，但选项把它绑到"**in-memory row store**"和"**inter-query parallelism only**"上——P10 恰恰讨论了 **intra-query parallelism 随核数增加变得更重要**，而且它既没有解决高可用/多 sort order，也不是为"集群 + 不可预知负载 + 高可用"这组约束设计的。
</details>
