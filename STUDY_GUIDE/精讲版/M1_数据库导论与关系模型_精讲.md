## 1. 数据库系统（DBMS）是什么？为什么要学这门课？

**📖 原文：**
> *"A database system is basically a software system designed for efficiently storing, retrieving, and manipulating data."*

**💡 大白话：**
DBMS（DataBase Management System，数据库管理系统）= **一个专门帮你"存、查、改"数据的软件**。

别想得太玄。你手机的"备忘录"也存数据。但当数据变成**几百万条、很多人同时用、而且绝对不能丢**的时候，备忘录就崩了——这时候你需要一个专业的"数据管家"，就是 DBMS。

- 🏦 银行：你的余额、每一笔转账，都是 DBMS 在管。
- 🛒 淘宝：几亿件商品、你的订单、你的评论。
- ✈️ 航空：订票、座位、航班时刻。

**为什么学这门课？** 原文说：写得出数据库的代码，就写得出任何复杂软件。因为造一个数据库会用到计算机科学几乎所有硬核东西——怎么管磁盘、怎么优化查询、怎么设计索引、怎么用多线程。这门课就是带你**亲手造一个数据库（叫 BuzzDB）**。

## 2. 最土的存法：flat-file（平面文件）数据库

**📖 原文：**
> *"we can organize the application's data using three simple flat text files... This design is known as a flat-file database where the data is organized in a bunch of simple text files."*

**💡 大白话：**
**flat-file 数据库 = 直接拿几个记事本(.txt 文件)存数据**，没有任何高级机制。

课程用的例子是一个**社交媒体应用**（这也是你 PA1 作业的真身），用 3 个文件：

| 文件 | 存什么 | 例子（一行 = 一条记录） |
|:---|:---|:---|
| `users.txt` | 用户：姓名, 地点 | `Timothee Chalamet, Paris` |
| `posts.txt` | 帖子：编号, 用户名, 内容 | `1001, Timothee, "new movie!"` |
| `interactions.txt` | 互动：谁对哪条帖子点赞/评论 | `like, Liu Yifei, 1001` |

听起来挺简单挺好用，对吧？**问题就在后面**——人一多，毛病全来了。

## 3. ⭐ flat-file 的六大毛病（核心！每个都配具体例子）

> 一句话总览：flat-file 就像**把全公司的信息记在几个共享记事本上**——开始能用，人一多就全是坑。

### 毛病① 冗余 / 不一致（redundancy & inconsistency）

**📖 原文：** *"the flat-file database stores user information alongside each post, resulting in repeated user details for every post... wasting storage space."*

**💡 大白话：** Timothee 发了 100 条帖子，于是 `posts.txt` 里他的名字 `Timothee Chalamet` 被**抄了 100 遍**。
- 浪费空间（一个名字写 100 次）。
- 更糟：他改名 `Sir Timothee`，你得**找出这 100 行逐个改**；漏改一行，数据就**自相矛盾**了（同一个人两个名字）。

> 🔵 类比：通讯录里同一个朋友存了 100 次，他换号码你要改 100 处，改漏就乱套。

### 毛病② 删除慢（slow deletion）

**📖 原文：** *"deleting a single record might require rewriting the entire file... removing a single entry from a one gigabyte text file could take several minutes."*

**💡 大白话：** 记事本里删掉中间一行，电脑其实要**把整个文件重写一遍**。文件 1GB 大的话，删一行要好几分钟，期间别人都得等。

> 🔵 类比：撕掉一本书中间的一页，却要求你把整本书从头重抄一遍。

### 毛病③ 查询慢（slow lookup）

**📖 原文：** *"the only way to accomplish this is by sequentially scanning the entire file."*

**💡 大白话：** 想找"所有住在 Mumbai 的用户"，记事本没有目录，只能**从第一行一直读到最后一行**（这叫**顺序扫描 sequential scan**），一个个看是不是 Mumbai。几百万行就慢死了。

> 🔵 类比：一本没有目录的字典，查个字要一页页翻到底。

### 毛病④ 并发更新乱（concurrent update anomaly）

**📖 原文：** *"both updates can occur simultaneously resulting in the data being overwritten."*

**💡 大白话：** 两个人**同时**改同一行，会互相覆盖。具体例子（一定要会讲）：
- 初始：`Timothee Chalamet, Paris`
- 用户A 想改名字 → `Xavier Laurent`
- 用户B 同时想改地点 → `New York`
- 没协调时，两次写互相覆盖，最后变成 **`Xavier Laurent, New York`**
- 但这俩**谁都没想要**！（A 只想改名、B 只想改地点）

> 🔵 类比：两个人同时编辑同一份 Word 文档、各存各的，后存的把先存的改动冲掉了。

### 毛病⑤ 崩溃后不一致（no crash recovery）

**📖 原文：** *"imagine a scenario where we are adding a country column to all of the user profiles, and that is a disk failure that interrupts the database update."*

**💡 大白话：** 你正在给所有用户加一个"国家"字段，加到一半**断电**了。重启后，有些用户加了、有些没加，甚至有的加了两次——数据一片混乱，而且你**没法知道刚才加到哪了**。

> 🔵 类比：装修装一半停电，再来一遍，结果装了两个门。

### 毛病⑥ 查询要自己写代码（no declarative query）

**📖 原文：** *"performing complex queries requires users to write custom code... like the one shown here [a Python function]."*

**💡 大白话：** 想做个统计（比如"Lana 的所有评论"），记事本没有查询功能，你得**自己写一段 Python**。会编程才行、慢、还容易写错。

> 🔵 类比：想查个账，结果还得自己先学会编程。

> 🎵 **六毛病记忆口诀**：**冗余、删慢、查慢、并发乱、崩溃乱、要编程**（"两慢两乱一冗余一编程"）。

## 4. 解药登场：关系模型（Relational Model，Codd 1970）

**📖 原文：**
> *"In 1970, Ted Codd... introduced the idea of a relational database. A relational database is a new way to organize data as a collection of tables."*

**💡 大白话：**
1970 年 IBM 的科学家 **Ted Codd** 提出：别用记事本了，把数据organize成**一堆有关联的表格(tables)**，就像 Excel 那样。他后来因此拿了图灵奖（计算机界的诺贝尔奖）。

几个术语（其实就是 Excel 的说法换个名）：

| 数据库术语 | 就是 Excel 里的 | 例子 |
|:---|:---|:---|
| 表 (table / relation) | 一张表 | `users` 表 |
| 行 (row / **tuple 元组**) | 一行 | `(1, Lana Condor, LA)` |
| 列 (column / **attribute 属性**) | 一列 | `location` 列 |
| 域 (domain) | 一列允许的取值范围 | location 只能是字符串 |

社交例子就变成 3 张表：`users`、`posts`、`interactions`。

**为什么叫"关系(relation)"？** 原文说这个词来自**数学的集合论**——一个"关系"就是把几组信息关联起来。比如"学生集合"和"成绩集合"，关系 R 告诉你"Alice 得 B、Bob 得 A"。你不用记这个数学背景，记住"关系 ≈ 一张表"就够了。

## 5. 关系模型的骨架：主键 & 外键

**📖 原文：**
> *"The primary key is a column that serves as a unique identifier for each row... A foreign key is a column in one table that refers to the primary key in another table."*

**💡 大白话：**

**主键 (Primary Key) = 一张表里能唯一认出每一行的那一列。**
> 🔵 类比：**身份证号**。全国人可能重名，但身份证号绝不重复。`users` 表里 `UserID` 就是主键。

**外键 (Foreign Key) = 一张表里"指向另一张表主键"的那一列。**
> 🔵 类比：`posts` 表里每条帖子记一个 `UserID`，这个 UserID **指向** `users` 表里的某个人。就像你写信封时写对方的"身份证号/地址"——你不在信封上重抄对方全部信息，只写一个能找到他的"指针"。

**外键保证"引用完整性(referential integrity)"** —— 原文说得很直白：
> *"there cannot be a post posted by a user whose information does not exist in the user table."*

**💡** 就是说：**不能有一条帖子，它的作者在 `users` 表里根本不存在**。外键帮你挡住这种"幽灵作者"。

【课本 ch2 补充的更细术语，了解即可】：
- **超键 (superkey)**：能唯一认出一行的列组合，但可能带多余列（如 `{ID, name}`，其实光 ID 就够了）。
- **候选键 (candidate key)**：**最小的**超键（去掉任一列就不唯一了，如 `{ID}`）。
- **主键**：从候选键里**挑一个**当代表。

## 6. ⭐ 关系模型最大的优势：逻辑设计 vs 物理设计（数据独立性）

**📖 原文：**
> *"Logical design is all about how we model our data as a collection of tables... physical design concerns with how the tables are stored and indexed on disk. Application developers do not need to worry about physical design."*

**💡 大白话：**
关系模型把"数据库设计"**劈成两层**：

| | 逻辑设计 (logical) | 物理设计 (physical) |
|:---|:---|:---|
| 管什么 | 数据**长什么样**：有哪些表、列、主外键 | 数据**怎么存**：存哪、用什么索引、什么格式 |
| 谁管 | 写 SQL 的应用开发者 | 数据库管理员(DBA) / 数据库内部 |

> 🔵 **绝佳类比**：你去餐厅，只看**菜单点菜**（逻辑设计）；后厨**怎么做、用什么锅、买哪家的菜**（物理设计）你不用管。

**这带来一个巨大好处，叫"数据独立性(data independence)"** —— 这也是 Codd 论文(Paper 1)从头到尾在讲的事：
> 后厨换了新灶具、升级了冰箱（改了物理设计），你**点菜的方式（逻辑设计）一点不用变**。

换成数据库：DBA 可以换索引、升级硬盘、改存储格式（物理变了），而**应用代码一行都不用改**（逻辑没变）。这就是为什么大公司的数据库能不停升级而不影响业务。

## 7. 关系模型怎么逐个治好 flat-file 的六大毛病（对照看）

**📖 原文（节选）：**
> *"user details are stored once in the user's table with posts referencing the users by ID, thus eliminating data redundancy."*

**💡 大白话对照表：**

| flat-file 毛病 | 关系模型怎么治 | 一句话原理 |
|:---|:---|:---|
| ①冗余 | 用户只在 `users` 存**一份**，帖子只存 `UserID`（外键） | 改名只改 1 行，不是 100 行 |
| ②删除慢 | 删用户 = 从表里移除一行，几毫秒 | 不用重写整个文件 |
| ③查询慢 | **索引(index)**：给数据建"目录" | `WHERE location='Mumbai'` 直接跳过去，不全扫 |
| ④并发乱 | **事务(transaction) + 并发控制** | 保证不会出现"谁都不想要"的中间态 |
| ⑤崩溃乱 | **事务原子性 + 日志恢复** | 断电就整体回滚到上一个好状态 |
| ⑥要编程 | **SQL**（声明式语言） | 说"我要什么"，不用说"怎么一步步取" |

**关于③索引，原文有个超好的类比：**
> *"Think about your smartphone filled with hundreds of apps. Without organization, finding a specific app... is hard. Now imagine organizing all these apps into folders like social, games, and work."*

**💡** 没分类的手机，找个 App 要划好几屏；把 App 分进"社交/游戏/工作"文件夹后，一下就找到。**索引就是给数据分文件夹**，查询不用一个个翻。（索引的内部实现是 M7 哈希表的内容。）

**关于⑥的"声明式(declarative)"：**
- **SQL 是声明式**：你说"给我所有 Mumbai 的用户"，至于怎么找是数据库的事。
- **Python/C++ 是命令式(imperative)**：你得一步步写"打开文件、读第一行、判断是不是 Mumbai、读下一行……"。
- 这就是 SQL 好用的根本原因——**你只说要什么，不说怎么做**。

## 8. ⭐ 关系代数（Relational Algebra）—— SQL 背后的"积木"

**📖 原文：**
> *"Relational operators are functions that operate on tables... they take in one or more tables as input and yield a single table as output."*

**💡 大白话：**
关系代数 = **一组运算，每个吃 1~2 张表、吐出 1 张表**。因为输入输出都是表，所以能像**搭乐高**一样一层套一层，组合出复杂查询。**SQL 的威力就来自这套积木。**

下面每个运算，给你"**它干嘛 + 一个小例子**"。符号要认识（考试会用）：

| 符号 | 名字 | 干嘛（大白话） | 小例子 |
|:---:|:---|:---|:---|
| **σ** (sigma) | 选择 Select | **挑行**：留下满足条件的行 | `σ_{地点='Paris'}(users)` = 挑出所有巴黎用户 |
| **Π** (Pi) | 投影 Project | **挑列**：只保留某几列（去重） | `Π_{姓名}(users)` = 只要姓名这一列 |
| **∪** | 并 Union | 两张表的行**合起来** | A∪B |
| **∩** | 交 Intersection | 两张表**都有**的行 | A∩B |
| **−** | 差 Difference | 在 A **不在** B 的行 | A−B |
| **×** | 笛卡尔积 | 每行配每行（结果巨大） | A×B |
| **ρ** (rho) | 改名 Rename | 给表/列**改个名** | ρ_x(E) |
| **⋈** | 连接 Join | 按条件把两张表**拼起来** | `posts ⋈ users`（按 UserID 拼） |
| **γ** (gamma) | 分组聚合 | 按某列**分组再统计** | `_{帖子ID}γ_{count(*)}` = 每条帖子几个赞 |
| **τ** (tau) | 排序 Sort | 把结果**排个序** | `τ_{赞数降序}` = 按赞数从多到少 |

> ⚠️ **最容易混的两个**（考试必考）：
> - **σ（选择）挑的是"行"**，对应 SQL 的 **`WHERE`**。
> - **Π（投影）挑的是"列"**，对应 SQL 的 **`SELECT 列名`**。
> - 坑点：SQL 里写 `SELECT 列` 看着像"选择"，**但它其实是投影 Π**！别被名字骗了。

**怎么用积木拼一个真实查询**（原文例子：找点赞最多的帖子 + 点赞的人）：
1. **σ** 先挑出 `like` 类型的互动
2. **⋈** 把互动表和 users 表按 UserID 拼起来
3. **γ** 按帖子 ID 分组，数每条帖子的赞数
4. **Π** 只留要显示的列
5. **τ** 按赞数降序排，取第一名

> 🔑 一句话：**一条复杂 SQL = 一串关系代数运算的组合**。会把 SQL ↔ 关系代数互相翻译，是高频考点。

## ✅ M1 一页总结（看完能不能讲出来）

1. **DBMS** = 专门存/查/改大量数据的软件管家。
2. **flat-file 六毛病** = 冗余、删慢、查慢、并发乱、崩溃乱、要编程。
3. **关系模型** = 把数据存成一堆有关联的表（Codd 1970）。
4. **主键** = 身份证号（唯一）；**外键** = 指向另一张表的身份证号。
5. **数据独立性** = 改物理存储不影响应用代码（点菜不管后厨）。
6. **关系模型逐个治六毛病**：一份存储+外键、快删、索引、事务、日志、SQL。
7. **关系代数** = SQL 背后的积木：σ挑行、Π挑列、⋈拼表、γ分组、τ排序。
