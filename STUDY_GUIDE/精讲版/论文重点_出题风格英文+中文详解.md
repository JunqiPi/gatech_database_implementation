## 🧊 关键术语秒懂（英文 = 中文 = 大白话）

- **OLTP** = Online Transaction Processing（在线事务处理）= 一笔笔小操作，又快又小。🔵 像便利店收银台。例：ATM 转账、下单。
- **OLAP** = Online Analytical Processing（在线分析处理）= 一次扫一大堆历史数据算汇总。🔵 像财务部做年度报表。例：算 5 年销售额。**data warehouse（数据仓库）**就是干 OLAP 的。
- **data lake**（数据湖）= 各种原始文件一股脑倒进便宜的对象存储(如 S3)，不管结构。🔵 大杂物间。
- **Lakehouse**（湖仓）= data lake + 一层管理层(Delta Lake/Iceberg/Hudi) 补上 ACID/表结构/time travel。🔵 大杂物间里装智能货架。**面向 OLAP，不擅长低延迟事务。**
- **columnar**（列式/列存）= 按列存，压缩好、扫描快，适合 OLAP。
- **row store**（行存）= 按行存，适合 OLTP 点读写。
- **NoSQL** = 非关系型，2000 年代主张弃 SQL/ACID(用 **BASE** 弱一致)；后来又加回。
- **NewSQL** = 既要 NoSQL 扩展性又要关系模型 + ACID。
- **object storage**（对象存储）= 云上便宜大容量存储(如 Amazon S3)，延迟比本地盘高。

# 📕 Paper 1 — Codd《A Relational Model of Data》(1970)

> **主旨**：用户不该被迫知道数据怎么存（**data independence 数据独立性**）。

### 重点1 · 数据独立性 + 要消灭的三种依赖
✅ **EN:** *"Users must be protected from having to know how the data is organized in the machine; three dependencies must be removed: **ordering dependence**, **indexing dependence**, and **access path dependence**."*
💡 **中文（每个英文术语都给）：**
- **ordering dependence（排序依赖）**：程序假设记录**按某顺序存**——换个顺序就读错。
- **indexing dependence（索引依赖）**：程序**写死某个索引的名字**——删了那个索引程序就崩。
- **access path dependence（访问路径依赖）**：程序**写死树/网状结构的访问路径**——结构一变就找不到数据。
❌ **Trap:** *"An application may reference a specific index name for performance tuning."* —— 错！这正是 **indexing dependence**，Codd 要消灭的。

### 重点2 · 关系模型 = n 元关系
✅ **EN:** *"The relational model represents data as **n-ary relations** (sets of tuples), removing pointer-based access paths."*
💡 **中文：** 把数据看成**一堆表(relations 关系)**，每行是 tuple(元组)。不用像层次/网状模型靠指针找数据。

### 重点3 · 范式化
✅ **EN:** *"**Normalization** eliminates **non-simple (nested) domains**, producing flat relations."*
💡 **中文：** normalization(范式化) = 把嵌套复杂数据拆平成规整二维表。🔵 例：把员工"工作经历"拆成单独一张表，用员工号关联。

### 重点4 · 主键/外键
✅ **EN:** *"A **primary key** uniquely identifies each tuple; a **foreign key** holds values that are the primary key of some relation."*
💡 **中文：** primary key(主键)=身份证号；foreign key(外键)=指向另一张表主键的列。外键保证 **referential integrity(引用完整性)**——不能有指向不存在记录的外键。

### 重点5 · 连接陷阱
✅ **EN:** *"The **connection trap**: following pointer paths is not equivalent to relational composition and can give wrong results."*
💡 **中文：** 别以为"顺指针一路走"=正确的关系连接。🔵 供应商→零件→项目，顺着走不能断定"这些项目都他供货"。

### 重点6 · 通用数据子语言（SQL 的雏形）
✅ **EN:** *"The model permits a universal **data sublanguage** based on **predicate calculus**, decoupling description from access."*
💡 **中文：** 关系模型能配一种基于"谓词演算"的高层查询语言——这就是后来 **SQL** 的思想源头（你只描述"要什么"）。

# 📗 Paper 2 — Stonebraker & Pavlo《What Goes Around Comes Around… And Around…》

> **主旨（标题即结论）**：**风水轮流转**——挑战者不断出现，但 RM(relational model)+SQL 始终主导，SQL 把别人的好点子吸收过来。⭐**考得最多最细。**

### 总论
✅ **EN:** *"The relational model and SQL remain dominant; rather than being replaced, SQL absorbs the best ideas from alternatives. The major changes are in **implementations**, driven by hardware."*
💡 **中文：** RM+SQL 一直赢；变的是"怎么实现"(被硬件推动)，不是数据模型本身。

## 🅰️ 八类数据模型 / 查询语言（全覆盖）

**① MapReduce（MR）**
✅ **EN:** *"MapReduce systems (Hadoop) are now at best a legacy technology; they died as distributed RDBMSs and SQL-on-Hadoop (Hive/Presto) took over."*
💡 MapReduce(谷歌 2003)= Map(过滤/UDF)+Reduce(GROUP BY)。后来 Hadoop 火过又崩，被分布式 RDBMS 取代。

**② Key/Value Stores（键值存储）**
✅ **EN:** *"Key/value stores (Redis, DynamoDB, RocksDB) suit simple single-value access (caching, sessions); they are dangerous for records needing multiple fields, joins, or secondary indexes."*
💡 KV 存储=最简单的"键→值(一团字节)"模型。适合缓存；复杂多字段就力不从心，很多 KV 后来长成 record store。RDBMS 能轻松模拟 KV。

**③ Document Databases（文档数据库，NoSQL/JSON）**
✅ **EN:** *"Document DBMSs (MongoDB) store JSON; they are on a collision course with RDBMSs and have largely added SQL + ACID."*
❌ **Trap:** *"Denormalizing into nested documents is always faster than joins."* —— 错！预连接的老问题：非一对多会重复数据、不一定更快、丧失数据独立性。
💡 文档数据库=存 JSON、低层 API、弱事务。和当年 OO/XML 数据库一个套路；后来都加了 SQL/ACID。

**④ Column-Family / Wide-Column（列族/宽列）**
✅ **EN:** *"Despite its name, **column-family is a reduction of the document model — NOT a columnar model**; it remains a niche (BigTable, Cassandra, HBase)."*
❌ **Trap:** *"Column-family is a columnar data model tailored for OLAP."* —— ⭐**最爱考的陷阱，错！**
💡 名字带 "column" 但不是列存，是文档模型简化版(每行可有不同字段)。

**⑤ Text Search Engines（文本搜索引擎）**
✅ **EN:** *"Text engines (Elasticsearch, Solr/Lucene) build **inverted indexes**; they have weak transactions and are typically used alongside an RDBMS in a **polystore**."*
💡 文本搜索=给文档建"倒排索引(inverted index)"。事务弱，常和 RDBMS 配合用(polystore 多存储架构)。

**⑥ Array Databases（数组数据库）**
✅ **EN:** *"Array DBMSs (SciDB, Rasdaman) are a niche for scientific data; SQL has added multi-dimensional array support (SQL/MDA)."*
💡 数组数据库=存多维数组(科学/基因/气象)。小众市场。

**⑦ Vector Databases（向量数据库）**
✅ **EN:** *"Vector DBMSs are essentially document stores with **ANN (approximate nearest neighbor)** indexes; specialized vector DBMSs will likely become unnecessary as RDBMSs add native vector types/indexes."*
❌ **Trap:** *"Vector databases are a fundamentally new architecture RDBMSs cannot replicate."* —— 错。
💡 向量数据库=存 AI 的 embedding 做相似度搜索(ANN 近似最近邻)。作者说它终将不必要(RDBMS 已在加向量索引)。

**⑧ Graph Databases（图数据库）**
✅ **EN:** *"Graphs can be simulated as Node/Edge tables, so RDBMSs are always an option; OLTP graph apps will be largely served by RDBMSs (SQL/PGQ), while analytic graphs need in-memory specialized structures."*
💡 图数据库(Neo4j)=点+边。但图能用两张表(Node, Edge)模拟，RDBMS 总是个选项；SQL:2023 加了图查询(SQL/PGQ)。

> 📌 **八类小结**：✅*"Non-SQL/non-relational systems are either a niche market or are fast becoming SQL/RM systems."*（要么小众，要么向 SQL/RM 收敛。）

## 🅱️ 六类系统架构（全覆盖）

**① Columnar Systems（列存系统）**
✅ **EN:** *"Columnar storage revolutionized OLAP: better **compression**, **vectorized execution**, minimal per-record overhead; all data-warehouse vendors moved row→column."*
❌ **Trap:** *"Column stores are best for OLTP point writes."* —— 错(那是行存)。
💡 列存彻底改变了 OLAP(数据仓库)。例：50 列只查 2 列，列存只读那 2 列。

**② Cloud Databases（云数据库）**
✅ **EN:** *"The cloud upended DBMS design; **object storage (S3)** + disaggregated compute enables **serverless** elasticity; multi-node **shared-disk** is back thanks to faster networking."*
💡 云让"算"和"存"分开，按需弹性(serverless 无服务器)。Snowflake 是代表。"shared-disk(共享磁盘)又转回来了"也是"风水轮流转"一例。

**③ Data Lakes / Lakehouses（数据湖/湖仓）**
✅ **EN:** *"A lakehouse keeps data in **open formats (Parquet/ORC)** on cheap **object storage** and adds a **metadata/table layer (Delta Lake, Iceberg, Hudi)** for **ACID and time travel**; it targets **OLAP**."*
❌ **Trap:** *"Lakehouses outperform PostgreSQL on low-latency transactions."* —— ⭐错！对象存储延迟高，**不擅长低延迟事务(OLTP)**；其 PK/FK 常是 **informational(信息性)**，不强制。
💡 湖仓=便宜湖 + 智能管理层。给分析(OLAP)用。

**④ NewSQL Systems**
✅ **EN:** *"NewSQL (CockroachDB, TiDB, Spanner, VoltDB) seeks NoSQL-like scalability for OLTP while keeping the **relational model and ACID**."*
💡 NewSQL=我全都要：又能横向扩展，又保留 RM+ACID。

**⑤ Hardware Accelerators（硬件加速器）**
✅ **EN:** *"Custom hardware (FPGA/GPU) DBMS accelerators rarely pay off outside the major cloud vendors; commodity CPUs in the cloud are too cheap."*
💡 专用硬件(FPGA/GPU)加速数据库，几十年来基本没成功，只有大云厂商玩得起。

**⑥ Blockchain Databases（区块链数据库）**
✅ **EN:** *"Blockchain DBMSs are an **inefficient technology (≈5 orders of magnitude slower) looking for an application**; major crypto exchanges run on traditional RDBMSs."*
💡 区块链数据库慢约 10 万倍，"一个在找应用场景的低效技术"。

## 🅾️ 收尾教训（Parting Comments，也可能考）
- ✅ *"Never underestimate good marketing for bad products"* —— 烂产品靠营销也能赢一阵(Oracle/MySQL/MongoDB)。
- ✅ *"Beware DBMSs from large non-DBMS vendors"* —— 大科技公司开源的内部数据库常不成熟。
- ✅ *"Do not ignore the out-of-box experience"* —— 上手体验重要(DuckDB 因此火)。
- ✅ *"NL-to-SQL via LLMs will not replace SQL"* —— 大模型把自然语言转 SQL 很强，但取代不了 SQL(OLTP 用 ORM，OLAP 需精确)。
- ✅ **结论**：*"What goes around will continue to come around; new models won't supplant the RM."*

# 📘 Paper 3 — Stonebraker《Operating System Support for Database Management》(1981)

> **主旨**：OS 的服务对 DBMS 要么太慢、要么不对路，所以**数据库自己造**缓冲池/存储/调度。(BuzzDB 自建 StorageManager/BufferManager 的理由。)

### 🅰️ Buffer Pool Management（缓冲池）
✅ **EN:** *"OS **LRU** buffering performs poorly for DB access patterns like **sequential scans**, where **toss-immediately** is better; the OS also can't **prefetch** the DB-specific next block, nor provide **selected force-out** for commit ordering."*
❌ **Trap:** *"A DBMS should rely on the OS buffer cache rather than build its own."* —— 错。
💡 OS 的 LRU 缓存对顺序扫描很差(该"用完即扔" toss-immediately)；预取方向不对；缺"选择性强制刷盘"(崩溃恢复要先刷改动再刷 commit 标志)。所以 DBMS 自建用户态缓冲池。

### 🅱️ File System（文件系统）
✅ **EN:** *"The OS file system offers a **character-array** abstraction, but a DBMS wants **record management** with keyed access; **physical contiguity** (extent-based) matters because DBMSs do heavy sequential access."*
💡 OS 给的是"字符数组文件"，DBMS 想要"带键访问的记录管理"。文件块若散落各处，顺序扫描时磁臂乱跑很慢，所以要"按 extent(区段)连续存"。

### 🅲️ Scheduling / Process / IPC（调度/进程/通信）
✅ **EN:** *"The **convoy phenomenon** occurs when the OS deschedules a process holding a short-term lock others need; OS **task switches and messages** are expensive (thousands of instructions), undermining both process-per-user and server models."*
💡 **convoy(护航现象)**：持锁的进程被调度走，其它进程全堵后面。🔵 拿着公厕唯一钥匙的人去睡了，后面排长龙。任务切换/消息开销大(上千指令)。

### 🅳️ Consistency Control（一致性控制）+ 结论
✅ **EN:** *"OSes rarely provide fine-grained (page/record) locks a DBMS needs; if buffering stays in user space but consistency control doesn't, code is duplicated. **Conclusion: OS services are too slow or inappropriate, so DBMSs provide their own.**"*
💡 OS 通常只锁整个文件，DBMS 需要更细粒度(页/记录)锁。结论：OS 服务太慢或不合适，数据库自己造。

# 📙 Paper 4 — Neumann & Freitag《Umbra: A Disk-Based System with In-Memory Performance》

> **主旨**：纯内存数据库快但装不下大数据；Umbra 用**低开销、可变大小页**的缓冲管理器，做到"内存级快 + 超内存也优雅"。

### 重点1 · 动机（硬件经济性）
✅ **EN:** *"Pure in-memory systems degrade/fail when data exceeds RAM; since SSDs are far cheaper than DRAM (≈40×), combining a large in-memory buffer with fast SSDs is more economical."*
💡 内存贵且涨不动，SSD 便宜又快(2TB:$500 vs DRAM $20000)。所以"大内存缓冲+快 SSD"。

### 重点2 · 可变大小页
✅ **EN:** *"Umbra's buffer manager uses **variable-size pages** organized into **size classes**, storing large objects natively and consecutively."*
❌ **Trap:** *"Fixed-size pages are universally superior."* —— 错(处理大对象更麻烦)。
💡 传统固定页(4KB)塞不下大对象要切碎；可变大小页整块连续存，简化全系统。

### 重点3 · 避免外部碎片（虚拟内存技巧）
✅ **EN:** *"External fragmentation is avoided by exploiting the **virtual-to-physical memory mapping** (reserve a virtual address range per size class via mmap)."*
💡 多种大小页混在一起易碎片；用虚拟内存映射(给每种大小预留虚拟地址)避开。

### 重点4 · 指针混写（pointer swizzling）
✅ **EN:** *"References use **swips**: a swip is either an in-memory pointer (swizzled) or an on-disk page ID (unswizzled), avoiding a central hash-table bottleneck."*
💡 swip(混写指针)=64 位，要么是内存指针、要么是磁盘页号。避免"全局哈希表查地址"的瓶颈。

### 重点5 · 版本化/乐观闩锁
✅ **EN:** *"**Versioned latches** support **exclusive**, **shared**, and **optimistic** modes; **optimistic latching** (record a version, validate on release) eliminates contention for read-heavy access."*
💡 三档闩锁：独占(写)、共享(多读，=M8 shared_mutex)、乐观(读不上锁、只记版本号、读完校验)。🔵 乐观=看一眼黑板就走，走前再瞄确认没被改。

### 重点6 · 其它（B+树关系 / 字符串 / 恢复 / 编译）
✅ **EN:** *"Relations are stored in **B+-trees** with synthetic tuple IDs; leaf pages use a **PAX** layout; strings ≤12 chars are inline; recovery uses **ARIES (write-ahead logging)**; an **adaptive compilation** strategy balances compile vs execution time."*
💡 关系用 B+树存；叶页用 PAX 布局(定长列在前、变长在后)；短字符串内联；崩溃恢复用 ARIES(写前日志)；查询用"自适应编译"。

### 重点7 · 开销结论
✅ **EN:** *"The buffer manager adds **negligible overhead (<6%)**; the bottleneck is storage I/O bandwidth, addressable by adding more SSDs."*
💡 缓冲管理器开销<6%，瓶颈是 SSD 带宽，多插盘即可。
